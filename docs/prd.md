# HappyVibe PRD — Direction v1

*Mirror of the Notion main PRD (source of truth for product discussion). Decisions are folded in place using the document's "Decision (…)" convention.*

## 1. Product Positioning

**HappyVibe is a local-first desktop app for beginner-friendly vibe coding — macOS first, with Windows and Linux support wherever possible.**

Its promise:

> **HappyVibe = vibe coding that allows you to actually understand what you and the agent are doing.**

The wedge audience (V1 target) is:

> **AI-curious tinkerers — junior developers, technical-adjacent people (PMs, designers, data analysts), and self-taught builders who want to *understand* what the agent is doing, not just get results.**

The original persona — *an AI-curious person who is scared to vibe code* — remains the aspirational north star. But true beginners mostly want results, not understanding; the people who crave seeing the context window are one notch above. Product decisions target the tinkerer wedge first, while the UX must stay simple enough that the scared beginner can grow into it. Think: **a GUI-native Pi — radically simple surface, deep personalization underneath** (prompts, agents, permissions, models).

HappyVibe should feel like a **friendly learning tool for vibe coding**, but one that can become a serious coding tool when used carefully.

The product should be accessible to beginners, while still giving experienced developers deep customization options:
- system prompt editing;
- agent prompt editing;
- tool visibility;
- permission configuration;
- model/provider control;
- context inspection;
- eventually skills and custom agents.

The tone should be **playful**, because working with AI should feel fun, but the product must remain trustworthy enough for real coding work.

## 2. Core Product Promise

Most agentic coding tools are powerful but opaque. Users often do not understand:
- what the agent is doing;
- what tools it is calling;
- what permissions it has;
- what context it sees;
- why it edits a file;
- what sub-agents are doing;
- how much they are spending in tokens.

HappyVibe turns agentic coding into a visible, understandable, and editable workflow.

The user should not feel like a mysterious terminal agent is running "Chinese bash commands in the background." Instead, they should see a clean, readable, human-friendly representation of the agent's work.

## 3. Technical Foundation

HappyVibe is a **tightly coupled wrapper above Pi Agent**.

**Decision (Round 2):** HappyVibe ships as a **curated Pi distribution**: the Pi runtime and all required extensions are embedded with the app at a pinned, tested version. HappyVibe does not depend on a user-installed Pi, because the UI can only guarantee support for the exact Pi version it embeds.

**Decision (2026-07-16):** the packaged app is **fully standalone** — it must run on a machine with no developer tooling installed (no Node, no npm, no Pi). Everything the runtime needs ships inside the bundle; child processes (Pi, sub-agents) run through the bundled Electron helper as Node (`pi-runtime/bin/pi-node.sh`). The only accepted exception: MCP stdio servers the *user* configures with `node`/`npx` commands require those on their machine — that is user config, not part of the distribution.

Pi Agent is the underlying coding-agent harness. HappyVibe should not attempt to become a generic multi-runtime product in V1.

However, because Pi appears intentionally minimal, the V1 architecture should probably include:
1. **Pi Agent core**
2. **A HappyVibe runtime layer**
3. **A curated set of Pi extensions/packages**
4. **A visual UI layer**
5. **Local persistence for workspaces, sessions, permissions, settings, and audit logs**

Pi's philosophy is extensibility rather than built-in product completeness. This means HappyVibe's V1 value is not only the interface. It is also the **curated agentic setup** that makes Pi feel usable to beginners out of the box.

## 4. Platform

V1 is:
- local-only;
- desktop-only (macOS first; Windows and Linux builds where possible);
- desktop-first;
- no account system;
- no cloud workspace;
- BYOK only.

Possible implementation frameworks: Electron; Tauri; React Native Desktop if the tech lead prefers; final choice left to technical leadership, but the framework must support cross-platform builds (macOS, Windows, Linux). The PRD should not over-specify the framework for now.

## 5. Workspace Model

In HappyVibe, a **workspace is a local project folder on disk**. The user can have multiple workspaces. Each workspace can contain multiple coding sessions, including sessions running in parallel.

A workspace contains: local path; session history; active sessions; archived sessions; permission configuration; AGENTS.md files; model overrides; agent configuration; tool permissions; audit logs; context state/history.

Workspaces are added manually. No automatic GitHub import in V1. GitHub support is out of scope for V1.

**Decision (Feedback round 11, 2026-08-04) — removing a workspace is a confirmed choice between two outcomes, and it stops orphaning sessions:** removal moves out of the hover-revealed `×` beside "New session" — one accidental click from losing a workspace, asking nothing — into a **confirmed danger zone at the bottom of the workspace settings page** (§16), after MCP. The confirm names **how many sessions are affected** and offers two outcomes, because "remove" means two different things: **Forget workspace** takes the workspace out of the list and **archives its sessions**, so re-adding the folder restores them and nothing on disk is touched; **Delete permanently** forgets it *and* permanently deletes its sessions and their session files. Both halves reuse §17's existing archive and confirmed-permanent-delete paths rather than inventing a "removed workspaces" concept. This also closes a silent defect: removal currently drops only the registry entry, leaving every session's `workspaceId` pointing at a workspace that no longer exists — invisible in the UI and never cleaned up.

## 7. Chat Experience

The product is chat-first. The user sees: their own messages; agent messages; high-level agent work state; readable tool requests; tool status/progress/results; expandable diffs; sub-agent activity; final answers.

The user should **not** see raw chain-of-thought. They should see high-level working state — e.g. "Inspecting the project structure", "Reading authentication-related files", "Preparing an edit", "Running tests", "Asking Code Explorer to investigate the routing layer", "Summarizing previous context before continuing".

Tool calls should be represented in readable product language:

```
Tool: Read file
Purpose: Inspect the authentication middleware
Status: Completed
Result: Found the middleware in src/server/auth.ts
```

Expandable details may show raw command, path, output, or diff when useful.

**Decision (Feedback round 1):** tool cards lead with a tool-kind icon and a human headline, never the raw call. Registered tools (sub-agent calls, AskUserQuestion, and every future registered tool) carry a required `intent` parameter — a customer-facing sentence saying what the model is doing and why. Pi's built-in tools cannot take extra parameters (their schemas are fixed), so their headlines are derived from the tool and its arguments — including parsed shell explanations ("Installing dependencies (npm install)", "Running tests (vitest)") with destructive commands flagged. The raw technical call always remains available behind a details toggle.

**Decision (Feedback round 2):** the chat bar uses icon Send/Stop buttons; a model chip shows the session's current model with its tier source ("workspace default", "session override") and a dropdown to override per session; the model list refreshes live when providers change; a "+" attach menu offers image attachment when the model supports vision (disabled otherwise, extensible later). Sending while the agent runs steers — the message is delivered between tool calls; queued messages appear as chips. There is no separate queue button, and queued chips cannot be individually removed yet: Pi's RPC surface has no dequeue command (an upstream feature request is filed).

**Decision (Feedback round 2) — AskUserQuestion:** the model can ask the user questions through a dedicated tool: 1–4 questions per call, each with a short header chip, single or multi select, and 2–4 options (label, description, optional monospace preview shown side-by-side). The UI always adds a free-text "Other" option; the recommended option comes first, labeled "(Recommended)". The picker blocks the agent until answered and never times out; questions from background sessions badge the sidebar like permission prompts, and the answer is echoed into the transcript.

**Decision (Feedback round 3, 2026-07-14):** several chat-readability refinements. (1) **Large-paste guard** — pasting more than 100k characters into the composer prompts a confirm before inserting. (2) **Long-message collapse** — a user message longer than ~10 "pages" renders collapsed with a "Show more" toggle. (3) **In-conversation search** — a message-text search with an icon and a keyboard shortcut (distinct from session-title search in §17 and the post-V1 file-name search in §21). (4) **Per-message copy** — a copy button at the bottom-right of every user question and every assistant answer. (5) **Code-block copy** — fenced code blocks in answers carry a copy-content button. (6) **Intent readability** — the tool-card intent headline may wrap (no longer clipped to one truncated line) so a long customer-facing sentence stays legible. (7) **Rewind a user message** — see §9.

**Decision (Feedback round 4, 2026-07-15):** two chat refinements. (1) **Search highlights, it does not filter** — the in-conversation search keeps every message visible and **highlights** matching substrings, with **next / previous** navigation (Enter / Shift-Enter and on-screen arrows, wrapping) and an `n / total` match counter; the active match scrolls into view. This supersedes the round-3 phrasing where search filtered non-matching messages out. (2) **Icon buttons** — the per-message copy, code-block copy, and rewind controls are **icon** buttons with tooltips (not text labels), for a quieter chat surface. (3) **Links open in the OS browser** — clicking a link in a chat answer opens it in the user's default browser via the system, never inside the app window (which would navigate the SPA away).

**Decision (Feedback round 5, 2026-07-16) — chat-surface restructure:** (1) **Split view** — the center area supports one 2-way split, horizontal or vertical; each pane has its own tab strip and tabs (the chat included) can be dragged between panes. (2) The in-conversation **search icon and the context bubble move into the tab-strip row**, next to the files icon; the chat header (the AGENTS.md chip and the whole section above the chat) is removed. (3) The composer "+" menu gains an **MCP submenu** — connected servers with status (read-only) plus a "Manage…" shortcut to the MCP, Tools & Agents page (§13). (4) **Intent wrapping** extends to the delegation call line — it wraps rather than truncating with an ellipsis.

**Decision (Feedback round 5.1, 2026-07-17) — chat-UI corrections (after GUI testing):** (1) The **search icon and context bubble leave the tab strip** for a small **right-aligned bar inside the chat pane** (a thin in-flow row at the top of the chat content — NOT a floating overlay, which could bleed over an adjacent split pane); the code editor's own ⌘F search is styled to the warm-workshop look. (2) The **code editor gains ⌘F search** (CodeMirror's built-in find/next/prev/highlight), the same keyboard trigger as chat search; editor focus routes ⌘F to the editor, chat focus to the chat. (3) The **split-view buttons (vertical/horizontal), unsplit, and the file-panel toggle live in a persistent toolbar pinned to the top-right of the center area** at the same height as the tab bar — always visible regardless of split; the tab strips become tabs-only. (4) The **file panel is a right-side overlay drawer** (top aligned below the tab bar) that overlays the content instead of a grid column, so it no longer shrinks the split panes (refines §21).

**Decision (Feedback round 6, 2026-07-18) — composer, mentions, shortcuts, sidebar (after GUI testing):** (1) **Multiline composer** — the chat input becomes an auto-growing textarea: **Enter sends, Shift+Enter inserts a newline** (the old single-line input had no way to enter a newline). (2) **`@file` references with autocomplete** — typing `@` opens a dropdown of workspace files AND directories (recursive, respecting the existing ignore filter — node_modules/.git/dotfiles) whose name contains the typed text; Tab picks the first, Arrow keys + Enter or the mouse pick, and the token completes to `@<basename>` (full relative path shown as a disambiguating subtitle, and used as the label when two basenames collide). On send, each reference's content is appended to the prompt as hidden `<file path="…">…</file>` blocks the model sees; a **directory** injects all its text files recursively **capped at ~200k chars total** — over the cap it warns the user and injects a recursive **file listing** instead. Binaries (NUL-sniffed) and ignored dirs are skipped. The transcript renders `@toto.md` as a **highlighted chip**, never the injected content (stripped at render time so live sends, queued steers, and reopened sessions all read the same). (3) **Keyboard shortcuts + help dialog** — a standard set (⌘N new session · ⌘W close tab · ⌘S save · ⌘F search chat/editor · ⌘B toggle left panel · ⌘⇧E toggle file drawer · ⌘, settings · ⌘/ shortcuts dialog · Esc closes dialogs) driven by a single shortcut registry, surfaced in a new **"Keyboard shortcuts" dialog** (⌘/ or the Help footer). (4) **Collapsible left panel** — the sidebar collapses to a slim ~48px **icon rail** (workspace initials; MCP/Settings/Help icons at the bottom); a chevron or ⌘B toggles it and the collapsed state is persisted.

**Decision (Feedback round 8, 2026-08-01) — one collapsible Settings group, and shortcuts become editable (amends round 6's items 3 and 4):** the sidebar footer had grown into a flat list of seven entries, so **every configuration destination folds into a single collapsible "Settings" group** — Skills · MCP · Agents · All Tools first (the round-6 four, order and identity unchanged), then Models · Permissions · System prompt · Stats · Audit log · Keyboard shortcuts (§16). The group's open/closed state persists, and the **collapsed icon rail shows one gear** that expands the sidebar rather than stacking ten icons. The **keyboard-shortcuts dialog becomes a full page where the bindings are editable** — a list you can only read is a manual, one you can edit is a feature. Rebindable are the shortcuts the app itself dispatches (new session, close tab, save, search, toggle the workspace panel, toggle the file drawer, open settings, open shortcuts) — **search is one action with two focus-scoped consumers**, the conversation or the open file, because modelling them separately would make the default ⌘F self-conflicting; **Enter · ⇧Enter · `@` · Esc are listed but fixed and tagged "built-in"**, because they are composer and dialog semantics rather than bindings and rebinding them breaks typing. A combo already owned by another action is **refused with that action named**, never silently stolen; every row has Reset and the page has Reset all; bindings persist with the rest of the app's settings. The **Help entry and its dialog are deleted** — a four-step checklist did not earn a permanent seat in the navigation. The first-run welcome overlay (§22) still appears once for a new user, simply with no re-open path; a real help page is post-V1 rather than a placeholder kept alive.

**Decision (Feedback round 11, 2026-08-04) — the sidebar's two halves get a draggable split, and workspaces get an emoji (amends round 6's item 4 and round 8):** a **draggable horizontal handle** separates the workspace tree from the Settings group, its position persisted like the other sidebar state. This is also the fix for a defect the handle makes visible: the Settings footer is **content-sized with no upper bound**, so its own scroll never engages and — with round 8's group expanded to ten entries — it squeezes the workspace tree down to its minimum floor. The handle gives the split an explicit position instead of letting the footer win by default. Separately, each workspace row shows an **emoji before its name**, **derived from the workspace path** — no picker, no stored field, nothing to configure, and therefore no migration; the trade-off (moving or renaming the folder changes the emoji) is accepted for a purely decorative cue. It **replaces the two-letter initials in the collapsed icon rail**, which is where it earns its place: a column of emoji is scannable where `HA` / `FL` / `DE` is not. This is a §20 "warm workshop" affordance, not information — nothing depends on it.

**Decision (Feedback round 12, 2026-08-13) — the Settings half is pinned to the bottom, and the split is stored as a proportion (completes the handle above):** three corrections to the same layout. (1) **Collapsed, the only thing left is the `Settings ›` row, at the very bottom** — no handle, no adjustable height, and no indication of which settings page is open. The row exists to re-expand; a collapsed group that still reports state is a group that did not collapse. (2) **Expanded, the handle returns**, and the height is remembered as a **fraction of the sidebar** rather than a pixel count, so resizing the window before expanding again keeps the split where the user put it — a px value silently means something different at a different window height, which is the failure the user predicted before the code did. It is clamped so the list can never be given more room than it needs: at most exactly the settings list. (3) **The dead space under the footer is the handle's own doing, and it goes.** Dragging gives the tree an explicit height (`flex: 0 0 auto`) and *nothing else claims the remainder*, so the footer floats up and leaves a gap — the "weird margin" reported. The footer takes the leftover space instead of the tree keeping it, which is also what pins it to the bottom in case (1) for free.

**Decision (Feedback round 18, 2026-08-31) — the session filter hides behind an icon, and a dragged split stops binding when nothing is open (completes round 12's handle):** two sidebar-layout corrections. (1) **The filter field is 44px of permanent chrome that is empty at rest and has no keyboard route at all.** The *input* hides; the *affordance* does not — a **search icon** joins the header row left of the collapse `«`, and clicking it or pressing its shortcut expands the field **in place, directly below the header**, autofocused, with the same `"Filter sessions…"` placeholder. It gets **its own rebindable action, `findSession`, default `⌘K`** — `⌘F` is taken by §7 round 8's *"search is one action with two focus-scoped consumers"* and `findConflict` refuses duplicates, so a second claim on it is not available; finding a session is a different action on a different surface. `⌘K` while the sidebar is rail-collapsed **expands it first**, because a shortcut that silently does nothing is a bug. **Blur while the filter is non-empty keeps the field open** — losing an active filter because you clicked a result would be hostile — while **`Esc` collapses AND clears**. That last clause is what removes a piece of state rather than adding one: the only route to *collapsed with a live filter* is `Esc` with text in the field, so clearing on `Esc` makes **"a collapsed search can never mean a filtered list"** true by construction, where the alternative was a persistent "filter active" dot on the icon. (2) **A dragged split stops binding when every group inside Settings is shut.** Round 12 established that *"a dragged height with the group collapsed is a division of nothing"*; with §16 round 18's groups the same is true one level down, and without this clause a user who had dragged the handle keeps a 325px tree while a ~204px settings block is handed two thirds of the sidebar — ~420px of dead pegboard, the exact defect round 12 fixed. The condition gains one term; **no default fraction is introduced**, because there is none to fix: the default is `AUTO`, which is flex, and flex is right. `max-h-[60%]` also stays — it is the guard that stops four opened groups eating the tree, it never binds while they are collapsed, and lowering it would make the inner scroll worse.

**Decision (Feedback round 11, 2026-08-04) — the center area becomes a 2×2 grid of resizable panes, and a chat tab is per session (supersedes round 5's "one 2-way split"):** four changes to one data model, because they are one refactor and not four features. (1) **A chat tab is per session.** The chat was a single sentinel tab per workspace, so opening a session *replaced* the one in front of you; a tab is now keyed by session id, so opening or creating a session **adds** a tab and reopening an already-open one **focuses** it. Tabs stay **per workspace** — each workspace keeps its own set and is returned to as it was left — and **every chat tab stays live-mounted**, so two sessions can stream at once and either can be watched. This is the visible form of §17's "sessions can run in parallel", which until now had no way to *see* two at once. (2) **Splits nest exactly one level — a 2×2 grid:** split vertically then split either half horizontally, or the mirror. Arbitrary depth is **deferred, not dropped**: 2×2 is what the request describes, and a flat four-slot grid keeps the invariant that a tab's content is mounted **once** and placed by CSS grid area, which is what stops an editor tab from losing its unsaved buffer when dragged between panes. A layout tree would force those buffers to be lifted out of the components first, and would break the round-5.1 reason the context and files surfaces are overlays. (3) **Every divider is draggable** — pane sizes become part of the layout instead of a fixed 50/50, which the model previously had no field to express at all. (4) **A `+` at the end of each pane's tab strip** offers New session or Open file, so a pane can be filled without leaving it. Consequences, stated because they are where the bugs will be: a single global "selected session" becomes per-pane focus, the sidebar's selection highlight becomes a **set** rather than one row, and the context bubble and cost pill follow the **focused** chat.

**Decision (Feedback round 11, 2026-08-04) — EVERY layout control lives in its own pane's tab strip; there is no global centre toolbar (supersedes round 5.1's items 3, and its own first form):** with more than two panes a single top-right toolbar cannot say *which* pane it will divide. It acted on the **focused** half — state the user cannot see — and when asked for a direction the model cannot divide a half on, it silently **rotated the whole layout** instead of adding a pane. Both were guessing games, and GUI testing reported the cluster as "not dynamic and clear enough". So each strip carries **its own** controls and renders only what is **legal for its pane**: both directions on an undivided pane, the **cross axis only** once a primary split exists (a half's partner sits across it), and **nothing** on a cross partner or an already-divided half. A visible button therefore always acts on the strip it sits in, and the 2×2 ceiling is expressed by a control's **absence** rather than by a click that does nothing. Closing gains a per-pane form — **this pane's tabs move to a sibling and the layout collapses** — beside the layout-wide "merge every pane into one". The glyphs are also made distinguishable, which was the other half of the complaint: three near-identical boxes-with-a-line sat in a row, so **divided rectangles split**, an **undivided rectangle merges**, and an **✕ closes this pane**. **And the global toolbar is deleted outright.** Keeping it for the "genuinely layout-wide" pair was this decision's own first form, and it was wrong for a measurable reason: a layout-wide control cannot share a per-pane row. As a grid column it existed only in row 1 while content below spanned into it, so a pane measured 628px while its own strip measured 552px; as an overlay it pushed the top-right pane's controls 96px inward while every other pane's sat flush at its edge. Three GUI rounds reported that corner as broken, and each fix moved the asymmetry rather than removing it. So: **"merge every pane into one" is dropped** — closing panes one at a time *is* the merge, since a closed pane's tabs move to a sibling — and the **file drawer becomes a per-pane button**, which also reads better with four panes, because a file picked from the drawer opens into the pane you asked from. ⌘⇧E still toggles it. Every strip is now identical and every control acts on the strip it sits in, which is the property the previous three attempts lacked.

**Decision (Feedback round 11, 2026-08-04) — three chat-surface defects, each fixed at its root:** (1) **Scrolling up during a response works.** The transcript re-ran an unconditional scroll-to-bottom on *every* animation frame while text streamed, so the view was pinned and reading back was impossible. It now follows the stream only when the user is **already near the bottom**; scrolling up leaves them there. The same guard applies to the in-conversation search's active-match re-center, which re-centered every frame whenever a query was present. (2) **Stop is clean.** Pressing Stop closed the streaming message *before* the abort reached the agent, so text still in flight arrived after the message had been closed and **began a second one** — the reported "words cut to a new line". Late text now merges into the message it belongs to. The fix lives in the stream-commit path, not in the Stop button, because **eight** call sites close a message the same way; and it is scoped to the abort window so the *intentional* break — a message ending because a tool call begins — is preserved. (3) **Tool errors are collapsed by default**, showing a one-line summary with the full text behind the existing details toggle, reusing the pattern a failed sub-agent delegation already uses. This reverses the earlier deliberate choice to keep error bodies always visible: the agent usually recovers by itself, so an expanded error per attempt is noise rather than transparency. **Provider errors and the "agent process stopped" banner stay expanded** — they carry a Retry and are not the agent recovering.

**Decision (Feedback round 13, 2026-08-16) — Files and Changes become two panels behind one small cluster in the top bar; round 11 is amended in ONE clause, not reversed:** round 11 made the file drawer a per-pane button, which was right about layout controls and wrong about this one: the drawer is a single global overlay, so a split workspace showed the button twice and a 2×2 showed it four times — four entry points to one surface. §29's Changes panel then made it worse by riding in as a second *tab inside* that drawer, giving a branch bar, message box, baseline selector, file list, stashes and history the width of a filename tree. So **Files and Changes become two panels**, one open at a time, each remembering its own width (256 for the tree, wider for Changes — sharing one number is what made Changes cramped), opened by **two small icons in the top bar**: `⌘⇧E` and `⌘⇧G`, both rebindable. **Round 11's finding stands and is not being re-litigated:** every *layout* control — split, close pane — remains in its own strip and still acts on the strip it sits in, and no toolbar TRACK returns. **A full-height rail beside the grid was built first and rejected on sight**: geometrically perfect (every strip flush, nothing composited over a `WebContentsView`) and visually wrong, because it left a dead empty gutter running the height of the window. The cluster is therefore the **last item of the top-right strip** (`topRightSlot`, derived from the same cell mapping `paneNeighbours` uses), in normal flow — no track for content to span under, no overlay, no reserved padding. **The cost is named rather than hidden:** that one strip's own split/close controls sit inboard of the cluster while every other strip's sit flush. Round 11 rejected exactly this asymmetry, for a **96px** cluster of *layout* controls whose target pane was ambiguous; these two are **~44px** and act on neither pane — they open a global panel, so there is nothing to disambiguate. Two smaller consequences: a file opened from the cluster lands in the **focused** pane (visibly tinted, unlike the invisible focus round 11 objected to), and the pane `+` menu keeps its own "open the file panel" entry, which still focuses that pane first. **The right drawer keeps the plain content background, deliberately** — the sidebar's `pegboard` texture was tried here and reverted within the round: the texture is how the app marks its OWN chrome, the surface where you pick a workspace or open settings, and this drawer holds the workspace's own contents. Sharing the sidebar's surface said the opposite of what it is.

**Decision (Feedback round 12, 2026-08-13) — a tab can be renamed, and for a terminal the user's name wins over the poller:** right-clicking a chat or terminal tab offers **Rename**, reusing the file tree's context-menu pattern (the app's only one) rather than inventing a second. Renaming a **chat** tab renames the **session everywhere** — it is the session's name and not a per-tab alias, so the sidebar row changes with it and it rides the rename that already exists behind that row's inline edit. Renaming a **terminal** tab is the case with a rule in it: §26 titles a terminal from its *foreground process*, **polled**, precisely because a command that prints nothing (`sleep 30`) would otherwise leave an event-driven title reading `zsh` forever. A user title therefore has to beat the poll — **it wins outright, and the live command moves to the tooltip**. A file tab is not renameable here: its title is its filename, and renaming the file is the file tree's job.

**Decision (Feedback round 12, 2026-08-13) — images appear in the chat wherever they already exist, and paste/drop finally attach:** three gaps that read as one missing feature, and measurement showed they share a shape. Pi persists images as a `{type:"image", data:<base64>, mimeType}` content block — verified across 61 real session files (8 blocks: 7 on tool results, 1 on a user message) — which is the same shape the composer's own attachment helper already turns into a data URL. So: (1) **an attached image survives a reopen.** It renders live today and vanishes on restore, because the restore path concatenates only `text` blocks and the restored-message type has no field to carry an image — the exact silent field-drop `restoreMap.ts`'s own comment was written about after §24's `command` was lost the same way. (2) **A screenshot the agent takes is shown.** Those blocks arrive on a **tool result**, which the live path already receives in full and renders with `JSON.stringify` — so a screenshot is currently a megabyte of base64 behind the details toggle. Pulling image blocks out of the result and rendering them as thumbnails fixes the missing picture *and* removes the wall of text; this is what makes an MCP browser screenshot legible, which is the case the user actually hit. (3) **Paste and drag into the composer attach**, joining the "+" file picker; the paste handler already exists and only guards large *text*. All three render through the one zoomable-image component (§21 round 3), so there is a single lightbox. **Named ceiling:** restore now carries base64, and the worst real session measured is 1.80 MB of image inside a 1.86 MB file — inside the budget that keeps §17 round 10's ~25 ms reopen, but a session of fifty screenshots is not. Restore caps what it carries and marks the remainder *image not shown* rather than silently inflating the payload; the upgrade path, if that cap is ever reached, is fetching images lazily by locator instead of inlining them.

**Decision (Feedback round 12, 2026-08-13) — the model chip moves up, the mic moves right (amends round 5.1's bar):** the composer row had accumulated everything — attach, model, plan, mic, text, stop, send — and one of those is not composing. The **model chip moves to the left of the round-5.1 in-chat top bar**, where the session's *state* already lives, and the existing badges (skills, the active-plan pill) stack after it; search, cost and context keep the right. The **Plan toggle stays in the composer** — it is something you flip *before typing*, part of the act of composing a turn, where the model chip is a property of the session you read. The **mic moves to the right end of the composer**, beside Stop and Send, because it is an input control and belongs with the other two — this is a placement change only, and §27's chip semantics (red while recording, click to stop, hidden when the setting is off) are unchanged.

**Decision (Feedback round 15, 2026-08-16) — the chat surface reads active and icon-first:** five fixes in one register. (1) The **model chip gets the active treatment** of its top-bar neighbours (border, card background, ink text) — a borderless muted mono chip read as a disabled control. (2) **Tool cards go icon-first: every word becomes an icon with its text on hover** — the status (done ✓ / error ✕ / denied ✕ / skipped ⏭; running keeps the pulse dot), the details pill becomes a ⋯ icon, and the word badges (allowed · session pass · destructive · denied · not-in-plan-mode) become icons with tooltips too. (3) The **pane `+` menu rows carry the tab-kind glyphs** they open (session, terminal, browser, file). (4) **Browser and terminal panes draw the same left divider line** chat, file and empty panes already do — `paneDivider` was applied to three of the five pane kinds, so a browser beside a session (or beside another browser) had no separating line, only the browser view's inset gap. (5) The **sidebar settings-split handle gets the pane divider's exact treatment** (10px hit strip, 5px centred tint) instead of its thinner bar, so the app's two draggable dividers feel like one control.

**Decision (Feedback round 15, 2026-08-16) — intent leads on browser cards (amends §28's URL-first card rule, for the CARD only):** `browser_open`/`browser_navigate` headlined the URL even when the model wrote an intent — §28's deliberate "where the agent went is the fact worth reading". Reversed for the transcript card: the **intent is the headline and the URL demotes to the small mono chip beside it**, exactly as edit/write cards carry their path. The **permission prompt is untouched** — it has always shown the factual URL, never the model's sentence, and that rule is what makes the card free to be a headline.

**Decision (Feedback round 15, 2026-08-16) — the transcript knows what time it is:** every **user prompt** shows an ago-format timestamp with the exact time on hover; the **turn's last assistant message** carries a quiet duration ("· 34s") measured from the prompt that started the turn. Restored sessions read timestamps from the session file (they were always there); live ones stamp at commit. The sessions-list age is §17's half of the same round.

**Decision (Feedback round 15, 2026-08-16) — sending scrolls, opening lands at the bottom, and long sessions tail-render:** sending a prompt **always** scrolls to the bottom — round 11's near-bottom guard governs the *stream*, not the user's own send, which is an explicit statement of "I am at the end now". Opening a session **lands at the bottom** (it landed at the top, because the follow guard only fires near the bottom it never reached) and renders only the **last ~50 items** behind a "Show earlier messages" divider — the §9 boundary affordance reused for plain length, not a virtualization layer.

**Decision (Feedback round 15, 2026-08-16) — the cost and context panels anchor below the chat top bar:** both open as **in-pane panels below the bar that owns their pills** (the way Files and Changes sit below the top bar), replacing the full-window scrim drawers that slid over everything from the screen edge. They stay **per-pane** surfaces following the chat that owns them — deliberately NOT drawer panels, which are workspace-global where cost and context are properties of one session.

**Decision (Feedback round 15, 2026-08-16) — the intent audit closes as a constraint, and describeCommand grows:** reviewed tool by tool: every registered tool carries `intent` (the browser ten, `terminal_run`/`terminal_kill`, ask_user, use_skill, mcp proxy + direct, the three plan tools; `subagent` optional per §12; `terminal_read` deliberately none — a sentence per poll is noise), and Pi's **built-ins cannot** (round 1 above: fixed schemas, unknown params stripped) — which is why bash cards show derived labels. The improvement therefore lands in the derivation: **`describeCommand`'s vocabulary grows** so fewer bash calls fall back to a raw "Running: `<cmd>`".

**Decision (2026-08-16) — intent descriptions ask for the why first:** the intent parameter is documented to the model **only** through its schema `description` strings (there is no system-prompt text about it), and those strings led with the what — "what you are typing and why" — so a model economizing into one short sentence kept the action and dropped the goal. Every description is reworded **goal first** ("why you are typing this, then what you are typing"), and the shared `INTENT_PARAM` — the widest surface, injected into every MCP tool — carries the one example, because examples move model output more than adjectives: *"'Looking for the failing order in the logs' beats 'Running a log query'"*. Three read-tools keep their existing text ("what you expect to find", "why you are closing it") — for a read, what you expect to find **is** the why. No behavioral claim is made: the live gate confirms the model still authors intents under the new wording, but whether the sentences got *better* would need interleaved trials (the §26 retraction's rule), not a before/after eyeball.

**Decision (Feedback round 16, 2026-08-31) — the transcript stops showing JSON, and stops saying "now ago":** two defects at the same altitude, both found by reading the two paths against each other. (1) **A tool card's result is rendered as JSON on the live path and as text on the reopened one.** `TechnicalDetails` hands `card.result` to `JSON.stringify(…, null, 2)`, and a tool result is `{content:[{type:"text",text}], details, usage}` — so a `bash` command's output reaches the user as an escaped-newline JSON envelope with the tool name and arguments stacked above it, while the *same* command in a *reopened* session reads perfectly, because `restore.ts` sets `result` to a plain string first. The live path adopts what restore already does: the text blocks are extracted the way `resultImages` already extracts image blocks, and command output renders as output. This is the fix for "terminal cards are systematically JSON" and it lands on every tool at once, because none of them wanted JSON — `bash`, `terminal_run`, `terminal_read` and `terminal_kill` simply share the generic card. The raw envelope stays available behind ⋯ for a bug report; it stops being the *only* rendering. (2) **"now ago"** — `timeago()` answers `"now"` under a minute and the transcript appends `" ago"` unconditionally, so a just-sent message reads "now ago". Under a minute the stamp reads **"just now"**; the sidebar's bare form is unaffected. It does **not** tick — a stamp that re-renders on a timer is motion with no information (the reason `timeago` collapses seconds in the first place), and it already refreshes whenever the transcript does.

**Decision (Feedback round 16, 2026-08-31) — the agent's thinking is shown, collapsed by default (reverses this section's "no raw chain-of-thought", and closes §12's stated asymmetry):** the rule above — *"the user should not see raw chain-of-thought"* — was written when the alternative was a wall of unstructured reasoning in the flow. It has since been overtaken twice: §12's fleet round put a **child's** reasoning on the delegation card and recorded the result as "the FIRST thinking surface anywhere in HappyVibe — the main agent's own reasoning is not rendered today … that asymmetry is accepted deliberately", and the high-level working state this section asks for is now carried by tool cards and intents, which is where it belongs. So the main agent's thinking becomes visible **inline in the transcript, collapsed by default, and re-collapsed on every message the user sends** — the user opens the reasoning for the one turn they are curious about, and nothing stays open across turns. Collapsed-by-default is the whole safety of it: the flow still reads as high-level working state, and §12's argument for a toggle rather than always-on ("a child's reasoning is the one the user has no other way to see") now applies to the parent too. **Three things this rests on were measured rather than assumed, and all three say it is cheap:** Pi's RPC **already streams** `thinking_start`/`thinking_delta`/`thinking_end` over the same `assistantMessageEvent` channel the app reads for `text_delta` and `modes/json-event.js` forwards the event untouched, so there is no upstream ask, no bridge change and no pin bump; the user's own stored sessions **already hold 1,304 thinking blocks** across 40 files, which `restore.ts` drops on purpose today, so a reopened session can show the same thing a live one does; and the worst session on that machine carries 407k chars of thinking against a median of 6k, which is 5% of the restore payload budget images already live under. Because it is collapsed, **live text is streamed only into an expanded block** — the same rule the sub-agent card follows, where nothing is read until the card is opened.

**Decision (Feedback round 16, 2026-08-31) — a notice pill's content is bounded, because that is what broke it and not its shape:** the transcript's notice is the only `rounded-full` surface among cards that are otherwise `rounded-xl`, and the retry notice was reported as looking wrong. The radius is **not** the fault: the same shape is the top bar's own idiom for the model chip and the context and cost pills, and it reads correctly there. What breaks is the *content* — the retry text is `Retrying (attempt 1/3, next in 5s) — <the provider's entire error message>`, an unbounded string poured into a surface designed for a short chip, so a full-radius lozenge wraps to several lines. The pill therefore stays a pill and the text becomes short and fixed in shape — **`Retrying 1/3 · 5s`** — with the provider's message on the hover title and a max width plus truncation as the structural guard, so no future notice can explode it either. Nothing is lost: if the retries are exhausted, that message lands in the error card at `agent_end`, which is `rounded-xl` and built to carry it. "Compacting context…" and "Recovered after N retries" share the pill, are already short, and are unaffected.

**Decision (Feedback round 16, 2026-08-31) — a tab in its own window is wanted at full parity, and is deferred to its own round (extends round 11's grid rather than amending it):** a second window is to be a **full peer** of the first — any tab kind can be opened in it and it splits into its own 2×2 grid with the same per-strip controls, not a reduced "pop out one thing" surface. It is **not** in this round, and the reason is structural rather than a matter of appetite: the app is single-window by construction in four independent places — `createWindow()` is called once and its result handed to `registerIpc(win)`, which closes over that one window so that **every** renderer push in the app goes through a single `send()`; `BrowserManager` takes `win` in its constructor and calls `addChildView` on it directly, and a `WebContentsView` belongs to exactly one window; and `App.tsx` holds every session's transcript, streaming refs, tool-card index and delegation state in one component. **The four tab kinds also cost wildly different amounts, which is the part that is not visible from outside:** a terminal is nearly free, because main already owns the PTY and the `@xterm/headless` mirror precisely so they outlive a renderer reload; a browser is moderate and physical; a file tab necessarily **remounts** and so loses an unsaved buffer, which is exactly what round 11 chose the flat grid to prevent *between panes* and cannot be preserved *between windows*; and a chat is the expensive one. Two smaller collisions are recorded now so the round does not rediscover them: `setLayout()` writes a **single** `layout` record in `config.json`, so two windows writing it is last-write-wins and the stored shape has to grow a window dimension, and `activeWs` lives in `localStorage`, which every renderer of the same origin shares, so a second window would silently follow the first one's workspace. Requirements and the staged route: the "Multi-window" Notion page under Feedbacks v12.

When the agent edits files, the UI should show: which file changed; a short summary of the change; status; an expandable diff; whether the edit succeeded or failed. This is important because HappyVibe's educational value depends on users understanding what the agent changed.

## 9. Context Management

Context visibility is one of HappyVibe's core differentiators. The app should show: exact token count; percentage of context used; color-coded context state (green healthy / orange heavy / red needs attention); context composition; beginner-friendly explanation; technical details for advanced users.

When context gets high, HappyVibe should: warn visually → suggest compaction → ask the user before summarizing → let the user manually remove context items.

**Decision (Round 2):** Compaction is performed by a **dedicated Summarizer Agent**, not by ad-hoc prompting of the main session.

**Decision (Round 2):** Users can remove **everything except mandatory system/runtime context** — previous chat messages, loaded files, tool results, and sub-agent outputs are all individually removable.

Context breakdown should include, where possible: system prompt; AGENTS.md; current conversation; loaded files; tool definitions; available agents; sub-agent outputs; active task state; prior summaries. This feature is a core learning mechanism: users learn how agents work by seeing what the agent actually sees.

**Decision (Feedback round 2):** the context panel opens on a **summary of the categories** (name, item count, size, share of the window) and the user clicks a category to drill into its items — the full detail was too visually complex as a landing view.

**Decisions (Feedback round 1, implementation-verified):** the token gauge is always labeled — **measured** when Pi reports live context usage, **estimated** when derived, and an explicit "measuring…" state right after compaction (Pi cannot measure until the next response; showing cumulative totals there was misleading). Manual removal is pairing-aware (a tool call and its result are removed atomically — orphaning one causes provider errors) and only items from **completed turns** can be removed (removing the in-flight turn's items sends the model into a re-execution loop). Removal marks persist in the session file and survive compaction, reload, and resume.

**Decision (Feedback round 3, 2026-07-14) — rewind:** a user question carries a **rewind** (refresh) affordance. Rewinding shows a confirm dialog stating **files on disk are NOT rolled back**, then removes every message after that point from the transcript and from Pi's context, and returns that message to the composer for edit + resend. It builds on the existing completed-turn context-removal mechanism (above); the in-flight turn is never rewound (the session must be idle). **V1 scope is chat-only** — reverting file/shell side-effects is explicitly deferred to **V2**.

**Decision (Feedback round 7, 2026-07-30) — rewind restores files too (supersedes the round-3 "chat-only" scope):** rewinding a user message offers **three scopes** — *Conversation only* (the round-3 behaviour, and the default), *Conversation + files*, and *Files only* — with the **affected file list shown in the confirm dialog** before anything is committed. This supersedes the round-3 rule that V1 is chat-only: file rollback is **V1**, not V2. The mechanism is a HappyVibe-native **content-addressed snapshot store with no git binary** — consistent with §14's tarball-based git import and §3's standalone promise — taking **one whole-workspace manifest per user prompt**, keyed by the turn's first `toolCallId` (the only identifier durable across a reload; renderer transcript ids renumber). Whole-workspace capture is what makes the promise honest: bash and MCP side effects are covered without having to attribute them to a tool, so there is no "we could not restore this" gap. It also needs **no bridge changes** — main already sees both the single user-prompt entry point and the Pi event stream — so nothing in the pinned runtime is touched. Three published Pi extensions were read at source before deciding to build rather than vendor: `@ayulab/pi-rewind` is **GPL-3.0** and its picker is a silent no-op in RPC mode (`ctx.ui.custom` resolves `undefined` — the same class of finding as V6), `pi-chrono` restores conversation via `ctx.fork` which mints a new session id (colliding with respawn-resume), and `pi-rewind` (arpagon) writes commits and refs into the user's own repository and is inert outside a git repo. Guardrails: restore is **human-only and audited** (`who:"human"`; there is no rewind tool the model can call, mirroring §23's security invariant), a **safety snapshot** precedes every restore, and every file is **stale-checked** — one changed since the agent touched it (by a parallel session, by the user in the built-in editor, or externally) is **skipped and named in the result**, never overwritten. Edits outside the workspace root (§10) are never captured and therefore never restored (the walk starts at the workspace root). Snapshots are deleted with their session, capped per session, exclude the file tree's ignore list plus common build outputs (an excluded path is outside the manifest *and* outside restore, so a build directory can never be deleted), and record files over the editor's size ceiling as *not captured* rather than dropping them silently. Full proposal in Notion ("Rewind with file rollback").

**Decision (Feedback round 12, 2026-08-13) — the file scopes appear only when there are files (refines the round-7 dialog):** *Conversation + files* and *Files only* are **hidden**, not merely disabled, when a rewind would restore nothing. Two cases count as nothing and both hide: **no snapshot anchored at that message** (a steer, or a capture that failed), and **a snapshot whose diff is empty** because the agent only read. Today only the first is handled, and only by greying *Files only* — which still asks the user to reason about a control that cannot do anything. The ordering rule matters more than it looks: the preview is asynchronous, so while it resolves the dialog shows **Conversation only alone** and reveals the file scopes when the answer arrives. The reverse — render all three, hide on arrival — would make options disappear from under the cursor, which is worse than a control that was never offered.

**Decision (Feedback round 4, 2026-07-15) — complete, itemized breakdown:** the context panel must make every consumer of the window individually visible, not lumped into one "system prompt" figure. It enumerates, each with its size: the **base system prompt**, **custom instructions** (root + nested AGENTS.md and the user's system-prompt additions), **tool definitions** (count and, where derivable, their token weight), context files, conversation, tool results, and prior summaries. Anything Pi does not expose a measurement for is **labeled "not measured"** rather than silently omitted — the panel's job is an honest, teachable account of what the agent sees.

**Decision (Feedback round 5, 2026-07-16) — context UX overhaul:** the chat chip becomes a small clickable **% bubble** — green <35%, orange 35–80%, red >80% (supersedes the earlier 70/90 thresholds) — that opens the context panel. The panel gains a **visual composition surface** (color-coded proportional segments, inspired by Claude Code's `/context` view); **tool definitions become a drill-in** listing every tool with an *estimated* token size and a total (estimates from schemas, labeled "estimated" per the honesty rule); the **"Other" category is eliminated** by categorizing items properly bridge-side — it appears only when genuinely needed, clearly labeled, and is hidden when empty. **Compaction is Pi-native:** the implementation always used Pi's `compact` RPC — this supersedes the Round-2 "dedicated Summarizer Agent" decision (the agent was never wired to compaction and is removed, §12) — and a manual **"Compact now"** is always visible in the context panel, not only in the red zone.

**Decision (Feedback round 6, 2026-07-29) — the breakdown must name things:** the panel's rows have to be a **meaningful named list**, not counts of anonymous items — falling back to "N items, total size" is acceptable only where no name exists, and anything genuinely unmeasurable stays **labelled** (never silently dropped). Three corrections. (1) **Tool definitions was a defect, not a presentation choice:** every row rendered as `(tool) ≈1 tok` because the bridge mapped Pi's `selectedTools` as spec objects when Pi passes plain **name strings** — losing the name *and* the size, so a 40-tool session reported ≈40 tokens instead of several thousand and its category share and composition segment were understated by ~100×. Tool definitions now show real names with per-tool estimates derived from each tool's actual schema. (2) **Skills become a drill-in** (per-skill name + estimated weight), superseding the round-5-era choice to keep the two skill lines informational on the grounds that per-skill detail lived in the Skills view — in the context panel the user is asking a different question ("what is this costing me right now"). (3) **Pi session-bookkeeping entries are hidden** (session, model change, thinking-level change, session info): they carry no message and zero tokens, and were the only remaining occupants of "Other", which round 5 already promised to eliminate.

**Decision (Feedback round 9, 2026-08-01) — compaction is a visible transcript boundary:** the transcript must not imply the model remembers what compaction removed. A compacted session restores **back to the most recent compaction and no further**, ending at an **info bubble** ("Earlier messages were compacted into a summary") that names the compaction **reason** (manual / threshold / overflow) — because Pi's auto-compaction is on by default, so a compaction the user never asked for has to be legible as such. Above the bubble, **"Load earlier messages"** is **display only**: it reveals the pre-compaction history from the session file, dimmed under an "earlier — not in the agent's context" divider, with no warning and nothing irreversible — displaying old messages and re-injecting them into context are different operations, and re-injection is not offered at all (it would duplicate the summary Pi already wrote, cost real tokens, and Pi exposes no un-compact API). **One bubble per session, at the latest compaction**, counting any earlier ones: Pi honours only the most recent compaction, so that is the only honest boundary — and a real session was found holding two compaction entries with the same `firstKeptEntryId`, which a per-compaction bubble would have rendered as two identical adjacent markers. **Removal marks (above) are applied to the loaded region too** — removed means removed everywhere, so the dimmed region means exactly "compacted away" rather than "everything that ever happened". The boundary is **derived, never persisted**: Pi's `compaction` entry carries `firstKeptEntryId` and its own context rule is `[latest compaction] + entries from firstKeptEntryId onward`, so the split is Pi's rule read back from the session file — the same "one source: the file, not `get_messages`" reasoning as the cost ledger (§19), and it needs no bridge change, no new RPC and no pin bump. **Live sessions keep today's behaviour** (everything shown, compaction notice inline): the renderer's items carry no session-entry ids, so anchoring the boundary live is disproportionately expensive and every cheap approximation is wrong by the size of the kept tail (73 entries in the session measured). Deferred with reasons: **disabling Pi's auto-compaction** so the red-zone banner is the only trigger — it removes Pi's safety net, turning an overflow into a hard provider error, and deserves its own decision — and live-session parity. Full proposal in Notion ("Compaction UX improvements").

**Decision (Feedback round 11, 2026-08-04) — the files the user has open are part of the context, as paths only:** the agent is told which files the user currently has open in the built-in editor — **workspace-relative paths, never contents** — so it can see what the user is looking at without being handed the bytes. It rides the **per-prompt** seam the `@`-mention blocks already use, so it needs no new channel: the renderer already holds the open-tab list and already passes an array through the prompt IPC. Consequences of that choice, taken deliberately over the per-turn system-prompt hook: the paths are counted under **Conversation** in the breakdown (like mentions, so no new category and no silent inflation of the system-prompt figure, which §9's honesty rule would otherwise require disclosing), and they are **stripped at render time** exactly like mention blocks so the user's own message bubble reads as typed. Because a per-prompt block would otherwise leave turn 1's stale list sitting in context beside turn 5's, the block is **sent only when the list has changed** since that session's previous prompt — so the most recent block is always current, and an unchanged set costs nothing. One **global** setting, **on by default**, on the System prompt page (§16) — not per workspace: "which files am I looking at" is a property of the user's habit, not of a project, and the tri-state that per-workspace scoping implies buys nothing here.

## 10. Permissions

Permissions are central to the product. The app supports a layered permission model:
- **Layer 1 — Tool permission** (e.g. allow file reading in this workspace);
- **Layer 2 — Project permission** (e.g. allow file editing only inside this workspace folder);
- **Layer 3 — Command pattern permission** (e.g. always allow `npm test`, ask before `rm`, deny dangerous shell commands).

**Decision (Round 2):** HappyVibe is a **wrapper over Pi's permission capabilities**: enforcement delegated to Pi's extension ecosystem, HappyVibe providing the UI. **Superseded by the feasibility spike (V6) and shipped accordingly:** the candidate permission extension turned out to be TUI-only in RPC mode, so the **HappyVibe bridge extension owns the 3-layer rule engine itself** (tool / project-path / command-pattern; allow-ask-deny; most-restrictive-wins). Rules exist at two scopes — a **global ruleset plus per-workspace overrides** — with global rules edited in Settings and workspace rules edited in each workspace's own settings, and a live "test a call" preview using the same engine.

Dangerous mode should be visible, not hidden. When enabled: it must remain visibly active; the UI should warn the user; there should be an obvious way to disable it; it does not need to expire automatically. HappyVibe maintains an audit log of agent actions.

**Decision (Feedback round 3, 2026-07-14) — workspace-scoped grant:** the permission prompt offers five choices — **Allow · Allow for session · Allow for Workspace · Always allow · Deny**. "Allow for session" stays ephemeral (in-memory, reset on respawn); "Allow for Workspace" persists an allow rule at the workspace scope and "Always allow" at the global scope, both written through the same rule engine as Settings (so they show up as editable rules). V1 persists these at the **tool layer** (allow this tool in this workspace / everywhere); command-pattern granularity for one-click grants can follow.

**Decision (Feedback round 3, 2026-07-14) — persistent full bypass (reverses the "never auto-allow" invariant):** in addition to the session-only dangerous mode, a persistent **"Bypass ALL permissions"** toggle is available in **global and workspace settings**. This deliberately **supersedes the earlier invariant that permission prompts never auto-allow** — the user asked for a persistent YOLO mode. Guardrails: enabling requires a scary confirm dialog; while active a **red banner** shows in every affected session (reusing the dangerous-mode banner); every auto-allowed call is still audit-flagged. Precedence mirrors model resolution — **workspace overrides global** (`workspace ?? global ?? off`, per-workspace tri-state so a workspace can turn a global bypass off). The setting is resolved at spawn and re-applied on respawn (unlike session dangerous mode, which resets to safe on respawn). Changing it applies live to affected sessions (global → all; workspace → that workspace's), reusing the MCP live-reload scoping.

**Decision (Feedback round 5, 2026-07-16) — workspace confinement:** by default, file tools (read/write/edit/grep/glob/ls/…) targeting a path **outside the workspace root** trigger an **ask** prompt — including reads that are normally auto-allowed inside the workspace. Bash is deliberately not path-inspected (it stays under command-pattern rules — honest about what is enforceable). Explicit rules and one-click grants take precedence through the normal rule engine, and the full-bypass setting bypasses this check like everything else.

**Decision (2026-08-21) — the gate covers sub-agent children too, by boundary rather than by prompt:** the layered model above described the *parent* turn only, and a sub-agent child sat outside all three layers. It cannot be brought inside them the same way — a child process has no route to a human, so a prompt raised in one silently fails closed — so the same guarantee is reached differently: the human approves the child's whole reach at delegation time, a capability ceiling makes that reach unexceedable, and the identical rule engine runs inside the child with **ask clamped to deny** (there is nobody there to ask). Layer 3 in particular only exists inside a child because of that guard: upstream's native child gate refuses `bash` rules outright. Full details, including why bypass still extends to children and what an unattended run does, are in §12. This is what makes the product claim true as stated rather than true of the parent turn only.

**Decision (2026-08-30) — the prompt names identifiers verbatim:** three of the gate's rule names are *virtual* rather than real tool names — `subagent:<agent>`, `mcp:<server>_<tool>` and `browser:<host>` — and the tail of each is an identifier the user themselves supplied: an agent filename they wrote, a server's own tool id, a hostname. The modal's headline ran all three through the same prettifier that turns a built-in tool name into prose, so `subagent:code-explorer` rendered as **"Subagent:code explorer"** — title-cased, hyphen eaten — in the headline of the very prompt that grants that delegation, while the boundary block immediately below correctly said `code-explorer` and the audit row said `subagent:code-explorer`. Three spellings of one name on one screen. Identifiers now render exactly as written (**"Sub-agent: code-explorer"**, **"MCP: github\_create\_issue"**, **"Browser: example.org"**). This is the smaller sibling of the standing rule that a prompt shows the **factual** action and never the model's `intent` (2026-07-14, §7 and §28): editing the name of the thing being approved asks the user to consent to a string that appears nowhere else — not in their agent file, not in the rules editor, not in the audit log. It matters most for **MCP and browser** calls, which have no boundary block beneath them and whose factual summary sits behind the collapsed details toggle, so there the headline is the only name on screen.

## 11. Audit Log

The audit log records important agent actions: tool calls; command executions; file reads/edits; created/deleted files; permission approvals/denials; dangerous mode activation/deactivation; model/provider changes; context compactions; AGENTS.md edits; sub-agent invocations; rewind file restores (§9).

**Decision (Round 2):** the audit log is available at **both session level and workspace level**. Export as JSON/Markdown is post-V1.

**Decision (Feedback round 15, 2026-08-16) — "dangerous" stops eating the log, and one-shot model calls join it:** with bypass on, every call logged `source:"dangerous"` in red, so the column carried nothing. Three fixes together: (a) that source **renames to `bypass`**, calm colour — red stays reserved for the *destructive* badge, which is about the command, not the mode; (b) **the rule engine still runs under bypass** and the row records what *would* have happened ("bypass · rules would have asked") — the teachable version, and the reason the column exists; (c) the page gains **decision/source filters**. Separately, the **one-shot model callers** (session titles, the commit message and the PR draft — §19) each log an audit entry naming what ran, which model, and the estimated tokens. *(Corrected 2026-08-30: this said **four** and counted the AGENTS.md draft among them. There are **three**. The AGENTS.md draft is a delegation and is audited as one — §15. Worse, the `agents-md` row type was wired on 2026-08-16 into a handler that had already been dead for a month, so **no such row has ever been emitted**: the type, its unreachable "drafted AGENTS.md" label and the dead handler are all removed rather than kept for a history that does not exist.)*

**Decision (2026-08-21) — sub-agent children get audit rows of their own, and deliberately not one per tool call:** "sub-agent invocations" in the list above meant the parent's *delegation*; what the child then did was invisible. The child guard (§12) now records every decision it makes, and those land in the log with the run id, the agent name and their own source label, so a denial inside a child reads as clearly as one in the parent turn. Each run also leaves **one rollup row** (tools attempted, tools denied) so a completely uneventful child still leaves a trace rather than nothing. Ingesting *every* child tool call is deliberately deferred even though the route is cheap and already on disk: a forty-tool child run becomes forty rows, which buries the permission story these rows exist to tell. Ingestion reads the run's JSON artifacts — never rendered text.

## 12. Agents and Sub-Agents

V1 includes three built-in agents:
1. the **Code Explorer Agent** (sub-agent for codebase exploration);
2. the **Summarizer Agent** (used for context compaction);
3. the **agents-md-maker Agent** (explores a project and drafts an AGENTS.md for the user to review — it never writes the file itself; see §15).

**Decision (Feedback round 5, 2026-07-16):** the **Summarizer Agent is removed** — compaction always ran on Pi's native `compact` and the agent was never wired to it (§9). V1 ships **two** built-in agents: Code Explorer and agents-md-maker. The agents-md-maker's write behavior is also revised (structured output written by the app — see §15).

**Decision (2026-07-17) — async delegations (supersedes the "single blocking tool call" model):** sub-agent delegations are **asynchronous by default** (`asyncByDefault` in the bundled pi-subagents config; the model may still pass `async:false` for a quick inline lookup it wants to block on). The main agent's turn **ends when the delegation is dispatched**, so **the user keeps chatting while sub-agents run** — this reverses the earlier "messages queue because a delegation is a single blocking tool call" behavior, which now applies only to explicit synchronous (`async:false`) delegations. The sticky run cards track a **detached** run for its whole life (spawn → live status → completion), decoupled from the tool-call lifecycle, each with an **interrupt (stop)** control; a card turns amber when its run needs attention. Results are **auto-delivered**: pi-subagents injects a `subagent-notify` message and triggers an assistant turn to fold the result in — only the final output enters the main context (the isolation contract is unchanged). An **active async run protects its session from hibernation and MCP live-reload** (it counts as busy) so a respawn can never orphan a running delegation. Wire shapes: `docs/validation/d1.md` §hv.subagent.

**Decision (2026-07-17, refinement) — never block on the result:** to actually deliver "keep chatting", the main agent must NOT sit and wait after delegating. pi-subagents otherwise steers the model to call its `wait` tool (which re-blocks the turn); HappyVibe intercepts `wait` and returns guidance to end the turn instead — the result folds in on its own turn when ready. The model is told which sub-agents exist and to delegate directly (skip the discovery `list` step). Behavior varies by model: instruction-following models do this cleanly, looser ones occasionally still list first — acceptable, not a correctness issue.

**Decision (2026-08-17, measured during the 0.50 bump) — the run card is raised by the app, and the live child transcript is gone until upstream restores it:** pi-subagents 0.50 routes every top-level delegation through its workflow/mission machinery, and that path emits a completion event but **no start event** — so a card raised by upstream's lifecycle relay never appeared at all, showing the user nothing for a whole async run. The card is therefore raised and identified by HappyVibe itself, from the delegation's own tool result (`details.asyncId`), which needs no cooperation from upstream and survives whichever path it takes next. In the same change 0.50 stopped streaming child progress altogether (`tool_execution_update` is not emitted), so the sticky card's expansion shows **per-child status while running and the transcript on completion** — the "live child transcript" promised above is not currently deliverable for either foreground or async runs, and the app must not pretend otherwise. Everything else in §12 holds: the run card still appears at dispatch with the task text, still tracks status and elapsed time, and still slides away on completion. Measured shapes and the probe that found this: `docs/validation/d1.md` §pi-subagents 0.50.

**Note (2026-08-17, measured) — isolation holds, but a blocking delegation is no longer cheap:** the child transcript still never enters the main agent's context, so §12's isolation contract is intact. The *volume* is not: a `async:false` delegation now inlines the whole workflow return record (launch-contract digest, extension hashes, artifact paths, usage, acceptance scaffolding) and measured ~5 KB of context to carry a one-word answer, against ~1.2 KB for the async path the app defaults to. Recorded rather than accepted: it is upstream's shape, it is watched by a test bound, and it is the argument for keeping delegations async. **Re-measured at 0.51 (2026-08-19): ~14.8 KB**, of which the child's own answer was only 4.6 KB — so upstream's envelope around the answer roughly doubled again, to ~10.2 KB, while the async receipt is unchanged at ~1.2 KB. The test bound now watches the ENVELOPE separately from the child's answer, because a more talkative sub-agent legitimately costs more and a fatter wrapper does not. Async remains the default and the recommendation; nothing about the isolation contract changed.

**Decision (2026-08-17, Migrate-to-0.50 round) — the wait tool is disabled at source, and the name guard stays:** pi-subagents 0.50 adds an official off-switch (`waitTool: {enabled: false}`, written by `writeSubagentConfig` alongside `asyncByDefault`), under which `subagent_wait` returns immediately instead of re-blocking the turn. HappyVibe sets it AND keeps the `WAIT_TOOLS`/`isWaitTool` guard as the second layer: a renamed config key fails silent, a renamed tool name fails the contract test loudly — and the guard's guidance text remains what the model actually sees when it tries to wait. Per-task blocking discretion is unchanged and lives where it always did: `async:false` at dispatch (the 2026-07-17 decision above), never in a post-dispatch wait. Upstream's `nonBlocking` wake-subscriptions are not used — completion already wakes the session on its own turn.

**Decision (2026-08-19, Migrate-to-0.51 round) — a respawn must not orphan a delegation, and 0.51 made that our job:** pi-subagents 0.51 scopes async completion delivery to the Pi **process** that launched the run (upstream #1225, guarding against two concurrent windows sharing one session file). The owner id is a random UUID minted per process, and delivery is refused outright when it does not match — with no config off-switch and, unlike the result watcher, no fallback. HappyVibe respawns Pi deliberately (hibernation wake, MCP live-reload, app relaunch) and resumes the SAME session file precisely so a detached run is never orphaned, so at 0.51 that promise would break silently: the child's artifact lands on disk, the run card resyncs, and the answer never reaches the model. HappyVibe therefore **claims the owner id itself**, deriving it deterministically from its own session identity before pi-subagents can mint one — same session respawned, same id; two different sessions, two different ids. This restores the 0.50 behaviour and is what #1225 actually intends, because HappyVibe never runs two Pi processes against one session file. It is a reach into an upstream internal and is pinned like the other ones: a contract test asserts the name, the mint site and the refusal, so the day upstream changes any of them fails loudly rather than quietly dropping results.

**Note (2026-08-19, measured in the running app) — an async delegation does NOT outlive its session's Pi process, which makes the busy-gate load-bearing:** the word "detached" above describes how a run behaves in the CHAT (the turn ends at dispatch, the user keeps typing, the result folds in on its own turn) — it does **not** describe an OS process that survives its parent. Measured while a real delegation ran: the run's own record names the **session's Pi process** as its owner, its child agent is an ordinary child of that process in the app's process group, and no detached process group existed on the machine at all. So the guarantee in the 2026-07-17 decision above — an active async run keeps its session busy, so hibernation and MCP live-reload cannot respawn it mid-run — is not a belt-and-braces nicety: **it is the only thing standing between an in-flight delegation and being destroyed outright.** If that gate ever regresses, the user loses the answer with no error, which is why it is covered by tests rather than left to review. Quitting the app mid-delegation likewise ends the run, and its artifact remains on disk unread. The one case that DOES survive is a sub-agent that had already finished and written its result when the session went away: that result is picked up and delivered when the session is next opened — which is what the completion-owner claim above exists to make work, since upstream would otherwise refuse a result written by a process that no longer exists, permanently and without telling anyone. Everything else in §12 is unaffected — the chat-level behaviour users see is exactly as described.

**Decision (2026-08-19) — the isolation contract is written down, not inherited:** 0.51 adds a `defaultSubagentContext` setting deciding whether a child starts `fresh` or **forks the parent's session**. Its default is `fresh`, which is what §12's isolation contract has always assumed, so nothing changes today. HappyVibe writes `fresh` explicitly anyway (beside `asyncByDefault` and `waitTool`), because a future default flip to `fork` would hand every sub-agent the parent's entire transcript — an isolation break with no user-visible symptom and no failing test to announce it. Stating the value costs one line; inheriting it costs the contract.

**Decision (2026-07-17) — sub-agent `intent` is optional (carve-out from §7):** the delegation `task` is already a good customer-facing headline, so `subagent` **advertises but does not require** the model-authored `intent` (the UI uses `intent ?? task`). This reverses §7's "every registered tool requires intent" for `subagent` only — a hard requirement made looser models fail their first delegation on a missing `intent`. `mcp`/AskUserQuestion keep required intent (they have their own factual fallbacks).

**Decision (2026-07-19, locked) — sub-agents are blocked in Plan Mode (V1):** while a session is in Plan Mode (§23) the `subagent` tool is blocked — a child Pi process carries its own tool set, so guaranteeing read-only across the child needs its own validation pass, deferred past V1. An in-flight async delegation started *before* Plan Mode is entered is **not** cancelled (the plan gate applies to new calls only); its completion lands normally. **Superseded in part on 2026-08-21 — see the plan-mode half of the boundary decision below; the in-flight carve-out survives unchanged.**

**Decision (2026-08-21, Subagents-permission-gap round) — a delegation is a BOUNDARY the human approves, and the child is physically held inside it:** until now a sub-agent child ran with no permission prompt, no audit envelope and no rule engine — the one live hole in the claim that everything goes through the same gate, and the reason plugin `agents/` is still refused (§25). A child **cannot** be brought into the existing gate: it runs `--mode json -p` with stdin ignored and a no-op UI context, so a prompt raised inside it returns `undefined` — fail-closed, but mislabeled and silent. The model is therefore approval **at the boundary**, enforcement **below it**, in four layers: (1) the delegation itself prompts as today, but the prompt is enriched from pi-subagents' side-effect-free `preflight` — agent, effective tool allowlist, an explicit callout when that set includes `bash`/`write`/`edit`, declared skills, fan-out ability and context mode — and it gates under the virtual rule name **`subagent:<agent>`** (the `mcp:<server>_<tool>` / `browser:<host>` pattern), so "Allow for session" on a read-only explorer never covers a bash-wielding one. The resolved model is deliberately *not* shown; it would cost real plumbing and the user already knows their session model. (2) A **capability ceiling** registered by the bridge makes the approved boundary unexceedable by the child and every descendant, whatever the agent file, a plugin or the model asks for; it rests at read-only plus `denyExtensions`, which also closes a hole the parent never had — a child with no declared `extensions` was ambient-loading anything planted in `<agentDir>/extensions`. Because upstream treats a present ceiling as the declared tool set for an agent that declares none, this **also** replaces "no `tools:` means Pi's full builtin set" with a read-only default. (3) A **child guard** injected by the `pi-node.sh` wrapper applies the same rule engine inside the child with **ask→deny clamping** — a call the parent would prompt for is denied, with a reason naming the boundary and pointing escalation back to the parent turn. It is the only place `bash` policy can live, because upstream's native gate refuses bash outright. (4) ~~pi-subagents' own native `permissions` config sits underneath as a redundant floor~~ — **built, measured and removed on 2026-08-21; the app deliberately writes no `permissions` key.** The floor is written once at startup while a boundary is approved *per delegation*, so any rule in it is unconditional, and upstream's decision function takes only `(rules, toolName)` — there is nowhere to pass a boundary. That makes it redundant when a tool is outside the approved boundary (the ceiling has already removed it from the child's `--tools`, so there is nothing left to deny) and actively harmful when it is inside: measured, a child whose boundary included `write` and whose rules explicitly *allowed* it had the write silently fail. The prompt would promise "It can change things with: write", the user would grant it, and nothing would happen — a worse failure than having no boundary at all, because the user believes they granted something. Three layers, not four; the absence is pinned by test so it cannot be reintroduced by good intentions. Bypass extends to children — bypass means bypass — and their calls are still audited. Detached and scheduled runs enforce identically with no human present: the ceiling travels in the environment and the guard travels in the wrapper, so neither needs a UI to be reachable. **The plan-mode half:** with the child's toolset now a fact the host controls rather than a property of the agent file, the 2026-07-19 block above loses its stated reason, so a delegation whose resolved toolset is read-only is **permitted while planning** and launches under a read-only ceiling — blocking exploration during the phase that exists for exploration was cost without benefit. Anything wider stays blocked, and the mechanism is a typecheck failure rather than a silent allow (§23). Requirements, measured mechanics and the adversarial-agent cases: the "Subagents permission gap" Notion doc.

**Consequence worth stating (2026-08-21):** an existing permission rule or grant written against the bare tool name `subagent` **stops matching** — the engine anchors a tool-layer pattern, so `subagent` no longer covers `subagent:code-explorer`. That is deliberate and is left to break: a blanket "allow all delegations" is exactly what per-agent naming exists to remove, and the failure direction is more prompting rather than less, so it needs no data migration. Anyone who genuinely wants the old blanket grant can write `subagent*`, which still works. The three directions (old exact rule no longer allows, glob still allows, per-agent rule covers only its own agent) are pinned by test.

**Decision (2026-08-21) — the live child transcript comes back, on demand:** the 2026-08-17 note above records that 0.50 stopped streaming child progress and that the app "must not pretend otherwise". pi-subagents 0.52 supplies the honest replacement: `/subagents-inspect-rpc` returns a child's task, a bounded transcript window and its final output **on request, with no model turn**, and it keeps working after the result has been delivered. Main drives it as a slash command exactly like `/hv-tools`, so the sticky run card's expansion shows a real transcript again rather than status-only. Upstream has separately documented the *absence* of inline live projection for async workflows as intended (#1229/#1230), so this is the supported route rather than a wait for streaming to return — pull on expand, not push on every child token. **Amended 2026-08-28 (pi-subagents 0.58): streaming DID return for the blocking path**, so read #1229/#1230 as scoped to async workflows rather than to delegations in general — the sentence above over-generalised it. A blocking (`async:false`) delegation now emits `tool_execution_update` again, measured 53 times on one run, carrying the same `partialResult.details.results[]` projection the renderer has mapped all along; only the delivery had been withdrawn, not the shape, so nothing needed rebuilding to take it back. The pull-on-expand route stays exactly as described and stays the one that serves ASYNC runs, which is the path the app defaults to — so this is an addition to what the card can show, not a replacement for it.

**Decision (2026-08-29) — a model the app is silently NOT using has to say so:** pi-subagents 0.57 caches "this model failed" verdicts and then **skips that model on every later delegation**. One flaky child is enough — the reason seen in the wild was *"Subagent produced no output (possible model cold-start or empty response)"* — the default TTL is **24 hours**, and the store is keyed per-UID, so it spans every session and every workspace rather than the run that tripped it. Upstream's only signal is a `console.warn`, which reaches a developer's terminal and a user not at all. So the chat kept showing the model the user chose while their sub-agents ran on a fallback and were billed at that fallback's rate — the exact inverse of §2's "see what you are spending" and of this section's rule that the app never quietly substitutes. Observed on a real install: `openrouter/qwen/qwen3.8-flash` excluded for a day with nothing on screen. 0.58 sharpens it (upstream #1556): an *explicitly* requested model now fails **closed** instead of falling back, so a per-agent model override plus one empty response makes that agent's delegations simply fail for a day. **Two responses, and neither is to fight the mechanism** — absorbing a genuine cold start is what it is for. First, the TTL is configured down to **five minutes**, which still absorbs a blip but cannot cost a day; because setting the key explicitly also shortens records already on disk, a stale 24-hour entry self-heals at the next start rather than needing a file deleted. Second, every live exclusion becomes an **audit row** naming the model, the reason and when it lapses — §6's home for what the app did on your behalf, reported when a delegation starts, because that is the call being rerouted. **The row is a third row TYPE, not a decision.** `AuditDecision` is allow / allow-session / deny, a permission vocabulary; bending a model-availability fact into it would repeat precisely the misreport that `wouldHave` exists to prevent (§6). It follows the one-shot row's shape instead, and like that row it carries **no cost and no token figure**, because it has none — §19 ruling 3's "unknown price rendered as a number" applies here too. **Main owns the store's path rather than re-deriving it:** upstream defaults to an internal `os.tmpdir()/pi-subagents-<scopeId>` layout, and re-implementing an upstream storage location is the move the MCP keychain drift already punished (§13), so the app sets pi-subagents' own documented `PI_MODEL_EXCLUSIONS_PATH` and reads a file it chose. Evidence: `tests/model-exclusions.test.ts`; wire shapes in `docs/validation/d1.md`.

**Decision (2026-08-22, Sub-agent-cost round) — a running delegation shows what it is costing, on the line that stops it:** §2 promises the user can see what they are spending, and a delegation was the one place that money moved with nothing on screen. The run card's status line gains live tokens and dollars beside the elapsed time — `working · 3m 18s · 41k tok · ~$0.04` — climbing turn by turn while the child works, on the same line and the same glance as the existing STOP control, so "this is getting expensive" and the means to end it are never separated by a navigation. The numbers come from the child's own Pi session file on the poll we already run (see §19's sub-agent-cost decision for the source and the billing rules; every figure is Pi's own, and the app never prices anything). Two shape constraints, both measured rather than chosen. **The collapsed card gets no cost footer:** it lingers briefly on completion and then slides away, so a total placed there would be a number that vanishes — the permanent record is the in-flow tool card in the transcript, whose expanded trace already carries per-child `tokens · turns · cost` and now keeps it honestly (`~` for an estimate, `plan` for a flat subscription, `$?` for tokens burned at an unknown price). **A reopened session shows the same numbers**, re-derived by the same parser over the same file rather than by a second mechanism that could agree only by coincidence. Nothing here gates or limits a delegation: there are no budgets and no thresholds, so the display stays neutral and factual with no colour-coded panic state (§19).

**Decision (2026-08-28, pi-subagents-0.58 bump round) — upstream's own external-CLI agents are refused at source, because the three-layer guarantee cannot reach inside them:** pi-subagents 0.58 grows upstream's builtin roster from 7 agents to **13**, and the six new ones (`claude-code`, `claude-code-writer`, `codex-exec`, `codex-exec-writer`, `cursor-agent`, `cursor-agent-writer`) are `runner: external-cli` — a third-party CLI in its own process, governed by *its* configuration. The capability ceiling cannot bound it, the child guard cannot run inside it, and its tool calls never reach the audit log; upstream refuses `ask`/`deny` rules for external runners by design and withholds extension authority from them. They are delegatable the moment the pin lands, with no external-CLI-specific gate upstream and no user-visible sign — so the 2026-08-21 decision above would quietly stop being true for six agents the model can pick on its own, and the `-writer` variants would write to the tree under no boundary at all. HappyVibe therefore **disables exactly those six at startup** (`subagents.overrides.<name>.disabled = true`, the same startup-write as `writeSubagentConfig`) and keeps the seven native ones, which are ordinary Pi children the ceiling governs like any other. Upstream's blunt `disableBuiltins: true` was rejected: it is all-or-nothing and would also remove `worker` and `reviewer`, the two the next round wants to adopt. The absence is pinned by test, so a later pin cannot re-open the hole by accident. Running an external agent stays a **product** decision, taken deliberately with the honesty it requires — a delegation modal that says "external agent — HappyVibe's rules do not apply inside it; its own permission config governs" — and never a side effect of a version bump. **The isolation contract gains its second stated default:** 0.58 flips `inheritGlobalContext` so a child no longer inherits the operator's global context file, which is what §12 has always assumed, so both bundled agents now state `inheritGlobalContext: false` explicitly for the same reason `defaultSubagentContext: "fresh"` is stated — a future flip back would hand every sub-agent the operator's global context with no user-visible symptom and no failing test to announce it. **One correction to the record:** "every delegation is a workflow", true from 0.50, is false from 0.55 — an async single-child delegation returns `mode: "single"` with `asyncId`, not `mode: "workflow"` with a `missionId`. The run card is unaffected because it was already keyed off `asyncId` rather than off the mode, which has now changed twice underneath that key. **Corrected 2026-08-29:** this decision first recorded that `subagent:async-started` is never emitted — it is, from `async-execution.ts`, and the claim came from a grep that matched only the constant's own definition while every emitter references it by name. The narrower 0.50 measurement it was generalised from still holds (the WORKFLOW path never emitted it), and 0.55's unwrap put delegations back on the direct async path, which does. The card's re-keying from the foreground call stays load-bearing for a different reason: the notify carries no tool-call id, so it cannot caption a card correctly when two same-agent delegations are in flight (see the run-card caption decision). **Known gap, recorded not closed:** the seven native builtins are delegatable but invisible on the Agents page, which lists only the app-owned and project directories — users have agents the UI never shows. Surfacing them belongs with the write-capable-worker item, not with a pin bump. **Three product facts the bump's probes settled, recorded here because two of them retire open questions rather than opening work.** (1) *The child never thinks it is Pi* — already true, and now pinned: every agent except upstream's `delegate` resolves to `systemPromptMode: "replace"`, which selects `--system-prompt` over `--append-system-prompt` at launch, so a child receives only its own prompt. (2) *A child's thinking is available* — the child's own transcript carries real thinking blocks and 0.58 newly hands us its path (`results[].transcriptPath`), so showing a sub-agent's reasoning needs a path-confined file read and no upstream ask; not built here. (3) *The Agents page under-reports by more than upstream's builtins* — a probe found a user agent discovered from `~/.agents` that no HappyVibe surface lists, so "users have agents the UI never shows" is wider than the seven native builtins. All three belong to the fleet round. Evidence and the measured wire shapes: `docs/validation/d1.md` §pi-subagents 0.58.

**Decision (2026-08-29, the fleet round) — the delegation card finishes the glanceable-fleet story, and the Agents page stops lying about what exists:** five changes, one round, all resting on surfaces that already exist. **(1) A child gets the same context gauge the session has.** pi-subagents 0.57 added live context-window occupancy to a run's status file, separate from cumulative spend, and 0.58 delivers it: `steps[].tokens.window` (the child's latest turn, input plus cache-read) against `steps[].contextLimit` (the model's window, resolved from Pi's own registry), both rewritten on every child turn. It rides the 500 ms poll the card already runs and reuses the session gauge's own calm/amber/red thresholds, so "how full is this agent's head" reads in colours the user has already learned — the headline differentiator of §9, per child, which no competitor shows at all. **The card grows a second line to make room:** the status line already carries elapsed time, tokens and cost, so the gauge takes the header and the delegation's intent moves beneath it, rather than a fifth figure crowding one row. When the resolved model is absent from Pi's registry there is no limit to divide by, and the gauge then **does not render at all** — never a 0% or a full bar standing in for "not measured", the same rule §19 applies to an unknown price. **(2) A write-capable `worker` is bundled, and HappyVibe authors it rather than adopting upstream's.** The original P4 ask was a general-purpose sub-agent that can actually change things; it was unsafe to bundle before the 2026-08-21 boundary existed and is safe now for exactly the reasons that decision sets out — the modal already names `bash`/`write`/`edit` explicitly, gates under `subagent:worker` so a grant for a read-only explorer never covers it, and the capability ceiling holds the child to what was approved. No new safety machinery is required, which is the whole argument for doing it now. Authoring rather than adopting costs nothing and buys three things: agent precedence is builtin < package < user < project, so a file in the app-owned agent dir **shadows upstream's builtin of the same name outright**, meaning `worker` keeps `installBuiltinAgents`' content-hash edit detection, keeps the strict-tools contract test, and cannot change wording or defaults under us on a pin bump. It also takes upstream `worker`'s `defaultContext: fork` and its `defaultReads` out of play rather than inheriting them unexamined. **(3) The agent inventory is told honestly, because today it is not.** The Agents page reads two directories; pi-subagents discovers from six — its own packaged builtins, an env-supplied extra path, the app-owned agent dir, `~/.agents`, and both project agent dirs — plus agents contributed by installed packages, and it resolves the project root by walking *up* from the working directory rather than trusting it. So the gap is wider than the seven native builtins recorded above: a probe found a user agent from `~/.agents` that no surface lists, and no surface has ever listed a package agent at all. **The same enumeration also feeds the roster injected into the model's prompt each turn, which states that the agents listed are the full current list — a sentence that is false today**, and that is the more serious half: a user seeing a short page is inconvenienced, a model told a falsehood every turn delegates worse. Both are repaired at one source, by calling pi-subagents' own discovery rather than re-deriving six directories that would drift the first time upstream adds a seventh; it is a third reach into an upstream internal and is pinned by contract test exactly like the other two. **Package agents are listed, not refused** — unlike the external-CLI six they are ordinary Pi children the ceiling and the child guard govern, so being invisible *was* the problem and showing them is the fix. **(4) A fan-out's children can be stopped one at a time.** The card's STOP ends a whole run; upstream 0.55 added a child-scoped stop, and the app wires it as a second control that appears only when a run has more than one child — a single delegation has exactly one, where a per-child stop would be the run's own STOP wearing a second name. **(5) A sub-agent's reasoning is visible on request.** 0.58 exposes the child's own transcript path on both the foreground and async routes, and that transcript carries real thinking blocks, so the card gains a toggle that reads it on demand — off by default, costing nothing until asked. Two things are stated because they are easy to get silently wrong: the confinement root is the **app's sessions directory**, where pi-subagents writes its artifacts, and *not* the temp dir the status poller guards, so reusing the wrong guard returns nothing at all rather than failing; and this is the **first thinking surface anywhere in HappyVibe** — the main agent's own reasoning is not rendered today, so a sub-agent card will show something the chat does not. That asymmetry is accepted deliberately: a child's reasoning is the one the user has no other way to see, and it is the argument for a toggle rather than always-on. **What this round does not do:** nothing here clamps `context: "fork"`, which a model may still request per delegation. §12's isolation contract governs what enters the *parent's* context, and a fork changes what a child starts with, not what comes back; authoring our own `worker` removes the only agent that asked for it by default, which is most of the exposure. **Consequence for the count:** the round-5 decision above reduced V1 to two bundled agents; `worker` makes it **three** — Code Explorer (read-only), agents-md-maker (read-only, structured output) and worker (write-capable, boundary-gated).

**Decision (2026-08-30, UX-feedback round) — the resting state of a running agent is an avatar, not a card; and a finished delegation's card in the chat stops lying:** two reports, one round, and the first one amends the card anatomy the fleet-round decision above had just enlarged. **(1) The card is right for detail and wrong at rest.** A run card is ~3 rows tall and the fleet round deliberately gave it a fourth, so two concurrent runs plus a terminal push the conversation off the screen — the card became the resting state of something that is mostly *background* work. Every running sub-agent and every running agent terminal is therefore represented first as a **circle with an icon in it** (the robot glyph, the terminal glyph), laid out as one horizontal row where the stacked cards sat, **for both families and for a single run as well as for many** — "too big at first" means the first thing shown is small, not that it shrinks once things get crowded. The circle **animates its state** (pulsing while working, still when finished, amber pulse when the run needs attention) and its hue is **derived from the agent's name** — the deterministic-glyph argument `workspaceEmoji` already makes for the collapsed workspace rail, one surface over, and it means no new field to author on an agent and no migration. Clicking a circle opens **today's card, unchanged**, as an **overlay anchored to the left of the row**: it paints over the transcript rather than pushing it, at the stacking level the cards already use and deliberately **not** dialog tier, since it is a readout and not a modal. One expanded at a time, which is already the terminal stack's rule. **Two things the collapse must not cost, because both are locked decisions.** The 2026-08-22 decision put a running delegation's spend "on the line that stops it", and an avatar has no line — so **hover carries the facts and the STOP**: agent or terminal name, task or intent, elapsed, tokens, cost, and the control. And a run in `needs_attention` **promotes itself back to a full card**, because attention is the one state that must not be reachable only by a click; the amber pulse announces it, the card is what answers it. The context gauge the fleet round added is hover/expanded content now rather than header content, which is what buys the row back.

**Decision (2026-08-31, UX-feedback round 2) — the card the rail opens IS the expanded state, and its top-right control CLOSES rather than collapses:** the first cut kept each card's existing expand/collapse toggle, so clicking a circle opened a card that was still *shut* — one click short of showing anything, which is the opposite of what the avatar was meant to buy. A card now opens **fully expanded**: the delegation card shows its child transcript immediately, and the terminal card mounts its live emulator on open with no second click. The chevron in the top-right becomes a **✕ that closes back to the circle** — the run is untouched (main owns the PTY, and a delegation keeps running), which is why the control is a close and not a stop. Both cards' **header titles stop being toggles**: with no collapsed state to return to there is nothing to toggle, and on the terminal card a stray click on the title used to tear down the emulator you had just opened. Two consequences worth stating. A **promoted** (`needs_attention`) card gets **no ✕** — it has no circle to return to, and that state must not be dismissible, which is the whole reason it is promoted. And the terminal card's collapsed body — §26's cheap three-line tail — had nowhere left to live, so it **moves into the rail's hover readout** exactly as the 2026-08-30 decision said it would: `TerminalTail` reads main's rendered grid (never a second parser over raw PTY bytes, the mistake that once rendered `sleep 600` as `ssleep 600`) and is mounted only while a circle is hovered, so it polls in bursts rather than forever. **(2) A finished async delegation's in-chat card never updated, and had not since async delegations shipped.** Reported from a real session: twenty minutes after completion the transcript card still read "Waiting for the subagent to respond…". The cause is structural rather than a slip — an async delegation's `tool_execution_end` carries a dispatch receipt with no results in it, and the completion arrives later as an `hv.subagent` notify that updates only the **sticky** card, so the transcript card was stale three ways permanently: its dot read *dispatched*, its collapsed summary read "running in the background — result arrives when it finishes", and expanded it claimed to be waiting. Completion now also updates the **transcript** card, through the async-id → tool-call-id link the app already holds at dispatch and threw away, and the run's final cost lands on it — the card already refuses to say "waiting" when it has a cost, a guard written for reopened sessions that simply never fired live. **Expanding a finished delegation now shows the child's real transcript and final answer**, by wiring the on-demand inspection route that has been built and callerless since 2026-08-21: it costs no model turn, is scoped to the current session's children, and keeps working after the result has been delivered — so the card is worth opening rather than merely honest. The sticky card's own behaviour is untouched: it still shows the outcome briefly, still slides away, and the "Subagent finished — delivering results…" notice stays.

## 13. Tools

The tools list includes: tool name; human-readable description; source; permission status; enabled/disabled state; whether built-in, extension-provided, or coming soon. Future tool categories: MCP tools; CLI tools; API tools; skills; custom workflow tools. For V1, API import and CLI import are not supported.

**Decision (Round 2, revised in the feedback rounds):** MCP support is **deferred until after the post-V1 feedback improvements land**. When it ships, it will be provided through a Pi extension/package bundled in HappyVibe's curated runtime (candidate already identified: `pi-mcp-adapter`).

**Decision (2026-07-13):** MCP ships via the vendored **`pi-mcp-adapter`** (exact-pinned), not a native client — it embeds the official MCP SDK and registers through `pi.registerTool()`, so every MCP call flows through the existing bridge permission gate as `mcp:<tool>`. **Proxy mode by default** (one low-token `mcp` tool; the UI unwraps to the real server/tool everywhere — transparency lives in the rendering layer, not burned context), with a per-server "expose tools directly" toggle. Config is standard `mcpServers` JSON: global tier in the app agent dir, workspace tier in `.mcp.json` (shareable with other MCP hosts). Managed from the Agents & Tools page. Out of scope for v1: roots, MCP prompts, live `tools/list_changed`, session-tier config. Spec: `docs/superpowers/specs/2026-07-13-mcp-support-design.md`; plan: `docs/superpowers/plans/2026-07-13-mcp-support.md`.

**Decision (2026-07-13, Phase 2):** MCP OAuth is **host-driven in HappyVibe main** — the pi-mcp-adapter's interactive OAuth path is gated on `ctx.hasUI` and is a no-op in RPC mode. `src/main/mcpOAuth.ts` implements `OAuthClientProvider` from `@modelcontextprotocol/sdk`, opens the authorization URL in the system browser via `shell.openExternal`, listens on a `127.0.0.1` loopback callback server, validates the `state` parameter (CSRF), and calls `transport.finishAuth` to complete the code exchange. After successful auth, the transport is replaced with a fresh instance (SDK transports can't restart) and the server reconnects. Tokens are persisted as `AuthEntry` (stamped with `serverUrl`) in `<agentDir>/mcp-oauth/sha256-<sha256hex(serverName)>/tokens.json` so the adapter reads them at runtime with no re-auth. UX: servers requiring OAuth show a confirm-with-tools modal at add-time; per-server Authenticate / Log out actions are available in the Agents & Tools page; a non-blocking startup status sweep surfaces `needs-auth` servers. The contract test `tests/mcp-adapter-authformat.test.ts` gates any pi-mcp-adapter pin bump. Plan: `docs/superpowers/plans/2026-07-13-mcp-support.md`; validation: `docs/validation/m1.md`.

**Decision (2026-08-14) — the shared token file is gone; main asks the adapter instead (supersedes the storage half of the decision above):** `pi-mcp-adapter` 2.17.0 moved MCP credentials into the **OS keychain** (service `pi-mcp-adapter.oauth`, account `sha256-<hex>`) and now treats `<agentDir>/mcp-oauth/…/tokens.json` as a legacy artefact to **import and delete** — there is no opt-out. So the sentence above is false in the running app: main and the adapter share nothing, and it breaks in **three directions, not one**. The status read is the symptom that was noticed: main's probe answers from a file the agent does not read, so the badge is simply unrelated to what the session has, and it errs in **both** directions. Measured on the live install 2026-08-14: `miro` exists in both stores with **different access and refresh tokens ten days apart** — main's file fresh, the agent's keychain copy already expired — so the page reports `connected` about a server the session may be unable to use, which is §13 round 8's "signs in on the page but is unusable in a session" split running *forwards*. The mirror-image case (page says signed-out, session works) is structurally possible for any migrated server holding live tokens; it was initially reported for `notion`, but `notion` turned out to hold no tokens in either store, so its `needs-auth` badge was honest. Recorded because the wrong half was nearly built on. The other two are worse: **signing in again never reaches the agent**, because once a keychain entry exists the adapter returns it and deletes the fresh file unread; and **Log out does not log out**, because `deleteAuthEntry` removes only the file while the keychain credential survives and the session stays signed in. All three are fixed together — a Log out button that leaves a live credential behind is a promise the app makes and does not keep. The fix is **not** to re-mirror the keychain in main: that payload is chunked at 1000 characters behind a private manifest key with a Linux keyring-recovery subprocess behind it, and re-implementing an undocumented internal is exactly the move that just broke. Instead main uses the adapter's **public `pi-mcp-adapter/oauth` subpath** (added in 2.22.0 for "URL-bound OAuth token reuse by cooperating Pi extensions" — HappyVibe main is precisely that): `inspectMcpOAuthTokensForUrl` for the status read (status-only and deliberately non-migrating, so a probe never consumes anything), `updateMcpOAuthTokensForUrl` for persistence, and the same route for logout. **The division of labour is unchanged** — the adapter's interactive OAuth is still `ctx.hasUI`-gated, so main still owns the handshake; only *storage* moves behind the adapter's API. Because the adapter ships TypeScript source and a native `@napi-rs/keyring` dependency, main reaches it through a **one-shot Node sidecar** spawned on the existing `nodeExecPath()` route rather than a new root dependency or a native module inside the Electron bundle; ops batch per invocation so the startup sweep costs one spawn, not one per server. That sidecar must be an **esbuild bundle built at install time, not a script that imports the subpath** — measured, not assumed: Node refuses to strip types for files under `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, Node 22.21.1), a deliberate restriction rather than a missing flag, and a bare Node child has none of the `.ts` loader Pi gives its own extensions. `@napi-rs/keyring` stays external to the bundle so the native binding is required at runtime. **This forces a runtime pin bump, and that is not a one-line change:** adapter 2.21.2+ declares `peerDependencies: { "@earendil-works/pi-ai": "^0.84.1" }` (2.20.1 and earlier were `*`), so taking 2.25.0 drags `pi-coding-agent` 0.83.0 → 0.84.2, with `pi-subagents` 0.40.0 → 0.49.0 in the same pass and `typebox`/`yaml` following Pi as they must — the full pin-bump gate, contract tests plus the 14 live-Pi tests. Caveats surfaced by that bump are recorded on their own page, not folded here; the sub-agent consequences are addressed together in a later pass. The contract test keeps using the adapter's own `PI_MCP_ADAPTER_TEST_AUTH_STORE=memory` escape hatch (2026-08-14) so it can never read or write a developer's real keychain, and additionally pins the reverse drift — a future version dropping the subpath or returning to plaintext files would leave main talking to a store nobody writes, this bug with the arrows swapped. **One consequence for the startup sweep, and one non-consequence.** Reading a credential can raise a macOS keychain dialog, so the boot sweep now probes **stdio servers only** and remote servers are swept when the MCP page mounts, latched once per app run — an app must not open behind a password prompt, and a badge that resolves a moment after you open the page it belongs to is the better trade. That is a UX change, **not** an amendment to what the badge means. The non-consequence is the one worth recording: it was nearly concluded that main must stop reading the keychain altogether, on the evidence that "Always Allow" did not stick. It does stick — for a properly *signed* binary (measured: the Pi child, plain `node` in dev, is granted once and then reads in ~1 s silently). It fails only for the **ad-hoc-signed dev Electron helper** that main's sidecar runs as, which makes this a dev-signing artifact rather than an architectural one. Two further intuitions measured false: the binary that *created* an item still gets prompted, and aligning the sidecar's executable with the Pi child's fixes nothing. Separately and pre-existing: **the agent itself prompts** on its first MCP call per grant and has since 2.17.0 — main has never been in that path, so it belongs to the pin, not to this rewrite. Signing the app is expected to collapse all of it to one prompt ever; that is untested and is the first thing to check when signing lands. Source: Notion "☔ MCP issue"; validation: `docs/validation/m1.md`.

**Decision (2026-07-14):** MCP tool calls carry a **model-authored `intent`** like other registered tools (§7), so the agent's behavior reads as "Fetching this page to look for opinions…" rather than "MCP → notion_fetch". The bridge injects a required `intent` into the adapter's proxy tool schema (`requireIntent`, same mechanism as sub-agents/AskUserQuestion); the tool card shows the intent, falling back to a factual label enriched with a key argument (url/query/…). The **permission prompt always shows the factual action** (server/tool + key arg), never the model's self-authored intent, so a benign-sounding intent can't mask a risky call at approval time. Validation: `docs/validation/m1.md`.

**Decision (2026-07-14, direct-mode intent):** intent also covers **"expose tools directly" mode**. The adapter's direct executor forwards params verbatim to the MCP server (a strict server would reject an unknown `intent`), so the bridge injects the required `intent` into each direct tool's schema (identified via `sourceInfo.path` = pi-mcp-adapter) and then **strips it in its `tool_call` handler before execution** — Pi's documented mutable-input hook. The UI still sees the intent because `tool_execution_start` is emitted with the original model args before the strip; the server never sees it. Server tools that declare their own `intent` param are left untouched (no injection, no strip). The factual-permission-prompt rule above applies unchanged. Unit contract: `tests/intent-direct-tools.test.ts`.

**Decision (2026-07-14, live-reload):** MCP config/auth changes apply **live** to running sessions. Since Pi/the adapter read MCP config only at spawn (no live tool-reload API), adding/removing/authenticating/logging-out a server respawns the affected live sessions **resumed** (conversation preserved via the session file — the hibernation-restore path). Scope: a global change reloads all live sessions; a workspace change reloads that workspace's. Idle sessions reload immediately; sessions mid-turn or awaiting a permission prompt defer until they finish (never disrupted). Accepted trade-off, disclosed to the user via a transcript notice: a respawn resets that session's "allow-for-session" permission grants and dangerous-mode toggle to safe defaults. Validation: `docs/validation/m1.md`.

**Decision (Feedback round 1):** the tools list shows each tool's live permission state (allow / ask / deny), evaluated by the same rule engine that enforces it — the logic never forks.

Disabling Plan mode must do three things at once — hide the top-bar indicator, hide the composer chip, **and unregister `plan_start` / `plan_complete` / `plan_status_update`** — because the model can *enter* Plan Mode itself via `plan_start` while leaving is human-only (§23); hiding only the UI would strand a session in a mode with no visible exit. **Prompts are shown read-only, in full, with an append box** (never an override): the built-in text stays authoritative and visible and the user adds to it, reusing the append pattern of the global/workspace system-prompt additions — seeing the real prompt is the educational point, the same promise as the context panel. The **user's** own terminal is not switchable there — it is not a model capability.)* This supersedes three parent-page TODOs (editable plan-mode prompts · custom tool setup · disable built-in tools to limit context).

**Decision (Feedback round 8, 2026-07-31) — curated one-click MCP catalog:** the MCP page gains a **static bundled catalog** of **13** recognised servers (brand icon, name, category, one-line description) that install in one click, with a small input where the server needs one — delivering the catalogue the round-6 decision above promised as "a separate later build". The install mechanism itself is **already built** (`mcpSetServer` → `writeMcpServer` → `scheduleMcpReload`, and `McpConnectResult` already shows the discovered tools), so what this decision fixes is the six ways a one-click list could be unsafe. (1) **Remote-first** — an entry ships as a remote HTTP server wherever one exists; only the inherently-local three (shadcn reads the project on disk, Chrome DevTools and Playwright drive a browser on the user's machine) ship as `npx` stdio, and those cards are badged **"needs Node"** behind a one-time `node`/`npx` preflight. §3's standalone promise is kept by **disclosing the machine dependency before the click**, not by letting the existing red `failed` badge explain it afterwards. (2) **Bundled, not fetched** — a file shipped with the app and updated per release, consistent with the brand-icon font ("no network fetch — local-first") and §14's curated shortlist ("a static in-app list, not a marketplace"); the accepted cost is **staleness**, mitigated by verifying every entry against live vendor documentation at build time, because the source research's own headline finding is four archived servers still taking 380,000 installs a week. (3) **Secrets never enter the config file** — an entry needing an API key stores it **safeStorage-encrypted in app config** and writes only a `${HV_MCP_<NAME>_KEY}` placeholder into `mcp.json`, reusing §22's custom-endpoint pattern. This is load-bearing rather than cosmetic: the workspace tier writes `.mcp.json` **at the repository root, shareable and therefore committable**, where a plaintext key becomes a key in someone's git history. (4) **A confirm-install dialog** — clicking a card never installs immediately. It opens a dialog that **briefly presents the server** (what it is, what it lets the agent do, its category and vendor link), shows **exactly what will be written** (remote URL or the literal `npx` command, and which config file receives it), carries the **scope toggle defaulting to global** and any required input, and surfaces the "needs Node" warning for the three stdio entries. This is the **pre-install twin of the existing post-install confirm-with-tools modal**: that one tells the user what they actually got (the discovered tool list), this one tells them what they are about to add — a one-click list without it is a one-click list that installs things the user never read. (5) **The catalog never overwrites** — `writeMcpServer` is a blind upsert, so a click on a name the user already configured by hand **refuses to install** and names the collision, telling them to rename or remove the existing server first; the catalog never edits a server it did not create. (6) The adapter's interpolation contract is **verified in source, not assumed** (`pi-mcp-adapter@2.11.0`, `utils.ts:interpolateEnvVars`): the syntax is **`${VAR}` / `$env:VAR`, never bare `$VAR`** (that belongs to Pi's separate `models.json` interpolator — copying §22's spelling here fails silently), it applies to stdio `env` and remote `headers` but **not** to `url`/`command`/`args` (so a key belonging inside a URL path is header-configured or the entry is dropped — never written plaintext), and **an unresolved variable resolves to the empty string with no error**, so the install path verifies the secret actually reached the process instead of trusting interpolation. That contract now gates `pi-mcp-adapter` pin bumps with a contract test, exactly as `tests/mcp-adapter-authformat.test.ts` gates the auth format. **Slack and Figma are deliberately excluded, and GitHub ships token-based** — both allowlist pre-registered OAuth clients, and `mcpOAuth.ts` implements Dynamic Client Registration only, so either tile would be a button that cannot succeed. Slack documents confidential OAuth (pre-registered `client_id`/`client_secret`, DCR explicitly unsupported). Figma advertises a `registration_endpoint` but returns a bare `403 Forbidden` to every well-formed DCR request — verified 2026-08-01 with and without `scope=mcp:connect`, with `client_secret_post`, and with a browser UA, the `x-figma-rest-api-request-id` header proving the request reached Figma rather than a CDN edge. **GitHub hit the same wall** — its authorization-server metadata advertises no `registration_endpoint` at all — but was **kept as a key entry** rather than dropped: the server evaluates a bearer personal access token (a bad one returns `401 invalid_token`, not a rejected method), so it authenticates without DCR. All three wait on OAuth until HappyVibe registers a real client with them. The remaining OAuth entries were **audited live on 2026-08-01** by POSTing a well-formed DCR request to each advertised `registration_endpoint`: Atlassian, Notion, Linear, Supabase and Neon all returned 200/201 with a real `client_id`. A test pins that audited set, so adding an unaudited OAuth entry fails the suite rather than shipping a button that 403s. A further consequence: because a catalog server's key is stored encrypted and the config file holds only a `${HV_MCP_…}` placeholder, **main resolves that placeholder before probing** (`mcpResolve.ts`, mirroring the adapter's contract) — otherwise HappyVibe's own status badge would report `needs auth` for a server the agent can use perfectly well. **Installing also runs the whole chain automatically** (`hv:mcp-connect-flow`): connect, escalate to browser OAuth *only* on a genuine 401, then report the discovered tools — probe-first is what lets one path serve stdio, key- and OAuth-based entries alike. Firecrawl ships on its **header** form (`Authorization: Bearer`) — the vendor's URL-path key form is legacy and, being uninterpolatable, would have meant a plaintext key on disk. Source list: Notion "Curated MCP List" (§Build spec). Out of scope: remote-refreshed feed, community/user-submitted entries, a marketplace, install analytics, auto-update of installed servers.

**Decision (2026-08-03) — MCP-by-import, and the catalog/marketplace split (amends the round-8 out-of-scope line above):** §25 ships plugin marketplaces, which reverses that line's "a marketplace" for **plugins** while leaving the **MCP catalog** exactly as round 8 built it. The two surfaces differ in kind, and the split is recorded here so neither later reads as drift. A marketplace is a remote list **by definition**, so plugin marketplace files are **fetched** over HTTPS at the user's request; the MCP catalog stays a **bundled module**, and not merely for consistency — `McpCatalogEntry.build()` is a *function* that composes a server config from user input plus a secret placeholder, so that catalog cannot become JSON without a redesign that buys nothing. Separately, a plugin's `.mcp.json` / `mcpServers` declaration is **imported** into HappyVibe's own MCP config, which is the single largest compatibility win available (79 plugins are blocked by MCP and nothing else) precisely because it needs no new runtime: an imported server is an ordinary server, gated in-band as `mcp:<server>_<tool>`, reloaded by `scheduleMcpReload`, and written through `writeMcpServer(…, {failIfExists:true})` so it can never overwrite one the user configured by hand. Imported servers land in the **global tier only** — MCP has config *tiers*, not the per-workspace *activation* axis skills and prompt templates have (`skillsActive` / `promptTemplatesActive`), and the two ways to invent one were both worse: a new `mcpActive` map is fresh per-workspace machinery in the layer round 8 deliberately kept thin, and writing into each workspace's `.mcp.json` would put plugin-derived servers in a repo-root, committable file — the same hazard point (3) above exists to avoid. Tool bloat is bounded by disabling or removing the plugin. Every imported server carries `origin: { plugin, marketplace }` inside its entry (unknown keys already survive a `readMcpFile`/`writeMcpServer` round-trip), which is what makes plugin removal able to take its servers with it; that link must exist on the **first** write or every install made before it becomes an unattributable orphan.

**Decision (Feedback round 11, 2026-08-04) — a server's tool count opens:** clicking the tool count on an MCP server row reveals **every tool with its description**, as a native disclosure rather than a modal. No new IPC and no re-fetch: the probe already returns descriptions, main already stores them on the status record, and the renderer already has them in state — the badge was destructuring the list away and keeping only its length. The list rendering already exists too, written for the post-connect confirm-with-tools modal (§13, round 8's point 4) and until now reachable only in the seconds after an install. This is the §13 round-4 "rows expand to reveal the full description" affordance applied to the surface where the count is the only thing the user can see.

**Decision (Feedback round 12, 2026-08-13) — servers that "fail then connect on a click" are timing out, and the timeout is ours:** reported as flakiness on Miro and Context7, where Reconnect then worked immediately. It is not flakiness, and the probe says so. **One 5-second deadline covers `connect` AND `listTools` together**, so a slow handshake spends the budget the tool listing still needs; **there is no retry**, making a single miss final until the user clicks; and the **startup sweep probes every configured server concurrently** — every TLS handshake, every silent token refresh and every `npx` cold start racing at boot, which is the busiest moment the app ever has. Reconnect succeeds because the second attempt is warm: DNS and TLS cached, server awake, token already refreshed. All three are fixed — **a longer deadline measured per phase rather than shared, one automatic retry on a genuine failure (never on `needs-auth`, which is an answer and not a timeout), and a concurrency cap on the sweep.** Stated because it is easy to misread in both directions: this badge is **HappyVibe's own probe** (`mcpClient.ts`), while the agent's connection is the **adapter's**, made at spawn — so a red badge does not by itself mean the running session lost those tools, and a green one is not proof it has them. That split is the same one §13's round-8 OAuth note records for a different symptom.

**Decision (Feedback round 12, 2026-08-13) — the `intent` parameter becomes a global switch on All Tools (amends §7's round-1 "every registered tool carries intent"):** the model-authored headline is bought with tokens, so it gets an off switch, on the **All Tools** page beside the built-in tools that already switch off there "to limit context" (round 6) — that page is where the app discusses what tools cost, which Models is not. It is one more key in the same spawn-resolved toggle object (`HV_BUILTINS`), read once when the session starts. **Sized honestly, because it decides what the switch is worth:** in the default **proxy** mode — one `mcp` tool in front of every server — intent is injected into five tools and the resting cost is small; what it really costs is the sentence the model writes *per call*. With a server switched to **expose tools directly** it is injected into every tool that server publishes, and the cost scales with the catalogue. The switch earns its place on the second case. Turning it off changes **labels, never safety**: cards fall back to the factual derived label they already use when the model omits one (`intent ?? task`, `intent ?? unwrapMcpCall().display`), and the permission prompt has *always* shown the factual action rather than the model's sentence (2026-07-14, above) — that rule is untouched, which is why this is a taste-and-cost setting rather than a security one.

**Correction (2026-08-14) — off has to mean off, and the first implementation only got half of it:** gating `requireIntent` was not enough, because that function *skips any tool whose schema already carries `intent`* ("already wired") — and **every tool the bridge registers declares it directly** in its own `Type.Object`. So the switch removed intent from the MCP proxy, the adapter's direct tools and `subagent`, while `ask_user`, `use_skill`, `terminal_run`, `terminal_kill` and the three plan tools kept theirs. Measured on a real Pi child with the switch off: **seven tools still carried it**, which is how it was reported. A matching `stripIntent` now removes it from the bridge's own tools, selected **by owner** (`sourceInfo.path`) rather than by a name list — a list drifts the moment a tool is added, and owner-matching cannot touch an MCP *server* tool that legitimately declares its own `intent`, which the direct-mode rule above deliberately leaves alone. This also supersedes the earlier note that `ask_user` keeps its intent either way: it does not, and an exception nobody asked for is exactly what made "off" untrue. Same measurement after the fix: seven with the switch on, **none** with it off. The switch still resolves at **spawn**, so a session already running keeps whatever it started with until it respawns — which the row on the All Tools page says.


**Decision (Feedback round 18, 2026-08-31) — "All Tools" was two pages, and it becomes two pages:** the single page opened with *"Everything the agent can call"* and then rendered, above that list, the **global on/off switches for HappyVibe's own agent features** — Plan mode, Ask user, Terminal (three tools), Browser (ten tools) and the `intent` injection. Those switches are not an inventory and not read-only: turning one off **unregisters its tools and respawns every live session**, resetting that session's grants and dangerous mode. Sitting them above a read-only list under one heading meant the page's own sentence described only half of it, and the destructive half was the half nobody announced. They split. **`Built-in tools`** carries the switches and sits under *Abilities*; **`Agent tools`** keeps the inventory and sits under *Control*, beside the rules that gate it. The switches were briefly moved to *Control* on the argument that every one of them is on by default, so every visit is a restriction — **that argument is wrong because it does not separate anything**: `Skills`, `Prompts`, `Agents` and `Plugins` are each a list of capabilities with an on/off too, which the IPC surface states outright (`hv:skills-set-enabled`, `hv:prompt-templates-set-enabled`, `hv:set-agent-enabled`, `hv:plugins-enable-installed`). *Abilities* is precisely the group of capability lists you switch on and off, and this is one. The name is the app's own words, the block already reading *"Built-in Custom Tools — App-provided tools implemented as ordinary tool calls, not part of Pi core."* Three constraints. The pointer runs **one way — switches → inventory** (§20 round 17's rule is that a pointer *is* a link, not that every page carries one): after turning something off you want to see what the agent is left with, whereas from a list of tools "where are the switches" is not a question anyone is asking, and a second pointer beside the existing Permissions one is noise. They carry **different icons**, or two adjacent rows saying "tools" read as one row duplicated. **No label may mean two things**: the switch row for the agent's three terminal tools is `Agent terminal`, because the nav already has a `Terminal` page — the *user's* shell and its settings — and `Browser` follows it to `Agent browser`. **And no two rows may draw the same picture**: `Prompts` and `Terminal` were rendering byte-identical SVG (`M4 17l6-5-6-5`), two nav rows and one glyph, with `System prompt` a third member of that `>_` family; the terminal keeps the chevron and Prompts leaves the family for stacked cards, a template being a reusable saved thing. The same defect sat one level down on the **Models page**, whose *Providers* and *Default model* sections both drew the chip — `Providers` becomes a **link**, a provider being something you connect to (a plan, a key, or a local URL), and the chip stays with the model. Both sets are pinned by a test comparing SHAPE DATA rather than component identity, because two different components drawing one picture is exactly what identity comparison misses. And **`Agent tools` now shows every tool** — it previewed ten behind a "Show all N tools" toggle, which made its own opening sentence false on arrival for a page whose entire job is *everything the agent can call* (30 tools on a stock install, measured). And the old label goes entirely: *"All Tools"* claimed to be the complete catalogue while the switches for half of it lived on the same page under a different heading, which is the confusion the split exists to end. This grows the settings nav to **17 destinations**; a test pins the count and the absence of the old label.

**Decision (Feedback round 20, 2026-09-04) — Built-in tools gains a *Web tools — 4 tools* row:** one switch, `web`, in the same spawn-resolved `HV_BUILTINS` object as Terminal, Browser and Documents, with the shared respawn note. Off unregisters `web_search` / `web_fetch` / `web_map` / `web_crawl` at the next spawn and drops the steer line that names them (a prompt must never name a tool the model does not have — §26's rule). The row carries a collapsed **Web service** sub-block (HappyVibe's service / your own, with URL, optional key and a Test button) — a setting main reads per call, so it is the one control on this page that applies without a respawn, and the row says so. The **Agent tools** page is where the switch is observed. All four declare a required `intent` like every bridge-registered tool. Spec: §32.

## 14. Skills

Skills (the Agent Skills standard — `SKILL.md` folders, natively supported by the pinned Pi) are a first-class HappyVibe surface: **visible, reviewable, and gated**. Pi loads skills silently; HappyVibe turns that into a differentiator consistent with the permission story. Pi facts the design builds on: discovery from `<agentDir>/skills/`, `~/.agents/skills/`, project `.agents/skills/`, settings, and repeatable `--skill <path>`; `--no-skills` disables discovery but explicit `--skill` paths still load; skills register as `/skill:name` commands; descriptions enter the system prompt at startup with no runtime add/remove API.

**Decision (2026-07-22, scope):** V1 = visibility + trust + import + agent-assisted creation. Marketplace/library is V2. Spec: `docs/superpowers/specs/2026-07-22-skills-integration-design.md`; plan: `docs/superpowers/plans/2026-07-23-skills-integration.md`.

**Decision (2026-07-22, trust — review-before-active):** main (not Pi) scans skill locations and keeps an approval record per skill keyed by **path + content hash** (SKILL.md + referenced files). New skill → "needs review" with a SKILL.md preview; content change → hash mismatch → back to needs-review. The registry is a JSONL-backed store (no SQLite), scoped global vs workspace. **Approval and activation are separate**: approval lives at the skill's scope; activation is a **per-workspace checklist** over all approved skills (global and workspace), so a global skill can be on in one workspace and off in another. A session loads approved ∩ active-for-its-workspace. Skills imported or created through the app are approved at import time.

**Decision (2026-07-22, enforcement):** Pi is spawned with `--no-skills` plus one `--skill <path>` per approved+active skill — Pi never sees unapproved content; no bridge involvement in gating. Enable/disable/import/approve apply live via **respawn-resume** (the MCP live-reload machinery generalized to a runtime-config reload: debounced, idle-only, deferred while busy, session resumed from the session file). A file watcher on skill dirs flags on-disk changes live. **Bypass is orthogonal**: dangerous mode / `HV_BYPASS` affect tool-call gating only — the skill gate is spawn-time config with no bypass path.

**Decision (2026-08-02, the gate covers every resource tier, not just skills):** `--no-skills` gated one of Pi's four auto-discovery tiers; `<agentDir>/extensions/*.ts` and `<agentDir>/prompts/*.md` loaded **ungated**, and an extension registers `tool_call` handlers — the same surface the permission gate itself uses. This is a persistence path rather than a drive-by: the agent's `bash` tool is the one fs writer that is **not** path-confined, so a single approved bash command can write a bare `.ts` into `<agentDir>/extensions/` (no manifest, no install step) which then loads with full privileges on **every future session**. The user approved "run a bash command", not "install a permanent extension". Spawn therefore passes `--no-extensions`, `--no-prompt-templates` and `--no-themes` beside `--no-skills`. All are additive, so HappyVibe's own resources — the bridge, pi-mcp-adapter and pi-subagents (all via `-e`), approved skills via `--skill`, and the `/hv-*` commands (`registerCommand`, source `extension`, not prompt templates) — are untouched. Themes are inert JSON with no RPC surface and are gated anyway, so `<agentDir>` is uniformly deny-by-default. The project tier was already closed, accidentally, by `8467c7e` (project-trust's plain-string `ui.select` is answered `{cancelled:true}` → untrusted); these flags make that defence-in-depth rather than luck. `--no-context-files` is deliberately **excluded** — AGENTS.md-style context loading is wanted behaviour. `tests/resource-gate-contract.test.ts` pins both directions (explicitly-passed loads, auto-discovered does not) and joins the pin-bump gate: if a future Pi made `--no-extensions` absolute, the app would silently lose its whole permission layer at spawn, and that must be a red test rather than a red app.

**Decision (2026-07-22, import sources; bundled set fixed 2026-07-23):** five sources, all flowing into the same review gate: (1) **bundled skills** shipped in the runtime — **skill-creator plus 2–3 curated skills vendored from `anthropics/skills`** (pinned commit, provenance recorded), pre-approved (we vetted them) but **off by default**; (2) **local folder** copy-in; (3) **linked Claude Code dirs** (e.g. `~/.claude/skills`) referenced in place via a `linkedDirs` setting — still review-before-active; (4) **git URL, tarball-based** (forge archive over HTTPS, no git binary; provenance `{sourceUrl, ref, commitSha-or-archiveHash, importedAt}`; "update" = re-fetch → hash change → needs-review; no auto-update; SSH/private repos are V2); (5) a **curated shortlist** — a static in-app list, not a marketplace. All imports are path-confined writes.

**Decision (2026-07-23, creation):** a **"New skill" button** in the workspace view fires `/skill:skill-creator` in the current session; the skill interviews the user and writes into the workspace's `.agents/skills/` through normal gated tools (path-confinement holds; no agent ever writes to `<agentDir>`). The result is already-approved (user authored it interactively). **"Promote to global"** copies it main-side into the managed global dir; approval carries over (same hash). No form editor in V1 — "edit" opens SKILL.md via the file tree.

**Decision (2026-07-22, UI, amended ×2):** the "MCP, Tools & Agents" view is renamed **"Skills, MCP, Agents & Tools"** and gains a **"Global skills"** section (managed + linked + bundled only — multiple workspaces can be live at once, so workspace skills don't belong there; a persistent hint points to workspace settings). Rows: name, description, source badge, status; executable files are flagged ("includes N scripts"); the inspector shows rendered SKILL.md, file list, provenance, per-skill token estimate, and a **before/after diff on re-review**. `WorkspaceSettingsModal` is the ONLY surface for workspace skills: review + the per-workspace activation checklist. The per-session tools list shows loaded skills under a "skill" category with scope badges (the §13 future-categories slot, now real). The composer autocompletes `/skill:name` from the session's active set. Unreviewed project skills surface as a non-blocking badge — never a modal wall.

**Decision (2026-07-22, context visibility):** skills' system-prompt overhead appears in the context panel as two lines — global skills and workspace skills — with estimated token weights; the inspector shows the per-skill estimate (name + description are paid every turn; the SKILL.md body only when loaded).

**Decision (2026-07-23, invocation transparency):** loading a skill surfaces as a transcript card with a **model-authored intent** via a bridge-registered `use_skill(name)` tool (goes through `requireIntent` like MCP; returns the SKILL.md content). A raw `read` of an active SKILL.md is detected as a fallback and cards with a derived label. `hv.skill` events land in the EventLog: discovered, approved, revoked, imported (with source), created, invoked; raw-read detections are logged as heuristic (`detected: true`).

**Decision (2026-07-23, delivery):** all of the above is V1, phased **trust core → imports → creation**, each phase validated (full gate + live tests) before the next; implemented straight through in a single run. Testing: unit (discovery/hash/registry), a `--no-skills`+`--skill` contract test added to the pin-bump gate (`docs/validation/sk1.md`), and a live bridge test (approved skill loads, unapproved absent, `use_skill` carries intent).

**Decision (Feedback round 6, 2026-07-29) — removal, and who may approve what:** four amendments, all consistent with review-before-active. (1) **Bundled skills are trustworthy and approved by default** — already true, and they **stay off by default** (the 2026-07-22 default is confirmed, not reversed: approval and activation are separate, one click enables one). (2) **Skills can be deleted, not just disabled**, with semantics per source because "delete" means different things for a folder we own and one we point at: an imported **global (managed)** skill is deleted from disk (confirm names the path); a **workspace** skill likewise, but the confirm must state it removes a file **from the project**, typically git-tracked; a **bundled** skill has **no delete** (the runtime reinstalls it at startup, so it would silently return) — enable/disable only; a **linked directory** is **unlinked, never deleted** (it belongs to another tool). (3) **The import picker gains "Select all" / "Deselect all"** — narrowing a forty-skill repository down currently costs forty clicks. (4) **Workspace settings separate global from workspace skills, because their rights differ:** a **global** skill is clickable for its description/SKILL.md but **cannot be approved there** (approval belongs to the global scope — the Skills page); the workspace may only switch it off for itself. A **workspace (project)** skill is clickable *and* approvable there, since it is the workspace's own. This amends the 2026-07-22 "WorkspaceSettingsModal is the ONLY surface for workspace skills" rule: it remains the only surface for *workspace* skills, and is now explicitly **not** an approval surface for global ones.

**Decision (Feedback round 6, 2026-07-29) — session visibility + `/` commands land on Pi's existing surface:** the chat top bar, which already shows active Plan Mode, also shows **which skills this session loaded**, marking the ones actually opened or triggered during the session — one indicator covering both what was available and what the agent reached for. And the composer's `/skill:name` autocomplete (promised in the 2026-07-22 UI decision, then deferred in `docs/validation/sk1.md` for lack of a slash-command framework) **ships without one**: Pi already registers each loaded skill as a `/skill:<name>` command and enumerates them over its `get_commands` call (the same call the enforcement contract test queries), so the composer autocompletes on `/` from that list by reusing the existing @-mention machinery. Typing the command already worked; only discovery was missing. The deferral is closed rather than scope-cut.

**Decision (2026-08-03) — the marketplace lands, the curated shortlist does not (amends both the 2026-07-22 scope decision and the out-of-scope line below):** import source (5), *"a curated shortlist — a static in-app list, not a marketplace"*, is **dropped**, and §25's marketplace ingestion replaces it. Curation was screened and failed on its own terms — 8 clean, 6 degraded, 4 not viable across the 18 candidates, *after* the PATH fix, with one entry resolving to zero `SKILL.md` and another carrying 46–72 hardcoded `~/.claude/skills/` references whose every call is error-suppressed, so it installs and then **fails silently**. Hand curation bought no quality here, only a per-release re-verification tax worse than the one already felt on the 13-entry MCP catalog, because skills repos are young and volatile where MCP servers are stable identities. The work survives as §25's **ingestion screening rules** rather than as a second catalog type. This also settles the §13/§14 contradiction the round-6 decision left behind (import source (5) promising a static list while this section's out-of-scope deferred it): there is one answer now, and it is the marketplace. Three consequences for the machinery in this section, all additive: a marketplace install is source **`managed`** with `plugin`/`marketplace` on its existing provenance record — **not** a fifth `SkillSource` value, because §24 removed its own fifth source three days earlier for exactly this reason; approval is unchanged, since *"skills imported or created through the app are approved at import time"* already makes the import picker per-plugin consent writing one record per component; and the *"'update' = re-fetch → hash change → needs-review, no auto-update"* rule needs no amendment, because a marketplace entry's pinned `sha` changes what gets fetched, not how a change is detected. The one behavioural change is **enablement**: skills installed from a plugin are approved with `enabled: false` (§25), so the picker's ticks are the enabling gesture — today's `enabled: true` on import would put a 62-skill repo's whole card cost on every turn the moment it lands.

**Decision (Feedback round 11, 2026-08-04) — "New skill" reported as doing nothing, and it was right twice:** the 2026-07-23 creation decision above was fully implemented end to end, and still read as a dead button for two independent reasons. (1) **It did not render where this section put it.** The button is gated on having a session, and the *workspace* surface passes none — so on the workspace view, the one this section names, it was simply absent; on the global Skills page it disappeared whenever no session was selected. It now renders on the workspace settings page too, and with no session selected it **creates one** rather than sitting disabled. (2) **When it did fire, the work happened on a screen the user was not looking at.** Firing `/skill:skill-creator` forwards a prompt to Pi but emits no user-message echo, and nothing navigated — so the interview streamed into a chat tab the user could not see, which is indistinguishable from nothing happening. Clicking now **navigates to that session's chat tab** and the prompt is echoed as a user message. Both are the same lesson: a feature whose only output lands on another surface has not shipped until it takes the user there.

Out of scope (V2+): SSH/private-repo git import + system-git fallback, upstream update notifications, a skill-editing UI, honoring the experimental `allowed-tools` frontmatter, per-skill tool-permission narrowing. *(The marketplace/library and the curated one-click-install list moved out of this list on 2026-08-03 — see the decision above and §25.)*

## 15. AGENTS.md

HappyVibe supports AGENTS.md in V1: read it; show it in the context breakdown with its token cost; edit it (plain markdown editor); propose creating it if missing; explain which instruction files are active and their priority/order.

**Decisions (Feedback round 2):** HappyVibe follows the [agents.md standard](https://agents.md/) — a root file plus **nested AGENTS.md files in subdirectories**: the nearest file for the subtree a tool touches is injected for that turn (Pi only discovers upward from the project root, so HappyVibe's bridge provides the nested behavior) and nested files appear in the context breakdown. When no AGENTS.md exists, the app offers to copy an existing CLAUDE.md, or to draft one with the built-in **agents-md-maker** agent — the draft lands in the editor for review and is only saved explicitly.

**Decision (Feedback round 3, 2026-07-14):** the "propose creating it if missing" promise becomes **proactive**. Opening a workspace that has no AGENTS.md surfaces a one-time, dismissible banner offering "Generate one" (runs the agents-md-maker draft flow above) or "Dismiss". The dismissal is remembered per workspace so it never nags; the draft is still review-then-save (never auto-written).

**Decision (Feedback round 4, 2026-07-15) — auto-save the generated draft (reverses the round-2 "never auto-written"):** when the agents-md-maker draft completes it is **written to `AGENTS.md` immediately** — the file is fully editable afterwards, so a review-gate before the first save added friction without safety. The editor opens on the saved file with an "AGENTS.md created" notice; subsequent edits still save explicitly. This supersedes the earlier "the draft lands in the editor for review and is only saved explicitly" rule for the initial generation.

**Decision (2026-08-30) — the draft is an agent, and stays one:** it was nearly given a row on §19's new "On your behalf" page, on the argument that its prompt carries an invisible safety line — *"Do not create or modify any files yourself"* — living in a renderer string literal nobody can review. **Checking that argument is what settled it, and the argument was wrong.** The constraint is not in that string: it is in `agents-md-maker`'s own file twice (the frontmatter's *"It NEVER writes files"* and its Rules' *"NEVER create or modify any file"*), and it is not merely stated but **enforced**, because the agent declares `tools: read, grep, find, ls` and that list is a strict allowlist from pi-subagents 0.40 — there is no `write`, no `edit` and no `bash` to refuse. The renderer line's *"yourself"* addresses the **parent** session ("delegate this, don't do it by hand"), which is caller plumbing, not a configuration surface. Everything the new page would have given that row, the **Agents page already gives it**: the agent is source `bundled`, so it has Edit — its system prompt in full *and* an agent-tier model override — plus the per-agent switch and its per-turn context cost. **One category, not two:** a capability is an on/off tool the app calls, or it is an agent the Agents page governs; a second home would mean two pages disagreeing about one thing's model. The one honesty gap this leaves is closed with it — turning the agent off on the Agents page left "Draft it for me" visible and failing with *"No draft was produced this turn"*, so the button now says why instead.

**Decision (Feedback round 5, 2026-07-16) — structured, nested, app-written:** the agents-md-maker stays **read-only** and returns **structured output** covering the root AND any nested AGENTS.md it drafts (`{path → content}`); the **app (main process)** writes the files — path-confined and audited — extending round-4's root-only auto-save. The editor opens on the saved root file with a notice; unparseable output falls back to the draft-in-editor flow. Also: opening any AGENTS.md from the file tree opens the **AGENTS.md edition dialog** for that file rather than a plain editor tab (the chat-header AGENTS.md chip is removed, §7).

**Decision (Feedback round 17, 2026-08-31) — the priority explanation ships as prose now, the live list stays open:** this section's *"explain which instruction files are active and their priority/order"* and §6's matching V1 must-list line had **no surface at all** — the guidance audit looked and found none. Every page uses the **wide page shape** the MCP and Skills pages already use, not the narrow column the old scroll had. There is **no Settings landing page**: the group header only expands and collapses, its children are the destinations, and ⌘, — like first-run setup — lands on **Models**. **Workspace settings likewise stops being a dialog and becomes a full page**, opened from the workspace row's gear and headed by the workspace name, ordered **Model → Permissions → Skills → MCP**, with the permission rules and the bypass toggle merged into one section because they are one topic (the bypass sitting three sections below the rules read as unrelated). Stated rather than papered over: Pi discovers `<workspace>/.pi/APPEND_SYSTEM.md` by itself, so a workspace that already has one keeps having it read with no UI showing it; in beta we do not migrate or delete those files, since that is code written only to clean up after a feature nobody used. Global additions are unaffected.

**Decision (2026-07-30) — OpenAI-compatible custom endpoints (relaxes the round-1 "curated list" fence):** the **Cloud API keys** list stays curated; a **fourth group, "Custom endpoint"**, is added to LLM Setup for any OpenAI-compatible server (vLLM, LM Studio, llama.cpp, hosted proxies). The mechanism is the one Ollama already uses — a Pi `models.json` provider entry (`baseUrl`, `api`, `compat`, `models[]`) — **generalised, with Ollama itself becoming a preset on that shared path** rather than a hardcoded special case. `api` is restricted to `openai-completions`, the literal meaning of "OpenAI compatible"; a small **preset picker** (vLLM · LM Studio · llama.cpp · Other) fills known `compat` flags, because the two Ollama needed (`supportsDeveloperRole: false`, `supportsReasoningEffort: false`) differ per server and a wrong flag fails at request time, not at save time. Model ids are **fetched from `GET /v1/models`** into a checklist with an **editable context window per selected model** — Pi defaults to 128000 and §9's context gauge reads that number, so an unedited default would silently misreport the app's headline feature. **Secrets never enter `models.json`:** the file gets `apiKey: "$HV_CUSTOM_<id>_KEY"` and the real value is safeStorage-encrypted in config and injected as an env var at spawn, reusing the existing BYOK env path. **Security invariant:** Pi executes an `apiKey`/`headers` value beginning with `!` as a shell command at request time (and interpolates `$VAR`), so HappyVibe **escapes user-entered values on write** (`$!`, `$$`) — a key is only ever a key, never a command. Deleting a custom endpoint leaves sessions pinned to its models **falling back to the default model with a visible session notice** — never a silent switch, never a failed spawn; `resolveModel` is mirrored in `ipc.ts` and `composer.ts`, so both change together.

**Decision (2026-08-29, "Support more providers" round — second relaxation of the round-1 curated-list fence):** the **Cloud API keys** list stops being hand-curated. Pi ships 39 providers and for ~25 of the missing ones the mechanism is identical to the five already surfaced — one env var injected at spawn — so the catalog is **generated from Pi's own registry at build time** (`pi-ai`'s `builtinProviders()`, the `catalog:plugins` pattern), pinned by a contract test that RE-DERIVES it from the vendored tree rather than agreeing with the committed file, so a pin bump that adds a provider fails loud instead of drifting. **Every exclusion is derived from what upstream declares** — no API-key auth, no models, more than one env var (the multi-field cloud class), no usable base URL — so the deferred providers below fall out on their own rather than sitting in a hand-list that rots; the single hand-written exclusion is GitHub Copilot, which is a product decision (it is an OAuth provider here). One consequence worth stating because it is not obvious: **several brands ship a regional twin behind the SAME env var** (`moonshotai`/`moonshotai-cn`, `opencode`/`opencode-go`, two Qwen plans), so a catalog row is keyed by the VARIABLE, not by the provider id — two rows over one variable would make a single key look like two and report a key configured for a provider the user never touched. The UI keeps the onboarding ladder and the current **five featured cards** (DeepSeek, Anthropic, OpenAI, Google, OpenRouter); everything else sits behind one **"More providers…" search box** rendering the exact same key input + save flow — one component, N providers. Regional variants (Z.AI China, MiniMax CN, …) are **plain catalog rows** with prettified labels, no region-picker component. A saved key is **probed with a free `GET {baseUrl}/models`** (key as Bearer, the `fetchEndpointModels` pattern; pi-ai's registry carries the baseUrl), so a dead key is an inline error at entry; providers the probe cannot decide save anyway with a "couldn't verify" note (the free probe proves auth, not balance — a paid 1-token probe is a recorded follow-up only if dead keys keep slipping through). Three OAuth providers join the existing three on the same `/hv-login` path: **OpenRouter (PKCE — mints its own metered key from OpenRouter credits, no copy-paste)**, **xAI (Grok/X subscription)** and **Kimi Code** — every flow Pi ships, none withheld; the mechanism for withholding one (with its reason) exists and is asserted, so a pin bump that adds a seventh fails a test rather than surfacing an unreviewed sign-in button; local auto-detect extends from Ollama to **LM Studio (`localhost:1234`) and llama.cpp (`localhost:8080`)**, same probe pattern, reusing the existing presets. Finally, the **hardcoded no-model spawn fallback dies** (§16 finding 7): when no model tier resolves — the more providers exist, the more ways to end up holding a removed one — the app no longer silently pins the session to `deepseek/deepseek-v4-flash`, a provider the user may never have configured; it surfaces a clear "no model configured — set one up" error instead. Deferred until someone asks: the multi-field cloud providers (Azure, Bedrock, Cloudflare, Vertex — 2–4 fields each, and their env vars configure more than auth). Still out: Radius, non-`openai-completions` custom-endpoint APIs, provider extensions (resource-gate conflict), and recommended-model shortlists (search-only — `ModelSelect` is already searchable, and a shortlist would re-create the hand-curation the generated catalog exists to kill).

**Decision (Onboarding round, 2026-09-01) — a configured provider always resolves to SOME model, and this is not finding 7 coming back:** measured on a fresh profile during the §22 GUI pass — two provider keys, **348 models offered, `defaultModel: null`** — so the very first session died on finding 7's refusal, *"No model configured — add a provider in Settings → Models"*, which sends the user back to the page they have just finished. Saving a key has **never** set a default, and `ModelsView` **hides its Default-model section entirely while `firstRun` is true**, so the first-run path could not set one at all: every brand-new user's first session failed, and the wizard made it worse by creating that session for them. `ensureDefaultModel()` (ipc.ts) fills a **null** default — never a set one, which is also what stops it looping through `providersChanged()` — with the first model Pi's own registry offers from a provider the user has actually configured, and runs once at boot as well because a key supplied through the **environment** never passes through `providersChanged()`. **It must run AFTER the utility client respawns, and that order is the whole point (2026-09-03):** Pi reads its auth store once at process start, so on an OAuth success the pre-login client still serves the pre-login credential set — asking it for models returned nothing, no default was set, and nothing asked again, so finishing onboarding with a sign-in opened a session that died on finding 7's refusal, pointing the user at the provider they had just connected. `hv:create-session` calls it too as a backstop, free when a default exists and covering every caller rather than just the wizard. **Finding 7 stands untouched:** what it killed was a *hardcoded spawn-time* fallback that silently pinned a session to `deepseek/deepseek-v4-flash`, a provider the user may never have configured. This picks from the user's own providers, at the moment they configure one, writes it where the Models page shows and edits it, and leaves the spawn-time refusal exactly as it is — a default that is stale or removed still refuses. Two limits are accepted and stated rather than engineered around: with several providers configured the choice is registry order, so it can land on one whose **account is empty** (observed — a `402 Insufficient Balance` key was picked over a working one), and the fix for that is the provider's own error plus one click in the searchable picker, not a liveness probe on every launch; and no shortlist of "good" models is introduced, because that is exactly the hand-curation the generated catalog exists to kill.

**Validation resolved (spike + implementation):** the OAuth sign-in flows ARE drivable from the embedded RPC-mode Pi via bridge commands.

**Decision (Feedback round 11, 2026-08-04) — a subscription sign-in that succeeds must show as signed in:** the ChatGPT (Codex) flow completed on the provider's side and left HappyVibe still offering "Sign in". The spike's finding above — that the OAuth flows *are* drivable from RPC-mode Pi — held; the delivery of the result did not, in **three independent ways**, all fixed. (1) **The success signal had one listener, on one page.** It arrives as a single fire-and-forget notify, and only the Models page was listening — so navigating away during the browser round-trip dropped it permanently, with nothing persisting it. Auth state now lives in **main** and is pushed app-wide, the same shape as the MCP status sweep, so the result survives whatever the user is looking at. (2) **The "signed in" predicate was written for API keys** and did not recognise a stored OAuth credential, which would leave the card on "Sign in" forever even on a revisit; the predicate now accepts any stored credential and a test covers the OAuth shape, not just the api-key one that was pinned. (3) **Signing in did not restart the credential cache.** The key-entry path restarts the utility client; the OAuth path did not, and Pi's auth storage is read **once at process start** — so already-open sessions never saw the new account while the model list claimed it was available. The contrast that made this diagnosable is worth keeping: **MCP OAuth is hosted in main and its completion is awaited** (loopback, `state` check, `finishAuth`, reconnect), whereas provider OAuth runs its callback **inside the Pi subprocess** and reports back by notify — so for provider sign-in the delivery path, not the protocol, is the fragile part.

**Decision (Feedback round 12, 2026-08-13) — the Settings list is ordered by how often it is reached (amends round 8's ordering):** round 8 ordered the group by where each page *came from* — the round-6 four first, then the ex-Settings scroll — and §26 and §27 then appended Terminal and Voice after Keyboard shortcuts, which put two live features below a reference table. The order becomes **Models · Plugins · Skills · Prompts · MCP · Agents · All Tools · Permissions · System prompt · Terminal · Voice · Stats · Audit log · Keyboard shortcuts**: Models first because a beginner cannot do anything before it and ⌘, already lands there, the capability pages next, configuration after them, and the three you consult rather than change at the bottom. It stays **one flat group with no sub-headings** — round 8's shape is right, only its sequence was an artefact of history.

**Decision (Feedback round 18, 2026-08-31) — the Settings list becomes four collapsible groups (reverses the "no sub-headings" clause above, keeps its ordering rule):** round 12's *"one flat group with no sub-headings"* was right for fourteen entries and is wrong at sixteen. Measured in the running app, the expanded list is **640px of content in a 423px scroll region** while the session list — the thing you touch every minute — gets 325px, and the first three names a beginner reads in the primary navigation are `MCP`, `All Tools` and `System prompt`. The list gains four **group headers**, and they are short NOUNS in the same small-caps style as the `WORKSPACES` label directly above them — the sidebar's existing section idiom. **Models**, pinned above every group · **Abilities** (Built-in tools · Plugins · Skills · Prompts · MCP · Agents) · **Control** (System prompt · Permissions · Agent tools) · **App features** (Terminal · Voice · AI autofill · Keyboard shortcuts) · **The record** (Stats · Audit log · Changelog). The first cut of these names was *"Set up your agent / What it's allowed to do / What it did / This app"* — an imperative, a relative clause, a clause and a demonstrative, four grammatical shapes in one column, which reads as arbitrary however defensible each name is alone. Two of them were also filing pages wrongly, and **the names were doing the lying, not the buckets**: a system prompt is not a permission but it *is* something you control, and §19's page is not a record of what the agent did but it *is* something the app does for you. **`Models` is pinned above all four groups** (`group: null`): round 12 already called it first-among-equals — *"a beginner can do nothing before it and ⌘, already lands there"* — and it is the one member of *Abilities* that is not one, since the others are capabilities you switch on and off while this is *who the agent talks to*, and the app refuses to spawn without it (§16 finding 7). It costs **~40px permanently** (measured: the collapsed settings block goes 228px → 268px), which is the price of a destination that is never a click behind a shut group. Inside *Abilities* the group reads **have → get → got → author**. **`Built-in tools` leads**: it is the only member that costs nothing to use — plan mode, the agent's terminal and browser, and asking you a question are all ON by default, and they are the product's own differentiators (§23, §26, §28, §7), where every other row needs work before it does anything (install a plugin, approve a skill, add a server, author an agent or a prompt). Round 12's frequency rule argues the opposite, since the page is rarely *edited*; it loses here because **a page nobody opens because they never learned it exists is a discovery failure, not evidence it belongs at the bottom** — which is §19's own argument for the AI autofill page, one group over. Then **`Skills` · `Prompts` · `MCP` stay contiguous directly under `Plugins`**, because round 12's *"the source the three below it get their contents from"* is literal rather than a figure of speech: `ACCEPTED_COMPONENTS` (plugins/classify.ts) is `["commands", "mcpServers", "skills"]`, so those three rows are exactly what a plugin may contain and nothing else. A round-18 draft moved `Prompts` below `Agents` on the reading that Skills/MCP/Agents are things the agent reaches for on its own while a prompt template is something *you* type — true, but it is a taxonomy no one holds while navigating, and it cost a real adjacency to buy it. The order is pinned by a test that DERIVES the trio from the classifier, so widening what a plugin may hold fails there rather than quietly orphaning the sentence. Inside *Control*, **`System prompt` leads on VALUE rather than on round 12's frequency rule** — it is the highest-leverage page in the group and the least discovered — and the group then reads general → specific: what it is told, the rules, and the inventory those rules act on. **The record** goes last because round 12's own rule — *"the three you consult rather than change sit at the bottom"* — applies one level up, and that block is exactly §30's *"consulted, not changed"*. §29's *"one panel, two altitudes, one vocabulary"* is the governing rule: **group headers speak human, items keep their real names, and no third vocabulary is invented** — nothing is renamed, and a header is not a destination. Round 12's *"ordered by how often it is reached"* is **not superseded, it now applies within each group**, with one deliberate exception — `Permissions` leads its group ahead of `All Tools`, being both the more-often-reached and the group's own thesis. Four constraints make it correct rather than merely tidier. **The order stays in ONE place**: `NAV` remains the single flat exported array and each entry gains a `group` field, because `GoTo.tsx` derives `GOTO_LABELS` from it and `tests/go-to.test.ts` asserts against the sidebar's source text — a separate array listing item names per group would put the order in two places, which is exactly what §20 round 17's Principle 11 forbids. **Groups open and close independently, not as an accordion**: one-open-at-a-time collides with the standing rule against auto-collapsing a nav, because a `GoTo` link to **Stats** must open *What it did*, which would silently shut whatever the user had open. **All four are collapsed by default and the open set persists** beside the other sidebar state — the `Settings` toggle already had the machinery, the defect was the default. And **`navigate()` opens the group containing its target**, derived from that view's own `group` field, so a cross-page pointer can never land on a page whose nav row is invisible. Collapsed, the whole settings block is ~204px against today's 505px, and the second nested scroll region stops engaging in any state the user did not choose.

**Decision (Feedback round 16, 2026-08-31) — thinking effort becomes a setting the user owns, in two scopes, because today nobody chose it:** the app never touched Pi's thinking level, which sounds neutral and is not. Pi's own `settings.json` inside the app's agent dir carries `defaultThinkingLevel: "high"` — nothing in `src/` ever wrote it — and **41 session entries on a real install record `high`**, against Pi's own `"medium"` default. So every HappyVibe session has been running at high thinking, chosen by nobody, invisible on every surface, and billed: the exact shape of §2's "see what you are spending" failing quietly, one axis over from the model-exclusions decision in §12. It becomes **a global default on this page, beside the default model, and a per-session pill in the chat top bar next to the model chip** — two scopes, not the model's three, because a workspace tier would be a third place to look for a setting whose whole problem was being in none. **The spawn flag is the load-bearing half.** `--thinking <level>` exists, and Pi's spawn-time precedence is `--thinking` > the resumed session's own recorded level > Pi's settings default > `"medium"`; passing it **unconditionally**, exactly as `--provider`/`--model` are passed, is what stops Pi's settings default being consulted at all — which is precisely why the *model* setting has never had this bug. The live half mirrors `hv:set-session-model` verb for verb: persist on the session, apply over RPC, report back whether it took so the UI can say "applies on restart" honestly rather than lying. `set_thinking_level` does write Pi's global default as a side effect, and that is harmless for the same reason it is harmless for `set_model`, which already does it — spawn overrides it every time. **Three mechanics decide what the control looks like, and two of them are traps.** The levels are `off · minimal · low · medium · high · xhigh · max`, but `get_available_thinking_levels` is **per model** and a model may not support thinking at all: on such a model the pill **does not render**, the same rule the context gauge follows for a model with no known window and §19 applies to an unknown price — never a disabled control standing in for "not applicable". And **switching model re-clamps the level** upstream, so the app re-asserts the user's choice after a model change, or their setting changes underneath them with nothing on screen to say so.

Sub-agents can use different models from the main agent. For V1, the must-have is provider setup, model selection, token count, and context size visibility.

## 17. Sessions

Each workspace can have multiple coding sessions; sessions can run in parallel.

**Decision (Round 2):** parallelism means **multiple sessions can actively run agents at the same time**. Detached background jobs are out of scope for V1.

The user can: create, resume, archive, restore, **delete permanently** (confirmed — removes the conversation, its session file and everything its sub-agents left behind), search (by title), and view session history.

**Decision (2026-08-29) — delete means delete, including what the sub-agents left:** deleting a session removed only its own `.jsonl`, and everything its delegations produced stayed on disk permanently. Two places, both invisible to the user: the child Pi session files under `<sessionsDir>/<stem>/<runId>/run-<n>/session.jsonl`, which survived because the delete is `rmSync` on a FILE path with no `recursive`; and `<sessionsDir>/subagent-artifacts/`, which pi-subagents writes flat into the app's own session directory and which nothing in the app had ever referenced. Measured on a real install before the fix: **18 orphaned child directories and 13 artifact run-ids belonging to no surviving session**. The privacy half is specific — `_input.md` is *not* a leak, because pi-subagents redacts the child's input artifact, but `_output.md` holds the child's whole answer and `_transcript.jsonl` retains its thinking — so a user who deleted a session to remove its content still had the sub-agents' reasoning on disk. Deleting now removes both, and a startup sweep reclaims what earlier deletes already orphaned. **Two constraints make it correct rather than merely thorough.** The cleanup must run *before* the session file is deleted: an artifact's `_meta.json` records its run and its agent but never its parent, so the only place the association exists is inside the parent session file — which is exactly why the existing orphans can never be attributed and can only be collected by reference. And a **closed** session is not an orphan: its children stay, because §19's sub-agent cost readout re-parses those same child session files when the session is reopened, so a sweep that mistook closed for deleted would silently empty the cost history it depends on. The sweep therefore judges directories by name, matches artifacts only by exact run-id prefix, and abandons the artifact pass entirely if any session file is unreadable — leaking is a smaller failure than deleting a live session's data. Evidence: `tests/session-delete-children.test.ts`.

**Decision (Feedback rounds):** session lifecycle is **fully transparent** — no session limit visible to the user and no stop/end-session control anywhere (the in-chat abort of a running response is the only stop). An internal cap protects resources: when room is needed, the oldest **idle** session hibernates (never one that is mid-call, awaiting a permission answer, or running a sub-agent) and restores transparently when reopened. Sessions are titled automatically by the model after the first exchange (renameable).

**Decision (Feedback round 8, 2026-08-01) — collapsible workspaces in the sidebar:** with several workspaces of many sessions each, the session list becomes unreadable — so clicking a **workspace name** collapses or expands that workspace's sessions, an **explicit arrow** sits on the right of the row alongside the other icons (visible rather than folklore), and the collapsed state is **per workspace and survives a restart**. Typing in the session filter still expands everything, so a search can never hide its own results.

**Decision (Feedback round 4, 2026-07-15) — full transcript on reopen:** reopening a session reconstructs the **whole** visible transcript from the persisted history — user and assistant messages AND the tool cards (tool name, the model-authored intent headline, arguments, and result), not just the text. The intent and results are already persisted in the session file, so a reopened session reads the same as it did live. Reconstructed tool cards are shown **collapsed by default** to keep a long reopened conversation lean. (Live-only extras that aren't in the history — the approval badge and the expandable sub-agent trace — are not reconstructed.)

**Decision (Feedback round 9, 2026-08-01) — "whole" is bounded by compaction:** the round-4 promise above was silently false for any compacted session. Restore is fed by `get_messages`, which returns Pi's **live** context, so one measured session rebuilt **65 of its 318 messages** with no indication of the gap. Reopening now reconstructs the transcript back to the most recent compaction and stops at a visible boundary bubble, with the rest available on demand and marked as outside the agent's context — see §9. "Whole" now means *whole, and honest about where the agent's memory ends*.

**Decision (Feedback round 10, 2026-08-01) — reopening reads the file, not the child:** the round-9 work above left `get_messages` feeding the in-context half of the transcript, and a perf dig found that single RPC is **90%+ of every session restore — 1.35–2.86 s**. Not because it is expensive (it returns an in-memory array) but because it is the **first message a freshly spawned Pi has to answer**, so it absorbs the whole child boot: session load, three extensions, the MCP adapter. Reopening now rebuilds **both** halves from the session file (`history.ts contextItems`, alongside the `earlierItems` round 9 already added), which costs **1–5 ms** on real sessions up to 4 MB and needs no child at all — so the transcript paints *before* the spawn instead of after it. Measured end to end in the app on the same evidence session: `openSession` went from seconds to **25 ms**, same 65 items, same boundary bubble. This finishes the "one source: the file, not `get_messages`" rule already locked for the cost ledger (§19) and the compaction boundary (§9); the RPC survives only as a fallback for a young session whose file has not been captured yet, where the client is already warm and the boot cost does not apply. It also closes a quiet correctness gap: §9 removals are applied by the bridge at Pi's `context` event, so `get_messages` still returned messages the user had **removed** — the file path filters them, so removed now means removed on reopen too. Safe only while our reading of the file matches Pi's own `buildContextEntries` rule, so a contract test resumes a real Pi on a compacted session file and asserts the two agree — added to the **pin-bump gate** (`tests/history-contract.test.ts`), which is how a future Pi version that changed the rule surfaces as a red test rather than as a silently truncated conversation.

**Decision (Feedback round 10, 2026-08-01) — the live-Pi gate is a gate again:** the 14 live tests were red on main, and the cause was not what "flaky" implied. The repo had **no vitest config at all**, so the suite ran on vitest's **5-second default `testTimeout`** — less than the time it takes to boot one Pi child (5–15 s measured). Tests that happened to pass an explicit per-test timeout were fine; two in `agents-bridge.test.ts` that did not failed at exactly 5000 ms **in isolation as well as in the batch**. That is a missing default, not nondeterminism, and it is fixed once in `vitest.config.ts` rather than per test. Two genuine sources of nondeterminism remain, each fixed at the root rather than by widening timeouts. **Contention** — vitest ran files at ncpu/2, so the batch put five concurrent Pi children *and five concurrent DeepSeek sessions* on one machine; the observed symptom was turns coming back with no tool call at all, which no timeout can fix. The live batch is now **serial** (`--no-file-parallelism` in its canonical invocation, ~6 min), while the 86-file non-live suite keeps full parallelism — two suites with opposite needs, one flag at the call site instead of a config that penalises the common case. And **tests asserting on the model rather than on us**: `rules-bridge` took the *first* `hv.audit` notify, which is whatever tool the model happened to reach for first, and `intent-bridge` never told the model to fill the `intent` parameter it was checking for. The residual class — a small model declining to call the tool the test is about — is handled by **re-asking** (`tests/reask.ts`), with every assertion left exactly as strict; a longer wait does not make a model that already finished its turn produce a tool call. Standing consequence: **CI still skips these** (no key), so the gate is only real when it is run deliberately before a pin bump.

**Decision (Feedback round 12, 2026-08-13) — closing the last tab of a session ends its process (supersedes "no stop/end-session control anywhere"):** the transparency rule above produced a session the user cannot stop. A chat tab is a *view* (§7 round 11: closing it stops showing the session, nothing more), archiving only flips a flag, and the sole routes to the running child are hibernation at the eight-session cap or deleting the conversation outright — so "how do I stop this?" had the answer *delete it*, which is not an answer. **Closing a session's last tab now ends its process**, and **archiving ends it too** — that second one was a defect rather than a design. What makes this cheap is that the mechanism was already built and wired to nothing: an end-session path in main that captures the session's final stats (the §19 ledger's inputs) and stops the child. Reopening respawns and resumes, and since §17 round 10 the transcript paints from the session file *before* the spawn, so the user pays the next turn's boot rather than the reopen. A session that is **mid-turn asks first, naming what is running**, reusing §26's live-terminals confirm rather than inventing a second dialog. What does **not** come back is a stop *button*: the lifecycle stays invisible, and this is the tab's own semantics finally matching what closing something means.

**Decision (Feedback round 15, 2026-08-16) — an empty session deletes itself (refines round 12's close-ends-process):** a session with **no content — no user prompt was ever sent** (transcript empty, title still the fallback) — is **deleted outright, silently,** when its last tab closes and on app quit; **never on a workspace switch**, because two projects can be worked in parallel and the user will come back. No confirm is the point: a ⌘N created, glanced at and closed leaves nothing behind, which is what stops the sidebar accumulating "New session" rows.

**Decision (Feedback round 15, 2026-08-16) — ⌘W closes any tab (amends round 12's chat exemption):** ⌘W closes the focused pane's active tab **whatever it is — session, terminal or browser**. Round 12 exempted chats because closing now ends the process and "should not sit under a reflex keystroke"; the guard moves from the keystroke to the state: **any closure while a turn is ongoing is gated by a dialog** naming what is running (the busy confirm the tab's × already uses), live terminals keep their stop/keep dialog, and an idle chat closes silently — deleted if empty, per the decision above.

**Decision (Feedback round 15, 2026-08-16) — the session row: one trash, a two-outcome dialog, and an age:** the row's two hover icons become **one trash icon, on hover only**, opening a dialog offering **Archive** / **Delete permanently** — §5's two-outcome pattern applied to a single session, reusing the existing delete confirm. The one-click archive goes (archiving becomes two clicks, accepted); unarchive stays under "Show archived". When **not** hovering, the icon slot shows the session's **age** (m / h / d / mo, from `updatedAt`); a session that is working shows the pulse animation instead — so the resting sidebar reads as a timeline rather than a wall of identical rows.

**Decision (Feedback round 12, 2026-08-13) — "whole" includes the pictures:** round 4's promise that a reopened session reads as it did live was false for any message carrying an image. The bytes are in the session file; the restore path dropped them. Fixed in §7 (round 12), including the payload ceiling that keeps round 10's ~25 ms reopen honest.

Session data is stored locally only. No account system, no cloud sync in V1.

## 19. Success Metrics

MVP success: users complete coding tasks; users understand agent actions better than in CLI tools; users prefer HappyVibe to Claude Code for simple tasks.

**Decision (Round 2):** no remote telemetry in V1 — metrics live in a **local-only analytics dashboard** (the **Stats** page in the sidebar since Feedback round 8, §16) (tokens consumed, retention, session duration, session count; more candidates later: completed edits, permission approval rate, dangerous mode usage, context warnings, compaction usage, sub-agent calls, restored sessions, satisfaction).

**Decision (2026-07-30) — per-session spend, and why the estimate diverges from a provider's invoice:** §2 promises the user can see "how much they are spending", but until now that number existed only as a workspace aggregate in the dashboard. The chat tab strip gains a **cost pill beside the context bubble**; clicking it opens a **flat, time-ordered ledger of every billed API call** — timestamp, model, input, output, cache, cost — newest first, with a model column because a session may change model mid-way and one blended rate would be a fiction.

Four rulings, all of them about not stating a number the app cannot stand behind.

1. **One source: Pi's session file, not `get_messages`.** The RPC returns the live context, so a compaction erases calls the user was already billed for. The file is what Pi's own `get_session_stats` sums, so the pill and the ledger agree with Pi by construction rather than by coincidence. Main parses it (`src/main/calls.ts`, path-confined read) and returns the total *with* the rows, so the sum is computed once and the renderer never re-implements it.
2. **Cache reads get their own column.** This is where estimate and invoice diverge hardest: Pi prices from a table pinned at the vendored `pi-ai` version, and **128 of its 266 OpenRouter entries price `cacheRead` at 0** while cache reads are the large majority of a coding agent's prompt tokens (measured on real sessions here: 47.8M cache-read against 4.8M input). Folding cache into "input" would hide the one column that explains a mismatch.
3. **Billing has THREE states, not two — metered, plan, unknown.** A boolean "is it priced" was wrong in both directions. (a) A call that burned tokens but priced at zero is **unknown**: the pill shows `$?`, or `$X+?` when only part of the total is known. Live defect, not hypothetical — HappyVibe wrote custom endpoints to `models.json` with no `cost` block, so Pi defaulted every rate to zero and a real session reported 60,023 input tokens as free. (b) A **flat-subscription** provider is `plan`: its dollars are *never* shown or summed. `openai-codex` is a ChatGPT subscription yet Pi prices its models at full API rates ($1.25/$10 per Mtok for gpt-5.1), so a boolean flag called that "priced" and rendered several dollars of spend that was never charged — worse than the `$0.00` case, because nothing flagged it. `github-copilot` has the mirror problem: all-zero rates made it read as "unknown price" and pointed the user at a Custom-endpoint setting that does not apply to it. Plan rows show `plan`, stay out of the total, and stay **calm** — a covered call is a fact, not a gap; amber is reserved for genuinely unknown money.
   *Classification:* `PLAN_PROVIDERS` holds only the OAuth-**only** ids (`openai-codex`, `github-copilot`), which the provider id alone settles. **`anthropic` is ambiguous** — it is in both `BYOK_PROVIDERS` (API key → metered) and `OAUTH_PROVIDERS` ("Claude" Pro/Max → plan) and the session file records only `provider:"anthropic"`. Main resolves it by key presence at query time (no key ⇒ the subscription paid). Known ceiling: a session billed against a key, viewed after that key is removed, is relabelled `plan`; the upgrade path is to have the bridge stamp the resolved auth mode per call. **Decision (2026-08-29, more-providers round): `xai` and `kimi-coding` join the same key-presence resolution** — both ship a subscription sign-in beside a plain API key (`XAI_API_KEY`, `KIMI_API_KEY`), so each is plan-billed exactly when no key is configured, with the same known ceiling. The set is no longer hand-maintained: it is **derived from what upstream marks `isSubscription` while also offering a key**, and pinned by the catalog contract test, so the next such provider fails a gate instead of silently reporting a covered subscription's tokens as dollars owed. OpenRouter's PKCE OAuth mints a **metered** key billed from credits, so `openrouter` stays out on both counts.
4. **Custom endpoints can carry prices.** The add-endpoint form takes optional **$/Mtok in / out** per model. Both or neither — one rate alone yields a total that is quietly half right. `cacheRead` defaults to the input rate (a server that reports `cached_tokens` bills for them; zeroing them re-creates the defect above) and all four rates are written together, since Pi's `ModelCostSchema` requires the full set and drops the entire provider on a partial one.

**Not fixed here, and deliberately so:** OpenRouter returns the true charge in `usage.cost` when a request carries `usage:{include:true}`, and Pi neither sends the flag nor reads the field. Reconciling against it — or against OpenRouter's live price list — means changing vendored pinned `pi-ai`, so the app labels its number an estimate instead of pretending to match the dashboard. Sub-agent spend stays on each delegation card (separate Pi processes, separate session files) and the ledger footnote says so. **Superseded on 2026-08-22 — see the sub-agent-cost decision at the end of this section: "separate session files" turned out to be the reason to INCLUDE them, not to exclude them.**

**Decision (Feedback round 11, 2026-08-04) — Stats computes from the ledger, because it did not agree with the session pill:** asked whether the dashboard's cost matches the one shown in a session, the answer was no — and the disagreement runs in the direction the four rulings above exist to forbid. The dashboard summed the agent's raw per-session cost figure, so **none** of the ledger's policy applied: a ChatGPT-subscription session showed `plan` on its own pill and **several real-looking dollars on Stats**, which is ruling 3(b)'s exact failure — "worse than the `$0.00` case, because nothing flagged it" — reintroduced on the surface the user is most likely to read as authoritative. Stats now computes from **the same ledger the pill uses** (`src/main/calls.ts`, over session files), which makes the three policy filters apply by construction rather than by remembering: flat-subscription providers stay out of the total, unknown-price calls are **flagged** rather than silently added as zero, and cache reads keep their own column instead of being folded away. It also closes four data-loss paths that were dashboard-only, all of which quietly reported **$0**: only **ended** sessions were counted, so live ones contributed nothing; a **hibernated** session cannot be asked for its stats because hibernation already stopped its process, and hibernation is invisible by design (§17), so a normal long-lived session lost its whole spend; a **crashed** session was counted as an event but carried no stats; and a failed stats capture degraded to zero rather than to unknown. Same rule as ruling 1, applied one surface later: **one source, the session file** — and the reason it now holds everywhere is that both numbers are computed by the same function instead of two that agreed by coincidence.

**Decision (Feedback round 15, 2026-08-16) — the one-shot callers appear as estimates, outside the ledger:** the app makes model calls no session ever sees — **session titles (`titles.ts`), the commit message and the PR draft (`gitMessage.ts`)** *(three, not the four this decision originally listed — the AGENTS.md draft is a delegation, §15)* — and they run `pi -p --no-session`, which leaves **no usage record**, so their cost can only be *estimated* from prompt+output size. Each call logs an **audit-log entry** (what ran, which model, estimated tokens ≈ cost) and **Stats gains a small "assistant extras (estimated)" line** summing them. The ruling above is untouched: the ledger keeps meaning *what sessions cost* — these live beside it, labelled estimated, never summed into a session's pill.

**Decision (2026-08-30) — the calls the app makes for you get a page, and the setting nobody could reach is replaced:** logging these three was half the promise; a log tells you what already happened, and nothing anywhere told you they *exist*, which model runs them, or what they say. So they gain **their own settings page, "On your behalf"**, sitting after **System prompt** in the sidebar's Settings group (§16 round 8) — both pages answer *what does this app tell a model that I never typed*. Deliberately **not** a section on Models, which is about *which* model rather than *which task*, and **not** a block on All Tools, whose one promise is "what the agent can call" — these are calls the agent never sees. Each of the three rows carries **what it does and when it fires**; **its model**, defaulting to "Same as your default model" and overridable through the shared `ModelSelect`; **its prompt read-only and in full, with an append box, never an override**; and an **on/off switch**. The prompt rule is **inherited from §13 round 6, not invented here**, and for the same reason: all three callers *parse* what comes back (`titles.ts` takes the last non-empty line, `cleanSubject` the same for commits, `splitPrDraft` wants a title line then prose), so a rewritten prompt breaks the parse silently and reads to the user as "it stopped working". The row component is **shared with `BuiltinToolsBlock`**, which is already this exact shape, rather than built a second time. The two git rows show their prompt as a **template with the diff's insertion point marked**, because the real prompt does not exist until there is a diff. The switch is on all three even though two of them are button-triggered: hiding a button you never want is a real preference, and a switch on one row of three reads as broken. **An append is recorded, not silent** — `oneShotLog` measures characters, so an append would quietly inflate the estimated-token figure with nothing saying the prompt was modified; the audit row gains an `appended` flag. Two things are cleaned up in the same pass. **`gitMessageModel` is deleted rather than surfaced**: it was one setting that two rows would secretly share, and since no UI ever wrote it **no user has one on disk**, so there is nothing to migrate — it is replaced by one per-task record (model, append, on/off) mirroring `builtinTools`'s shape. And **session titles stop resolving the global default only**: `maybeTitle` already holds both `workspaceId` and `sessionId` yet called `resolveSpawnModel()` with no arguments, so a workspace model override was honoured for a commit message and ignored for the title of the session it belonged to; all three now resolve **session → workspace → global**, identically to a chat spawn. Where nothing resolves at all, §16 finding 7's honest `null` is **correct but invisible** — the title simply never appears — so each row states "no model configured" as a fact.

**Decision (Feedback round 18, 2026-08-31) — the page is renamed "AI autofill" and moves to the sidebar's *App features* group (supersedes the naming and placement above, not the page itself):** two corrections to the decision above, both found by reading the page rather than its label. **"On your behalf" described the product, not the page** — an agent acting on your behalf *is* HappyVibe, so the label told a beginner nothing, and it was the one nav row that was not a noun. It becomes **"AI autofill"**, which is literally what the three tasks do: fill in a session title, a commit message, a pull-request body — three fields you would otherwise type. **"AI" is the app's only use of the word** (the UI says *the agent* 101 times and *the model* 52, and had never once said *AI*), and it earns that exception by working as an ADJECTIVE, separating **generated** text from the browser-autofill sense of **remembered** text; it is not a second name for the agent or the model, which is the third vocabulary §29 forbids. A second use anywhere would be, so a test pins the count at one. **And it is not filed with System prompt.** That pairing was argued from the question the two pages answer, which is true but is not how the nav groups: this page carries a per-task **`(model, append, on/off)`** record — you can turn each call **off** here — so it configures app behaviour and belongs beside Terminal, Voice and Keyboard shortcuts. It is specifically **not** in *The record*, whose three pages are read-only. The Audit log's pointer to it is reworded in the same change, because a pointer naming a page that no longer has that name is worse than no pointer (§20 round 17).


**Decision (2026-08-22, Sub-agent-cost round) — a sub-agent is another Pi session file, so its spend belongs IN the ledger, and there are no budgets:** the "not fixed here" note above kept sub-agent spend off the ledger because children are separate Pi processes with separate session files. Measured, that is the argument for the opposite: ruling 1 says the one source is *a Pi session file*, and a child writes an ordinary one — at `<sessionsDir>/<parentSessionBasename>/<runId>/run-<idx>/session.jsonl`, rooted beside the parent's own file and therefore as persistent as the session a user can reopen. So `calls.ts` parses the child files alongside the parent's, a child's calls become ordinary ledger rows tagged with the agent name, and **CostPanel, the cost pill and the Stats dashboard all include them by construction** — the round-11 fix above is precisely why this cannot live anywhere else: a second path to the same number is how the pill and Stats disagreed last time. Three consequences worth stating. (1) **Billing classification applies unchanged**, and that closes a live defect rather than adding a feature: the delegation card already rendered a raw `fmtCost` of pi-subagents' own figure, which knows nothing about `PLAN_PROVIDERS` — so a Claude Max, ChatGPT or Copilot user was shown API-rate dollars they never owed (ruling 3(b)'s exact failure, on a surface nobody had checked) and an unpriced child read as `$0.00` instead of `$?`. Because the child is a Pi process, its cost comes from **Pi's own** price table, the same one as the parent's rows, so a child is priced exactly when its parent is and no second price table enters the app. (2) **A run has TWO identifiers, and only one of them names its child's directory** — measured three times in the running app, and the single most expensive thing to have got wrong here. Every id HappyVibe holds for a delegation (the status poller's key, the audit rows, `details.asyncId`) is the WORKFLOW async id, but pi-subagents names the directory it writes the child session into after the run's INNER id: async `72e6fd2e-…` wrote into `…/8a2f9f62-…/run-0/session.jsonl`. Deriving a child's path from the id we hold therefore finds nothing, and finds it **silently** — a card that simply never shows a number, which is exactly how the first implementation passed its whole unit suite and failed in front of a user. The link is `steps[].sessionFile` on the run's `status.json`, which the app already polls (the run level carries no `sessionFile` at all); `steps[].agent` supplies the name, which no path contains. Those paths are RECORDED on the completion audit row rather than re-derived, because `status.json` lives in a tmpdir a reopened session cannot count on. The one place that still resolves by layout is the whole-session ledger, which has to cover delegations from before any path was recorded; its rows fall back to a generic "sub-agent" label. Stated ceiling: a delegation for which the model passed its own `sessionDir` writes outside that layout and contributes no historical row. The layout and the id split are pinned by contract test, so a pin bump fails loudly instead of quietly returning nothing. (3) **No budgets, no limits, not even soft warnings** (product call, recorded verbatim: "overkill, and it kills the purpose of subagents if they can't do their work"). The app writes no `usageBudget` key and blocks no launch on cost; an absence test pins that so enforcement cannot arrive as a side effect of a pin bump. Copy rule that follows: the user-facing word is **cost**, never **budget** — budget implies a limit that does not exist here. Requirements and the measurements, including the retraction of a proposed `events.jsonl` cost tailer that turned out to have no cost data in it: the "Subagent cost visibility" Notion doc.

## 20. Product Taste

Inspired by Codex in layout, chat style, and workspace management — but not cold or enterprise. Playful, visually pleasant, easy to understand. Principles: simple; warm; clear; modern; friendly; not childish; transparent; low intimidation.

**Shipped direction:** "warm workshop" — cream paper and warm ink, tangerine primary, chunky borders with hard offset shadows, playful microcopy, bundled friendly typefaces. It satisfies the principles above and is the house style unless revisited.

**Decision (Feedback round 12, 2026-08-13) — the app icon is the brand mark, and the `hv` placeholders go:** the packaged icon (`build/icon.svg` — a tangerine squircle with a cream face) is the logo, and the three places that stand in for it with an `hv` wordmark use it instead: the sidebar header, the collapsed icon rail, and the first-run Models page. It keeps a slight rotation, because the tilt is what makes it read as a sticker rather than a badge, which is the whole §20 register. It ships as one inline-SVG component rather than an imported asset — the renderer's CSP is `img-src 'self' data:`, so the mark is drawn, not loaded, exactly like every other glyph in the app (`BrandGlyphs.tsx`, the file-tree icons, the nav set).

**Decision (Feedback round 17, 2026-08-31) — one guidance system, and guidance that describes a gate is derived from it:** an audit of every renderer surface found the copy right in spirit and inconsistent in shape — 18 pages, two of them with no intro at all; four page intros stated twice in a row; two components named `Section` (the shared one *requires* a subtitle, a local clone in `DashboardView` dropped it, leaving four charts unexplained); ~20 empty states in three visual shapes, half of them dead-ending with no next step; five phrasings for "go to another page" and none of them a link; and plan mode explained in exactly one hover tooltip. The fix is one system, entirely inside the existing design language — **no new nav entry, no new tones, no tooltip library, no help center, no tour framework**. Its rules: (1) **a page header says what the page is, once** — one `h1` shape, one sentence, and a section subtitle carries only the delta; (2) **one `EmptyState` component with one visual tier** (the existing dashed box — the illustrated card the audit thought it was generalizing does not exist, and a second tier is a second thing to keep consistent), whose sentence template *"No X yet — ⟨what to do⟩"* makes **every empty state name the next step**, promoted here to a standing principle beside "never nag"; (3) **every cross-page pointer is a link**, including the ones rendered in chat — a dead pointer is worse than a context switch the user chose by clicking, so the model selector's hint opens the settings drawer on Models rather than describing where the gear is; (4) **tooltip doctrine written down rather than migrated** — the 254 native `title=` sites stay, and the rule is that a fact needed *to decide* is inline while a fact for the curious is a tooltip, which is what turns the estimation caveats into one visible line per panel instead of a per-cell hover; (5) **the deleted Help page dissolves in place** as a collapsed native `<details>` titled *How ⟨X⟩ works*, living inside the section it explains — plan mode, how permission rules combine, what the MCP badge does and does not prove, measured-versus-estimated context, and how instruction files combine. **The load-bearing new rule is (6): guidance that describes a gate is DERIVED from that gate, never re-typed beside it.** The audit's own last finding is what re-typing costs — the plan-mode system prompt tells the model that *"sub-agents are blocked"*, which stopped being true when §12's capability ceiling let a planning session delegate a read-only search, and nothing failed in the months between. Where a disclosure states a rule the code enforces, its test pins the two to the same constant.

## 21. File Access (V1)

**Decision (Feedback round 3, 2026-07-14):** the file-tree reduce icon **closes the pane completely** (unmounts it) rather than minimizing to a slim rail — matching the "close top-right" intent above. Related polish: opening/resuming a session shows a loader instead of a blank/instant swap (§17), and image attachments open a zoom lightbox on click (§7).

**Decision (Feedback round 4, 2026-07-15) — file-tree context menu:** right-clicking an entry in the workspace file tree opens a menu with **Open**, **Delete**, and **Details**. Delete always shows a confirm dialog and moves the item to the **OS Trash** (`shell.trashItem`) — never a hard delete, so it's recoverable, matching standard OS behavior; it works on files and folders and is path-confined to the workspace like every other fs operation. **Decision (Feedback round 5, 2026-07-16) — files panel upgrade:** the panel's top edge aligns with the tab strip (same level as the chat); the tree **auto-refreshes via native filesystem watching** — catching agent, user, and external changes — and the refresh button is removed; **drag & drop** works in all three directions (OS → tree copy-in, within-tree move, tree → center open / composer attach); header icons offer **new file**, **new folder**, and **collapse all**.

**Decision (Feedback round 5.1, 2026-07-17):** the files panel is a **right-side overlay drawer** (opened from the persistent top-right toolbar, §7) — its top aligns below the tab bar and it **overlays** the content rather than occupying a grid column, so opening it no longer shrinks the chat or split panes.

*(Context, §9 addendum — Feedback round 5.1)* the composition surface is **scaled to the whole context window** and shows a **"Free space" segment** for the unused portion, so the empty context is visible alongside the used categories.

**Decision (Feedback round 6, 2026-07-18) — open-file auto-refresh:** an open editor tab **auto-refreshes when its file changes on disk** (agent edit, external tool, or the user's own tree actions), driven by the existing filesystem watch (push) rather than only the on-focus mtime poll. A **clean** buffer reloads silently; a **dirty** buffer surfaces the existing conflict banner ("Reload from disk / Keep mine") so unsaved edits are never discarded. (The on-focus poll stays as the fallback where `fs.watch` recursion is unavailable, e.g. Linux.)

**Decision (Feedback round 6, 2026-07-18) — rendered md/html preview:** `.md`/`.markdown`/`.html`/`.htm` tabs open in a **rendered view by default**, with a toggle icon to switch to raw, editable source (and back). Markdown renders with the **same renderer as the chat** (react-markdown + remark-gfm); HTML renders in a **sandboxed iframe** with no script execution (relative asset/style paths won't resolve — accepted). Editing and saving happen in raw mode; the rendered view reflects the current buffer, so it updates after an auto-refresh.

*(Cross-reference — §26)* the centre area gains a **third tab type**, the terminal, alongside the chat and the file. It uses this section's tab machinery unchanged; its own decisions live in §26.

**Decision (Feedback round 11, 2026-08-04) — send a selection from the editor to the chat:** with text selected in the built-in editor, **"Send to chat"** inserts it into the composer as a fenced block headed by the file path and line range. Scoped deliberately to the **selection**: whole-file reference is already covered by §7's `@file` autocomplete, so a second path to the same thing would be duplication — what the editor can do that `@file` cannot is point at *these twelve lines*. Insertion reuses the composer's existing external-write path (the same mechanism §9's rewind uses to return a message to the composer), so no store, event bus or ref plumbing is introduced. With no selection the action is unavailable rather than silently sending the whole file.

**Decision (Feedback round 12, 2026-08-13) — the editor's bar moves to the top, and the preview switcher becomes a pill:** the file tab carried its controls along the **bottom** while a chat tab carries its own along the **top** (§7 round 5.1), so two tabs in the same pane grid had opposite anatomies and the eye had to find the controls twice. The whole bar moves up, aligned with the tab strip. The **source/preview switcher leads it on the left as a two-icon toggle pill** rather than a labelled button that renames itself — a control whose label is the *other* state is a small riddle, where two icons with the current one lit are a switch. The rest becomes **icons with real tooltips** wherever an icon is honest: the file path stays legible text, because it is information rather than an action, and **Save keeps its unsaved state visible** rather than behind a hover — an icon that only announces "there is something to save" when pointed at is the one case where the tooltip arrives too late.

**Decision (Feedback round 15, 2026-08-16) — the file panel loses its close icon:** the header's `⇥` close button is removed — the top-bar rail button (§7 round 13) already toggles the panel, and the Changes panel lost its close button the same way in §29's GUI pass. One entry point, one exit, the same control.

The first magical moment combines: (1) **visible agent work** — the user watches a clean, readable trace of the agent working (tool calls, statuses, diffs); (2) **context understanding** — the user sees the context window and understands exactly what the agent knows. Onboarding steers the first session toward experiencing both.

**Decision (Feedback round 17, 2026-08-31) — the overlay's promised re-open path is deleted, not built:** three code comments and one validation note claimed the welcome overlay was *"re-openable from the Help affordance"* — an affordance §7's round 8 removed on purpose, so a dismissed overlay was gone for good while the code said otherwise. ## 23. Plan Mode

**Decision (2026-07-19, locked)** — full proposal in Notion ("Plan mode proposal", page `3a0d33dfffca80848f85c0ff0b6df04f`).

Plan Mode is a **per-session, read-only "think before you touch" mode**: the agent explores the codebase, asks clarifying questions, and delivers a structured implementation plan — **without being able to modify anything** — and the user approves implementation with one click. It is the permission story told forward (safety *before* the action, not only a gate *at* it) and the calm inverse of dangerous mode. Built natively in the HappyVibe bridge (not a vendored extension); the read-only bash allowlist and the 3-phase planning prompt are adapted from `@narumitw/pi-plan-mode` (MIT), the durable-plan-file and file-referencing implement handoff from `@bacnh85/pi-plan`.

**Entering / leaving.** A composer **toggle** turns Plan Mode on for the session; the model can also enter it from chat by calling a `plan_start` tool ("let's plan this first"). A persistent **calm banner** (dangerous-mode banner's twin, in a calm color) shows while active, with a one-click **Exit** and a **"Wrap up the plan"** nudge. Leaving Plan Mode — and starting implementation — is **human-only** (see the security invariant).

**Read-only gate.** While Plan Mode is active, the bridge's `tool_call` gate runs a plan clamp **before** the normal permission engine and **before** the dangerous/bypass check (Plan Mode wins over bypass — "read-only" must mean read-only or the banner lies): mutating built-ins (`edit`, `write`) are **blocked** and `subagent` is **conditional** (see the delegation decision below); `bash` is limited to a **fail-closed read-only allowlist** (inspection commands + safe `git`/`gh`/`npm` queries; redirects, substitutions, background jobs, and chains with any unsafe segment are rejected); read-only built-ins (`read`/`grep`/`glob`/`list`/`ls`) auto-run; **everything else** (MCP, unknown extension tools) falls through to the normal rule engine with a **floor of ask** (never auto-allowed in Plan Mode; explicit deny still denies). A blocked call renders as a quiet "Skipped — not allowed in plan mode" card, audit-logged like any gate decision.

**The plan is a workspace file.** On completion the model calls `plan_complete({plan})`; the **app (main process)** writes the plan to `.agents/plans/NNN-<slug>.md` (path-confined + audited, the agents-md-maker write pattern). The plan markdown must contain a **Tasks checklist** (`- [ ]` items) and a **Verification** section. The plan then lives on disk — visible in the file tree, openable in the built-in editor, hand-editable — so compaction can never eat it (the agent re-reads the file), and drift is handled by the plan being a **living document** the agent updates as reality differs. The implement handoff **references the file** ("Execute the approved plan in `<path>`: read it if needed, keep it scoped, update it if reality differs, run its verification") rather than pasting the plan into context.

**Status lifecycle.** The plan file carries **front-matter status** `draft → implementing → implemented | cancelled` (timestamped). "Implemented" comes from an **explicit signal, never inference**: the implementing agent calls `plan_status_update` when the Verification passes — the same structured-tool-call philosophy as `plan_complete`. If it forgets, status stays `implementing` (no worse than a latch) and the checklist `n/m` progress still tells the story. The **PlanCard** in the transcript shows the plan, live checklist progress, and status-dependent actions (draft → Implement / Keep planning / Discard · implementing → progress + Stop · implemented → ✓ · cancelled → Reopen). The user can always override the status from the card, including **Reopen** (human-only).

**Decision (Feedback round 9, 2026-08-01) — the plan is reachable without the transcript:** a PlanCard lives at its `plan_complete` position in history, so a compaction that eats that position leaves an *implementable plan with no Implement button* — and the bug that surfaced this was the workaround for it (a bottom-appended card frozen at "draft", claiming an implemented plan was still pending; removed in `833a966`). The plan therefore gets a home outside the transcript: a persistent **active-plan pill** beside the context % bubble, shown whenever the session holds a plan in `draft` or `implementing`, opening the same PlanCard. The plumbing already exists — the bridge preserves `planPath` across a respawn even after Plan Mode exits, and main holds it in `planState`; only a renderer reload lost it, closed by returning `planPath` from the open-session call. Rejected: pinning the card at the compaction boundary (a live **Implement** button inside a region explicitly labelled "not in the agent's context"), and a full Plans surface (a new lister, IPC and page for a problem the pill already solves — revisit if plans outlive their sessions often enough to want a workspace-level list).

**Decision (2026-08-21, Subagents-permission-gap round) — read-only delegation is allowed while planning, and the clamp is enforced by the type system:** the original clamp blocked `subagent` outright because a child carried its own tool set and nothing on our side could bound it (§12, 2026-07-19). §12's boundary decision removes that reason: a child's toolset is now decided by a host-registered capability ceiling. So a delegation is permitted in Plan Mode **iff** its preflight-resolved effective toolset is a subset of the read-only set, and it launches under a read-only ceiling; anything wider is blocked with the boundary named in the reason. This matters more here than anywhere else — planning *is* exploration, and delegating a long codebase search to a read-only explorer is the single most useful thing a planning session can do, while being exactly the thing the old clamp forbade. Mechanically `subagent` leaves the blocked-tools set and the plan gate grows a fourth outcome for it, so a caller that fails to handle the boundary check **fails the typecheck** rather than silently allowing the call — the one property that keeps a read-only mode honest is that its gate cannot be removed by accident. Plan Mode still wins over bypass, and the in-flight carve-out is unchanged: a delegation dispatched before Plan Mode was entered is not cancelled.

**Security invariant.** The model may only **restrict itself** (`plan_start`) or **record terminal facts** (`plan_status_update` → implemented/cancelled). Every transition that **grants power** — Implement (restores full tools), exiting Plan Mode, Reopen — is **human-only** (button/confirm). There is no `plan_off` tool. Model-side transitions are auto-allowed (they never touch permissions) but audited with **who** set them (model | human).

**Model nudges (Decision, 2026-07-20).** Because planning rewards reasoning and implementation rewards throughput, the UI **nudges both ways**: entering Plan Mode suggests using your **smartest model** for planning; the Implement action lets the user **pick a reasonable model** for the implementation turn (pre-filled with the session model, reusing the session model override).

**Lifecycle & interplay.** Exiting mid-turn **aborts the running turn first**, then restores tools (the "must be idle" rule, like rewind). Each fresh entry into Plan Mode starts a **new** numbered plan file; a revision within one planning phase updates the **same** file. Discard clears the session's plan state but **leaves the file on disk** (the user's artifact). Plan state is **persisted in the session file** (`pi.appendEntry`) and restored on respawn — unlike dangerous mode, it survives hibernation and MCP live-reload. Parallel sessions in one workspace never collide because the main process serializes plan-file numbering. Sub-agents in Plan Mode: see §12.

## 24. Prompt templates

Prompt templates are user-authored `/slash` prompts — the name is Pi's own, and its CLI flags are `--prompt-template` / `--no-prompt-templates`. The format is byte-compatible with Claude Code's `.claude/commands/*.md` (frontmatter `description` + `argument-hint`, body with `$1` / `$ARGUMENTS` substitution). They are the third resource tier HappyVibe makes **visible, reviewable and gated**, after skills (§14) and MCP (§13). Full proposal in Notion ("Prompt templates", page `3b0d33dfffca81f69b39d064851130a7`).

**Decision (2026-08-02, scope and reuse):** V1 = discovery + trust + import, in **both global and workspace scopes**, reusing §14's machinery wholesale. The gate is the additive pair the §14 resource-gate decision already ships and already tests: `--no-prompt-templates` (always) plus one **`--prompt-template <file>` per approved template** — the same shape as `--no-skills`/`--skill`, pinned in both directions by `tests/resource-gate-contract.test.ts`. Approval is **per file, never per directory**: approving a directory would silently approve files added to it later, which breaks review-before-active. Prompt templates are strictly simpler than skills — one `.md` file, no scripts, no subdirectories — so the three-axis approve/enable/activate model, the JSONL registry, the re-review diff, the removal semantics and the debounced respawn-resume reload all carry over unchanged, while two skills concepts are **dropped**: `scriptCount` (replaced by a `` !`bash` `` risk pill, see below) and the `loadable`/`error` axis, because Pi loads a description-less template fine (it falls back to the first body line). **The bridge is not involved in gating at all** — Pi expands templates itself, so there is no `use_prompt_template` tool, no system-prompt injection, no manifest entry, and consequently **zero resting context cost**; templates are excluded from the context gauge rather than reported as zero. Out of scope: a curated catalog (the §14 shortlist research found only one repo shipping real CC-format templates, so there is nothing to curate), `allowed-tools` enforcement, `` !`bash` `` emulation, and a template-authoring UI.

**Decision (2026-08-02, scopes — `.claude/commands` is read in place, never copied):** global = `<agentDir>/prompts` (managed) + `<runtimeDir>/prompts` (bundled) + linked external dirs; workspace = `<workspace>/.agents/prompts`. Pi itself discovers neither of the workspace paths (it knows only `.pi/prompts` and `<agentDir>/prompts`), which is immaterial because HappyVibe passes explicit paths — but it means the locations are a HappyVibe choice rather than a mirror of Pi, and `.claude/commands` support is ours to build. It is **discovered where it lives, never imported**: at global scope `~/.claude/commands` becomes a linked directory exactly like `~/.claude/skills` (referenced in place, user-added). Copying would be actively wrong — `.claude/commands` is typically git-tracked and team-owned, so a copy into `.agents/prompts` yields two files that drift. HappyVibe writes to `.agents/prompts` only for templates it creates or imports itself. Import sources are §14's four: bundled, local folder, linked dir, git URL.

**Decision (2026-08-02, invocation transparency — the prompt-template card):** typing `/review src/foo.ts` currently produces **three different transcripts from the same keystrokes** — the typed text when idle, the fully expanded prompt when steered into a busy agent (`queue_update` carries Pi's expanded text), and the fully expanded prompt again after any reload (the session file stores only what Pi stored). Pi builds the user message from the expanded text alone and preserves the original nowhere, so the short bubble silently becomes a wall of text after ⌘R, and rewind-to-composer then repopulates the composer with generated prompt the user never wrote. Meanwhile the context panel counts the expansion correctly — so **the cost is disclosed while the content is hidden**, the exact inverse of §9's promise. An invocation therefore renders as a **card**: header `/review src/foo.ts`, expanded prompt behind a collapsed disclosure, stable live, steered and rehydrated. The pairing is **exact rather than heuristic**: `pi.on("input")` fires with the original text and `before_agent_start` fires with the expanded text in the same call stack, so the bridge correlates them and notifies `hv.prompt-template {typed, expanded}`; main records `{typed, sha256(expanded)}` in the EventLog and the restore path re-pairs by hashing each restored user message. Unpaired messages render as plain text — today's behaviour — so the failure mode is degradation, not breakage. **This is the only new surface in the feature and it carries the feature's only real risk:** an `input` handler sits in the path of *every* user prompt, so it must fail open and be wrapped, with a test proving an ordinary non-slash prompt still lands (same class as the `before_provider_request` trap in `docs/validation/tc1.md`).

**Decision (2026-08-02, collisions and degraded templates):** Pi resolves a name clash in favour of the **extension command, silently** — `/hv-*` commands are matched and returned *before* template expansion, so a prompt file named `hv-plan` is completely unreachable while still appearing in `get_commands` as `source:"prompt"`. HappyVibe therefore **refuses an import** that would collide and names the conflict, and shows a permanent **"shadowed"** badge when such a file appears on disk without an import (a workspace file can arrive by `git pull`). Separately, a CC template using `` !`bash` `` inline injection produces a literal string under Pi rather than command output; that is detected at scan time and surfaced as a **risk pill** on the row — mirroring skills' "includes N scripts" — but never blocks the import, since a template that degrades is still a template the user may want. `allowed-tools` frontmatter is ignored, consistent with §14.

**Decision (2026-08-02, surfaces):** **Prompt templates is its own page** in the sidebar's Settings group (§7) and its own block in workspace settings after Skills — merging it with Skills into an "Extensions" page would rename a shipped surface and break the round-8 naming to save one row. The composer's `/` autocomplete already exists for `/skill:` and already reads Pi's `get_commands`; it widens to keep `source:"prompt"` as well. Argument hints come from HappyVibe's own scan, because `get_commands` does not carry `argumentHint`.

**Decision (2026-08-03, the feature is named "Prompt templates", not "Commands") — amends the surfaces decision above:** the feature shipped under Claude Code's word for it. Pi's own term is **prompt template** and its flags are `--prompt-template` / `--no-prompt-templates`, so "command" was doing two jobs at once: this feature, and a slash invocation in general. That ambiguity was not theoretical — `hv:list-commands` returns extension, skill *and* prompt rows, `RESERVED_COMMAND_NAMES` held *extension-command* names used to gate *template* names, and two of the four bugs found in the §24 GUI pass sat exactly on that boundary. **Renaming a shipped surface is what the decision above argues against, and that reasoning still holds — it is overridden here only because nothing had merged yet**, so the cost was one branch rather than a user-visible rename. The word **command** now means exactly one thing: a slash invocation (`/hv-*`, `/skill:*`, `/name`) or a shell command. Code uses `promptTemplate`, not bare `prompt`, because `hv:prompt-session`, `promptCommand` and `systemPrompt` already own that word. Deliberately unchanged: `hv:list-commands`, `get_commands`, `pi.registerCommand`, the `.claude/commands` paths, and the composer's `/` menu — which lists skills and templates together and is therefore genuinely command-generic. Persisted names moved with no compatibility shim (approvals file, event types, workspace and config keys), accepted because the only data was one dev machine's.

**Decision (2026-08-03, the UI says "Prompts", the code says `promptTemplate`):** "Prompt templates" is implementation vocabulary; what a user has is a **prompt** they type as `/name`, so the product calls it that — sidebar, page title, section headings, empty states, import modal, confirms and the main-process errors users read. The **codebase keeps `promptTemplate`** (identifiers, IPC channels, filenames, persisted keys, event types), because that matches Pi's own term and its `--prompt-template` flags, which is what a maintainer needs. **The split is deliberate and is recorded here so neither side later reads as stale.** Two UI strings keep the full term where it draws a distinction rather than naming the feature — the shadowed warning ("Pi matches built-ins before prompt templates") and the `/`-menu subtitle, both contrasting against commands and skills — and the Prompts page's section subtitle keeps "Reviewed, gated prompt templates" as the single place a newcomer meets the full term and can connect it to Pi's docs and `.claude/commands` compatibility. Engineering docs (`docs/validation/pt1.md`, `d1.md`, `CLAUDE.md`) describe the code and keep "prompt template" throughout.

**Decision (2026-08-03, `.claude/commands` is never auto-discovered) — supersedes the scopes decision's `.claude` handling entirely:** the Prompts page already offers **Import folder** and **Link a directory**, so a third button that proposes one specific path was redundant — and it was the only place the app made a directory choice on the user's behalf. It is removed along with its `hv:prompt-templates-claude-dir` probe: a user who wants `~/.claude/commands` links it with the general control, which keeps them in charge of what the agent can reach. Going further, **`<workspace>/.claude/commands` stops being an automatic scan root too.** The app should not reach into a directory another tool owns without being asked — in either scope — and a user who wants those files gets them through **Import folder** (which still looks inside a picked repo's `.claude/commands`, because that is user-initiated) or **Link a directory**. This also removes the `claude` source, so prompt templates now have exactly the four sources skills has (`managed` · `workspace` · `linked` · `bundled`). **That consistency is the tell that the original design was wrong:** skills never auto-scanned `.claude` anywhere — `~/.claude/skills` is only ever a user-added linked dir — and prompt templates invented a fifth source without a reason skills didn't also have. A workspace now has exactly one prompt root, `.agents/prompts`, mirroring `.agents/skills`. Support is unchanged: linked and imported `.claude/commands` files behave exactly as before.

**Decision (2026-08-03, a plugin's `commands/` install as prompt templates — top-level only) — amends this section's "nothing to curate" out-of-scope line:** §25 accepts `commands` as one of three component surfaces, so the marketplace is the route the shortlist research could not find; the out-of-scope line above was right about the *shortlist*, not about the format. A plugin's `commands/*.md` are byte-compatible with what this section already ships, so they install as ordinary prompt templates through the existing per-file approval — no new machinery. Two properties of Pi bound what that can mean. **Only top-level files install:** `loadTemplatesFromDir` is a flat `.md` readdir, so Claude Code's `commands/git/commit.md` namespacing is unreadable to Pi, and a nested file would be listed as a command that can never be invoked. Nested ones are therefore **counted in the install disclosure** (§25) rather than installed, silently listed, or flattened — flattening to `plugin--git-commit.md` was rejected because a command whose name no longer matches the author's docs is worse than one that is absent and named as absent. **The namespace is flat:** a template's name is its basename (Pi reads no frontmatter `name`) inside one `<agentDir>/prompts`, so two plugins each shipping `commands/review.md` collide with each other; the import refuses and names the conflict, extending the same `refuseReservedNames` guard that already does this for `/hv-*`. Accepting `commands` is consequently worth less than the raw 26.8% of plugins that ship them, but no plugin's accept/reject verdict changes — it installs with fewer commands and a line saying which.

**Rejected (2026-08-02): `resources_discover` as a hot-reload path.** The hook is real, is additive, and does work under `--no-prompt-templates` — but it fires only at session boundaries, never per-turn, and the resource loader **never removes** a previously-added path within a runtime lifetime, so a deleted template would survive until a full reload anyway. It buys nothing over the existing debounced respawn-resume path and is not used.

**Decision (Feedback round 7, 2026-07-30) — Implement is snapshotted (closes the baseline-capture pointer below):** the baseline capture at Implement is **in V1**, built on §9's snapshot store rather than a git baseline. Implement takes a **labelled snapshot** and the PlanCard gains **Revert implementation**, restoring the workspace to its pre-implementation state with the same human-only, safety-snapshotted, stale-checked semantics as rewind. This supersedes the out-of-scope pointer below, which deferred it to V2 and assumed a git baseline (prior art `@bacnh85/pi-plan`'s `/rewind` remains the design donor).

**Out of scope for V1 (post-V1 pointers):** a per-tool selector for opting extra tools into planning. Wire shapes: `docs/validation/d1.md` §Plan Mode.

## 25. Plugin marketplaces

A Claude Code **plugin** is a directory bundling any of eleven component types (skills, commands, agents, hooks, MCP servers, LSP servers, monitors, workflows, output-styles, themes, channels) behind a `.claude-plugin/plugin.json` manifest, listed for install by a **marketplace** — a `marketplace.json` in a git repo. HappyVibe ingests them through the surfaces §13, §14 and §24 already gate, filtered to the components whose execution funnels through `tool_call`. Full design in Notion ("Plugin marketplaces + MCP-by-import", page `3b0d33dfffca81959ccfc197e48a0eb6`), with the measured survey in its "Exploration on marketplaces and hooks" child page.

**Decision (2026-08-03, scope — accept skills + commands + mcpServers, reject the rest):** the accepted **component surface** is `skills`, `commands` and `mcpServers`; `hooks`, `lspServers`, `monitors`, `workflows`, `channels`, `outputStyles` and — for now — `agents` are rejected. Measured against 408 resolvable plugins across the four largest marketplaces, that accepts **59%** of the official marketplace (up from 30% under a skills-and-commands-only filter) and ~50% overall, while adding **zero** new out-of-band execution paths. The cut is not "no code": a `SKILL.md` may perfectly well say *run `scripts/build.sh`*, and it executes through the model's `bash` call — our gate, our prompt, our audit envelope, our `gatePlanCall` clamp. Hooks, monitors and LSP servers execute on *events* rather than on the model asking, so they reach none of those. The rule is HappyVibe's existing invariant restated as an install rule: **all code funnels through `tool_call`**. `agents/` is excluded for a different reason and only until the subagent permission gap closes — `spawn.ts` loads the bridge into the parent session only and `writeSubagentConfig` injects neither a bridge nor a tool allowlist, so child tool calls run today with no prompt, no audit envelope and no plan clamp. That is a pre-existing gap independent of plugins, on its own track; accepting plugin-declared agents before it closes would widen it. **Update (2026-08-21):** that track now has a named closing condition — §12's boundary decision, and specifically its adversarial-agent requirement, which is the test a plugin-supplied agent file has to survive (frontmatter that widens its own permissions, path-like `tools:` entries that load as extensions, a `.ts` shipped beside the agent definition, nested delegation). Until that requirement is *demonstrated* rather than merely implemented, plugin-declared agents that also declare skills, extensions or inherited skills are refused; `agents/` stays out of the accepted component surface, and the narrower product claim above stands as written. The product claim is scoped to match what is true: *"every plugin skill and every plugin MCP call goes through the same permission gate as the agent's own tools"* — deliberately narrower than "everything a plugin does", which the subagent gap still falsifies.

**Decision (2026-08-03, the classifier is an allowlist over the file tree AND the manifest):** accept a plugin iff its manifest keys are a subset of `{name, version, description, author, homepage, repository, license, keywords, skills, commands, mcpServers}` **and** its component surface is a subset of `{skills, commands, mcpServers}`; reject on anything else. A denylist is wrong in kind here — Anthropic keeps adding executable component types (monitors and channels are recent), so a denylist fails open on the next release while an allowlist merely fails *closed* on something new until we understand it. Classifying from the manifest alone is **unsound**, not merely incomplete: every executable component type has both a convention path and a manifest field, and this was confirmed empirically rather than reasoned about — the `airtable` plugin declares no `mcpServers` yet ships a `.mcp.json`, so a manifest-only filter passes it. Note the tree walk must read dot-paths deliberately: `scanSkillsDir` skips every entry beginning with `.`, which makes `.claude-plugin/plugin.json`, `.mcp.json` and `.lsp.json` invisible to the existing scanner. **Decision (2026-08-04, the two halves of the check are calibrated against the real marketplace, which the design-as-written got wrong twice):** verified by downloading `anthropics/claude-plugins-official` (278 entries) and reading 25 bundled manifests plus one external plugin at its pinned commit. (1) **Unknown *directories* are ignored, not rejected.** The accepted-component check is a **known-name** test over the convention paths (`skills/`, `commands/`, `agents/`, `hooks/`, `workflows/`, `monitors/`, `output-styles/`, `themes/`, `channels/`, `.mcp.json`, `.lsp.json`) plus the matching manifest fields; a plugin rejects only when a *known* component falls outside the accepted three. Real plugin roots ship `hooks-handlers/`, `scripts/`, `core/`, `utils/`, `matchers/`, `examples/`, `assets/` and `references/` as ordinary payload, so "reject on unknown component dirs" would have rejected working plugins for shipping a source folder. (2) **The manifest key allowlist needs the benign metadata real plugins actually use, and it is a data list kept honest by evidence rather than by guessing.** `category` is the proof: the survey validated `42crunch-api-security-testing` **by hand as clean**, yet its manifest carries `category`, so the allowlist as first written would have rejected the one plugin used to prove the classifier worked. Observed and accepted: `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords`, `category`. Unknown-key reject is **kept** rather than relaxed to "ignore unknown metadata", because a manifest field is exactly where the next executable component type will announce itself — but the reject message names the offending key, so a genuinely benign addition is a one-line data change instead of an unexplained missing plugin. The allowlist covers the **component surface, not every file** — rejecting on payload directories costs compatibility for no safety gain. The resolver handles the shapes actually present — `url` (143), `git-subdir` (80), a bare `./path` string relative to the marketplace repo (53), and `github`+`repo` (2), where `url`/`git-subdir` may carry `path` and `ref` — and survives dead entries: two of the official marketplace's are already dead links. ~~**Rejected plugins are shown greyed with the reason**~~ — reversed on 2026-08-04, see the next decision.

**Decision (2026-08-04, verify at release time and list only what installs) — supersedes "show rejects, do not hide them", and with it two more decisions in this section:** unsupported plugins are **not listed at all**. The argument for greying them was that *"a user who searched for a plugin they read about and found nothing concludes the store is broken"* — but a store full of things you cannot install is the worse message, and the listing could not even identify most of them: of 278 entries, 12 declare `lspServers`, 4 declare `skills`, and **zero** declare `hooks`, `agents`, `mcpServers` or `commands`, so ~90 rows that refuse on click looked installable. Instead a committed generator (`tools/plugin-catalog/build.ts`, `npm run catalog:plugins`) resolves every entry at its pinned `sha`, classifies it with **the app's own `scanPluginDir`**, and writes `src/main/plugins/catalog.generated.ts` — which the app then serves with **no network at all**. Two further reversals follow from it. **(a) The official store is generated and embedded, not fetched** (amending "marketplace lists are fetched" above), which puts it on §13 round 8's *"bundled, not fetched … the accepted cost is staleness"* posture, minus that decision's manual per-entry tax because generation is automated; the trade is that a plugin added upstream after a release is invisible until the next one, disclosed in the UI as "checked &lt;date&gt;". **(b) The survey scripts ARE committed** (amending the Appendix), because this is no longer research reproducing numbers — it produces a shipped artifact. Reusing the app's real scanner rather than a second classifier is load-bearing: the store's promise is that everything listed installs, and any drift between two implementations would surface as a refusal in front of the user. Tarballs rather than the GitHub API means the generator needs **no token** and cannot be rate-limited; extracted trees cache by `sha`, so a re-run only fetches repos that moved. Measured result: **181 of 278 listed (65%)**, every rejection a genuine executable component. Cards carry a brand icon via the existing `BrandMark` (auto-matched against the 3445 slugs the installed simple-icons font really ships, so a class can only be emitted if it renders, with `tools/plugin-catalog/brand-overrides.json` for the wrong ones — 83 of 181 get one, the rest a monogram) and the verified component counts, so no card needs a download. Guarded by `tests/plugin-catalog.test.ts`, which runs in the normal suite on the committed data. The generator's **run summary is part of the design**: it is what exposed both of the bugs recorded in the next decision.

**Decision (2026-08-04, two bugs the verification pass exposed, both in already-shipped code):** running the classifier over all 278 real entries — rather than over fixtures — found two defects that green tests had hidden. **(1) A plugin's `.mcp.json` comes in two shapes, and we read only one.** Measured: **169 wrapped** in `{mcpServers:{…}}`, **26 bare** as a straight `name → config` map — and the bare set is `github`, `linear`, `context7`, `playwright`, `asana`, `firebase`, `gitlab`, `terraform`. `scanPluginDir` read them with `readMcpFile`, which requires the wrapper, so it returned **zero servers** for all 26: they classified as *having* `mcpServers` while offering none, and were dropped as "nothing to install". MCP-by-import — this section's largest single win — silently imported nothing for every first-party MCP plugin. Fixed with a dedicated `readPluginMcpServers`; `readMcpFile` stays strict because it parses HappyVibe's **own** config and loosening it would change how we read the user's files. **(2) The manifest allowlist was rejecting 44 plugins (16%) on benign metadata** — the same class as the `category` bug, found the same way. `$schema`, `displayName`, `logo`, `problem`, `interface`, `userConfig`, `categories`, `defaultEnabled` and `minClaudeCodeVersion` are now allowed, each read in a real manifest first. `userConfig` got the most scrutiny, since it declares config fields (some marked `sensitive`) that Claude Code collects and HappyVibe does not: of the 17 plugins declaring it, **zero are MCP-only and 15 carry skills or commands**, so rejecting them was pure loss, and the per-server confirm still gates whether such a server is added at all — the residual gap is that its credentials may be missing, not that anything unsafe runs. **`experimental` is the one key that could not be waved through:** `convex` declares `experimental: {monitors: "./monitors/monitors.json"}`, and a monitor runs a shell command for the session's lifetime, unsandboxed, at hook trust level. `detectComponents` therefore inspects nested namespaces, and `convex` correctly rejects. Reject-by-name is **kept**, not relaxed to "ignore unknown metadata", precisely because a manifest field is where the next executable component type will announce itself.

**Decision (2026-08-03, many marketplaces in the resolver, one in the data):** the resolver, schema and UI support **N marketplaces**; V1 ships listing exactly one, **`anthropics/claude-plugins-official`**. Adding another is a user action — the app lists no directory or repo on the user's behalf, the same posture as §24's decision to stop auto-scanning `.claude/commands`. The official list is the one users arrive already expecting, since it ships in every Claude Code install, and at 276 entries with 59% surviving the filter it is not thin; pre-listing the other three surveyed marketplaces would spend day-one trust on repos we do not control to solve a fullness problem we do not have. Building the **plural** form first is what makes a HappyVibe-owned `marketplace.json` a later data decision rather than a code decision — it is **deferred, not rejected**, and when it lands it is listed like any other, less privileged than the app itself: no bundled snapshot, no special trust, no second code path. Ref policy is to **inherit the marketplace's own pin** rather than float `main`: it means the marketplace's verification plus ours and no bump tax on our side. **The pin is `source.sha`, and it is universal** — verified 2026-08-04: all 225 entries with an object `source` carry a `sha`, and it resolves as a real git commit on codeload (tested against two entries in different repos), while the separate `ref` field is only a human-readable branch or tag and is absent on 146 entries. So `sha` is what we fetch, `ref` is what we show; the earlier reading of `sha` as some marketplace-internal hash requiring a float fallback was wrong. The 53 bare-`./path` entries need no pin of their own — they live inside the marketplace repo and are pinned by whatever commit we fetched the marketplace at.

**Decision (2026-08-03, ingestion screening — because the failure mode is silent):** a skill that cannot find its own files does not error; the hardcoded-path call is typically `2>/dev/null || true`, so the user gets confident prose with the machinery quietly dead. Three rules, applied **per file at ingestion** rather than per repo by hand (the original screening sampled only 1–2 `SKILL.md` per repo). A hardcoded `~/.claude/skills/...` is a **hard reject** — nothing at install time can repair a path into another tool's tree. A bare `$SKILL_DIR` is a **soft warning**: the agent can resolve it from the manifest, so the skill degrades rather than breaks. `${CLAUDE_PLUGIN_ROOT}` is **substituted at install, not rejected**: import already copies the skill directory to a path HappyVibe chose and hashes it *after* the copy, so the plugin root is known exactly when the content is written, and the substitution lands **inside** the content the user then reviews and approves. Rejecting instead would discard a class of otherwise well-formed plugins over a variable Claude Code sets and Pi does not — Pi sets **no** skill-path variable at all, verified against the pinned version, so this is an install-time screen or nothing. Two consequences are accepted deliberately: HappyVibe rewrites third-party content, so the substitution is **disclosed on the row and visible in the reviewed `SKILL.md`**; and the resulting hash differs from upstream's bytes, which is already true of every path-confined copy.

**Decision (2026-08-03, install lands disabled, and discloses what it dropped):** skills installed from a plugin are approved with **`enabled: false`** — the picker's ticks are the enabling gesture. This closes a live hole rather than adding caution: import currently approves with `enabled: true` and per-workspace activation is opt-**out**, so one click on a 62-skill repo would today pay 62 skills' card cost on **every turn in every workspace**, straight past the ~50-visible-tools threshold past which the agent measurably picks worse tools. Bundled skills already default off; plugin installs now match them. The alternative — keep `enabled: true` and warn past a token threshold — spends UI on a number to argue the user out of a default we can simply not set. Separately, deferring hook *support* does not defer hook *awareness*: the importer already walks the tree, so it **computes** what it is dropping and discloses only when non-empty ("installing 3 of 14 skills · 5 hooks and 2 namespaced commands will not be installed, so behaviour may differ from the author's setup"), which needs no per-entry copy and stays correct as upstream changes. This matters more than it looks — ponytail's persistence is a `SessionStart` **hook**, not a skill, so installing its skills alone gives working slash commands and a mode that never auto-activates; caveman (14 hooks) and impeccable (24 agents) are the same class. The banner also carries the two install-time transformations, so neither is silent: nested commands skipped, `${CLAUDE_PLUGIN_ROOT}` substituted.

**Decision (2026-08-04, prompts land disabled too, and the handover is explicit) — completes the decision above:** plugin-installed **prompts** are also approved with `enabled: false`. They were landing enabled while skills landed disabled, which made the obvious sentence — *nothing from this plugin is active yet* — false for half the install. Consistency is the point: a plugin install must not change what the agent can do until the user switches something on. (Reachable, not theoretical: `promptTemplates/view.ts` renders DISABLED off that flag and `resolveActivePromptTemplates` gates the spawn on it.) The confirm dialog states it **before** the click — installing copies things in and nothing more, skills and prompts arrive off, MCP servers arrive unconnected — and the success banner repeats it with real counts as a per-page checklist (*enable on Skills · enable on Prompts · connect on MCP*), naming **only the parts that apply** so a skills-only plugin is never told to connect a server. No second modal: the dialog already is the confirmation, and another one would be a click that buys nothing.

**Decision (2026-08-04, exclude plugins whose MCP server no HappyVibe install could authenticate with):** `mcpOAuth.ts` implements **Dynamic Client Registration only**, and some vendors issue credentials solely to clients they have pre-registered. Audited 2026-08-01: **Figma** returns a flat `403` to every well-formed DCR request and **Slack** documents DCR as unsupported — Claude, Cursor and VS Code work because they are on those allowlists and we are not. Listing such a plugin offers a server that can never connect, which is the same broken promise the decision above exists to remove, so the **whole plugin is excluded**, not merely the server. Accepted cost: `figma` (12 skills) and `slack` (7 skills + 5 prompts) disappear; the store goes 181 → **179**. A plugin whose headline capability cannot work should not be offered for its side dishes. **The criterion is "no DCR *and* no token path", not "no DCR"** — and that distinction is load-bearing rather than pedantic: **GitHub** advertises no `registration_endpoint` either, yet its server genuinely evaluates a bearer PAT, which is exactly why §13 round 8 kept it as a *token* entry. A rule written the obvious way would have dropped the most-installed connector in the research. Two further limits: loopback is never gated (Figma's local Dev Mode server is unauthenticated and works — it just needs the desktop app), and a stdio server never authenticates at all. Data plus matcher in `src/main/mcpPreregistered.ts`; both traps pinned by `tests/plugin-preregistered.test.ts`. The gate runs inside `classifyEntries`, **not** the generator, because it is policy — phase 2's runtime indexer for user-added marketplaces inherits it for free, which is the reason that seam exists. What would actually unlock these is HappyVibe registering a real client with each vendor.

**Decision (2026-08-04, our copy names HappyVibe, not the tool the format came from):** user-facing strings describe what HappyVibe supports — *"Install plugins. HappyVibe supports plugins composed exclusively of skills, prompts and MCP servers"* — and the drop banner leads with what the plugin ships rather than branding another product. Deliberately **not** rewritten: the ~180 upstream plugin descriptions, which are their authors' words and mention the tool they were written for. Rewriting them would misrepresent the author and add a per-release editing tax for no user gain, so they render verbatim. Code comments, this PRD and CLAUDE.md keep the term too, because there the provenance of the plugin format *is* the information.

**Decision (2026-08-03, provenance and removal need no new store):** a plugin is not a fourth persistence mechanism. The link lives on the three surfaces that already persist — `origin: { plugin, marketplace }` inside the `mcp.json` server entry (unknown keys already survive the round-trip) and `plugin`/`marketplace` fields on skills' and prompt templates' existing provenance records (`SkillProvenance.source` is a plain string, not a closed union, so both are additive with no migration). Removing a plugin scans the three surfaces for its id. A dedicated `plugins.jsonl` would turn that scan into a lookup at the cost of a fourth store to keep consistent with what is actually on disk — the wrong trade at this scale.

**Decision (Feedback round 12, 2026-08-13) — the store paginates, sorts brands first, and finishes the install where it started:** three things the 179-entry list needs now that it is real. (1) **It stops rendering every card at once** — a first page plus **Show more**, not numbered pagination, which would need a cursor kept in sync with the search box *and* the category chips to buy nothing a Show-more does not. (2) **Recognised brands sort first, then alphabetically inside each group.** "Recognised" means *the generator resolved a brand icon* — mechanical, 83 of 179 today, and inheriting `BrandMark`'s existing guarantee that a class is only emitted if it renders. A hand-picked "featured" list was rejected for re-introducing exactly the per-release curation tax the generated catalog exists to remove. (3) **Installing hands over in place.** The handover stops being a checklist naming three other pages and becomes where the work happens — *Enable all 3 skills*, *Enable the prompt*, *Connect the server*, calling what those pages call. This does **not** reverse the 2026-08-04 rule that a plugin install activates nothing: the click is still the enabling gesture, it has simply stopped being a page hunt, and only the parts that apply are named.

**Correction (2026-08-14) — the handover has to be where the click was, and the first version was invisible:** putting those controls in the success banner was not enough, and the report was "I see no difference, still need to go to the Skills and MCP pages". The buttons existed; they could not be **seen**. The banner sits above the card grid, so installing from the confirm dialog rendered it at **576→652 in a 638px viewport** — the button below the fold — and further off-screen for anyone who had scrolled through 179 cards to reach the plugin. This is §14 round 11's lesson a second time: *a feature whose only output lands where the user is not looking has not shipped*. So the **confirm dialog now stays open and becomes the handover**, with `Done` closing it; the banner keeps the same controls for afterwards, and both render **one** `Handover` component so they cannot drift. The **pre-install disclosure stays** — an install must never read as activation — but its second half no longer hands over a to-do ("turning each one on … is your move", pointing at three pages) and instead says what happens next: *then this dialog offers to switch them on, in one click, without leaving the page*.

**Decision (2026-08-04, a user-added marketplace is INDEXED, not listed unverified) — replaces "pre-listing third-party marketplaces" in the out-of-scope line below:** the embedded store covers the official marketplace only, so a marketplace the user adds themselves has no verified data. It must not be listed unverified — that would reinstate exactly the refuse-on-click experience the decision above removes. Instead, adding one triggers an **indexing pass**: the same `classifyEntries` policy as the generator with a different fetcher (the trees API and `raw.githubusercontent.com` rather than tarballs, since a user's machine cannot absorb hundreds of downloads), throttled to the unauthenticated 60/hour budget, persisted incrementally to `<userData>/plugin-index/<marketplaceId>.json` so a pause resumes rather than restarts, and refreshed when the list's sha changes or the index is older than ~30 days. Measured, so throttling is scoped to the tail rather than the norm: `trailofbits/skills-curated` needs **0** API calls (29/29 entries are marketplace-local, i.e. one tarball), `obra/superpowers-marketplace` needs 10, and only a `wshobson/agents`-sized list (95) needs real pacing. `classifyEntries` already takes its fetcher as a parameter for this reason — the seam was built in phase 1 rather than retrofitted, because retrofitting it would mean editing the generator, the one component whose agreement with the app is the point. **This is designed but not built:** the add-a-marketplace control stays hidden until it ships. Full plan in Notion ("Let user add markeplace", page `3b2d33dfffca809aae03db4eefda0131`).

Out of scope: hooks · LSP servers · monitors · workflows · channels · output-styles · `agents/` until the subagent permission gap closes · nested (namespaced) plugin commands · a per-workspace activation axis for MCP servers · a HappyVibe-owned marketplace · listing a user-added marketplace before it is indexed (see the decision above) · install analytics · vendoring `@nklisch/pi-plugins` (rejected: it bundles forks of the two packages we pin exact, its management surface is TUI-only in RPC — the §10/V6 failure mode again — and its hook runtime spawns plugin-declared commands out-of-band, before our `tool_call` handler).

## 26. Terminals

A real shell, in the app, in a tab, with its cwd at the workspace root. Two halves with different UX and different permission stories, specced as two Notion pages under one PRD section: **part 1, the terminal a human types in** (page `3b5d33dfffca81e09d1eda876ae2d322`) and **part 2, the terminal the agent drives** (page `3b5d33dfffca8118a09ac7553a59502b`). Part 1 is built first and is a prerequisite for part 2. The stack is the standard one Hyper, VS Code and Tabby all ship: `node-pty` in main, `@xterm/xterm` in the renderer, bytes over IPC.

The governing rule is the product's existing one, restated: **permissions gate the agent, not the human.** Part 1 has no gate at all. Part 2 puts the whole gate back.

### Part 1 — the user's terminal

**Decision (2026-08-07, a third tab type):** the terminal is `:term:<id>`, a third prefix beside §21's file path and §7's `:chat:<sessionId>`, in the existing 2×2 pane grid — draggable, splittable, closable, and mounted once and placed by CSS `grid-area` like every other tab. The layout that motivates the feature (chat left, terminal bottom-right, file top-right) therefore needs no new layout work. **⌘T** opens one in the focused pane (the binding was free) and joins the pane's `+` menu beside *New session* and *Open file…*; **⌘W** closes it, confirming first and naming the process when one is running, because closing a terminal tab **kills its PTY** — a terminal tab *is* its terminal. The tab title is the running command, falling back to the shell name, falling back to `Terminal 2`. Two consequences of the prefix are named because they are silent defects rather than new work: `allFiles()` means "every tab that is not a chat", so a terminal would be classified as a **file** by the editor mount list, the filesystem watcher **and §9's open-files context block** (the agent would be told a file named `:term:a1b2` is open) — fixed once in `allFiles`, where all three callers route through; and ⌘W deliberately skips non-file tabs today, so the terminal branch and the shortcut's label are additions, not inheritance.

**Decision (2026-08-07, per workspace, never per session):** a terminal is bound to a project directory, so it belongs to the workspace — cwd from `WorkspaceRegistry`, no limit on how many, and switching workspaces switches which you see. It therefore **survives a neighbouring session ending, hibernating, or being respawned by an MCP reload**, because it never belonged to one. Removing a workspace kills its terminals, joining §5's confirmed two-outcome removal flow. **The agent never opens a tab** — part 2's terminals are transcript cards, and only a human promotes one here via *Open as tab*.

**Decision (2026-08-07, PTYs are owned by main and the whole tab layout is persisted):** the renderer is a view. The pane/tab layout was React state only, so ⌘R dropped every chat, file and terminal tab alike; it is now serialised to `config.json` exactly as the keyboard bindings already are and restored on boot, with tabs whose session or file no longer exists dropped on restore. Terminal re-adoption is then a **consequence** rather than a mechanism — the PTY never died, so a restored tab attaches a fresh emulator and repaints. A terminal-only re-adoption path was rejected for making the newest tab type the only one that survives a reload, which reads as a bug in the other two; persisting the layout costs about the same and fixes a defect that predates the feature.

**Decision (2026-08-07, the scrollback buffer lives in main as a headless terminal):** main runs one `@xterm/headless` instance per PTY, fed the same bytes as the renderer, capped by the scrollback setting. One buffer, three readers, and the third is why it is not a raw byte ring: the **live renderer** takes raw bytes straight to `term.write()` (never through React state, per §7's standing perf invariant); a **re-attaching renderer** repaints via `addon-serialize`, which is correct even mid-TUI where a replayed byte ring shows noise until the program next redraws; and **part 2's `terminal_read`** reads the rendered grid, so the model receives clean plain text with cursor-addressed output already resolved rather than ANSI that a `strip-ansi` pass turns to gibberish the moment a progress bar rewrites its line. Cost: one dependency, ~2 MB per terminal.

**Decision (2026-08-07, no gate, one audit entry):** no permission prompts and no keystroke audit — the human typed it. **One EventLog entry when a terminal opens**, so the audit trail (§11) is not silent about the existence of a shell, and not one per command or per keystroke.

**Decision (2026-08-07, settings are global and all of them ship):** a **Terminal** page in the sidebar's Settings group (§16). Scope is **global**, because every setting is appearance or personal habit; the one per-workspace candidate is the shell, and a project needing `nvm use 20` should say so in its own dotfiles where every other tool reads it. All sixteen settings ship in v1 because the count overstates the work: they live in a **single `terminal` config object**, so the app's config plumbing pattern runs once, and eleven of them are keys xterm's own constructor already accepts, passed through verbatim. Only shell path, shell arguments and extra environment need real editors — and they are also the only three that can stop a terminal opening, so each gets validation and a reset, and a shell that fails to spawn shows the same inert "process exited" state as any other exit, naming the path it tried. Three presets — **Workshop** (default; the §20 ink-on-paper treatment chat code blocks already use, so a terminal beside a transcript reads as the same object), **Paper** (the app's cream, for bright rooms and screenshots) and **Carbon** (neutral dark) — with no custom-colour editor in v1. Addons: `fit` (required), `web-links` (URLs open in the OS browser via §7 round 4's rule, never in-app), `search` (so ⌘F means the same thing here as in the chat and the editor — a third focus-scoped consumer of §16's single `search` action). `webgl` is taken only if the canvas renderer stutters; ligatures are skipped as a dep for a taste preference.

**Decision (2026-08-07, the font field is a verified monospace picker, with no free-text option):** the family was a text box, which is weak for a reason worth stating: nobody knows what is installed on their own machine, and a terminal is the one surface where the font *must* be fixed-width. Measured on a stock Mac — `queryLocalFonts()` reports **180 families, of which exactly 7 are monospace**. A list of 7 is a choice; a text box against 180 is a guessing game. It also failed *silently*: `SF Mono`, the obvious thing a Mac user types, **does not resolve from a web context** (Apple restricts it to system UI), so it fell back with no feedback anywhere. The field becomes a **dropdown of families verified by measurement** — present (compared against two different fallbacks) *and* fixed-width (`i`/`l`/`W` share an advance), since the Local Font Access API reports style but nothing about advance width. **Symbol families are excluded by name**, because no measurement catches them: `Wingdings 2` is genuinely fixed-width and passes every check while rendering ASCII as pictograms. Rendering each row in its own font was the first answer to that and it was not good enough — *a list you have to visually discard entries from is still a list with garbage in it*. A denylist is acceptable here where it would not be in a security filter: the set is small, stable and decades old, and the cost of missing one is a silly row rather than a broken terminal. **The per-row preview stays**, because it is how you choose between the fonts that *do* belong — and it is where JetBrains Mono's ligatures become visible. **There is no "Custom…" escape hatch** — the value of the control is that everything in it works — so the list must never be empty: it unions enumeration with a probed list of ~30 known coding fonts, each still verified, because `queryLocalFonts` throws `SecurityError` on a backgrounded window (measured), does not exist on every platform and may be permission-gated. The stored value is now a **family name rather than a CSS stack**, normalised on read so an older config keeps working with no migration step, and the renderer appends `ui-monospace, monospace` so a font uninstalled after it was chosen degrades to *a* monospace rather than to the proportional default, which would silently ruin every column. A stored family that is no longer present is shown, selected, and labelled *not installed* rather than silently swapped.

**Decision (2026-08-07, the contrast rule stands and the hexes move):** every **normal-intensity** ANSI colour must clear **4.5:1** against its own background, asserted in a unit test over the palette constants. Measuring the palettes as first drafted failed the rule on the *default* style — Workshop red 3.10, green 4.25, blue 3.77, magenta 3.02, and Paper yellow 4.31, cyan 4.44 — so the four Workshop hues were lightened and the two Paper ones darkened, hue and saturation held, until each passes. The palettes are consequently no longer byte-identical to §20's CSS tokens while staying recognisably the same colours. The two alternatives were rejected as excuses in disguise: lowering the bar to 3:1 is a threshold picked to fit the data (Workshop's magenta clears it by 0.02), and asserting the xterm-*adjusted* colours ships an unreadable palette rescued by `minimumContrastRatio`, a setting the user can switch off — precisely what the rule exists to forbid. That setting stays as the mitigation for badly-behaved *programs*, which is what it is for. Three exemptions, each stated in the test rather than assumed: **`black` and `white`** — the achromatic pair, which programs use as *backgrounds*; black on a dark background is 1.00 by definition and no light theme can make white readable on white (Solarized Light has the same property and ships) — and **the brights**, because the rule says normal-intensity and a bright is by construction an emphasis variant of a colour already proven readable. So the rule binds the six chromatic normal-intensity colours, which is what it was always about.

**Platform:** macOS-first, per §4. `node-pty` works on Windows, but the shell default, the `-l` argument and the login-shell PATH trick are POSIX assumptions — and `shellPath.ts` already returns `undefined` on win32, so the app has taken this position before. The shell path and arguments settings are the escape hatch, which is a second reason they ship in v1. The main risk in the whole feature is **packaging, not product**: `node-pty` is the first native module in the root tree, and the ad-hoc re-sign step is the same class of problem already solved for the pi-subagents shebang.

### Part 2 — the agent's terminal (built 2026-08-07)

Recorded here because several part-1 decisions exist to serve it. The problem is precise: Pi's `bash` tool is `{command, timeout}`, spawns a fresh shell per call, is turn-blocking, truncates at 2 000 lines, and **cannot be extended** (built-in schemas strip extra parameters). So an agent that wants a dev server has exactly one move — `npm run dev &> /tmp/log &` — which is invisible in the UI, unkillable by the user, unattributed in the audit log, and read back through a file. Every property this product exists to provide, broken in one line, and the model reaches for it unprompted because it is the only thing that works. **Long-running commands currently escape the product's entire visibility and permission story**; that is the gap part 2 closes.

Locked: **three tools — `terminal_run` · `terminal_read` · `terminal_kill`** — rather than one tool with an action enum, so §10's tool-layer rules can distinguish them without a new gate branch. The parameter is named **`command`**, because `ruleMatches` reads `call.input.command` for a `layer:"command"` rule without checking which tool it came from — so every command-pattern rule the user already has gates agent terminal commands the day the tool ships, with no second policy to drift from `bash`. **Multiple commands per terminal, each individually gated**, treating every write as a candidate command line: a deliberate over-approximation, wrong only in the harmless direction, because a PTY write reaches whatever owns the tty and knowing whether you are at a prompt is unsolvable without shell integration. **One command line per call, newlines rejected** — otherwise `describeCommand` shows the user only the harmless first line of what they are approving. `terminal_write` (raw keystrokes) is deferred as the one thing that cannot be pattern-gated. `terminal_read` is in `SAFE_TOOLS` and capped (~200 lines) with a `waitMs`; the permission prompt shows the **factual** command, never the model's `intent`, per §13's MCP rule. An agent terminal is a **card in the transcript**, sibling to the sticky delegation card — not a tab, because a tab is a surface the user opened — pinned while running, capped and collapsed beyond two, with only the expanded card hosting a live emulator. **The user can type into it, ungated**, with agent writes held while the user is mid-line. All three tools must be **named explicitly** in `gatePlanCall` (an unrecognised tool falls to `floor-ask`, which prompts forever but never blocks). **No hibernation gating** — a PTY owned by main is not a child of the Pi process, so unlike `asyncRuns` there is nothing to coordinate. Every `terminal_run` is audited with its command. Ending a session with live terminals asks, two named outcomes (*Stop them* / *Keep them as terminals*), reusing §5's removal-confirm pattern.

**Decision (2026-08-07, part 2's open questions close):** eight items, each resolved against what part 1 actually built rather than in the abstract. (1) **A soft cap of three agent terminals per session**, enforced by `terminal_run` refusing and naming what is running — soft because the tool is the only way in, so a second enforcement point in main would guard a door nobody else can reach. (2) **`terminal_run` refuses to reuse a terminal whose `foreground()` is non-null**, naming the process that holds the tty; the agent otherwise chooses whether to reuse. This is the §2 hazard arriving through the parameter that was supposed to be safe — `npm test` sent into a terminal running `npm run dev` is keystrokes into Vite, not a command — and part 1 already built the detector (`terminals.ts:254`), which is the only reason "the agent chooses" is safe rather than a coin flip. (3) **No `cursor` on `terminal_read`**: `readText` reads the *rendered grid*, where scrollback trims from the top and `baseY` moves, so a cursor is a watermark that silently skips lines under exactly the firehose it was meant to help with — missing output while believing you have all of it is worse than a cap that says what it is. `lines` and `waitMs` are the whole surface, and `readText`'s existing default is already the specced ~200. (4) **`intent` is required** on `terminal_run` and `terminal_kill`, per the standing rule for bundled registered tools; the `subagent` demotion to optional intent is not copied, because a terminal that starts is a card in someone's transcript and must carry a headline saying why. (5) **Open terminals ride §9's open-files context seam *and* its single global toggle**, disclosed in that setting's description — one setting, one answer, and the disclosure is load-bearing: with it off an agent starts a dev server and loses track of it after a compaction. (6) **The stack cap of two is terminal-only**, not shared with delegation cards, which are uncapped today and outside this feature's diff; worst case is two terminal rows plus whatever delegations are live. (7) **The interleave rule is an approximation and is named as one** — nothing in the app can see the user's input line (part 1's own `foreground()` comment records that knowing you are at a prompt is unsolvable without shell integration, which this section puts out of scope), so main holds the agent's write when the user has typed since their last `\r`/`\n`/`^C`/`^U` and releases on a ~1.5 s idle debounce, telling the agent it was queued. Shell integration is the upgrade path. (8) **Disabling the grouped built-in needs no promotion path**: `HV_BUILTINS` resolves at spawn and `hv:builtins-set` respawns nothing, so the toggle cannot take tools from a running session; on a later unrelated respawn (MCP live-reload, hibernation restore) **the card goes and the PTY stays**, since an agent terminal already *is* an ordinary workspace terminal in main — still listed, still openable as a tab, with no mechanism to build. Plan mode's three placements are likewise spelled rather than implied: `terminal_run` in `BLOCKED_PLAN_TOOLS`, and **both `terminal_read` and `terminal_kill` in `PLAN_PASS_TOOLS`** — `floor-ask` clamps `allow` to `ask`, so a planning agent polling a log would raise a modal on every poll, contradicting the `SAFE_TOOLS` decision that exists to prevent exactly that; `terminal_kill` removes power rather than exercising it.

**Decision (2026-08-30, UX-feedback round) — agent terminals join the avatar row, and the two-card cap becomes moot (amends item (6) above):** §12's decision of the same date collapses the resting state of every background run to a circle-with-glyph in one shared horizontal row, and an agent terminal is one of those runs — same row, terminal glyph instead of the robot, hover for title/intent/elapsed and STOP, click for today's card. Item (6)'s reasoning is retired rather than contradicted: it capped the terminal stack at two *because* a shared cap would have changed how delegation cards behave, and the avatar row is that shared treatment, arrived at deliberately. The cap and its "n running · titles" summary strip therefore go — a row of circles is already the summary the strip was standing in for, and it does not stop being legible at three. Two behaviours are unchanged because they are terminal-specific and load-bearing: only the **expanded** card ever hosts a live emulator (one at a time, so exactly one is ever mounted), and the collapsed cheap text tail moves into the hover readout rather than disappearing.

**Decision (2026-08-07, `bash` is steered away from `&`, and only while there is somewhere to steer it):** once terminals exist, `npm run dev &` in a `bash` call is the model reaching for the broken thing with the working thing beside it. Both halves ship — a **system-prompt line** pointing long-running commands at `terminal_run`, and **detection in the bridge's `tool_call` handler**, which already blocks-with-a-reason for `isWaitTool`, so this is one more branch on an existing seam. It matches a genuine **trailing `&` background operator and never `&&`**, blocks, and names `terminal_run` in the reason; blocking rather than nudging is the right severity precisely because the alternative is available and better. The constraint that makes it safe: **the detection fires only while the Terminal group is enabled**, because with the group off there is no `terminal_run` to redirect to and blocking `&` would turn a context-saving setting into a capability removal it never advertised.

**Decision (2026-08-07, RETRACTED 2026-08-07 — a tool group does *not* measurably dilute tool choice):** this section briefly claimed that registering three terminal tools made the model stop calling `bash` (3/5 → 0/5 on an unrelated `touch` prompt), and drew a product conclusion from it — that the grouped toggle buys back "a more decisive agent". **Both the finding and the conclusion are withdrawn.** The original comparison was five trials per configuration, run sequentially in differing app states; 3/5 vs 0/5 is **p = 0.167** by a two-sided Fisher exact test, never significant, and its tidy monotone shape was noise sorted by the expected story. Two interleaved re-runs settle it: with a probe extension varying only the tool list (n=8 per cell), 0 tools gave 1/8 `bash` and the three real tools gave **7/8** — the sole significant comparison (p = 0.010), running the **opposite** way; and in the shipped configuration with only `builtins.terminal` toggled (n=12 per arm), off 4/12 vs on 6/12 (p = 0.68, no detectable effect). The steer line's bash-affirming rewrite **stays**, on prose grounds rather than measured ones: a description that names `bash` only as the wrong answer is bad writing whatever it does to the model. The grouped toggle also stays, on its original §13 grounds — context cost and the fact that the three tools are not independently useful — but **not** on a decisiveness claim it never earned. The live-suite prompt changes stay too, as a straightforward flakiness fix: at baseline the model calls `bash` on roughly half of attempts, so `askUntil`'s three tries failed ~12% of the time, and the explicit wording measured 5/5. Retraction, tables and method: `docs/validation/d1.md`.

**Out of scope:** an "Open in Terminal" escape hatch launching Terminal.app (named as the honest baseline and rejected — it fails the goal of staying *in* the app, and part 2 needs the embedded terminal anyway, so it would be throwaway work) · a custom-colour editor · ligatures · shell integration (OSC 133 prompt markers) · per-workspace terminal settings · subagents getting the terminal tools (v1 answer: no).

## 27. Voice input

A microphone button in the composer that turns speech into text, transcribed **entirely on-device** by a model the user downloads once — no cloud, no API key, no audio ever written to disk. Specced in full on the Notion page `3b5d33dfffca80b9b1dcf5525a2dabe2` (engine benchmarks measured on an M5, the model manifest, the 25-language accuracy table); the decisions are here. **Voice *input* only:** no text-to-speech, no wake word, no spoken commands, nothing outside the composer. "Voice" in the settings nav means voice input.

**Decision (2026-08-07, this has to beat the dictation the OS already gives away, and the answer is §4):** macOS types into this composer today for free — fn-fn, no download, no native dependency, no signing work — so the feature owes an account of what it adds. Four things, and the first decides it. **It is macOS-only**, and §4's "Windows and Linux where possible" is taken here as a real commitment rather than an aspiration: a capability that exists on one platform of three is a Mac tip. **It cannot be pinned to a language** — OS dictation follows a system-wide setting, so a French speaker writing English prompts goes to System Settings and comes back, where ours is per-app and remembered. **It reports nothing**, and the level meter is the single control that separates "my microphone is dead" from "the model is slow". And **the privacy claim would be Apple's rather than ours**: macOS dictation is on-device only when the language pack happens to be installed. We neither block nor discourage it — it keeps working in the composer, and for a user it already satisfies that is the right answer.

**Decision (2026-08-07, the engine is CPU ONNX, and the fast path is deliberately refused):** `sherpa-onnx-node` running an int8 export of a 600M FastConformer/TDT model with `provider: 'cpu'`. Measured against three alternatives on identical audio, the Apple Neural Engine path is four times faster and thirteen times lighter — 91 ms and 135 MB against 308 ms and 1.83 GB — and is still rejected, because **35× real-time is already imperceptible** (nobody feels 300 ms against 90 ms at the end of a gesture they just finished), because it costs a Swift helper, Xcode at build time and a second notarization surface on every release, and because it is macOS-arm64 only where a CPU engine is one engine for all four targets. One finding is worth carrying because it inverts the obvious assumption: ONNX Runtime's **CoreML execution provider is 3–4× slower than its own CPU provider** for this model — dynamic sequence lengths force graph partitioning — so `provider` is pinned to `cpu` by a contract test precisely so nobody "optimises" it later. What we accept: **1.83 GB resident while loaded**, mitigated by running inference in a `utilityProcess` (the same isolation argument as `pi/spawn.ts` — a native OOM must not take the app down, and a big working set must be reclaimable by killing a PID) that loads lazily and unloads after five idle minutes.

**Decision (2026-08-07, the weights are downloaded, pinned by revision SHA and verified per file):** 671 MB over four files, fetched on first use from an ungated Hugging Face repository at an **exact revision, never `resolve/main`**, each file checked against a committed SHA-256 before it is ever handed to ONNX Runtime's native parser. `main` is a mutable pointer on a third party's repo and 671 MB of unverified bytes landing in `userData` is a supply-chain surface, not a theoretical one — the same instinct as the pinned, vendored Pi runtime, applied to weights. Downloads are resumable, land in a `.part` file renamed only after the digest verifies, and run **in main rather than the renderer**, which sidesteps the `default-src 'self'` CSP rather than weakening it. This is the one piece of genuinely new infrastructure: the app has no byte-level progress plumbing today.

**Decision (2026-08-07, three permission layers must pass and one of them is self-inflicted):** Chromium auto-approves `getUserMedia` because no permission handler is installed, so that layer needs nothing. The plist and entitlement changes do, and `entitlementsInherit` is not optional — Chromium captures audio in a **helper** process signed from the inherit plist, so an entitlement present only at app level means macOS never shows the TCC prompt at all while the configuration looks correct. The third is ours: **`build/afterPack.mjs` runs `codesign --force --deep --sign -` over the whole bundle last**, after electron-builder has applied the entitlements, and `codesign` writes only the entitlements it is handed — so without `--entitlements` that repair step strips the audio entitlement from every binary it touches, including the helper. The two config changes are necessary and, alone, useless. Verification is a command against the built helper, not a screenshot. Separately, **main checks `getMediaAccessStatus('microphone')` before capture is ever attempted**, because Chromium on macOS resolves `getUserMedia` with a live track producing **nothing but zeros** when TCC has not granted access — for dictation the worst possible failure, since it is not an error the user can act on but a silent empty transcript.

**Decision (2026-08-07, the dictation gesture is fixed rather than rebindable):** hold the right-hand modifier — right ⌘ on macOS, right Ctrl on Windows and Linux — with a tap starting a toggled recording and a second tap ending it. It does **not** join `SHORTCUT_ACTIONS`, because the registry cannot express it for three independent reasons: `eventToBinding` returns null when the key *is* a modifier and null again when no modifier accompanies it, so a modifier-only binding is unrepresentable by construction; the canonical form carries no left/right distinction (`e.key` is `"Meta"` for both Commands); and the format is CodeMirror's *because one dispatch site is a CodeMirror keymap*, which has no representation for press-and-hold. It joins **`FIXED_SHORTCUTS`** instead — the list that already exists for composer semantics that are not bindings, kept so the Shortcuts page stays a complete map — and rebinding is deferred with the registry work it would need. Right ⌘ does not travel: on Windows `MetaRight` raises the Start menu and is not reliably suppressible from a renderer. One guard makes a modifier usable as a trigger: **if any other key goes down while it is held, the gesture is abandoned**, so ⌘+S never starts a recording.

**Decision (2026-08-07, superseded 2026-08-13 — the transcript lands at the CARET, and is never sent):** it was originally appended at the end of the composer, blank-line separated, to match what the editor's *Send to chat* already did. That was a taste call and it was the wrong one: dictation's actual use is describing intent *mid-sentence* and then typing the file path, and appending put the words somewhere the user was not looking. **It now inserts at the caret, padded with single spaces and never a newline** — replacing the selection if there is one, and leaving the caret immediately after the inserted text so typing continues naturally. Both paths still share **one** helper (`insertAtComposer`), so they cannot drift; the accepted cost is that a multi-line selection sent from the editor now splices at the caret rather than landing as its own block, and the fix if that proves wrong is one conditional in that single function. The padding never doubles a space the inserted text already carries. Auto-send is refused for two product-specific reasons rather than general caution: a mis-transcription in an agent prompt is expensive because the agent acts on it, and people mix modes inside one prompt, dictating the description and typing the file path. **Escape cancels, last in the composer's Escape chain** — search, the slash-command menu and the `@`-mention dropdown each get it first, so with a dropdown open the first Escape closes the dropdown and a second cancels the recording. Two guards stand between silence and a fabricated prompt and both run in the renderer before any IPC: clips under 300 ms are discarded, and audio whose peak RMS never clears the noise floor returns empty **without invoking the model at all**. Four lines of code, and they are the difference between "nothing happened" and "the agent received a sentence I never said".

**Decision (2026-08-13, the recording indicator is an overlay, and the chip is optional):** the level meter moved out of the composer chip into a **bottom-centre, viewport-fixed overlay** — a translucent pill with a mic glyph and a glow whose radius tracks the same RMS the worklet already posts at ~30 Hz. Two complaints drove it and both were fair: at chip size the meter was hard to read, and it taxed the width of the control row permanently for a state that is transient. The chip keeps a red tint so it remains the click target that stops a recording; the overlay is also clickable and names its own escape (*"Click to stop · Esc to cancel"*). The glow staying level-driven is not decoration — it is the only thing that distinguishes a dead microphone from a slow model, which is this category's largest reported support burden. One consequence had to be made real rather than left to luck: `ChatView` is mounted per chat tab and two composers can be visible at once, so **a module-level microphone token now enforces one recording app-wide** — previously nothing stopped two panes opening two capture streams, which the overlay would have made visible by stacking.

**Decision (2026-08-13, technical readiness and functional activation are separate settings):** a "Ready" status pill that doubles as an off switch is an overloaded control, and *disable voice* must never read as *delete 671 MB*. So the Voice page gains a **Voice input** section above the model: **Enable voice input** (off ⇒ the gesture is inert, no activation modal, and the microphone is never opened — the downloaded weights are kept) and **Show mic in the chat bar** (off ⇒ the chip is gone but the gesture and the overlay still work, which is why it is a second setting rather than a mode of the first). The **Speech model** section stays purely informational: status plus its own Remove. Both settings are **global**, like the rest of §27, and are **owned by `App` and passed down** rather than fetched inside the dictation hook — a hook-local fetch resolves once at mount, so a toggle would never reach an already-open composer. That is the same ownership `termSettings` uses, and it is what makes the toggles apply without a reload.

**Decision (2026-08-07, an explicit language picker, never automatic detection):** 25 European languages, defaulting to the system locale and saying so plainly when the locale is not among them rather than guessing. Auto-detection is rejected because **out-of-set input fails catastrophically rather than gracefully** — measured character error rates of 171 for Korean, 159 for Japanese, 124 for Chinese, which is not a degraded transcript but confident, fluent-looking garbage handed to an agent that acts on it. Accuracy is uneven *within* the set too (Italian 3.0% against Slovenian 24.0%), so the weaker half carries a quiet "lower accuracy" note; discovering that one bad prompt at a time is worse than being told. Settings are **global only**, like §26's, and the microphone processing toggles (echo cancellation, noise suppression, gain control) default on with an off switch, because people on real audio interfaces reliably want them off.

**Decision (2026-08-07, privacy is enforced in code, not promised in copy):** audio is **never written to disk** — a renderer ring buffer and one transferred `Int16Array`, both collected after transcription — **never leaves the machine** (the only network call the feature ever makes is the one-time model download), and **transcripts never reach the EventLog, the audit log or any analytics surface**. A dictated prompt is recorded exactly as a typed prompt is, and there is no separate voice trail. No usage telemetry. For a product positioned on trust this is a feature rather than a disclaimer, so it appears on the Voice page in one sentence, not only in the spec. The model is CC-BY-4.0 and **never named in the dictation flow** — the button, the activation modal and the progress UI say "voice model"; attribution lives in a collapsed licenses block at the bottom of the Voice page and in a repo `NOTICE`.

**Out of scope:** voice output of any kind · a wake word or spoken commands · system-wide dictation · live streaming transcription (the model is an offline transducer with no native streaming path; a sliding window would flicker and rewrite mid-sentence to save nothing when the whole utterance transcribes in 300 ms) · voice activity detection, which the explicit endpoints make unnecessary · automatic language detection · punctuation commands ("new line", "comma") · per-workspace voice settings · caret-aware insertion · a rebindable dictation key · the ANE engine, whose return is gated on the resident-memory measurement rather than on merit, and which would also open Apple's `SpeechTranscriber` as a zero-download tier covering the CJK languages this model cannot handle.

## 28. Embedded browser

An embedded browser pane the agent can drive through registered tools — open a page, read it, screenshot it, click it, watch its console and network traffic — with every risky capability behind the existing permission gate. Feasibility notes and the full locked spec live on the Notion page `3a5d33dfffca814daa10fc3905639867`; the decisions are here. The automation layer rides Electron's own `webContents` (navigation, `capturePage`, `executeJavaScript`, `sendInputEvent`, the `console-message` stream) — no Playwright, no CDP port, no attach step. Discharges §13 round 6's "later builds add the embedded browser … to the same block". Compounds with §26 for the demo loop: agent runs `npm run dev` in a terminal, opens the browser on `localhost:5173`, reads the console, fixes the bug it sees.

**Decision (2026-08-14, embedding):** **`WebContentsView`**, chosen future-proof over the `<webview>` tag. Accepted cost: it composites *over* the renderer DOM, so main owns its bounds — sidebar collapse, divider drags, tab switches and window resizes all need a bounds-sync IPC, and the guest is hidden while any modal is up. **The permission modal must always win** — that z-order rule is the non-negotiable in the bounds-sync work.

**Decision (2026-08-14, tool surface):** **ten separate tools, no action enum** — §26's locked reasoning applied again, so §10's tool-layer rules can distinguish them without a new gate branch: `browser_open` · `browser_navigate` · `browser_screenshot` · `browser_get_text` · `browser_read_console` · `browser_read_network` · `browser_click` · `browser_type` · `browser_evaluate` · `browser_close`. All thin shells over blocking `hv.browser-*` envelopes; main owns panes, claims and every rule (the §26 shape). `browser_evaluate` gets its **own, stricter rule** — arbitrary JS inside an allowed page is the capability that turns "the page can reach X" into "the agent can exfiltrate through X". `browser_read_network` is fed from the egress observer's ring buffer (`webRequest` `onCompleted`/`onErrorOccurred`), **not** `webContents.debugger` — raw CDP is the recorded upgrade path for response bodies, deferred because attaching the debugger shows Chromium's warning banner and conflicts with DevTools. **Text-first reading:** `browser_get_text` (rendered text / a11y tree) is the primary primitive; `browser_screenshot` attaches its PNG to the model only when the session's model is vision-capable (`supportsVision`), otherwise it still renders for the user and the result says so and points at `get_text`.

**Decision (2026-08-14, egress — the headline control):** a **two-tier network gate** on the guest's session partition via `webRequest.onBeforeRequest` — the enforcement point JS inside the page cannot bypass. **Top-level navigations** are gated through the rules engine as virtual rule names **`browser:<host>`** (the `mcp:<server>_<tool>` pattern applied again): `localhost`/`127.0.0.1` silently allowed by default, everything else prompts with the normal Allow / Allow for session / Deny and pattern rules. **Subresources of an allowed page** are silently allowed but every request is logged to the EventLog and the ring buffer. Accepted trade-off, recorded honestly: in-page `fetch` can reach any domain the page itself can, so the headline is "the agent's browser only *navigates* where you allow", not "no byte leaves without approval" — the stricter `evaluate` rule is the companion mitigation, and a subresource-blocking tier stays open as later hardening. **User-initiated navigation bypasses the prompt** (a typed URL or clicked link is consent, logged like everything else); agent-initiated navigation always gates — mirrors §26, where the user's own terminal was never gated. The `browser_navigate` permission prompt summarizes as **the URL**, never the model's `intent` (same `summarize()` special-case as `bash`/`terminal_run`).

**Decision (2026-08-14, sandbox + partition):** all mandatory: `sandbox: true` + `contextIsolation: true`, no `nodeIntegration`, **no guest preload at all** (the agent drives from main, outside the sandbox), separate session partition, `setPermissionRequestHandler` denies camera/mic/geolocation by default, `will-navigate` blocks `file://`, `setWindowOpenHandler` blocks popup escapes. The partition is **persistent** (`persist:hv-browser`) so authenticated dev flows survive restarts — caution recorded: a logged-in partition raises the value of exfiltration; the egress gate and the `evaluate` rule are the mitigations, and a **Clear browsing data** action ships on the All Tools browser entry so the persistence is reversible. Page-derived text is **untrusted input**, labeled as such in tool results — prompt injection has no mechanical fix anywhere; the mitigation is the product thesis itself (consequential actions hit the gate regardless of why the agent wants them).

**Decision (2026-08-14, plan mode):** reads pass (`screenshot`, `get_text`, `read_console`, `read_network`, and `close` — removing power, like `terminal_kill`); `open`/`navigate` **floor-ask** (navigating to read documentation is legitimate planning, so it prompts every time rather than being blocked); `click`/`type`/`evaluate` are **blocked** (named in `BLOCKED_PLAN_TOOLS`).

**Decision (2026-08-14, cap + placement + UX):** **one agent browser per session, reuse-by-navigate** (a full Chromium renderer is heavier than a PTY; terminals cap at 3). Opening never covers the session: split the workspace horizontally if no split exists; if one already exists, the browser joins the other pane's tab strip (the layout supports exactly one 2-way split). New tab kind `:browser:` — excluded from `allFiles` in the same commit that adds it, like `:term:`. Top bar: back, forward, URL bar, refresh, plus the element-picker toggle. One grouped **Browser** entry on the All Tools page, enabled by default (one `HV_BUILTINS` key unregistering all ten tools). Load failures, crashed renderers and blocked navigations render as states in the pane, never silent blanks.

**Decision (Feedback round 1, 2026-08-15) — a human can open a browser, and ⌘B is the key:** the browser shipped agent-only, so there was no way to open one yourself. **⌘B** now opens a blank pane in the focused pane with the URL bar focused, alongside a **New browser** row in the pane `+` menu, and it is an ordinary editable binding on the shortcuts page like ⌘N and ⌘T. ⌘B was `toggleSidebar` (the VS Code convention) and bindings are unique, so **the sidebar moves to ⌘\** — a swap, not an addition. Consequence recorded so nobody "fixes" it: **human-opened panes are UNCAPPED**; `MAX_AGENT_BROWSERS = 1` governs only what the agent may create, exactly as §26 caps agent terminals at 3 while the human's are unlimited. And because a pane dies with the app, a restored `:browser:` tab whose pane is gone is **pruned on layout restore** (`AliveSubjects`) rather than shown as a ghost.

**Decision (Feedback round 1, 2026-08-15) — the agent ADOPTS the browser you opened:** asking about the page you are looking at should not produce a second tab beside it. A session with no browser of its own takes over the most recently *visible* unclaimed pane in the same workspace before creating one; a pane another session already claimed is never stolen. Ending a session still only releases the claim, so an adopted pane stays as the human's.

**Correction (Feedback round 1, 2026-08-15) — "the modal always wins" was implemented as a class check, and 31 of 35 floating surfaces did not carry it:** a `WebContentsView` composites over the whole renderer, so `BrowserTab` hid it whenever `.hv-overlay` matched — a class that exists on the four Radix modals and nothing else. Every dropdown, the `@file` autocomplete, the file drawer, ~20 hand-rolled confirms and the pane divider were therefore drawn *under* the page and swallowed their own clicks; it surfaced as **"none of this menu is clickable"**. Marking the other 31 was rejected: it drifts the moment someone adds the 36th, and the menu that actually broke shares neither the class nor the styling nor the dismissal idiom of the others, so no selector would have found it. The rule is now **geometric** — a 3×3 hit test inside the pane's own rect, hiding whenever the topmost element at any sample is not the pane. It needs nothing from the other components, covers ones that do not exist yet, and hides only when the overlap is real. The view additionally **insets itself from every pane divider**, which is what makes the drag strip (widened 6px → 10px) grabbable beside a browser. The three pane top bars (chat, editor, browser) now share `h-11 px-3` so they line up with each other and with the 44px tab strip.

**Decision (Feedback round 1, 2026-08-15) — the URL bar picks the scheme, and a failure offers the fix:** typing `localhost:3000` was prefixed to `https://` and died on a raw `ERR_SSL_PROTOCOL_ERROR` behind a "Try again" button that retried the identical URL. A scheme-less **local** address now resolves to `http://` (a dev server is the case this feature exists for) and everything else to `https://`; a scheme HappyVibe does not open (`file:`, `about:`, `chrome:`) is **named** rather than silently prefixed into nonsense. A failed load reads as a sentence with the raw code demoted to detail, and where the code says the site answered without TLS the button becomes **"Try http:// instead"** and performs it. The mapping is built on **measured** codes, not guessed ones (`-107` TLS mismatch, `-102` refused, `-105` unresolvable; `-20` is the egress gate's own cancel and must never paint over the blocked state).

**Decision (Feedback round 1, 2026-08-15) — a page comment goes to the session that OWNS the pane:** asked directly: how does a comment know which chat to land in? It did not — it used whichever chat was last clicked, which is usually the agent driving the page and never guaranteed to be. The rule is now **owner first**: the session that opened *or adopted* the pane (the renderer learns it from the `opened` notify, which fires for an adoption too), falling back to the selected chat, which is all a ⌘B pane can have since nobody owns it. Filing into a composer that is off screen is the same as losing it, so the receiving chat is brought forward. And when there is no chat at all — a ⌘B browser in a workspace where none is open — the popup **says so and keeps what was typed**, where it previously dropped the comment silently with no feedback at all.

**Decision (Feedback round 1, 2026-08-15) — a commented element reads as a PICTURE in the chat, not as markup:** the message carried the selector and the full outerHTML as visible text, so the user's own sentence ("It should have a glowy effect as well.") sat on top of fifteen lines of machinery — including the selector §28 had just stopped showing them elsewhere, and a ```` ```html ```` fence rendered literally because user bubbles are plain text, not markdown. One string was serving two audiences. It now serves them separately: the element is **cropped from the still already captured at pick time** and attached as an ordinary image, so the bubble is the sentence plus a picture of the thing (zoomable, and legible to a vision model); the selector and markup move into a `<page-element>` block, which `stripInjectedBlocks` cuts from the bubble exactly as it already cuts `@file` context. The model reads everything; the person who pointed at the button reads their own words.

**Decision (Feedback round 1, 2026-08-15) — the comment popup pins to the element:** the picker's centred dialog with Cancel / Add-to-composer buttons becomes a **small pill next to the element itself** — its label, one text field, and the composer's paper-plane. Enter sends, Escape cancels, a click outside cancels. Because a popup over the live page cannot be seen (no z-index), main captures the page **while it is still visible** and the pill floats over that still with the element re-outlined, so the user keeps looking at what they clicked. The Comment control in the top bar is now an **icon**. One consequence had to be fixed with it: a page-ref alone could not be sent (the composer required typed text), which would have made the paper-plane hand over a composer that then refused.

**Decision (2026-08-14, element picker — ships in v1):** a selection mode where hovering highlights the component under the cursor with a dynamic border and clicking opens a popup for a comment sent to chat. Payload is **trimmed outerHTML + a CSS selector path**, shown user-friendly as a chip in the composer beside the comment; comments **stack** in the composer (the existing attachment-stacking pattern) and the user decides when to send.

**Decision (Feedback round 20, 2026-09-04) — the `browser:<host>` rule is shared with §32's web tools, and its label becomes "Web":** `web_fetch` / `web_map` / `web_crawl` gate under the same virtual rule, so one grant covers both surfaces, and the `VIRTUAL_RULE` kind label reads **Web** wherever a rule name is rendered as a HEADLINE — the permission prompt, and any card whose tool is the rule itself. The Permissions page and the audit log keep the verbatim `browser:<host>` on purpose: the first is a rule editor showing the pattern you would type, the second is a record. Two further consequences are recorded so neither reads as a bug. (1) **The pane's own Allow button stays per-pane:** a blocked page's Allow clears the host in that pane's egress state only (`allowBlocked` → `EgressState.approveHost`); the bridge never learns of it, so a later `web_fetch` of that host still asks — exactly as a second pane does today. "Allow for session" in the prompt is the shared grant, and the How-it-works copy says so. (2) **Plan mode differs on purpose:** `browser_navigate` keeps its floor-ask (a persistent, possibly logged-in Chromium where a navigation can act) while the four web tools pass (headless, no cookies, no side effects — and the host gate still runs inside plan mode).

## 29. Git integration

The review + version-control layer: HappyVibe shows what the agent *does* (tool cards, context panel, audit log) but nothing about what it *left behind* on disk — §9's rewind answers "undo that prompt", nothing answers "what has changed in this project since I started", and nothing lets the user keep a version or push one. This is the visibility differentiator applied to the filesystem instead of the conversation. Full spec on the Notion page `3b1d33dfffca807ca1cad8b48c86b7a4` (round run 2026-08-16); the decisions are here. Two standing rules hold throughout: **git is a feature, never a runtime dependency** (§3's standalone promise — nothing else in the app changes when git is missing, and §9's snapshot-based rewind works in every outcome below), and **GitHub stays out of V1** (§5) — *Sync* uses whatever credentials git already has and adds no auth UI of ours.

**Decision (2026-08-16, scope and vocabulary):** a **full-ish client** — branch / commit / push / pull / stash, no worktrees — kept beginner-safe by **one panel, two altitudes, one vocabulary**: the top of the panel speaks a closed human verb set (**Save a version · Sync · Undo**), everything below it is real git named in git's own words (staged, stash, amend, merge-base), and no third vocabulary is ever invented. Every action shows the command it ran, in mono — the tool cards' honesty rule; this is a teaching surface, not only a productivity one. The panel's actions are **human-only**: there is no `git_commit` tool, the same security invariant as plan mode (§23) and rewind (§9). Risk accepted in the round, with the guard named: the thing to watch in review is any change that lets a git word float up into the top altitude.

**Decision (2026-08-16, where it lives; amended by §7 round 13 the same day):** Changes is **its own panel, not a tab in the file drawer** — it and Files sit behind a thin **right icon rail**, one open at a time, each with its own remembered width (§7 round 13 carries the reasoning and the geometry). The rail's **branch icon is the one entry point**, and it carries the **change-count badge** — a property of the working tree, deliberately not of any session (several sessions can act on the same files; a turn-end chat card was rejected for attributing the tree's state to one of them) and deliberately not of the files icon either. **Review is user-initiated, always**: the badge is passive awareness and opens nothing. The badge speaks the app's existing colour language, measured in changed lines (one 800-line file outweighs ten one-liners): **green below ~50 changed lines, amber above, no red tier** — red means "broken" everywhere else in the app, and an uncommitted pile is never broken. The colour *is* the commit nudge. The branch button is **absent, not greyed, when git is not installed** (§5a) — but it is **present on a folder that is not a repository** (§5b), because that panel is where *Start tracking* lives and hiding the icon would make the on-ramp unreachable. The **sidebar** workspace row gains a second line — `⎇ main · 12 changes` — clicking opens the Changes panel; **absent, not greyed, when the folder is not a repo**. The branch name is cheap and shown for every workspace, kept fresh by a tiny non-recursive watch on `.git` (`HEAD` + `index` — necessary because the file-tree watcher deliberately filters `.git`); the change count costs a `git status`, so it is live for the **active workspace only**.

**Decision (2026-08-16, diffs open in the file tab, never a new tab type):** the editor's rendered/raw pill grows a third state — **Source / Changes / Preview** — with Changes present only when the file differs from the baseline. Deliberately not a `:diff:` tab type: `allFiles` feeds the watcher, the mounted-tab list *and* §9's open-files context block, so a fourth tab kind would need excluding in all three (§21's standing invariant). Deleted files have no tab, so their diff expands inline in the panel row. A mode never vanishes under the user: undoing the **last** hunk while standing in Changes snaps the pill to Source with a toast ("All changes undone") rather than letting the state you are in disappear.

**Decision (2026-08-16, the panel top to bottom):** branch bar (switcher, New branch, Fetch — sync state lives **on the action in the human verb**: the button reads **Sync (2)**, the ahead/behind figures demoted to its tooltip and the mono command line; Sync appears only when an upstream exists) · message box + contextual split button (changes present → **Save a version**, dropdown *Commit staged only* / *Amend last* / *Stash*; clean but unsynced → **Publish branch** / **Sync (n)**) · baseline selector (**Since your last save** = working tree vs HEAD, the default; **Against \<base branch\>** = merge-base with the detected default branch — git-only by decision, §9's per-prompt snapshots stay in the rewind dialog) · file list grouped by directory with per-file `+n −m`, status glyphs, hover actions (stage, open diff, undo file), untracked under their own heading and never swept into "undo" · **Stashes**, shown only when any exist — a count row expanding to *Restore* (`stash pop`) and *Delete* (confirmed), because a stash with no visible way back is data loss with extra steps for exactly this audience · **History**, collapsed by default — where "full-ish" earns its keep at zero cost to the beginner · a warm empty state ("All saved ✨") with a small celebration beat on a repo's first-ever commit. **Staging stays, but optional**: *Save a version* commits everything unless something is explicitly staged, then commits the staged set and says so (`Save 3 of 12`). "Everything" includes new files — `git add -A` scoped to the workspace, never `commit -a`, which would save nothing at the exact moment the on-ramp introduces the feature. And it **refuses to sweep junk silently**: when the set being saved contains a known-junk directory (the same derivation list init uses), the save pauses and offers to add those lines to `.gitignore` first — declining still saves everything, because it is their repo.

**Decision (2026-08-16, round 14 — the baseline selector is REMOVED; the panel is always "since your last save"):** the two-option dropdown above the file list (*Since your last save* / *Against \<base branch\>*) shipped and is now deleted, amending the panel order above in one clause. It was never the control it looked like: the file list and the `n files · +a −b` count beside it come from `git status`, which has **no baseline and is always working-tree-vs-HEAD**, so switching to *Against \<base\>* changed only the diff of a file you expanded. That made it wrong exactly where it mattered — a file also touched by an earlier commit on the branch expanded to more than the count next to it claimed, and files whose only changes were already committed never joined the list at all. Making the list follow the baseline was the other option and was rejected: **"Open a pull request" already answers "what does this branch contain", and answers it with the forge's own diff** rather than a second one of ours. The row keeps its counts and now states the baseline as a label. §5d's clause "*Against base branch* is absent" on an unborn HEAD is therefore moot. Main **keeps** `gitDiff(…, "base")` and `defaultBranch()` — that pair is what drafts the pull request (§7), and the branch list needs the second one to know which branch must not offer a delete control.

**Decision (2026-08-16, round 14 — a branch can be deleted from the branch list, and git's own refusal is the guard):** each row in the branch switcher gains a **trash icon on hover**, confirmed before it runs. It is **shown on every branch, disabled with the reason** on the two that cannot be deleted: the one you are standing on (git refuses outright) and the **default branch**, resolved by `defaultBranch()` rather than assumed to be called `main`. Hiding it was the first version and was reported within the hour as the feature missing — on a two-branch repo with the user standing on the feature branch, *both* rows qualified and the panel looked exactly like a build without the control. This is **not** a "don’t show what cannot work" case: that rule is about capabilities the app will never have, whereas standing on a branch is a state you leave by switching, and the tooltip says so. Implementation note that is easy to get wrong: `aria-disabled`, never `disabled` — a disabled control receives no pointer events, so its `title` never appears, and the reason is the entire point. Main runs `git branch -d` — **never `-D` first**: git's refusal on a branch holding commits no other branch has is a better check than any we could write, because it knows what is reachable from every ref. That refusal comes back as `unmerged:true` and raises a **second, sharper dialog** naming the loss, so force is opt-in per deletion rather than a flag on the first question. The remote branch is deliberately untouched — deleting `origin/x` is a push, i.e. a change to what everyone else sees, and this is presented as local tidying ("from this computer only"). **Not behind the idle gate**, consistent with the rule that the gate covers the WORKING TREE: deleting a ref cannot disturb a session working in the files, which is asserted rather than asserted-in-prose (`tests/git.test.ts` deletes a branch with uncommitted work present and checks the file survives).

**Decision (2026-08-16, "Write it for me"):** a button beside the message box fills it with an **editable draft** — it never commits and never fills silently. It runs as a one-shot `pi -p --no-session --no-tools --no-extensions` call on a cheap flash model (the `titles.ts` pattern — third precedent after session titles and AGENTS.md drafts), never the live chat session, so no commit message ever enters a transcript or a context window; it also works with no session open at all. Handed the diff being committed (staged set if staging is in use) truncated to a token budget — past it, the file list + per-file stats + head of each hunk, so a 400-file commit still drafts honestly — plus the **last ~20 subject lines from `git log`** so the draft matches the repo's existing style (Conventional Commits in, Conventional Commits out). Failure is quiet: no provider, no key, or non-zero exit and the button is simply absent. The **tooltip names the approximate cost** — no synthetic ledger line; the ledger keeps meaning "what sessions cost" and all three one-shot callers stay outside it — and the model it runs on is chosen on the **"On your behalf"** page (§19, 2026-08-30), not on the button — this clause originally put a small dropdown on the button itself, and the setting behind it (`gitMessageModel`) was built end to end in main and never given a UI, which is what the page exists to fix. One place, shared with the pull-request draft below.

**Decision (2026-08-16, per-hunk undo — the inline accept/reject, post-hoc):** each hunk gets **Undo**, each file **Undo file** — completing the Save/Sync/Undo verb set (git's own *revert* means a commit reversing a commit, so avoiding the word dodges a real collision). Post-hoc: the agent's edit lands on disk as today, and undo reverse-applies the hunk — which also covers bash and MCP side effects, because the baseline is the filesystem rather than a tool call. Four rules: **never silent** (audited as a human action, toast naming file and hunk count); **stale-checked** (`git apply -R --check` first — a file changed under us refuses and is named, §9's discipline, with the check *being* the mechanism rather than a second one beside it); **confirmed, not narrated** — one confirm dialog naming file and hunks; an earlier draft auto-wrote a note into the composer and was rejected as intrusive. Accepted, named limitation (argued in the round): between the undo and the agent's next read of the file, the model may claim an edit exists that does not — it self-heals on contact because the agent re-reads before editing and a mismatched `oldText` forces a re-read anyway; if it bites, the confirm dialog grows an opt-in "mention this to the agent" checkbox, never an automatic message; **untracked files are deleted, not undone** — the control reads *Discard new file* and confirms. Holding writes before they hit disk is **deferred with the reason**: the agent re-reads files it just wrote, so withholding a write needs a shadow filesystem — its own project. Relation to §9: rewind already shipped; this adds *granularity* (per hunk instead of per turn), not rewind.

**Decision (2026-08-16, safety gates):** **one idle gate covers every verb that mutates the working tree** — switch, stash, pull, per-hunk undo, discard — blocked with the reason named while any session in the workspace is busy (sessions share one working tree; reuses the `isIdle` gate MCP live-reload already uses). Commit, push and fetch stay available while busy — they change history or the remote picture, never the files. **Pull is `--ff-only`**: a non-fast-forward pull says so and stops, never opening a merge (§29 ships no conflict UI, and a beginner mid-conflict is the worst state this panel could produce). **Switching branches with unsaved changes gets a first-class choice, not git's refusal** — the one deliberate exception to the show-git's-message rule below, because it is the most common beginner state arriving at the moment of most confusion: a dialog offers *Take changes with me* (plain `switch`, which succeeds when nothing conflicts), *Save a version first*, or *Stash them*; when even a plain `switch` would conflict, the take-with-me option is absent and the dialog says why.

**Decision (2026-08-16, the agent and git):** the agent already has git through bash; both changes live inside the permission layer we own. **Default rules ship with the app**, seeded **once** into `permission-rules.json` on first run — visible and deletable in the Permissions UI like any user rule (suggestions, not policy; no third built-in rule scope): *ask* on `git push*`, `git reset --hard*`, `git checkout -- *`, `git clean*`, `git rebase*`; *deny* on `git push --force*` (liftable). Their job is narrower than it sounds — `bash` is not safe-default, so every git command already asks; the rules exist for the day the user adds `git *` as an allow, when most-restrictive-wins keeps the destructive verbs asking through it. Recorded honestly: the engine matches the whole command string anchored, so `cd x && git push --force` or `git -C repo push -f` slip past the deny **and fall back to ask** — the deny is best-effort steering, never a security boundary. **Git tool cards say more of what happened** within what the command string can tell: branch names and commit messages are in the string; file lists are not, so the card links to the Changes panel rather than pretending. The panel refreshes when the turn ends.

**Decision (2026-08-16, when there is no git — five outcomes, each answered where the gap lives):** never sniff `.git` (a `.git` *file* is a valid submodule or linked worktree) — always ask git (`rev-parse --show-toplevel`), once per workspace, cached. **(a) No git binary** — the gap is on the machine: the Changes tab is **not there at all** and the sidebar branch line is absent ("don't show what cannot work"); the capability surfaces once, on the workspace settings page — *"Version control: git not found · Install"* — triggering the OS installer. **(b) git present, no repo** — the gap is in the project, so it belongs in the panel: *"This project isn't tracking versions yet · Start tracking"*. The button previews before it writes (the `git init` path and a starter `.gitignore` derived from what is actually in the folder, editable), does **not** commit (init leaves everything untracked so the user's own first *Save a version* is their first commit — the teaching moment), follows `init.defaultBranch` else `main`, and **refuses on `$HOME`, `/` and volume roots**. **(c) Workspace is a subdirectory of a repo** — everything is **scoped to the workspace subtree by pathspec** (status, diffs, undo and commit alike; a repo-wide view would offer to revert files every other part of the app refuses to touch), the branch bar names the real root, Start-tracking is not offered (it would nest a second repo), and branch switching / push — repo-wide by nature — stay available with the root named. **(d) Repo with no commits** — the first state after our own Start-tracking button: the baseline is the **empty-tree object**, asked from git rather than hard-coded (a SHA-256 repo still works); every file reads as an addition; *Against base branch* is absent. **(e) git refuses** (dubious ownership, index lock, detached HEAD, half-finished merge/rebase) — show **git's own message** plus the exact fixing command, copyable, and never run it (`safe.directory` is a global security setting); writes that cannot work are disabled with the reason named while the panel keeps showing everything it can still read.

**Decision (2026-08-16, worktrees — designed for, not built):** every git call takes an explicit **repo root** rather than assuming the workspace path, and panel state is keyed by that root — no user-visible difference today; it is the difference between later adding worktrees as one new root-resolver versus threading a path through every call site. Post-V1, and a workspace-model change rather than a git-panel one.

**Decision (2026-08-16, "Open a pull request" — amends the out-of-scope line below in ONE clause):** the panel gains an **Open a pull request** button beneath the save cluster, and it does **not** create anything. It opens the forge's own new-pull-request page **in the user's normal browser**, with the title and description already filled in; they press *Create* there. That is why it does not touch the fence it appears to: HappyVibe stores no token, shows no auth UI, and makes no API call, so §29's "*Sync* uses the credentials git already has" still holds and **§5/§6 keep GitHub out of V1 unchanged** — no account, no integration, just a link. PR *creation* and GitHub *auth* remain out of scope. Details that are load-bearing rather than incidental: the **external** browser is the only one that works, because §28's embedded pane runs on its own `persist:hv-browser` partition and the user is not signed in there; three forges are recognised by hostname (**github.com** `/compare/base...head?quick_pull=1&title=&body=`, **gitlab.com** `/-/merge_requests/new` with its bracketed params, **bitbucket.org** `/pull-requests/new`, which gets **no** description param because it documents none — inventing a key that silently does nothing is worse than omitting it), and an unrecognised or self-hosted host **hides the button** rather than opening a guess that 404s. The body is **capped at 4000 characters**, because GitHub answers `414 URI Too Long` past a limit it does not document. The button appears only when a PR is possible at all — a recognised forge, a branch that is not the default one, and an upstream — so on `main`, or before you publish, it is simply absent and the panel is already offering **Publish branch**. The title and description are **drafted by the same one-shot model path as "Write it for me"** (§2b: no session, no transcript, no context-window cost) from the branch's commits and its diff against the merge-base; **failure is quiet and falls back to the commit list**, so no provider costs nicer prose and nothing else. The eligibility check that decides whether the button exists deliberately runs **without** the model or a diff, or publishing a branch would cost a model call.

Out of scope: merge-conflict resolution UI, PR *creation* and GitHub auth (opening a prefilled PR *form* is in — see the decision above), interactive rebase, submodules, LFS, blame, worktrees.

## 30. Versioning and changelog

HappyVibe is a **curated Pi distribution** (§3), so *which build you have* is a product fact rather than an implementation detail — and until 2026-08-30 there was no way for anyone to know it: `package.json` still carried the electron-vite scaffold default `1.0.0` after 699 commits, there were no git tags, no `CHANGELOG.md`, and the only surface showing a version was the native macOS About panel. This section defines the number, the notes, and where the user reads them.

**Decision (2026-08-30) — one number, SemVer, and `0.x` until the public launch:** `package.json`'s `version` is the **single source of truth** — electron-builder derives `Info.plist` from it, the renderer receives it as a build-time constant, and the git tag is `v<version>`; nothing else stores a version number, because two of them is how they disagree. The positions are defined in **user** terms, not code terms: **PATCH** is fixes and polish, where nothing is new to learn and nothing already set up changes; **MINOR** is anything new the user can see or do — a page, a tool, a provider, a setting — and is the normal release; **MAJOR** is *you have to do something*: a setting is gone or now means something else, a stored format changed and will not roll back, or a permission default became less restrictive. The app ships **`0.x` until the public launch**, where the MAJOR class instead lands in a MINOR carrying a **Heads up** block at the top of its changelog entry — and **`1.0.0` is the launch**, not the completion of §6's V1 list, because the promise a `1.0` makes is to users who can find the product, not to a checklist. **CalVer was rejected**: date numbering cannot say *this one needs you to do something*, and this app has two real breakage axes (the `config.json` schema and permission defaults) plus an update ecosystem that expects semver. **A runtime pin bump is not a version axis of its own** — a `pi-coding-agent` / `pi-subagents` / `pi-mcp-adapter` bump is MINOR when it changes something the user sees (new builtin agents, a new provider, a new tool) and PATCH when it does not — but **every release names the pins**, because §3's promise is precisely that the Pi inside is pinned and tested. The convention is self-enforcing through one invariant: **the top released entry in `CHANGELOG.md` must equal `package.json`'s version**, asserted by a key-free test, so a version cannot ship with no notes.

**Decision (2026-08-30) — the changelog is written for the person using the app, not for the person who changed it:** `CHANGELOG.md` lives at the repo root in [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format and is **written by hand at release time**, at the functional level — what the user can now *do* — with technical detail only where the user acts on it. Seven rules make that repeatable: (1) an entry says what you can now do, never what changed in the code (`feat(agents): per-agent on/off, with what each costs the context every turn` becomes *Turn individual sub-agents on and off, and see what each one costs your context every turn*); (2) a surface is named the way the app itself names it, honouring §20's locked vocabulary — **Prompts** never "prompt templates", **cost** never "budget", **Save a version** never "commit" — with the one qualification the first entry surfaced: where the app uses a git word as its own **label**, the label wins (the *On your behalf* tasks are literally titled **Commit message** and **Pull request description**), because the rule exists so the user can find the thing and renaming a page's own title hides it; (3) one line per change a user would notice and nothing else, so refactors, tests, docs and internal fixes are simply absent and a MINOR release is 5–15 bullets — past ~20 you are transcribing the commit log; (4) anything touching something the user already set up goes in a **Heads up** block at the top of the entry, never buried in *Changed*; (5) file paths, commit scopes, PR numbers and component names never appear, while the runtime pins line always does; (6) headings come from Added · Changed · Fixed · Removed, only the ones needed, plus **Heads up**; (7) no superlatives and no marketing — the changelog matches the app's own plainspoken copy. **Generating it from the commit log was rejected**, even though the commits are strict conventional-commits and would feed a generator today: at this repo's cadence a MINOR would arrive as ~100 scoped developer bullets, which is the wrong altitude for §1's wedge audience and the same two-altitudes call §29 already makes when the Changes panel says *Save a version* while the audit log says `bypass`. A release-PR bot was rejected for the same reason plus one more — it puts release mechanics behind a CI nobody watches. The mechanical half of the rule is testable and tested: no conventional-commit prose may appear in the file. The procedure has ONE home — the **`changelog` skill** (`.claude/skills/changelog/SKILL.md`), which owns the triage that compresses hundreds of commits into a dozen bullets (types that are invisible by construction; fixes that only count when the broken thing was in a release the user already has; one bullet per capability rather than per commit), the seven rules, and a `digest`/`check` script. The `/release` command calls it rather than restating it, because two copies of a rule is how a rule drifts. It runs at **release time only**: a per-PR cadence would keep the entry fresher but bolts a step onto every feature, and one moment of writing was preferred — the cost, named rather than hidden, is reconstructing intent from commit subjects weeks later, which is why a pin bump now records its user-visible effect in its commit body.

**Decision (2026-08-30) — the changelog is a page in the app, and the version lives on it:** a **Changelog** entry joins the sidebar's *"Consulted, not changed"* block beside **Stats** and **Audit log**, rendering the bundled `CHANGELOG.md` through the markdown renderer the app already uses, with the running version and the runtime pins in its header (`HappyVibe 0.2.0` over `Pi 0.84.2 · sub-agents 0.58.0 · MCP adapter 2.26.1`). This does **not** reopen round 8's deletion of the **Help** nav entry (§7): a changelog is product state like Stats and Audit, not documentation. After an update the row carries a **passive dot** — mirrored onto the collapsed Settings group so it is visible while the group is closed — cleared by opening the page; it is **never a modal and never a toast**, per the never-nag rule, and a **fresh install shows no dot at all**, because a new user has not been updated. *(Round 2, 2026-08-30)* **The dot bubbles up through collapse the user did not choose and stops at collapse they did**: it appears on the closed **Settings** group button but **not** in the ⌘B-collapsed 48px icon rail, because ⌘B is an explicit *get this out of my way* gesture rather than an oversight. That is knowingly not the app's other badge rule — a session's pending-permission badge does not bubble to a collapsed workspace row at all — because that badge is urgent and transient while this one is passive and waits to be read, and the Settings group is closed by default, so a row-only dot would be invisible to most users most of the time. `0.1.0` shows a dot to nobody: it is the first release, so the flag is seeded silently at first launch and the first dot anyone sees is `0.2.0`'s. The version is a **build-time constant** rather than an `app.getVersion()` IPC round trip, since it is a build-time fact and the honest representation of one is a constant. **Explicitly not built: an update check.** The page reports the version you are running and never claims to know whether a newer one exists — that needs a publish feed, which `electron-builder.yml` does not have, and it belongs with the open remote-update question rather than here.

**Decision (Feedback round 18, 2026-08-31) — the passive dot is deleted (reverses the marker half of the decision above):** the dot's justification was that it *bubbles up through collapse the user did not choose* — it appeared on the closed **Settings** group row precisely because a row-only dot would be invisible to most users most of the time. §7 round 18 groups the Settings list into four collapsible groups, so keeping that property now costs **two** levels of bubbling — Changelog row → *This app* → `Settings` — and a passive marker is not worth three places that must agree. `UnreadDot`, the `changelogUnread` prop and the startup seed/clear in `App.tsx` all go. What survives is the page: it still reports the version you are running and the runtime pins. This does **not** reopen *"explicitly not built: an update check"* — nothing anywhere claims a newer version exists, which is now true by construction rather than by restraint.

**Decision (round 2, 2026-08-30) — the page, the package identity and the `0.1.0` stamp ship in ONE change, because a version surface that is wrong on the day it appears is worse than none:** reading the code turned the "when do we cut `0.1.0`" scheduling question into a correctness constraint — `package.json` says `1.0.0` and `CHANGELOG.md`'s only heading is `[Unreleased]`, so a page shipped before the stamp renders *HappyVibe 1.0.0* over a body whose top entry is *Unreleased*, and the invariant test above fails the day it is written. The same change therefore carries the identity cleanup — `name: happyvibe`, `homepage: https://happyvibe.dev`, a real author and a description matching the changelog's own first line, replacing the electron-vite scaffold values that ship inside the built artifact — which is safe because `hv-scaffold` is read by **nothing at runtime** and Electron derives userData from `productName` (already `HappyVibe`), not from `name`, so nobody's data moves. The **tag** is still cut by hand afterwards. One further constraint the same reading surfaced, fixed here because the changelog is the first page to trip it: **`will-navigate` (`src/main/index.ts`) intercepts only `^(https?|mailto):`, so a RELATIVE markdown link navigates the whole SPA to a dead `file://` with no way back but restarting the app** — pre-existing and reachable today from a chat answer, a `SKILL.md` preview or any `.md` opened in the editor, so the guard goes in `will-navigate` (refuse any navigation that is not the current URL), which covers every caller at once, rather than in the changelog page. The pins are allowed to appear **twice** on that page — header and entry foot — because they answer different questions: the header is the build you are *running*, each entry is the build *it shipped in*, and they diverge on every entry but the newest.

Out of scope: auto-update and any "a new version is available" prompt; a release CI workflow that builds and attaches the `.dmg` (the first tags are cut by hand, to learn whether automating is worth it); notarization (§4's unsigned-build position is unchanged); a second, developer-facing changelog — the commit log already is one.

# Critical PRD Update: Pi Agent Reality Check

Pi intentionally keeps its core small and pushes workflow-specific behavior into extensions, skills, prompt templates, and packages. HappyVibe V1 therefore defines a curated Pi-based runtime bundle that includes or implements the required capabilities.

Validation research (July 2026) resolved the open questions: 15+ native providers with mid-session switching; `pi-subagents` for delegation (separate context per agent); extensions get full session access (`get_entries`, the `context` filtering event — the mechanism behind §9's manual removal); the `tool_call` extension event supports `{block: true}` (the RPC protocol alone cannot approve/deny — hence the bridge); RPC streams structured JSON events for the whole UI surface.

**Key architecture note — the HappyVibe bridge extension:** a small bundled extension that listens to `tool_call` events inside Pi, forwards permission requests to the UI, and returns allow or `{block: true}` from the user's decision and stored rules. This grew into HappyVibe's core Pi-side component (permissions engine, context marks, auth commands, registered tools).

**V1 runtime bundle (as shipped):** Pi core (`@earendil-works/pi-coding-agent`, pinned) · `pi-subagents` (pinned) · the HappyVibe bridge extension (in-house). `pi-mcp-adapter` joins when MCP ships (§13). `@gotgenes/pi-permission-system` was dropped after the spike's V6 finding (TUI-only in RPC mode) — it remains vendored solely for the regression test documenting that finding.

**Remaining open items for the tech lead:** the Pi upgrade/release process is contract-test-gated (every pin bump re-validates the wire shapes); Windows validation (tmux dependency, extension portability) still precedes any Windows commitment. *(Resolved 2026-07-16: the packaged sub-agent child process now runs through the bundled Electron helper as Node — `pi-runtime/bin/pi-node.sh` — no system Node required; see §3 standalone decision.)*

## 32. Web tools

The agent can search the web and read any public page as clean text: `web_search` (a query → results), `web_fetch` (a URL → readable markdown, capped and pageable), `web_map` (a site → its URLs) and `web_crawl` (a site → up to N pages of markdown in one bounded call). Pages are fetched by a **web service** the app talks to over HTTPS — by default a server HappyVibe operates, or one the user points the app at — so nothing runs in the user's browser, no cookies are involved, and JavaScript-heavy pages still come back as text. The promise: the agent can read the public web, the user sees every site it touched, it asks before the first contact with a host, and the context panel prices every page. The embedded browser (§28) stays the tool for pages you can see and click; this is headless reading. Locked spec and the live-server measurements live on the Notion page `3d0d33dfffca80ceb751e36bc534350d`; the decisions are here. Validation: `docs/validation/w1.md`.

**Decision (Feedback round 20, 2026-09-04, tool surface):** **four separate tools, no action enum** — §26/§28's reasoning a third time, and `web_search` needs a different default from the other three. All four are thin shells over blocking `hv.web-*` envelopes; **main calls the service**, owns the URL, the encrypted key, the caps, the deadlines and the audit row, and always answers (the `hv.terminal-*` / `hv.browser-*` contract — a dropped answer hangs the turn). Every result opens with §28's untrusted banner and a factual header (URL, title, page status, total chars, window shown). Caps are bounded by construction and stated on the card: fetch 16,000 chars default / 40,000 max with `startIndex` paging; search 5 results default / 10 max; map 100 / 500 URLs; crawl 10 pages default / 30 max, depth ≤ 3, 60,000 chars total; per-call deadline 70 s, crawl 120 s and then the job is cancelled on the server. A user abort cancels the in-flight request and any crawl job. No summarising side model (hidden spend), no app-side cache (the service caches two days), no `recency` parameter (the self-hosted backend ignores it — measured, so the tool must not claim freshness it cannot deliver).

**Decision (2026-09-03, gate — shared with the browser):** `web_fetch` / `web_map` / `web_crawl` gate per host under the **same virtual rule the embedded browser uses, `browser:<host>`** (§28), evaluated by the same engine: one fact — "the agent may reach docs.foo.com" — one allow-list, so "Allow for session", pattern rules and the Permissions page cover both surfaces. A separate `web:<host>` list was rejected as a second list that can disagree with the browser's about the same host. The prompt shows the **URL**, never the model's `intent` (§13's rule, stated absolutely). `web_search` is **allow-by-default** (`SAFE_TOOLS`): a query has no host the user could meaningfully approve; recorded honestly that the query leaves the machine to the service, and a deny rule exists for anyone who minds. `localhost`, private ranges and non-http schemes are **refused before the gate** with a sentence naming `browser_open` as the tool that can reach a dev server. **Plan mode: all four pass** (named in `PLAN_PASS_TOOLS`) where `browser_navigate` floor-asks — see §28's round-20 decision for why. Bypass skips prompts like every tool; cards, banner and audit are unchanged.

**Decision (2026-09-03, the service):** a **default service is baked in** (`DEFAULT_WEB_SERVICE_URL`, one constant; Firecrawl v2 API; https only) with an **own-service override** — base URL plus optional key, `safeStorage`-encrypted like `customKeys`, sent as a bearer header from main only and never present in the Pi child's env. The backend is **never named in the main UI** — the words are Web tools, Search, Read, Site map, Read a site, "web service" — with one exception: the custom-server field's helper reads *"Firecrawl-compatible API, v2"*, because a self-hoster has to know what to run. Main makes **no call at boot**; the service is contacted only by a tool call or the settings Test button. Privacy is disclosed in How-it-works: sites see the service's address, not yours; the default service is a server HappyVibe operates and can see the URLs and queries the agent sends; point the app at your own if that matters. **A busy or unreachable default service says so** (decided 2026-09-04) — one sentence pointing at Settings → Built-in tools, no retry loop, no remote kill switch; rate limiting is enforced on the server, not in the app. Firecrawl Cloud stays in the MCP catalog for the cloud-only extras (screenshots, actions, LLM extraction), with one sentence saying the built-in tools already cover search and reading without a key.

**Decision (2026-09-04, surfaces):** one **Web tools — 4 tools** row on Built-in tools (§13's round-20 decision) and a **How web tools work** disclosure (`HOWTO_COPY.webTools`). Cards: "Searched the web for …", "Read ‹title›" with the URL chip, "Listed N pages on ‹host›", "Read N pages from ‹host›" — never "scrape" or "crawl" in the UI; a fetch card shows "N of M chars" on its face and a crawl card's default view is the collapsed per-page list. One `web.call` EventLog row per call — tool, host or query length, chars, ms, ok, service default/custom — never the content and never the query text (§19). The four schemas land in the context panel's Tool definitions like every other tool; their resting cost is measured before the switch's saving is claimed.

**Deferred, with reasons (2026-09-04), so they are not re-litigated:** web tools for **sub-agents** — a child Pi loads neither the bridge nor a route to main; the route is a child-side extension calling the service directly, with hosts approved up front in the delegation modal, and it is a round of its own; async crawl in the run rail (the bounded crawl covers "read these docs"); screenshots, actions and LLM formats (the service cannot — measured); `curl` blocking in bash (a `bash` rule exists, and `curl -X POST` has uses `web_fetch` cannot serve); a per-workspace toggle or service; an "allow all hosts" switch (pattern rules do it visibly). Search runs through **SearXNG on the service box** (enabled 2026-09-04, measured the same day: every result carries a title and a real snippet, and the generic-query weakness that DuckDuckGo scraping showed is gone). It is a server-side concern with no app code either way, which is why it was not a gate for this round. Recency stays out regardless: upstream never maps a recency filter onto SearXNG, so the tool must not offer one.
