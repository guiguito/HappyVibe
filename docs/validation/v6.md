### Core V6 Question: Does pi-permission-system surface over RPC?

**NO.** pi-permission-system's `ask` enforcement does NOT produce `extension_ui_request` messages with `method=select` over RPC. It only sends `setStatus` messages (status bar updates).

**Root cause (verified against package source, v18.1.1):** pi-permission-system has TWO prompt paths, and BOTH are gated on `ctx.hasUI`:
1. Direct gate — `PermissionPrompter.prompt()` (`src/permission-prompter.ts`) → `PermissionForwarder.requestApproval()` (`src/permission-forwarder.ts`): when `hasUI=false` and the session is not a subagent, it returns `{ approved: false, state: 'denied' }` SILENTLY (no prompt).
2. Event-bus RPC — `permissions:rpc:prompt` channel (`src/permission-event-rpc.ts`, `handlePromptRpc()`): also checks `hasUI` and returns `{ error: 'no_ui' }` when false. This is an in-process Pi event bus for subagent→parent forwarding, NOT the cross-process `extension_ui_request` wire.

HappyVibe runs Pi with `--mode rpc`, where `hasUI=false`, so BOTH paths are inert, and neither path routes through the `extension_ui_request` wire that the HappyVibe bridge uses. Therefore pi-permission-system cannot surface interactive permission UI to HappyVibe's renderer under any current configuration. **The HappyVibe bridge is and must remain the sole permission-UI enforcement path in RPC mode.**

**Architecture implication:** pi-permission-system was designed for Pi's TUI mode (terminal interactive UI). In headless RPC mode (which is what HappyVibe uses), its `ask` enforcement is a no-op for the UI layer — there is no RPC-surfaced prompt. The happyvibe-bridge's own interception (`ctx.ui.select` called during a tool call gate) is what produces the RPC-accessible `select` prompt.

### Double-Prompt Finding

**NO double-prompt.** Only the bridge prompted for the write tool call. This is consistent with the above: pi-permission-system either skipped prompting (hasUI=false) or its prompt arrived after the bridge's deny already blocked execution.

### Coexistence Stability

Extensions coexist without conflict or crash. pi-permission-system loads and sends status updates; the bridge operates normally. No destructive conflict.

## PRD Architecture Implications

1. **Cannot rely on pi-permission-system for RPC-mode UI prompting.** Its `ask` policy does not translate into RPC-accessible prompts.
2. **HappyVibe bridge is the correct enforcement path for RPC mode.** It is the only extension that surfaces permission prompts over the `extension_ui_request` channel with `method=select`.
3. **Loading pi-permission-system alongside bridge is safe** (no conflict), but adds no UI enforcement in RPC mode. If pi-permission-system's silent enforcement (deny silently in non-UI mode) is desired as a secondary safety layer, it can be loaded — but users will not see its prompts; they will only see bridge prompts.
4. **If pi-permission-system RPC support is desired in the future:** it would require Pi to wire `ctx.ui.select` to produce `extension_ui_request` events in RPC mode (a Pi core change), OR pi-permission-system to use a different signaling mechanism (e.g., a custom RPC event) that HappyVibe then subscribes to separately.
