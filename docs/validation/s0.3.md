## 1. pi-subagents in RPC mode — PASS

### Source audit (the pi-permission-system question)

`grep -rn hasUI src/` in pi-subagents 0.33.1: all ~27 hits are **cosmetic or optional** — widget/status rendering (`src/extension/index.ts:391,566`, `src/runs/background/async-job-tracker.ts`), TUI render (`src/tui/render.ts`), and the opt-in `clarify` flow (`src/runs/foreground/subagent-executor.ts:2467,2795` — `if (params.clarify === true && ctx.hasUI)`; when false it just skips clarification and proceeds). **The core delegation path (registerTool "subagent" → spawn child Pi) has no UI gate.** This is structurally different from pi-permission-system, whose *enforcement* path was UI-gated (v6.md).

**Correction to v6's stated mechanism:** in Pi 0.80.3, `ctx.hasUI` is **true** in RPC mode. `rpc-mode.js:229-231` calls `session.bindExtensions({ uiContext: createExtensionUIContext(), mode: "rpc", ... })` and `runner.js:245-247` returns `hasUI = uiContext !== noOpUIContext`. The `.d.ts` comment agrees: "Whether dialog-capable UI is available (true in TUI and RPC modes)" (`dist/core/extensions/types.d.ts:213`). Empirically confirmed: pi-subagents emitted `extension_ui_request method=setWidget` at startup, which it only does when `ctx.hasUI`. v6's *empirical* result (pi-permission-system never emits `select` over RPC) still stands, but the reason is inside that package, not a blanket "hasUI=false in RPC".

### Loading

```
node pi-runtime/node_modules/@earendil-works/pi-coding-agent/dist/cli.js \
  --mode rpc --no-session \
  -e <scratch>/node_modules/pi-subagents/src/extension/index.ts \
  --provider deepseek --model deepseek-v4-flash
```

- Loads cleanly on 0.80.3. `get_commands` returned its slash commands: `run, chain, run-chain, parallel, subagent-cost, subagents-doctor, subagents-fleet, prompt-workflow, chain-prompts, subagents-models, subagents-profiles, ...` (all `source: "extension"`).
- Pi's extension loader **aliases** `@earendil-works/pi-agent-core`, `pi-tui`, `pi-ai`, `pi-coding-agent` (and stale `@mariozechner/*`) to its own bundled copies (`dist/core/extensions/loader.js:30-51` VIRTUAL_MODULES + jiti aliases). pi-subagents' declared `pi-tui@0.74.0` dependency is never used at runtime → the 0.74-era devDeps are not a compat constraint.

### CRITICAL for embedded HappyVibe: child spawn resolution

`src/runs/shared/pi-spawn.ts:125-147` — child Pi processes are spawned as **`pi` from PATH** on macOS/Linux, unless env **`PI_SUBAGENT_PI_BINARY`** is set (line 130). HappyVibe's embedded runtime has no global `pi`, so the spawn env MUST include:

```
PI_SUBAGENT_PI_BINARY=<runtimeDir>/node_modules/.bin/pi
```

Without it, delegation fails with ENOENT. (Test machine had no global `pi`; setting this env var is what made the run below work.)

### Real delegation test

Project agent at `<cwd>/.pi/agents/greeter.md` (Markdown+YAML: `name/description/tools/model` frontmatter). Prompt: *"Use the subagent tool (mode: single) with agent 'greeter' and task 'say hello'."*

Observed on the parent RPC stdout (full log: scratchpad `s03/events-real.ndjson`):

1. Model first called `subagent {"action":"list"}` → tool result enumerated 8 builtin agents (context-builder, delegate, oracle, planner, researcher, reviewer, scout, worker) **plus** `greeter (project)`.
2. Then the real delegation:

```json
{"type":"tool_execution_start","toolCallId":"call_00_CXBl...","toolName":"subagent","args":{"agent":"greeter","task":"say hello"}}
```

```json
{"type":"tool_execution_update","toolCallId":"call_00_CXBl...","toolName":"subagent",
 "partialResult":{"content":[{"type":"text","text":"HELLO FROM SUBAGENT"}],
   "details":{"mode":"single","results":[{"agent":"greeter","task":"say hello","exitCode":0,
     "messages":[{"role":"user","content":[...]},{"role":"assistant","content":[...]}]}]}}}
```

```json
{"type":"tool_execution_end","toolCallId":"call_00_CXBl...","toolName":"subagent",
 "result":{"content":[{"type":"text","text":"HELLO FROM SUBAGENT"}],
   "details":{"mode":"single","runId":"73f1ade9","results":[{"agent":"greeter","exitCode":0,
     "usage":{"input":1406,"output":636,"cost":0.00037,"turns":1},
     "model":"deepseek/deepseek-v4-flash",
     "artifactPaths":{"inputPath":".../.pi-subagents/artifacts/73f1ade9_greeter_0_input.md",
       "outputPath":"...output.md","jsonlPath":"....jsonl","transcriptPath":"..."}}]}}}
```

Parent's final assistant text quoted `HELLO FROM SUBAGENT` verbatim. Round trip complete.

**UI-trace implications (B6):** subagent activity streams through ordinary `tool_execution_update` events on the parent RPC stream — `partialResult.details.results[].messages` is the live child transcript (roles + content), and `_end.details` carries per-agent usage/cost/turns plus on-disk artifact paths under `<cwd>/.pi-subagents/artifacts/`. HappyVibe can render a live subagent panel from events it already consumes; no extra channel needed.

**Caveats:**
- pi-subagents injects an "acceptance contract" wrapper around the task (child's user message contains an `acceptance-report` JSON scaffold from its completion-guard) — the raw child transcript shown in a UI will include this noise.
- The subagent tool call itself is a normal `tool_call` → the HappyVibe bridge will gate it with the standard Allow/Deny select (coexistence pattern already proven in V6 for two extensions; not re-run here).
- Child processes inherit env (API keys) from the parent Pi process.

## 2. Context surface — PASS for B5

### `get_entries` over RPC

`{"type":"get_entries","since?":"<entryId>"}` → `{entries: SessionEntry[], leafId}` (`dist/modes/rpc/rpc-types.d.ts:110-114,319-327`). Entry types (`dist/core/session-manager.d.ts:23-101`):

| type | content |
|------|---------|
| `message` | full `AgentMessage` — roles `user`, `assistant` (with `toolCall` content blocks incl. `id`, args), `toolResult` (with `toolCallId`) |
| `compaction` | summary, `firstKeptEntryId`, tokensBefore |
| `branch_summary` | fromId, summary |
| `custom` / `custom_message` | extension data; `custom_message` DOES enter LLM context |
| `model_change`, `thinking_level_change`, `label`, `session_info` | metadata |

- Entries have `id`/`parentId` (session is a tree); baseline session starts with `model_change` + `thinking_level_change`.
- **System prompt and AGENTS.md are NOT entries** — get via `before_agent_start` event (`systemPrompt`, `systemPromptOptions`) or `ctx.getSystemPrompt()`.
- **Pairing:** `toolCall.id` ↔ `toolResult.toolCallId` — fully visible, pairs are removable atomically.
- No dedicated "entries changed" RPC event, but the stream's `message_end`, `compaction_start/end`, `session_info_changed` etc. (AgentSessionEvent union, `dist/core/agent-session.d.ts:40-77`) are sufficient triggers to re-poll `get_entries?since=`.

### Extension-side removal (B5 manual removal) — proven live

The `context` event fires before **every** LLM call with the full message array; returning `{messages}` replaces it (`dist/core/extensions/types.d.ts:489-492` ContextEvent, `:749-751` ContextEventResult, `:834` registration).

Probe (`filter-ext.ts` in scratchpad): drops every `toolResult` whose `toolCallId` is in a kill set and strips the paired `toolCall` blocks from assistant messages; kill set = all pairs older than the last user message. Live 2-turn run (turn 1: real bash tool call `echo s03-marker-12345`; turn 2: "reply OK" with the turn-1 pair filtered out). Verbatim output:

```
S03-FILTER: before=1 after=1 killed=0    ← turn-1 first LLM call (just the user msg)
S03-FILTER: before=3 after=3 killed=0    ← turn-1 second call (current-turn pair kept)
S03-FILTER: before=5 after=3 killed=1    ← turn-2 call: bash toolCall/toolResult pair removed atomically
== turn2 reply == {"text":"OK"}          ← provider accepted the filtered context (no orphan-pair 400)
== entries after == ... message:assistant message:toolResult ...  ← session file untouched; per-call, non-destructive
```

**Sharp edge (v1 of this probe):** a filter that also strips the *current turn's* pair makes the model re-run the tool forever — it never sees that the command already executed. Probe v1 looped for **579 turns** before being killed (DeepSeek accepted every filtered payload: 0 errors, 0 auto-retries, $0.023 total). Two consequences: (a) ~580 consecutive provider calls with pairs stripped is itself strong proof the atomic-pair-removal shape is provider-safe; (b) **B5 manual removal must only apply to entries from completed turns** (older than the last user message), and the client should keep an abort/turn-budget guard regardless.

**B5 design that falls out:** HappyVibe renderer shows `get_entries`; "remove item" = add the entry/toolCall id to a kill set held by the happyvibe-bridge extension, which filters in its `context` handler. UI→bridge signalling can reuse existing plumbing: bridge registers a slash command (e.g. `/hv-context-remove <id>`) invoked via the RPC `prompt` command, or a custom tool. Removal is reversible (kill-set delete) since the session file is never mutated. Destructive alternatives exist but are heavier: RPC `fork` (entryId) / extension `navigateTree`.

### Compaction hooks

- `session_before_compact` handler can cancel or supply its own `CompactionResult` (`types.d.ts:432`, registration `:829`).
- RPC: `compact` command (+ optional `customInstructions`); `compaction_start` / `compaction_end` events stream with reason `manual|threshold|overflow`.

## 3. Version compat — no conflict

- `pi-subagents@0.33.1` peerDeps: `@earendil-works/pi-{agent-core,ai,coding-agent}: "*"`, all optional. No engine/version gate anywhere in `src/`.
- Its only real `@earendil-works` dependency (`pi-tui@0.74.0`) is dead weight at runtime — Pi's loader aliasing (loader.js VIRTUAL_MODULES) substitutes the host's bundled copies.
- Empirically: loads, registers, delegates on 0.80.3.

## Implications

- **B6 (agents): UNBLOCKED.** Load pi-subagents via `-e <path>/src/extension/index.ts` (its `package.json` `pi.extensions` field confirms the entry). Required: set `PI_SUBAGENT_PI_BINARY` to the embedded pi bin in spawn env. Agent definitions: `<cwd>/.pi/agents/*.md`. UI trace comes free from `tool_execution_update` events.
- **B5 (context visibility): UNBLOCKED.** `get_entries` (+`since`) for the panel; kill-set filtering in the bridge's `context` handler for manual removal; pairs removable atomically; non-destructive.
- **README correction:** the "hasUI=false in RPC" generalisation from V6 does not hold on 0.80.3 — extensions DO have dialog-capable UI over RPC (that is exactly the `extension_ui_request` wire). V6's negative finding is package-specific to pi-permission-system.
