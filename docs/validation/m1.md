## Findings

### 1. pi-mcp-adapter loads and registers the `mcp` proxy tool

pi-mcp-adapter loaded successfully as a `-e` extension in `--mode rpc`. The adapter's
`shouldRegisterProxyTool` logic evaluated to `true` (workspace `.mcp.json` present with
one server, no `disableProxyTool` setting), so the `mcp` proxy tool was registered via
`pi.registerTool`. Pi's `tool_call` event fired for it and the bridge gate intercepted it.

### 2. Actual prefixed tool name: `mcp:echo_echo`

The adapter prefixes tool names with the **server key** from `mcpServers` plus an
underscore. For server key `echo` and tool `echo`, the result is `echo_echo`. The
`hv-mcp.ts` `unwrapMcpCall` reads `params.tool` off the proxy call's input and produces
`ruleTool: "mcp:echo_echo"`. This is what surfaced in the `hv.permission` prompt:

```json
{ "kind": "hv.permission", "tool": "mcp:echo_echo", "summary": "MCP → echo_echo" }
```

**Convention**: `mcp:<serverKey>_<toolName>` — rules should pattern-match accordingly
(e.g. `mcp:echo_*` to gate all echo-server tools; `mcp:github_*` for a GitHub MCP server
keyed `github`).

### 3. Discovery calls did NOT prompt

The model issued a discovery call (search/describe) before the invoke. The bridge's
`mcp?.kind === "discovery"` guard in `tool_call` safe-default-allowed it — no
`hv.permission` prompt was generated. The test's `nonInvoke` filter confirmed zero
unexpected prompts.

### 4. Config resolution — workspace `.mcp.json` honored

The adapter read `<cwd>/.mcp.json` (workspace-tier, written by the test). HOME and
XDG_CONFIG_HOME were redirected into the test's tmp dir so `~/.config/mcp/mcp.json` and
`~/.pi/agent/mcp.json` could not leak the developer's real servers. No other config
files were found, so the fixture echo server was the only one registered.

The app accepts the user-global read (`~/.config/mcp/mcp.json`) as intentional —
user-installed MCP servers should be visible across workspaces, consistent with
community-friendly behavior.

### 5. `ctx.hasUI` findings under RPC

The adapter's TUI-only paths (`/mcp` panel command, elicitation dialogs, sampling
dialogs) are all guarded by `ctx.hasUI`. Under `--mode rpc`, `ctx.hasUI` is `false`.
In this test run:
- The `/mcp` slash command was not called (not relevant to the proxy tool path).
- No elicitation or sampling was triggered (the echo tool has no elicitation schema).
- No crashes or visible errors from `ctx.hasUI`-guarded paths.
- All observable behavior came from the proxy tool's `execute()` branch, which is
  UI-agnostic. The guarded paths are silently skipped under RPC with no side effects.

**Open item**: the adapter's `/mcp` command does a `ctx.hasUI` check before showing
the panel UI. Under RPC it will likely log nothing or return an empty result. This is
not a blocker but should be replaced with an `hv-envelope` fallback (spec item) so the
renderer can show MCP status without a TUI. Tracked in docs/prd.md.

### 6. Open distribution item — stdio server runtime

The test configures the echo server as `{ command: process.execPath, args: [fixture] }`
(i.e. the Electron/Node binary). User-configured servers in production commonly use
`node` or `npx` as `command`. The packaged Electron app has no standalone `node` on
PATH, so servers with `command: "node"` will fail to spawn unless HappyVibe provides a
bundled runtime or rewrites `command` to the embedded binary. Same class as the
pi-subagents shebang item in CLAUDE.md. Open distribution item, not a V1 blocker.

## Phase 1 finding — HappyVibe main as the MCP management client

### Why the adapter cannot manage MCP from main or the bridge

The `pi-mcp-adapter`'s interactive OAuth is hard-gated on `ctx.hasUI`
(`pi-mcp-adapter/commands.ts:139`). Under `--mode rpc`, `ctx.hasUI` is `false`, so the
adapter's `/mcp` panel, elicitation dialogs, and auth flows are all silent no-ops.

The adapter's structured headless actions (auth-start, auth-complete, status, connect)
are exposed only on the `mcp` **tool**, not as RPC commands. Pi RPC's command union
(`modes/rpc/rpc-mode.js`) has no tool-execution verb — and neither does the ExtensionAPI.
This means neither main nor the bridge can invoke those tool actions programmatically;
only the **model** can call a tool during a conversation turn.

### Consequence: main owns MCP management

HappyVibe main is the MCP **management** client — connect, list-tools, and status queries
are handled by `src/main/mcpClient.ts` via `@modelcontextprotocol/sdk` (Client +
StdioClientTransport). Phase 1 scope: connect / list-tools / status / startup-check /
reconnect. OAuth + add-time confirmation is Phase 2.

The vendored pi-mcp-adapter stays the **in-session runtime path**: model tool calls →
proxy tool → permission gate → execute.

### Shared state: on-disk token store only

Main and the adapter share state exclusively on disk at:

```
<agentDir>/mcp-oauth/sha256-<sha256hex(serverName)>/tokens.json
```

`src/main/mcpAuthStore.ts` mirrors the `AuthEntry` format from `pi-mcp-adapter/mcp-auth.ts`
so Phase 2 OAuth tokens written by main are readable by the adapter and vice versa.
No in-memory coupling; no IPC coupling.

### Architecture summary

```
main  ──mcpClient.ts──► @modelcontextprotocol/sdk ──► MCP server (stdio)
                             connect / list-tools / status

Pi session ──adapter──► proxy tool ──bridge gate──► execute  (model-driven)
                                        ↑ hv.permission prompt

shared state: <agentDir>/mcp-oauth/sha256-*/tokens.json  (AuthEntry)
```

### Phase 1 scope

Connect, list-tools, status, startup sweep (non-blocking probe of all configured
servers at session start), reconnect via IPC `hv:mcp-reconnect`.
IPC: `hv:mcp-status` (full map), `hv:mcp-status-changed` (push update).
Renderer: status badge per server + reconnect button.

OAuth (`src/main/mcpOAuth.ts`), `hv:mcp-authenticate` / `hv:mcp-logout`, add-time
confirm-with-tools modal, and the `tests/mcp-adapter-authformat.test.ts` contract test
are Phase 2.

## Phase 2: Host-driven MCP OAuth

### Problem

The pi-mcp-adapter's interactive OAuth path (`mcp-auth.ts`) is gated on `ctx.hasUI` and is a no-op in RPC mode — there is no browser, no redirect handler, and no way to surface the authorization URL to the user via the adapter alone.

### Solution: main owns the OAuth handshake

`src/main/mcpOAuth.ts` implements `OAuthClientProvider` from `@modelcontextprotocol/sdk` and runs the full Authorization Code flow inside the Electron main process:

1. **Authorization URL** — obtained from the MCP server's OAuth metadata discovery; opened in the system browser via `shell.openExternal`.
2. **Loopback callback server** — `http.createServer` bound to `127.0.0.1` on an ephemeral port; the redirect URI is `http://127.0.0.1:<port>/callback`.
3. **CSRF guard** — `state` parameter generated with `crypto.randomUUID()`; verified on callback before proceeding.
4. **Code exchange** — `transport.finishAuth(callbackUrl)` hands the full callback URL to the SDK transport, which performs the token exchange internally.
5. **Fresh transport** — SDK transports cannot restart after `finishAuth`; after a successful exchange the old transport is discarded and the server reconnects with a new `SSEClientTransport` / `StdioClientTransport`.
6. **Token persistence** — tokens written as `AuthEntry` (format: `{ serverUrl, accessToken, refreshToken?, expiresAt? }`) to `<agentDir>/mcp-oauth/sha256-<sha256hex(serverName)>/tokens.json` via `src/main/mcpAuthStore.ts`, which mirrors the format from `pi-mcp-adapter/mcp-auth.ts`.
7. **Credential revocation on server removal** (2026-07-14): removing a server also deletes its `AuthEntry` (tokens + DCR client) — but only when no remaining config references the name, because the token store is name-keyed and shared across scopes/workspaces (`serverNameInFiles` guard; audited as `mcp.auth` / `credentials-deleted`). Ceiling: workspaces not currently registered aren't scanned; their same-named server just re-auths.
8. **Stale-client token drop** (2026-07-14, found live against Notion — "Client ID mismatch"): refresh tokens are client-bound, and our loopback port is fresh per flow, so a stored DCR client usually can't be reused (redirect URI drift → `clientInformation()` returns undefined → SDK registers a NEW client). The SDK then attempts the refresh grant with the OLD client's refresh_token and **re-throws** the resulting OAuthError instead of falling back to authorize (`auth.js authInternal`: only `ServerError`/non-OAuth errors continue). Fix in `authenticate()`: before connecting, if stored tokens exist but the stored client's `redirectUris` don't cover this flow's redirect URL, drop the refresh_token (and the whole token set when the access token is expired) so the flow goes straight to a fresh authorize. A still-fresh access token is kept — connect succeeds with it directly. Regression tests in `tests/mcp-oauth.test.ts` (mock AS rejects client-mismatched refresh like Notion does).

### Shared state: on-disk only

Main writes tokens; the adapter reads them at Pi-session start. No IPC coupling, no in-memory shared state. Path is deterministic from the server name so both sides resolve it independently.

### IPC surface

| Channel | Direction | Purpose |
|---|---|---|
| `hv:mcp-authenticate` | renderer → main | Trigger OAuth flow for a named server |
| `hv:mcp-logout` | renderer → main | Clear tokens + update status to `needs-auth` |

### UX flows

- **Add-time confirm**: when a new server requires OAuth, the renderer shows a connect-and-list-tools modal before writing config. If the connection requires auth, the Authenticate button is shown inline.
- **Per-server actions**: Authenticate and Log out buttons in the Agents & Tools page, conditional on `status === 'needs-auth'` / `status === 'connected'`.
- **Startup status sweep**: at session start, main probes all configured servers non-blockingly; servers returning `401 / needs-auth` surface the Authenticate prompt without blocking session start.

### Contract test

`tests/mcp-adapter-authformat.test.ts` asserts that `AuthEntry` written by `mcpAuthStore.ts` matches the shape expected by the adapter. This test is the pin-bump gate: any upgrade to `pi-mcp-adapter` must pass it before the pin is updated in `pi-runtime/package.json`.

## Model-authored intent on MCP calls (readability)

The adapter's tool schemas have no `intent` param, and the model only fills declared params — so we add `"mcp"` to the bridge's `INTENT_TOOLS`. `requireIntent` mutates the adapter's proxy tool's shared TypeBox schema at `session_start` to require an `intent` (same mechanism proven for `subagent`), so the model authors a customer-facing headline on every proxy call. Verified end-to-end by an extension of `tests/mcp-bridge.test.ts`: a real model's `mcp` invoke arrives at `tool_execution_start` with a non-empty `args.intent`.

In **proxy mode** the proxy `execute` reads `tool`/`args`/… and never forwards the top-level `intent` to the MCP server, so schema injection alone is safe. Renderer (`toolLabel.ts`) shows `intent ?? unwrapMcpCall().display`. The permission prompt keeps the FACTUAL `unwrapMcpCall().display` (now enriched with a key arg such as url/query, truncated) rather than the model's self-authored intent — a safety choice so a benign-sounding intent can't mask a risky call at approval time.

**Direct mode** (2026-07-14): `directTools` forward all params to the server verbatim (`pi-mcp-adapter/direct-tools.ts` — `arguments: params ?? {}`; a strict server would reject an extra `intent`), so injection alone is NOT safe there. Verified mechanism:

- Pi's `tool_call` extension event input is documented mutable ("Mutate it in place to patch tool arguments before execution" — `pi-coding-agent/dist/core/extensions/types.d.ts`), and the mutated object is exactly what the tool's `execute` receives (`agent-loop.js prepareToolCall` → `prepared.args`).
- `tool_execution_start` is emitted with the ORIGINAL `toolCall.arguments` BEFORE `beforeToolCall`/extension handlers run (`agent-loop.js executeToolCalls*`), so the renderer's tool card sees the intent even though execution doesn't.
- So the bridge (`requireIntent`) injects the required `intent` into every adapter-registered tool (`sourceInfo.path` contains `pi-mcp-adapter`; the proxy is excluded via `INTENT_TOOLS`), records the names in `strippedIntentTools`, and the `tool_call` handler deletes `input.intent` for those tools at the top — before `summarize`, so permission prompts and audit stay factual. Server tools that already declare their own `intent` param are skipped entirely (no injection, no strip — the param is server-owned).
- Renderer needs no change: `toolLabel.ts`'s default case is already `intent ?? prettify(toolName)`.

Unit contract: `tests/intent-direct-tools.test.ts` (injection targeting, idempotency, strip-for-direct, no-strip for proxy / server-owned intent, factual prompt title).

## Applying MCP changes live to running sessions

There is no live tool-reload path in Pi or the adapter: MCP config is read at extension init (process spawn); Pi RPC has no reload command, the ExtensionAPI has no tool-refresh, and the adapter's `/mcp` reload is TUI-gated (no-op in RPC). So "apply changes live" = **respawn the affected sessions resumed** — the exact hibernation-restore path (`startClient(meta, true)` → `--session <file>`), which preserves the conversation via the session file.

On `hv:mcp-set-server` / `hv:mcp-authenticate` (success) / `hv:mcp-logout`, main calls a debounced `scheduleMcpReload(scope, workspaceId)` (the debounce coalesces the add-then-authenticate sequence into one pass). A pass computes affected live sessions (`affectedSessionIds` — global → all; workspace → matching `workspaceId`), respawns the IDLE ones immediately, and defers busy ones (`pendingMcpReload`, drained on `agent_end` / permission-prompt close so a mid-turn or mid-prompt session is never disrupted). After respawn it fires `/hv-tools` to refresh the displayed tool list.

Accepted cost: a respawn is a fresh Pi process, so that session's in-memory `sessionGrants` ("allow-for-session") and dangerous-mode toggle reset to safe defaults. This is surfaced to the renderer via a `hv:session-reloading` event → a transcript notice. Preserving those across a reload is a documented future refinement.

## Phase 3: credentials moved to the OS keychain (2026-08-14)

`pi-mcp-adapter` 2.17.0 moved MCP OAuth credentials into the **OS keychain** and
turned the file this document's Phase 2 describes into a legacy artefact. Phase
2's *architecture* is unchanged — main still owns the interactive handshake,
because the adapter's own OAuth is still `ctx.hasUI`-gated — but its **storage**
half is superseded. Source: Notion "☔ MCP issue"; decision folded into PRD §13.

### Measured on the live install

| probe | result |
| --- | --- |
| keychain service | `pi-mcp-adapter.oauth`, accounts `sha256-<hex>` (= `sha256(serverName)`) |
| `<agentDir>/mcp-oauth` | still present, holding `miro` (rewritten by main) and `canva` (orphan, server deconfigured). `notion`'s dir was gone — migrated and deleted |
| `notion` in the keychain | `serverUrl` + `clientInfo`, **no tokens** — so its `needs-auth` badge was honest |
| `miro`, keychain | access `29730e78…`, refresh `5492c582…`, expires **2026-08-04T07:41Z (expired)** |
| `miro`, `tokens.json` | access `393d8a19…`, refresh `fedee5ab…`, expires 2026-08-14T16:50Z |

The two `miro` copies are the finding: main re-authenticated it that day, the
agent was still holding the credential from ten days earlier. Hashes, not
secrets, were compared.

### The three broken directions

1. **status read** — main's probe answered from a file the agent does not read.
   It errs BOTH ways: `needs-auth` for a server the agent can use, and
   `connected` for one it cannot (the `miro` case above).
2. **token write** — once a keychain entry exists the adapter returns it and
   deletes any fresh file **unread**, so signing in again never reached the agent.
3. **logout** — `deleteAuthEntry` removed only the file; the keychain credential
   survived and the session stayed signed in. The same held for *removing* a
   server, which was not in the original report.

### The sidecar contract

`pi-runtime/bin/mcp-oauth-bridge.mjs` — built from `.src.mjs` by
`scripts/build-mcp-oauth-bridge.mjs` (`postinstall`), gitignored. One JSON
request on stdin, one JSON line on stdout, ops batched per invocation:

```
→ { agentDir, ops: [ {op:"inspect",name,url} | {op:"migrate",name}
                   | {op:"writeTokens",name,url,tokens}
                   | {op:"writeClientInfo",name,url,clientInfo}
                   | {op:"remove",name} ] }
← { ok, error?, results: [ {name, status:"present"|"absent"|"unavailable"|"ok",
                            tokens?, clientInfo?, message?} ] }
```

`unavailable` is deliberately distinct from `absent`: reporting absent on no
evidence is the confident signed-out claim this whole phase exists to remove.

**It must be a bundle** — measured, not assumed. Node refuses to strip types for
files under `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, Node
22.21.1) and the adapter ships TypeScript source; Pi loads `.ts` through its own
loader, a bare Node child has none. esbuild leaves `@napi-rs/keyring` external
and **dedupes the bare `pi-mcp-adapter/oauth` and relative `mcp-auth.ts` routes
into one module instance** (verified) — without which the adapter's store state
would split in half.

Reads use `inspectAuthForUrl`, not the subpath's `inspectMcpOAuthTokensForUrl`:
the subpath narrows the entry to `tokens`, and the provider also needs
`clientInfo` for refresh and for the stale-DCR-client guard. Both are equally
non-migrating; `getAuthEntry` is the migrating read, used only by the one-time
sweep.

`src/main/mcpAuthStore.ts` keeps PKCE + CSRF state only, in **`flow.json`** —
`tokens.json` would be imported and deleted mid-authorization.

### Pin consequence

The `/oauth` subpath arrived in 2.22.0, and 2.21.2+ peers on `pi-ai ^0.84.1`, so
the fix forced `pi-coding-agent` 0.83.0 → 0.84.2. `pi-subagents` is **held at
0.40.0** — 0.49.0 is a delegation rewrite; see the caveats page and live-runs.md.

### The OS keychain prompts, and signing is what settles it (2026-08-14)

Moving credentials into the keychain gave them an **ACL**: a list of binaries
allowed to read an item without asking. Everything else raises *"X wants to use
your confidential information stored in pi-mcp-adapter.oauth"*. Measured on this
machine, and the first reading of the evidence was wrong twice — record the
measurements, not the intuitions:

| binary | role | "Always Allow" sticks? |
| --- | --- | --- |
| `node` (signed) | the Pi child / agent, in dev (`pi-node.sh` falls back off-bundle) | **yes** — after one grant, an MCP call completes in ~1 s with no dialog |
| dev Electron helper (ad-hoc signed) | main's credential sidecar, in dev | **no** — re-prompts on every access |
| signed HappyVibe helper | both, in a packaged build | expected yes — untested, and the first thing to check once signing exists |

Two intuitions that turned out false, both cheap to re-derive and expensive to
believe: *"the binary that creates an item can always read it back"* (it cannot —
a probe item created by the helper still prompted the helper) and *"identity
alignment between the sidecar and the Pi child would fix it"* (it would not —
identity is not the variable; the signature is).

**The agent prompts too**, on its first MCP call per grant, and has since 2.17.0.
Main has never been in that path, so this is a property of the pin rather than of
main's rewrite — but it is the same root cause and the same fix.

Consequence for the product: the startup sweep no longer reads credentials.
Boot probes **stdio servers only**; remote servers are swept when the MCP page
mounts (`hv:mcp-sweep-remote`, latched once per app run). An app that opens
behind a password dialog is worse than a badge that resolves a moment after the
page opens. This is a UX improvement, NOT an amendment to §13's badge — the badge
still means what it meant.
