## Findings

### 1. pi-mcp-adapter loads and registers the `mcp` proxy tool

pi-mcp-adapter loaded successfully as a `-e` extension in `--mode rpc`. The adapter's
`shouldRegisterProxyTool` logic evaluated to `true` (workspace `.mcp.json` present with
one server, no `disableProxyTool` setting), so the `mcp` proxy tool was registered via
`pi.registerTool`. Pi's `tool_call` event fired for it and the bridge gate intercepted it.

### 2. Actual prefixed tool name: `mcp:echo_echo`

The adapter prefixes tool names with the **server key** from `mcpServers` plus an
underscore. For server key `echo` and tool `echo`, the result is `echo_echo`. The
`hv-mcp.ts` `unwrapMcpCall` reads `params.tool` off the proxy call's input and produces
`ruleTool: "mcp:echo_echo"`. This is what surfaced in the `hv.permission` prompt:

```json
{ "kind": "hv.permission", "tool": "mcp:echo_echo", "summary": "MCP → echo_echo" }
```

**Convention**: `mcp:<serverKey>_<toolName>` — rules should pattern-match accordingly
(e.g. `mcp:echo_*` to gate all echo-server tools; `mcp:github_*` for a GitHub MCP server
keyed `github`).

### 3. Discovery calls did NOT prompt

The model issued a discovery call (search/describe) before the invoke. The bridge's
`mcp?.kind === "discovery"` guard in `tool_call` safe-default-allowed it — no
`hv.permission` prompt was generated. The test's `nonInvoke` filter confirmed zero
unexpected prompts.

### 4. Config resolution — workspace `.mcp.json` honored

The adapter read `<cwd>/.mcp.json` (workspace-tier, written by the test). HOME and
XDG_CONFIG_HOME were redirected into the test's tmp dir so `~/.config/mcp/mcp.json` and
`~/.pi/agent/mcp.json` could not leak the developer's real servers. No other config
files were found, so the fixture echo server was the only one registered.

The app accepts the user-global read (`~/.config/mcp/mcp.json`) as intentional —
user-installed MCP servers should be visible across workspaces, consistent with
community-friendly behavior.

### 5. `ctx.hasUI` findings under RPC

The adapter's TUI-only paths (`/mcp` panel command, elicitation dialogs, sampling
dialogs) are all guarded by `ctx.hasUI`. Under `--mode rpc`, `ctx.hasUI` is `false`.
In this test run:
- The `/mcp` slash command was not called (not relevant to the proxy tool path).
- No elicitation or sampling was triggered (the echo tool has no elicitation schema).
- No crashes or visible errors from `ctx.hasUI`-guarded paths.
- All observable behavior came from the proxy tool's `execute()` branch, which is
  UI-agnostic. The guarded paths are silently skipped under RPC with no side effects.

**Open item**: the adapter's `/mcp` command does a `ctx.hasUI` check before showing
the panel UI. Under RPC it will likely log nothing or return an empty result. This is
not a blocker but should be replaced with an `hv-envelope` fallback (spec item) so the
renderer can show MCP status without a TUI. Tracked in docs/prd.md.

### 6. Open distribution item — stdio server runtime

The test configures the echo server as `{ command: process.execPath, args: [fixture] }`
(i.e. the Electron/Node binary). User-configured servers in production commonly use
`node` or `npx` as `command`. The packaged Electron app has no standalone `node` on
PATH, so servers with `command: "node"` will fail to spawn unless HappyVibe provides a
bundled runtime or rewrites `command` to the embedded binary. Same class as the
pi-subagents shebang item in CLAUDE.md. Open distribution item, not a V1 blocker.

## Phase 1 finding — HappyVibe main as the MCP management client

### Why the adapter cannot manage MCP from main or the bridge

The `pi-mcp-adapter`'s interactive OAuth is hard-gated on `ctx.hasUI`
(`pi-mcp-adapter/commands.ts:139`). Under `--mode rpc`, `ctx.hasUI` is `false`, so the
adapter's `/mcp` panel, elicitation dialogs, and auth flows are all silent no-ops.

The adapter's structured headless actions (auth-start, auth-complete, status, connect)
are exposed only on the `mcp` **tool**, not as RPC commands. Pi RPC's command union
(`modes/rpc/rpc-mode.js`) has no tool-execution verb — and neither does the ExtensionAPI.
This means neither main nor the bridge can invoke those tool actions programmatically;
only the **model** can call a tool during a conversation turn.

### Consequence: main owns MCP management

HappyVibe main is the MCP **management** client — connect, list-tools, and status queries
are handled by `src/main/mcpClient.ts` via `@modelcontextprotocol/sdk` (Client +
StdioClientTransport). Phase 1 scope: connect / list-tools / status / startup-check /
reconnect. OAuth + add-time confirmation is Phase 2.

The vendored pi-mcp-adapter stays the **in-session runtime path**: model tool calls →
proxy tool → permission gate → execute.

### Shared state: on-disk token store only

Main and the adapter share state exclusively on disk at:

```
<agentDir>/mcp-oauth/sha256-<sha256hex(serverName)>/tokens.json
```

`src/main/mcpAuthStore.ts` mirrors the `AuthEntry` format from `pi-mcp-adapter/mcp-auth.ts`
so Phase 2 OAuth tokens written by main are readable by the adapter and vice versa.
No in-memory coupling; no IPC coupling.

### Architecture summary

```
main  ──mcpClient.ts──► @modelcontextprotocol/sdk ──► MCP server (stdio)
                             connect / list-tools / status

Pi session ──adapter──► proxy tool ──bridge gate──► execute  (model-driven)
                                        ↑ hv.permission prompt

shared state: <agentDir>/mcp-oauth/sha256-*/tokens.json  (AuthEntry)
```

### Phase 1 scope

Connect, list-tools, status, startup sweep (non-blocking probe of all configured
servers at session start), reconnect via IPC `hv:mcp-reconnect`.
IPC: `hv:mcp-status` (full map), `hv:mcp-status-changed` (push update).
Renderer: status badge per server + reconnect button.

OAuth (`src/main/mcpOAuth.ts`), `hv:mcp-authenticate` / `hv:mcp-logout`, add-time
confirm-with-tools modal, and the `tests/mcp-adapter-authformat.test.ts` contract test
are Phase 2.
