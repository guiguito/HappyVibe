# S0.2 — Risk Spike: OAuth login (`/login`) over RPC

**Date:** 2026-07-05
**Spike:** S0.2 — can Pi's OAuth login flows be driven over RPC, or must HappyVibe implement OAuth in-app? Unblocks B3 (providers & onboarding).
**Pi version:** `@earendil-works/pi-coding-agent@0.80.3` (vendored pin)

## Verdict: YES — RPC can drive OAuth login end-to-end, via a bridge extension command

There is **no native RPC `login` command**, and the TUI `/login` is intercepted in interactive mode only (same class of TUI-only-ness as pi-permission-system, V6). **But** unlike V6, the underlying machinery — `AuthStorage.login(providerId, callbacks)` — is UI-agnostic and **exposed to extensions** via `ctx.modelRegistry.authStorage`. A bridge-registered command maps the login callbacks onto `ctx.ui.input/select/notify`, all of which surface over the proven `extension_ui_request` wire.

**Proven empirically 2026-07-05** with a probe extension + RPC driver (no real accounts logged in; flows aborted after the provider issued a real device code / auth URL):

| Provider id | Flow | Evidence over RPC wire |
|---|---|---|
| `github-copilot` | device code | `input` request "GitHub Enterprise URL/domain…" → answered `""` → notify with real code `C152-28DB` @ `https://github.com/login/device` |
| `anthropic` | browser PKCE + localhost callback | notify with real auth URL `https://claude.ai/oauth/authorize?…redirect_uri=http://localhost:53692/callback…` |
| `openai-codex` | user choice | `select` request "Select OpenAI Codex login method:" `["Browser login (default)", "Device code login (headless)"]` → picked device → notify with real code `OC0E-KC34D` @ `https://auth.openai.com/codex/device` |

And the negative probe: sending `{"type":"login"}` as an RPC command returns
`{"type":"response","command":"login","success":false,"error":"Unknown command: login"}`.

Probe files: scratchpad `s02-login-ext.ts` (extension) + `s02-probe.mjs` (driver); run against a temp `PI_CODING_AGENT_DIR`, user's real `~/.pi` untouched.

## 1. RPC command surface (0.80.3) — no login command

Enumerated from `dist/modes/rpc/rpc-types.d.ts` (`RpcCommand` union, lines 14–130):

`prompt, steer, follow_up, abort, new_session, get_state, set_model, cycle_model, get_available_models, set_thinking_level, cycle_thinking_level, set_steering_mode, set_follow_up_mode, compact, set_auto_compaction, set_auto_retry, abort_retry, bash, abort_bash, get_session_stats, export_html, switch_session, fork, clone, get_fork_messages, get_entries, get_tree, get_last_assistant_text, set_session_name, get_messages, get_commands`

No auth/login/logout command exists. `dist/modes/rpc/rpc-mode.js` contains zero references to login.

**The RPC escape hatch:** `prompt` with a `/name` message executes **extension commands** before anything reaches the LLM — `dist/core/agent-session.js:731–745` (`prompt()` → `_tryExecuteExtensionCommand(text)`, returns early when handled). This is how the bridge's login command is invoked over RPC. Extension commands are discoverable via `get_commands` (probe confirmed `extension:hv-login` listed).

## 2. How `/login` works in the TUI, and what's reusable

- `dist/modes/interactive/interactive-mode.js:2108` — `if (text === "/login")` → `showOAuthSelector("login")` → provider selector → `showLoginDialog()`. Pure TUI component code; none of it runs in RPC mode.
- The dialog ultimately calls `this.session.modelRegistry.authStorage.login(providerId, callbacks)` (`interactive-mode.js:4108`) — and **that** call is mode-independent.
- `AuthStorage.login` (`dist/core/auth-storage.js:312–319`): looks up the OAuth provider, runs `provider.login(callbacks)`, then `this.set(providerId, { type: "oauth", ...credentials })` — which updates the in-memory credential map **and** persists to auth.json in one step. So a login performed inside the running RPC subprocess is live immediately (the `hasConfiguredAuth` preflight in `prompt()` passes without restart).
- Extensions receive `ctx.modelRegistry` (typed `ModelRegistry`, `dist/core/extensions/types.d.ts:220`) and `ModelRegistry.authStorage` is public (`dist/core/model-registry.d.ts:27`).
- The callback contract (`pi-ai/dist/utils/oauth/types.d.ts`, `OAuthLoginCallbacks`): `onAuth(url+instructions)`, `onDeviceCode(userCode/verificationUri/interval)`, `onPrompt(message/placeholder) → string`, `onSelect(options) → id`, `onManualCodeInput() → string`, `onProgress(message)`, `signal?: AbortSignal`. Every one of these maps 1:1 onto RPC-capable `ctx.ui` methods (`dist/modes/rpc/rpc-mode.js:82–...`: `select`, `confirm`, `input`, `editor` are full round-trip dialogs; `notify` is fire-and-forget).

## 3. auth.json — location, format, schema

- **Path:** `~/.pi/agent/auth.json`; the whole agent dir is overridable via env `PI_CODING_AGENT_DIR` (`dist/config.js:397, 412–418, 429`).
- **Format:** pretty-printed JSON (`JSON.stringify(merged, null, 2)`), file mode `0o600`, guarded by a lock file during read-modify-write (`auth-storage.js:16, 209–228`). No keychain, no encryption, no signing.
- **Top-level shape** (`auth-storage.d.ts:9–18`): `Record<providerId, ApiKeyCredential | OAuthCredential>`

```jsonc
{
  "deepseek":       { "type": "api_key", "key": "sk-...", "env": { /* optional provider env */ } },

  "anthropic":      { "type": "oauth",
                      "refresh": "<refresh_token>",
                      "access":  "<access_token — used directly as the API key>",
                      "expires": 1751700000000 },   // ms epoch = now + expires_in*1000 − 5min skew (anthropic.js:181–185)

  "github-copilot": { "type": "oauth",
                      "refresh": "<GitHub OAuth access token (long-lived; used to mint Copilot tokens)>",
                      "access":  "<short-lived Copilot bearer token>",
                      "expires": 1751700000000,     // expires_at*1000 − 5min (github-copilot.js:210–214)
                      "enterpriseUrl": "company.ghe.com",        // optional, only for GHE
                      "availableModelIds": ["gpt-5", "..."] },   // refreshed on every token refresh

  "openai-codex":   { "type": "oauth",
                      "refresh": "<refresh_token>",
                      "access":  "<access token (JWT)>",
                      "expires": 1751700000000,
                      "accountId": "<chatgpt_account_id extracted from the JWT>" }  // openai-codex.js:319–335
}
```

`OAuthCredentials` is `{ refresh, access, expires, [key: string]: unknown }` — extra per-provider fields ride along and are round-tripped on refresh.

**Token refresh is automatic**: `AuthStorage.getApiKey()` (`auth-storage.js:374–420`) refreshes when `Date.now() >= expires`, under the file lock (re-reads auth.json inside the lock, so concurrent Pi instances cooperate — `refreshOAuthTokenWithLock`, `auth-storage.js:330–366`). Resolution priority: runtime `--api-key` override → auth.json api_key → auth.json oauth (auto-refresh) → env var.

## 4. Fallback: writing auth.json directly — viable, with one freshness caveat

- The file is plain JSON with no coupling to keychain/encryption — writing `{ "<provider>": { "type": "oauth", refresh, access, expires, ... } }` (or an `api_key` entry) is exactly what Pi itself does.
- **Caveat:** `AuthStorage` loads the file **once at process start** (constructor → `reload()`, `auth-storage.js:155`); nothing re-reads it per request. Exceptions: the locked refresh path re-reads under lock, and refresh-failure re-reads (`auth-storage.js:403`). So writing auth.json is sufficient **if written before spawning Pi**, or if the running Pi is respawned afterwards. A bridge command calling `ctx.modelRegistry.authStorage.reload()` would also pick up external writes without a respawn.
- Not needed as the primary path — in-process login via the bridge (above) updates memory + disk atomically.

## Recommended B3 design

1. **Extend `happyvibe-bridge.ts`** with `pi.registerCommand("hv-login", …)` (and `hv-logout` → `authStorage.logout(provider)`, `hv-auth-status` → `authStorage.getAuthStatus(provider)` which never leaks credential values). Renderer invokes via the existing PiClient: `{"type":"prompt","message":"/hv-login <provider>"}`.
2. **Callback → wire mapping** inside the command handler (proven by the probe):
   - `onPrompt` → `ctx.ui.input(message, placeholder)` — surfaces as `extension_ui_request` `method:"input"`, answered with `{value}` (same response shape as `select`).
   - `onSelect` → `ctx.ui.select(message, labels)`, map label back to option id.
   - `onAuth` / `onDeviceCode` / `onProgress` → `ctx.ui.notify` with a structured JSON payload (reuse the `{"kind":"hv.…"}` title convention from `hv.permission`) so the renderer can render a "device code" card / open the URL via `shell.openExternal`.
   - `onManualCodeInput` → `ctx.ui.input` raced against the callback server (return a promise; Anthropic/Codex browser flows resolve whichever finishes first).
   - Wire an abort path (`callbacks.signal`) to a bridge `hv-login-cancel` command or a `cancelled: true` ui-response so a user can back out.
3. **No respawn needed after login** — `AuthStorage.set()` makes credentials live in the running session; `set_model`/`get_available_models` work immediately after.
4. **Localhost callback servers** (`53692` Anthropic, `1455` Codex) run inside the Pi subprocess — nothing for Electron to host; the OS browser redirects back to the subprocess.
5. Keep direct auth.json writes as the **fallback/import path** (e.g. BYOK API keys at onboarding): write before spawn, schema above.
