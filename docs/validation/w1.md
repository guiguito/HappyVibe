# W1 — the web service, as measured (§32 Web tools)

Everything here was **measured against the live service**, not read off
documentation. Re-measure with:

```bash
node scripts/web-service-probe.mjs [baseUrl] [apiKey]
```

That script is **manual only** — it hits a real server, so it is deliberately
not a test and never runs in CI. Run it after a service upgrade, after a config
change on the box, and **before believing any live-test failure that might be
the box rather than the code**. That last case is why it exists:
`d1.md §pi-subagents 0.50` records four "shape regressions" that were all one
dead provider account.

Service: `https://firecrawl.bzapps.eu` (Firecrawl-compatible **v2** API).
Probed 2026-09-03, re-probed 2026-09-04 after SearXNG was enabled.

## What works, and what the design does about it

| Capability | Measured | Consequence in the app |
| --- | --- | --- |
| `GET /` | `{"message":"Firecrawl API","documentation_url":"https://docs.firecrawl.dev"}`, 76 ms | The settings **Test** button. `probe()` requires that greeting, so a random web server that answers 200 is reported as "not a compatible web service". |
| `http://` anywhere | **nginx 404** | The client is https-only. This is also why a returned `http://` job URL is never followed. |
| Authentication | **none** — no key, any key and a bogus key all accepted | The service is open to whoever has the URL, which an open-source app publishes. Rate limiting is on the box (PRD §32); the app only explains a 429. |
| `POST /v2/scrape` | works. `onlyMainContent` defaults true, `maxAge` defaults 2 days | `web_fetch`. PDFs come back as markdown for free. |
| `POST /v2/search` | works, **SearXNG-backed since 2026-09-04** | `web_search`. See the search table below. |
| `POST /v2/map` | works | `web_map`. Links come back as `{url}` objects (sometimes bare strings — the client accepts both). |
| `POST /v2/crawl` → `GET /v2/crawl/{id}` → `DELETE` | works, async job, results expire after 24 h | `web_crawl`. Poll semantics are the interesting part — see below. |
| `GET /v2/concurrency-check` | **`maxConcurrency: 2`**, server-wide | Two scrapes at a time for every HappyVibe install **combined**. Every cap and the crawl cancel path are sized by this one number. |
| A 404 page | `success: true` + `metadata.statusCode: 404` | The page's own status is reported **separately** from the call's, or a model quotes an error page as documentation. |
| A private address | `success: false`, `code: BAD_REQUEST` | Belt only: the bridge refuses `localhost` and RFC 1918 **before** the gate, naming `browser_open`. A refusal with no reason is the thing this product exists to avoid. |
| `screenshot` format | `"The engine used does not support the following features: screenshot -- your scrape may be partial."` — silently degraded, not an error | Out. §28's `browser_screenshot` exists for that. Note it does **not** fail, so a caller that ignored `warning` would think it worked. |
| `actions` (click/type/wait) | `SCRAPE_ACTIONS_NOT_SUPPORTED` | Out. §28 does interaction. |
| `json` format | `BAD_REQUEST` (no LLM key on the box) | Out, and wanted out: the session model reads the text, so there is no hidden second model and no hidden spend. |
| Credits / usage endpoints | error (no DB) | Nothing to show as a quota. Cost is shown as context tokens, our own number. |

**Not available and not designed around:** screenshots, actions, LLM formats
(`json`/`summary`), `/v2/extract` (deprecated upstream), change tracking,
branding, monitors, interact sessions, webhooks. If an LLM key or fire-engine is
ever enabled on the box, each becomes its own decision, never a side effect of
this round.

## Search — SearXNG landed, and it fixed the one measured weakness

Before SearXNG the box fell back to DuckDuckGo scraping (upstream's chain is
Fire Engine → SearXNG → DuckDuckGo, and Fire Engine is cloud-only). The
weakness then was thin or empty snippets on generic queries. Re-measured
2026-09-04 with SearXNG on:

| Query | Results | With a snippet | First result |
| --- | --- | --- | --- |
| `vitest mock fetch injected` | 5 | **5** | `vitest.dev/guide/mocking` |
| `electron` (the generic one that used to come back with empty snippets) | 3 | **3** | `electronjs.org/` |
| `site:electronjs.org WebContentsView` | 3 | **3** | `electronjs.org/docs/latest/api/web-contents-view` |

Latency 0.36–2.0 s. Snippets arrive around 130–164 chars, capped by the
adapter's `content` → `description` mapping, which is why `includeContent`
exists for when a snippet is not enough.

**`tbs` recency is still ignored**, with SearXNG as without it: a past-week
filter returns undated documentation pages. Upstream never maps `tbs` onto
SearXNG's `time_range`, so **`recency` stays out of V1 permanently** rather than
pending — a filter the backend ignores would let the tool claim a freshness it
cannot deliver. `sources: ["images"]` is likewise ignored and returns web
results; `sources`/`categories` are cloud features and are not exposed.

## Latency and size — the numbers the caps are set from

| Measurement | Value |
| --- | --- |
| `example.com`, cached | 291 ms |
| `example.com`, `maxAge: 0` | 191 ms |
| A real docs page (`docs.firecrawl.dev/features/scrape`, 55,336 chars), fresh | 4,034 ms |
| The same page, cached (three consecutive calls) | 2,055 / 1,877 / 1,646 ms |
| Wikipedia "Electron" | **270,125 chars** of markdown |
| `map` on a real docs site, 20 links | 2,373 ms |
| **A full 30-page crawl** (`docs.firecrawl.dev`, the `web_crawl` maximum) | **32.0 s**, 20 polls, 30 unique pages, `completed` |

Two things to take from this. A tiny page is ~200 ms either way, so the
"cached is instant" intuition comes from toy URLs; a **real** page is ~2 s
cached and ~4 s fresh. And a 30-page crawl finishes in 32 s, comfortably inside
`web_crawl`'s 120 s deadline — the deadline is there for a slow or contended
box, not for the normal case.

270,125 chars against `web_fetch`'s 16,000-char default is the whole argument
for paging: that page is ~17 windows, and the header tells the model the total
and the next `startIndex` so it can choose rather than being truncated blind.

## The crawl job — why the obvious implementation is wrong

Written from the docs first and measured second. The measurement found two bugs
a hand-written fixture would never have shown.

```jsonc
// POST /v2/crawl → { "success": true, "id": "01a0…", "url": "http://firecrawl.bzapps.eu/v2/crawl/01a0…" }
// GET  /v2/crawl/{id} → { "status": "scraping",  "total": 1, "completed": 1, "data": [<page>],      "next": "http://…?skip=1" }
// GET  /v2/crawl/{id} → { "status": "scraping",  "total": 1, "completed": 1, "data": [<same page>], "next": "http://…?skip=1" }
// GET  /v2/crawl/{id} → { "status": "completed", "total": 1, "completed": 1, "data": [<same page>] }
```

1. **`data` is the accumulated slice from the requested offset**, not the pages
   completed since the last poll. Three consecutive polls of a one-page crawl
   each returned that same page, so appending what arrives duplicates every
   page once per poll.
2. **`next` is offered while `status` is still `"scraping"`** — and even on a
   poll that returned zero rows. Treating it as "there is more, fetch it now"
   is an unsleeping loop against a service with two worker slots for every
   install combined.

So `webService.crawl` keeps **its own cursor** (`skip` = records consumed, which
is exactly what `next` encodes) and never touches the returned job URL — which
also disposes of its `http://` scheme. The drain breaks on **new pages**, not on
an empty slice: a service that ignored `skip` and re-sent everything would
satisfy `rows.length > 0` forever, so an empty-slice condition is an infinite
loop waiting for a service upgrade. A `seen` set makes a re-sent slice harmless
either way.

Verified against the real service on the 30-page crawl above: **30 unique pages,
no duplicates**, arriving 1–4 per round across 20 polls.

## Failure shapes

Readable sentences with codes, which is why tool results surface the service's
own message rather than a stack trace:

- `SCRAPE_DNS_RESOLUTION_ERROR` — `"DNS resolution failed for hostname: …"`
- `SCRAPE_TIMEOUT`, `SCRAPE_ALL_ENGINES_FAILED`
- `BAD_REQUEST` for a private address or an unavailable format

The client maps **429 and a code-less 5xx** to its own `UNAVAILABLE`, because
"come back later" is a different sentence from "no such page" — and on the
**default** service that is the one the user sees, pointing at Settings →
Built-in tools. On a custom service they own the box, so they get the raw
reason.

## Wire shapes and the app side

The `hv.web-*` envelopes, the `hv.web-cancel` notify, the gate table and the
`web.call` EventLog row are in **`d1.md` §Web tools**. The measured fact worth
repeating here: Pi **does** fire `execute`'s `AbortSignal` on an interrupted
turn, so the cancel path is live code — without it an abandoned crawl holds one
of the two shared slots for its full two minutes.

## Resting context cost — measured in the running app (2026-09-04)

Read off the context panel's **Tool definitions** drill-in, which is the number
the user sees, in a session where all four tools were registered:

| Tool schema | Estimated tokens |
| --- | --- |
| `web_crawl` | 307 |
| `web_fetch` | 276 |
| `web_search` | 231 |
| `web_map` | 163 |
| **All four** | **≈977** |

Against **≈10,481** for every tool definition in that session, so the group is
about **9%** of the tool-schema budget — which is what turning the switch off
actually saves, and the honest version of the row's own "saves the context cost
of four tool schemas". For scale, `web_crawl` is the second-largest schema in
the session after the MCP proxy's (`mcpScript`, 363), because it carries six
optional parameters and their caps.

## Verified in the running app (GUI pass, 2026-09-04)

Against the **real** service and a real model, not a harness:

- a `web_fetch` of a fresh host raised **one** prompt, headlined `Web:
  example.com`, with `browser:example.com` and `https://example.com` under
  DETAILS and the model's own sentence nowhere in it;
- the card read the model's intent, carried the URL as a chip, and previewed
  `Read https://example.com (title: "Example Domain", status 200, 180 chars
  total, showing 0–180).` with **no** UNTRUSTED line on the face;
- **"Allow for session" covered a second page on the same host** — no second
  prompt;
- `https://example.com/index.html` really answers **404**, so the page-status
  branch fired live: the card added *"The page answered 404 — the text below may
  be an error page."* and the model reported the 404 rather than quoting the
  body as fact;
- the **pane's own Allow button is per-pane**, as specified: clearing
  `example.org` in a browser pane and then asking for a `web_fetch` of that same
  host **still prompted**;
- `web_search` is `ALLOW` on the Agent tools page while the three URL tools are
  `ASK`; with the group off and after the respawn, **no `web_*` tool is listed**
  and §26's and §28's groups are untouched;
- the word "Firecrawl" appears **nowhere** on the Built-in tools page until
  "Your own" is chosen, and then only inside the one helper line.

One claim the GUI pass **disproved**, recorded because it was written down
first: the "Web" label does **not** reach the Permissions page or the audit log.
`PermissionRulesSection` renders `r.pattern` into an editable input and
`AuditView` renders `r.tool`, both verbatim — and both are right to, one being
a rule editor and the other a record. The label lives on the permission prompt.
Pinned by `tests/hv-web.test.ts`.

## Version drift

The self-host guide pins `v2.11.162`. Nothing in the client depends on that
version string, but the **request shapes** are pinned by
`tests/web-service.test.ts` (key-free, in the non-live suite) so a service that
changes them fails there rather than drifting in production. If that test goes
red after a service upgrade, re-run the probe script first and update this file.
