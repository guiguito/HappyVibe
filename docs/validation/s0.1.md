# S0.1 Risk Spike — Parallel Pi Process Cost & Safety

## Verdict: SAFE — memory is not the binding constraint; recommend default cap 4, hard cap 8

N parallel Pi RPC processes are cheap (~140 MB idle, ~200 MB active each), fully isolated on disk (uuidv7-named session files, no shared writes at runtime), and leave no orphans, ports, or tmux state. The only concurrency cost observed is CPU contention at spawn time (ready latency 0.7 s solo → ~3.7 s when 8 spawn simultaneously).

## Numbers

Measured 2026-07-05 on macOS (arm64), Pi 0.80.3 spawned exactly like the app (RPC mode + happyvibe-bridge extension, `deepseek-v4-flash`), RSS via `ps -o rss=` (process tree summed — Pi spawned no children).

### Memory per process (RSS)

| State | N=1 | N=4 (diff dirs) | N=8 (same dir) |
|-------|-----|-----------------|----------------|
| Idle after spawn+ready | 164 MB | 165–167 MB | 115–148 MB (avg ~124) |
| After `new_session` | 164 MB | 166–176 MB | 126–154 MB |
| After one tiny real prompt | 190 MB | 191–193 MB | 169–179 MB (2 procs measured) |

Budget figure: **~200 MB per active session**. 8 concurrent active sessions ≈ 1.6 GB.

### Spawn → ready latency (spawn to first `get_state` response)

| Concurrent spawns | Ready latency |
|-------------------|---------------|
| 1 | 713 ms |
| 4 | 1.4–1.5 s |
| 8 | 3.3–3.9 s |

Startup is CPU-bound (Node boot + TS extension load), so simultaneous spawns contend. Staggering spawns by ~1 s would keep each near the solo number.

Real-prompt round trip (`prompt` → `agent_end`, one-word reply): 1.1–1.9 s.

## Shared-state safety

- **Session files**: Pi writes one JSONL per session to `~/.pi/agent/sessions/<encoded-cwd>/<ISO-timestamp-ms>_<uuidv7>.jsonl` (or to `--session-dir` when passed, as the app does). Each process generates its own uuidv7 session id and only ever appends to its own file — no shared file, no clobbering possible. Empirically: 2 processes prompting concurrently in the SAME workspace dir produced 2 distinct files; in the diff-dir run two files even shared the same millisecond timestamp and still had unique names (uuid suffix).
- **No session file is created until content is written** — idle processes touch nothing on disk.
- **Same dir vs different dirs**: no behavioral difference. Same-cwd processes share only the session *directory*, never a file. Different cwds get different encoded directories entirely.
- **Locks**: no `.lock` files observed. Code inspection: Pi's trust-manager uses `proper-lockfile` for `~/.pi` trust writes (interactive-mode only — never triggered over RPC in these runs); settings-manager/auth-storage writes are unlocked but are read-only during normal RPC operation. Runtime session appends need no lock because files are per-process.
- **Workspace dir**: Pi wrote zero files into the workspace cwd itself.

## Surprises / hazards

- **None serious.** Specifically checked:
  - **Orphans/zombies**: `pgrep -f pi-coding-agent` empty after `kill()` in every run; all exits clean (SIGTERM, code 143). No child processes under any Pi process at idle or after prompts.
  - **Ports**: no listening sockets; only an outbound HTTPS keep-alive to the DeepSeek API during/after a prompt.
  - **tmux**: not used.
- **Spawn-storm latency** is the one real finding: 8 simultaneous spawns quintuple ready latency. Mitigation is trivial (stagger, or pre-warm a small pool).
- RPC mode has a `kill_shell`-style cleanup path (`killTrackedDetachedChildren`) for detached bash children; not exercised here since no tool calls ran, worth re-checking in B1 if sessions run long shell commands.

## Method

Throwaway Node harness (scratchpad, not committed): spawns N Pi processes with the exact app args (`--mode rpc -e happyvibe-bridge.ts --provider deepseek --model deepseek-v4-flash`), per-run temp workspaces, measures ready latency via `get_state` round-trip, RSS via `ps -o rss=` on the process tree at idle / after `new_session` / after a one-word real prompt (2 processes max per run to limit API spend), diffs `~/.pi/agent/sessions` before/after, checks `lsof -i`, `pgrep -P`, and orphan `pgrep` after kill. Runs: N=1 same +1 prompt, N=4 same, N=8 same +2 prompts, N=4 diff dirs +2 prompts.

## Implications for B1 (session manager)

- **Recommended default concurrency cap: 4**, hard cap **8**, on a 16 GB baseline Mac.
  - Reasoning: memory alone would allow 20+ (8 active sessions ≈ 1.6 GB vs ~6–8 GB realistic headroom next to Electron + browser + OS). The cap is therefore set by UX/CPU/API-spend, not RAM: 4 concurrent agents is the most a user meaningfully supervises with permission modals, and 8 simultaneous spawns already show 5× spawn-latency contention. 4 default / 8 max leaves memory headroom even on an 8 GB machine (~1.6 GB worst case).
- Stagger process spawns (~1 s apart) or lazy-spawn per session; do not pre-spawn 8 at once.
- No cross-process coordination (locks, single-writer daemon) is needed for session files — per-process uuidv7 files make same-project parallel sessions safe by construction. Keep passing `--session-dir` per session as the app already does.
- Always `kill()` on session close; SIGTERM is sufficient and leaves no orphans.
