## Adaptation note — JSONL reader timing

During `session_start`, Pi's JSONL stdin reader is not yet attached (it's set up synchronously after `rebindSession()` returns). Calling `ctx.ui.confirm()` directly inside the `session_start` handler creates a pending promise with no active stdin reader — the Node.js event loop empties and Pi exits with code 0 before processing any response.

**Fix**: The probe extension fires the confirm asynchronously (detached via `void (async () => {...})()`) and returns synchronously from `session_start`. A 50ms delay ensures `rebindSession()` has completed and the JSONL reader is attached before `confirm()` emits `extension_ui_request`. Task 6/10 implementations MUST use the same async-detached pattern (or hook a later lifecycle event) when calling `ctx.ui.*` from RPC mode.

## B4 wire shapes — hv.audit / hv.rules / hv.dangerous (2026-07-05)

All three ride `ctx.ui.notify`, which surfaces over RPC as a **fire-and-forget** `extension_ui_request` with `method: "notify"` — no `extension_ui_response` is ever written (responding is a protocol error; main must only parse). The JSON payload rides the `message` field (notify carries JSON in `message`; input/select carry it in `title` — same convention as `hv.auth`).

### hv.audit — one notify per permission decision (bridge → main → EventLog)

**Verbatim `extension_ui_request` observed in rules-bridge.test.ts (real RPC, rule-deny of `touch forbidden.txt`):**

```json
{"type":"extension_ui_request","id":"…","method":"notify","message":"{\"kind\":\"hv.audit\",\"ts\":\"2026-07-05T…Z\",\"tool\":\"bash\",\"summary\":\"touch forbidden.txt\",\"decision\":\"deny\",\"source\":\"rule\",\"rule\":{\"layer\":\"command\",\"pattern\":\"touch *\",\"action\":\"deny\",\"scope\":\"global\"}}","notifyType":"info"}
```

Payload fields:

| field | values |
|-------|--------|
| `kind` | `"hv.audit"` (constant) |
| `ts` | ISO 8601, written by the bridge at decision time |
| `tool` | Pi tool name (`bash`, `write`, …) |
| `summary` | bash command or JSON'd input, ≤300 chars |
| `decision` | `"allow"` \| `"allow-session"` \| `"deny"` |
| `source` | `"rule"` \| `"user"` \| `"dangerous"` \| `"safe-default"` |
| `rule?` | `{layer, pattern, action, scope: "global"\|"workspace"}` — only when `source: "rule"` |
| `grant?` | `"session"` — user allow riding an earlier "Allow for session" grant |

Main (`src/main/ipc.ts`) intercepts these before renderer forwarding and appends them to the EventLog as `type: "permission.decision"` with `sessionId`/`workspaceId` — the payload above becomes the event's `data`.

### hv.rules — /hv-rules-reload acknowledgment

Rules file (`permission-rules.json` in userData, `{global: Rule[], workspaces: Record<absWorkspacePath, Rule[]>}`) reaches the bridge via the `HV_RULES_FILE` spawn env var. Main rewrites the file on UI edits then broadcasts the `/hv-rules-reload` slash command (fire-and-forget RPC prompt) to every live session.

```json
{"kind":"hv.rules","stage":"loaded","global":1,"workspaces":1}
{"kind":"hv.rules","stage":"error","message":"<parse error>"}
```

On parse error the bridge KEEPS the previous ruleset — a torn write never fails open.

### hv.dangerous — /hv-dangerous on|off acknowledgment

```json
{"kind":"hv.dangerous","on":true}
{"kind":"hv.dangerous","stage":"error","message":"Usage: /hv-dangerous on|off"}
```

Per-session, in-bridge-memory only — never persisted, always off after respawn. The renderer drives its warning banner from this notify (forwarded through `hv:ui-request` like all non-audit requests).

Contract coverage: `tests/rules-bridge.test.ts` (reload + dangerous need no model; the rule-deny hv.audit contract is DEEPSEEK-gated like bridge.test.ts).
