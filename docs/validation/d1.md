## Adaptation note — JSONL reader timing

During `session_start`, Pi's JSONL stdin reader is not yet attached (it's set up synchronously after `rebindSession()` returns). Calling `ctx.ui.confirm()` directly inside the `session_start` handler creates a pending promise with no active stdin reader — the Node.js event loop empties and Pi exits with code 0 before processing any response.

**Fix**: The probe extension fires the confirm asynchronously (detached via `void (async () => {...})()`) and returns synchronously from `session_start`. A 50ms delay ensures `rebindSession()` has completed and the JSONL reader is attached before `confirm()` emits `extension_ui_request`. Task 6/10 implementations MUST use the same async-detached pattern (or hook a later lifecycle event) when calling `ctx.ui.*` from RPC mode.

## B4 wire shapes — hv.audit / hv.rules / hv.dangerous (2026-07-05)

All three ride `ctx.ui.notify`, which surfaces over RPC as a **fire-and-forget** `extension_ui_request` with `method: "notify"` — no `extension_ui_response` is ever written (responding is a protocol error; main must only parse). The JSON payload rides the `message` field (notify carries JSON in `message`; input/select carry it in `title` — same convention as `hv.auth`).

### hv.audit — one notify per permission decision (bridge → main → EventLog)

**Verbatim `extension_ui_request` observed in rules-bridge.test.ts (real RPC, rule-deny of `touch forbidden.txt`):**

```json
{"type":"extension_ui_request","id":"…","method":"notify","message":"{\"kind\":\"hv.audit\",\"ts\":\"2026-07-05T…Z\",\"tool\":\"bash\",\"summary\":\"touch forbidden.txt\",\"decision\":\"deny\",\"source\":\"rule\",\"rule\":{\"layer\":\"command\",\"pattern\":\"touch *\",\"action\":\"deny\",\"scope\":\"global\"}}","notifyType":"info"}
```

Payload fields:

| field | values |
|-------|--------|
| `kind` | `"hv.audit"` (constant) |
| `ts` | ISO 8601, written by the bridge at decision time |
| `tool` | Pi tool name (`bash`, `write`, …) |
| `summary` | bash command or JSON'd input, ≤300 chars |
| `decision` | `"allow"` \| `"allow-session"` \| `"deny"` |
| `source` | `"rule"` \| `"user"` \| `"bypass"` \| `"safe-default"` \| `"plan"` \| `"terminal"` |
| `rule?` | `{layer, pattern, action, scope: "global"\|"workspace"}` — the matching rule; on a bypassed row, the rule that WOULD have matched |
| `grant?` | `"session"` — user allow riding an earlier "Allow for session" grant |
| `wouldHave?` | `"allow"` \| `"ask"` \| `"deny"` — round 15, bypassed rows only |

Main (`src/main/ipc.ts`) intercepts these before renderer forwarding and appends them to the EventLog as `type: "permission.decision"` with `sessionId`/`workspaceId` — the payload above becomes the event's `data`.

**Round 15 — `dangerous` became `bypass`, and a bypassed row records the verdict it overrode.** With a bypass active every single call logged `source:"dangerous"`, rendered in red, so the column named the *mode* once per row and distinguished nothing — reported as "everything ends up being marked as dangerous so this info ends up being useless". Two changes: the value is now `bypass` (calm colour; red is reserved for what a command DOES, i.e. the card's destructive badge), and the branch runs the rule engine anyway and reports `wouldHave` — the verdict a bypass-free session would have reached. `wouldHave` is the ENGINE's `RuleAction`, which has an `"ask"` that `decision` does not: a prompt is not an outcome, and mapping it onto one would be the exact lie the field exists to prevent.

**Old logs keep the old string.** Nothing rewrites history, so `AuditView` maps both `dangerous` and `bypass` to one label and one filter value, and `analytics.ts` folds them into a single `bySource` bucket — otherwise one fact appears as two half-sized buckets either side of the rename. Pinned by `tests/oneshot-audit.test.ts`.

## B5 wire shapes — hv.context / hv-context-marks (2026-07-07)

Context visibility rides the same fire-and-forget `ctx.ui.notify` channel as B4
(JSON in the `message` field; the renderer parses it and NEVER opens the modal).
Three `/hv-context*` bridge commands are driven from main via RPC `prompt`
(B3/B4 precedent); their replies stream back as `hv.context` notifies.

### Mark identity (the crux)

The panel identifies items by session-entry id (from `get_entries`), but the
`context` event — the only place removal takes effect — hands the bridge an
`AgentMessage[]` with NO entry ids. The only ids present in BOTH are:

- `toolCall.id` / `toolResult.toolCallId` → mark key `tool:<id>` (a pair)
- `message.timestamp` → mark key `msg:<ts>` (plain user/assistant messages)

So the renderer sends **mark keys**, not entry ids. Pairing is automatic:
`tool:<id>` drops the assistant's toolCall block AND the matching toolResult
(atomic), so selecting either half removes both.

### hv.context — snapshot (reply to /hv-context)

```json
{"kind":"hv.context","stage":"snapshot",
 "system":{"chars":8123,"estTokens":2031,"toolCount":4,
   "contextFiles":[{"path":"/ws/AGENTS.md","chars":512,"estTokens":128}],
   "toolDefs":[{"name":"read","chars":420},{"name":"bash","chars":880}]},
 "items":[
   {"markKey":"msg:1730000000000","entryId":"e1","group":"conversation","role":"user","preview":"turn one","chars":8,"estTokens":2,"removable":true},
   {"markKey":"tool:call-A","entryId":"e2","group":"tool","role":"assistant","toolName":"bash","toolCallId":"call-A","preview":"bash({\"command\":\"ls\"})","chars":21,"estTokens":6,"usage":{"input":100,"output":20,"total":120},"removable":true},
   {"markKey":"tool:call-A","entryId":"e3","group":"tool","role":"toolResult","toolName":"bash","toolCallId":"call-A","preview":"ok","chars":2,"estTokens":1,"removable":true}
 ],
 "marks":["tool:call-A"]}
```

- `system` is `null` until the first turn runs (captured at `before_agent_start`).
- Item sizes (`chars`/`estTokens`) are char-based ESTIMATES (≈ chars/4), labeled
  as such in the UI; `usage.total` on assistant items is MEASURED.
- `removable` reflects the completed-turn gate (s0.3): items at/after the last
  user message (the in-flight turn) are `false`. The bridge refuses to mark them.
- **v5:** `system.toolDefs[]` gives per-tool ESTIMATED sizes (from the LLM tool
  spec, ≈ chars/4) so the panel can drill into tool definitions with a total
  instead of "size not measured". `bashExecution` message entries now group as
  `tool` (not `other`), and the renderer hides any empty group — so "Other" only
  appears when a genuinely unknown entry type shows up.

### hv.context — removed / restored (reply to /hv-context-remove | -restore)

```json
{"kind":"hv.context","stage":"removed","accepted":["tool:call-A"],"refused":["tool:call-B"],"marks":["tool:call-A"]}
{"kind":"hv.context","stage":"restored","restored":["tool:call-A"],"marks":[]}
```

`refused` = keys rejected by the completed-turn gate (in-flight or unknown);
`notifyType` is `"warning"` when anything was refused. `marks` is the full
current kill-set after the operation.

### hv-context-marks — persistence (pi.appendEntry)

The kill-set is persisted as `custom` entries of type `hv-context-marks` with
`data: {marks: MarkKey[]}` — a full snapshot, newest wins. These do NOT enter
LLM context. Restored on `session_start` (survives reload + resume), and
re-appended in `session_before_compact` so they survive compaction. The bridge's
`context` handler applies the set via `filterMessages` (non-destructive — the
session file is never mutated, proven in s0.3).

### Compaction

Main fires the RPC `compact` command (`hv:compact-session`); Pi streams
`compaction_start` / `compaction_end` events (forwarded as `hv:pi-event`),
rendered as transcript notices. The red-zone auto-suggest banner and the
[Compact now] dialog are renderer-only; compaction is NEVER automatic.

Contract coverage: `tests/context-bridge.test.ts` (snapshot shape + in-flight
refusal need no model; the remove→resume-survival guarantee is DEEPSEEK-gated —
it proves the mark persists across a full Pi process restart from the session
file, i.e. the same `pi.appendEntry` + `restoreMarks` machinery
`session_before_compact` re-invokes; a manual `compact` refuses on a session
that small, so persistence is proven deterministically via resume). Pure logic
(marks/pairing/completed-turn gate + gauge/grouping/parsing) is unit-tested in
`tests/hv-context.test.ts` and `tests/context-renderer.test.ts`.

## MCP permission tool-name convention (m1.md, 2026-07-13)

The `tool` field in an `hv.permission` select prompt may be a virtual name for MCP
proxy calls:

| Value | Meaning |
|-------|---------|
| `mcp:<serverName>_<toolName>` | MCP invoke — per-tool identity; rules can pattern-match (e.g. `mcp:github_*`) |
| `mcp` | MCP discovery (search/describe/connect) — safe-default-allowed, no prompt |

The actual format is `mcp:<prefix>_<toolName>` where `<prefix>` is the server name
from `.mcp.json` `mcpServers` key (the adapter's tool-prefix behavior).
Empirically confirmed: server `echo`, tool `echo` → `mcp:echo_echo`.

Discovery calls (`search`, `describe`, `connect`) set `ruleTool: "mcp"` (bare) and
are safe-default-allowed at the bridge gate — they never surface as `hv.permission`
prompts unless an explicit rule matches `mcp`.

### Subagent trace projections — `messages` is gone (0.40.0)

The child transcript used to ride `tool_execution_update.partialResult.details
.results[].messages`. As of 0.40.0 it rides **nothing**:

| projection | source | `messages` | `toolCalls` |
| --- | --- | --- | --- |
| streamed update | `snapshotStreamResult` (`execution.ts:266`) | `undefined` **(new in 0.40)** | present, bounded to 64 |
| terminal end | `compactForegroundResult` (`utils.ts:405`) | `undefined` (unchanged since 0.34) | present |

Upstream's reason is in the code: one `tool_execution_update` is serialized as a
single child-stdout line, read under `MAX_CHILD_PENDING_LINE_BYTES` (16 MiB), and
an unbounded running transcript could cross it and kill the child with
`protocol_output_limit`. So this is the same change as the deep-fan-out robustness
fix — the regression and the win are one commit.

`ToolCallSummary` is `{text, expandedText}` (display strings only). The renderer
maps it into the existing `SubagentMessage` rows (`role:"tool"`, `expandedText ??
text`) and still prefers real `messages` when a payload carries them, so a future
pin that restores the transcript needs no renderer change. **The child's prose is
genuinely lost from this path**; its ANSWER survives as `finalOutput`, which
`SubagentTraceView` now renders. Live activity for the DEFAULT (async) path is
unaffected — that comes from the `status.json` poller, not this projection.

Pinned by `tests/agents-bridge.test.ts` (wire: asserts `messages` is absent) plus
`tests/agents-renderer.test.ts` (the toolCalls→rows mapping).

## Session restore reads the file, not `get_messages` (§17, round 10)

`get_messages` returns `agent.state.messages` — cheap in itself, but it is the
FIRST RPC a freshly spawned child answers, so it absorbs the whole boot: 1.35–2.86 s,
90%+ of a restore. `history.ts contextItems` rebuilds the same transcript from the
session file in 1–5 ms (measured on real sessions to 4 MB) and needs no child, so
`hv:open-session` paints before the spawn instead of after it.

Pi's rule (`session-manager.js buildContextEntries`) is
`[latest compaction] + entries from firstKeptEntryId onward`. The compaction entry
itself only yields a `role:"compactionSummary"` message, which `restoreItems` drops,
so the plain slice from `firstKeptEntryId` reproduces it exactly — and is the exact
complement of `earlierItems`.

Two consequences worth knowing:
- §9 removals are applied by the bridge at the `context` event only, so
  `agent.state.messages` still holds removed messages. The file path runs
  `filterMessages`, so a removed message no longer comes back on reopen.
- A session with no captured `piSessionFile` yet keeps the RPC (its client is
  already warm, so there is no boot to absorb).

Contract coverage: `tests/history-contract.test.ts` — key-free, part of the
**pin-bump gate**. It writes a compacted session file, resumes a real Pi on it, and
asserts `contextItems(file)` equals `restoreItems(get_messages)`. A Pi version that
changes the context rule fails here instead of silently truncating conversations.

## Prompt templates — hv.prompt-template (§24, 2026-08-02)

The only Pi wire this feature adds. Full Pi-side evidence is in `pt1.md`; this is

### hv.prompt-template — typed↔expanded pairing (fire-and-forget notify)

Pi expands a prompt template into the user message and keeps only the expansion
(`agent-session.js:867-875`), so the typed `/review src/foo.ts` exists on no event
and in no file. Two hooks straddle the expansion in the same `prompt()` call stack,
so the bridge pairs them:

```
input                (agent-session.js:810)  → original typed text
before_agent_start   (agent-session.js:882)  → expanded text (event.prompt)
```

Emitted from the bridge's `before_agent_start` handler, once per expanded
invocation, never for an ordinary prompt or an unexpanded `/hv-*`:

```jsonc
{ "kind": "hv.prompt-template",
  "name": "review",                       // basename of the template file
  "typed": "/review src/foo.ts",          // what the user wrote
  "expanded": "Review src/foo.ts for …" } // what the model received
```

Rides `ui.notify` (the ui-request channel, `method:"notify"`), like `hv.audit` and
`hv.skill` — never RPC stdout.

Main logs `{ type: "prompt-template.invoked", data: { sessionId, typed, expandedHash } }`
(sha256 of the expansion) and forwards the envelope to the renderer.
`applyPromptTemplatePair` folds it into the transcript; `restore.ts` re-pairs after a
reload by hashing each restored user message. **Hash, never ordinal** — ask-user
answers and queued messages also produce user messages.

**The `input` handler fails OPEN and must stay that way.** It sits in front of
every user prompt. Pi already wraps input handlers (`runner.js:933-955`) and a
handler returning `undefined` continues normally; only `{action:"handled"}`
swallows a prompt. The bridge wraps its own body too. `tests/prompt-templates-bridge.test.ts`
asserts a plain non-slash prompt still completes **before** it asserts anything
about the feature — if that goes red, revert the hook, not the test.

## Agent terminals — hv.terminal-* + hv.terminal (§26 part 2, 2026-08-07)

Three registered tools, each a thin shell over a **blocking** `ctx.ui.input`
envelope. Main owns the PTYs (part 1), so main owns the cap, the busy-reuse
refusal and the interleave hold; the bridge only carries the request and turns
the reply into a tool result.

### The three blocking inputs (bridge → main → tool result)

Sent as `ctx.ui.input(JSON.stringify(envelope), "")`, so the payload is in
**`title`** (a notify uses `message` — that asymmetry is the single easiest
thing to get wrong here, and it costs you a card that never appears).

```jsonc
{ "kind": "hv.terminal-run",  "command": "npm run dev", "terminalId": "t1?", "intent": "…" }
{ "kind": "hv.terminal-read", "terminalId": "t1", "lines": 200, "waitMs": 3000 }
{ "kind": "hv.terminal-kill", "terminalId": "t1" }
```

Main **always** answers, with a JSON string:

```jsonc
{ "ok": true,  "terminalId": "t1", "title": "zsh" }                                  // run
{ "ok": true,  "text": "…", "running": true, "exitCode": null, "userTyped": false }  // read
{ "ok": true }                                                                        // kill
{ "ok": false, "reason": "…" }                                                        // any of them
```

`terminalReply` (bridge) maps `ok:false` to the reason as the tool's text. **A
dropped response hangs the turn** — same contract, and same reason, as
`hv.plan-write`.

`intent` rides the run envelope only so main can echo it on the notify below;
the permission prompt was built from the factual `summarize()` long before, and
must never show it (§13's MCP rule).

### hv.terminal — card lifecycle (fire-and-forget notify, payload in `message`)

```jsonc
{ "kind": "hv.terminal", "stage": "started", "terminalId": "t1", "title": "zsh",
  "command": "npm run dev", "intent": "…", "workspaceId": "/abs/ws" }
{ "kind": "hv.terminal", "stage": "killed",  "terminalId": "t1" }
```

There is deliberately no `exited` stage: the renderer already learns that from
`hv:term-exit` on part 1's push channel, and the card stack is derived from the
live `terminals` map, so an exited terminal leaves it with no extra event.

### Gate placement (all three must be NAMED — nothing is automatic)

| Tool | `SAFE_TOOLS` | `gatePlanCall` |
|---|---|---|
| `terminal_run` | no (asks) | `BLOCKED_PLAN_TOOLS` |
| `terminal_read` | **yes** | `PLAN_PASS_TOOLS` |
| `terminal_kill` | no (asks) | `PLAN_PASS_TOOLS` |

`terminal_read` in `PLAN_PASS_TOOLS` is not cosmetic: the default is
`floor-ask`, which clamps `allow`→`ask`, so a planning agent polling a log would
raise a modal **on every poll**.

### Two guards run in `tool_call` BEFORE the permission prompt

The ordering is the mechanism, not an optimisation. A multi-line `command` is
refused (`describeCommand` labels the modal from the first segment only, so the
user would approve a string they are shown part of), and a `bash` command with a
genuine trailing `&` is blocked and redirected — **only while
`builtins.terminal` is true**, since with the group off there is no
`terminal_run` to redirect to. Both audit as `source:"terminal"`, which is also
the only way to observe them: `tool_execution_start` fires *before* tool_call
handlers, so it cannot distinguish a blocked call from an allowed one.

### ~~Registering three tools measurably dilutes a small model's tool choice~~ — RETRACTED

**This section previously claimed the terminal tools made the model stop calling
`bash`. That claim was wrong, and the retraction is kept in place because the way
it was wrong is more useful than the claim ever was.**

The original evidence (2026-08-07, deepseek-v4-flash, `touch forbidden.txt`,
counting `bash` calls) was five trials per configuration, run **sequentially**,
each in a different app state:

| Configuration | bash called |
|---|---|
| before the terminal tools existed | 3/5 |
| `builtins.terminal:false` | 2/5 |
| tools registered, no steer line | 1/5 |
| tools + steer line (first draft) | 0/5 |
| tools + steer line (bash-affirming rewrite) | 0/5 |

It reads as a clean dose-response curve. It is not one. **3/5 vs 0/5 is
p = 0.167 by a two-sided Fisher exact test** — never significant at any point,
and the monotone shape is what five-trial binomial noise looks like when you sort
the rows by the story you already believe.

Two controlled re-runs, **interleaved** so provider drift cannot masquerade as a
condition effect:

**A · No bridge, only a probe extension registering K tools (n=8 per cell).**
Isolates the tool list from everything else — no gate, no steer line, no MCP.

| Condition | bash called |
|---|---|
| 0 extra tools | 1/8 |
| 3 unrelated tools (calendar/contacts/notes, neutral wording) | 4/8 |
| 3 terminal tools, wording that never names bash | 4/8 |
| 3 terminal tools, the **shipped** wording | **7/8** |

**B · The shipped configuration — real bridge, only `builtins.terminal` toggled
(n=12 per arm).** `off` 4/12 · `on` 6/12.

So: the effect does not exist in the direction claimed, and the one significant
comparison runs the **opposite** way.

| Comparison | p (2-sided Fisher) |
|---|---|
| original claim, 3/5 vs 0/5 | 0.167 — not significant |
| 0 tools vs 3 shipped-wording tools | **0.010 — significant, more tools ⇒ MORE bash** |
| 0 tools vs 3 unrelated tools | 0.282 |
| neutral wording vs bash-mentioning wording | 0.282 |
| shipped config, group off vs on | 0.680 — no detectable effect |

There is also a confound the original never controlled for: `terminal_run`'s own
description says *"instead of backgrounding a bash command"* and `terminal_read`'s
says *"instead of sleeping in bash"*. The "tools, no steer line" row therefore
still disparaged bash — descriptions **are** wording. The "wording versus count"
question the original claimed to have answered was never actually asked.

**What stands.** The prompt changes in `tests/bridge.test.ts` and
`tests/rules-bridge.test.ts` stay, on their own merit rather than the retracted
one: at the shipped baseline the model calls `bash` on roughly half of attempts,
so `askUntil`'s three tries left those tests failing ~12% of the time. The
explicit wording measured 5/5. That is a flakiness fix, not a dilution fix.

**The transferable lesson is about method, not tools.** Five trials per cell,
run sequentially while other things changed, produced a table that looked
causal, survived my own review, and shipped into three documents. What broke it
was interleaving the conditions and computing a p-value — both cheap, neither
done the first time. Before recording a behavioural claim about a model here:
interleave the arms, hold everything else fixed, and if the result would not
survive a Fisher exact test, write down the uncertainty instead of the claim.

## Web tools — hv.web-* + hv.web-cancel (§32, 2026-09-04)

Four registered tools, each a thin shell over a **blocking** `ctx.ui.input`
envelope — §26's terminals and §28's browser a third time. Main calls the web
service, so main owns the URL, the encrypted key, the caps, the deadline and the
audit row; the bridge carries the request and turns the reply into a tool
result. `browserReply` is reused verbatim as the mapper, because a page fetched
headlessly is exactly as untrusted as one rendered in the pane.

### The four blocking inputs (bridge → main → tool result)

Payload in **`title`** (a notify uses `message`). Same asymmetry, same trap.
`toolCallId` rides along on every one — see the cancel notify below.

```jsonc
{ "kind": "hv.web-search", "toolCallId": "call_ab…", "query": "vitest mock fetch", "limit": 5, "includeContent": false }
{ "kind": "hv.web-fetch",  "toolCallId": "call_ab…", "url": "https://docs.foo.com/guide", "maxChars": 16000, "startIndex": 0, "fresh": false }
{ "kind": "hv.web-map",    "toolCallId": "call_ab…", "url": "https://docs.foo.com", "search": "guide", "limit": 100 }
{ "kind": "hv.web-crawl",  "toolCallId": "call_ab…", "url": "https://docs.foo.com", "limit": 10, "maxDepth": 2,
                           "includePaths": ["^/docs"], "excludePaths": [], "maxCharsPerPage": 2000 }
```

Main **always** answers, with a JSON string:

```jsonc
{ "ok": true, "untrusted": true,
  "text": "Read https://docs.foo.com/guide (title: \"Guide\", status 200, 41,203 chars total, showing 0–16,000).\nCall web_fetch again with startIndex=16000 for more.\n\n# Guide…",
  "meta": { "host": "docs.foo.com", "total": 41203, "start": 0, "end": 16000, "status": 200, "title": "Guide" } }

{ "ok": false, "reason": "HappyVibe's web service is busy or unreachable right now. Try again in a moment, or point the app at your own service in Settings → Built-in tools." }
{ "ok": false, "reason": "localhost is not reachable from the web service, which runs outside your network — use browser_open, which runs on your machine." }
```

`untrusted: true` ⇒ `browserReply` prefixes `UNTRUSTED_BANNER`. Verified live:
the banner is the first thing in the tool result the model receives.

### The one notify (bridge → main) — payload in `message`

```jsonc
{ "kind": "hv.web-cancel", "toolCallId": "call_0f54667b2a78452e920eec62" }
```

**Measured, because it was an open question rather than an assumption.** Pi
hands `execute` an `AbortSignal` and nothing else in this repo uses one, so
"does an interrupted turn actually fire it?" was probed before the cancel path
was trusted: a fetch was held open by a harness that never answered the
envelope, `{type:"abort"}` was sent, and the notify above arrived carrying the
same `toolCallId` as the envelope. So the path is live code. Two things learned
with it:

- **`{type:"abort"}` does not resolve while a tool call is pending.** Awaiting
  that RPC hangs to the test timeout, which is how the probe first failed. Send
  it un-awaited.
- Without this path an abandoned crawl holds one of the service's **two**
  worker slots for its full two minutes, and those two are shared by every
  HappyVibe install. Nothing else would have failed. Pinned by
  `tests/web-bridge.test.ts` ("an interrupted turn cancels the in-flight web call").

### The gate

| Tool | `permTool` | Default |
| --- | --- | --- |
| `web_search` | `web_search` | **allow** (`SAFE_TOOLS`, `source:"safe-default"`) |
| `web_fetch` / `web_map` / `web_crawl` | **`browser:<host>`** | ask — §28's own rule, so one grant covers both surfaces |

Verified live: `browser:example.com` is the rule name in the prompt, the summary
is `https://example.com` and never the model's `intent`, Deny stops the envelope
reaching main, and "Allow for session" makes a second page on the same host
silent. A private or non-`http(s)` URL is refused in the bridge **before** the
gate — `hv.audit {source:"web", decision:"deny"}`, no prompt, no envelope, and
the reason names `browser_open`.

### EventLog

```jsonc
{ "type": "web.call", "data": { "tool": "web_fetch", "host": "docs.foo.com", "resultChars": 16063, "ms": 1812, "ok": true, "service": "default", "status": 200 } }
{ "type": "web.call", "data": { "tool": "web_search", "queryChars": 24, "resultChars": 612, "ms": 940, "ok": true, "service": "default" } }
```

Lengths, never content — not the page text and not the query itself (§19).

### The crawl job — poll semantics, measured

Written from the docs first and measured second, which found two bugs a fixture
would never have shown (live service, 2026-09-04):

1. **`data` is the accumulated slice from the requested offset**, not the pages
   completed since the last poll. Three consecutive polls of a one-page crawl
   each returned that same page, so appending what arrives duplicates every page
   once per poll.
2. **`next` is offered while `status` is still `"scraping"`** (`total: 1`,
   `completed: 1`, `next: …?skip=1`), so treating it as "there is more, fetch it
   now" is an unsleeping loop against the two shared slots.

```jsonc
// POST /v2/crawl → { "success": true, "id": "01a0…", "url": "http://firecrawl.bzapps.eu/v2/crawl/01a0…" }
// GET  /v2/crawl/{id}       → { "status": "scraping",  "total": 1, "completed": 1, "data": [<page>], "next": "http://…?skip=1" }
// GET  /v2/crawl/{id}       → { "status": "scraping",  "total": 1, "completed": 1, "data": [<same page>], "next": "http://…?skip=1" }
// GET  /v2/crawl/{id}       → { "status": "completed", "total": 1, "completed": 1, "data": [<same page>] }
```

So the client keeps **its own cursor** (`skip` = records consumed, which is what
`next` encodes) and never touches the returned job URL — which also disposes of
its `http://` scheme, an nginx 404 on that box. The drain breaks on **new
pages**, not on an empty slice: a service that ignored `skip` and re-sent
everything would satisfy `rows.length > 0` forever, so an empty-slice condition
is an infinite loop waiting for a service upgrade. A `seen` set makes the
re-sent slice harmless either way. `tests/web-service.test.ts` models all of
this, including the skip-ignoring variant.

## Embedded browser — hv.browser-* + hv.browser (§28, 2026-08-15)

Ten registered tools, each a thin shell over a **blocking** `ctx.ui.input`
envelope, exactly like §26's terminals. Main owns the `WebContentsView`, so main
owns the cap (one pane per session), the egress gate and every lifecycle event;
the bridge carries the request and turns the reply into a tool result.

### The ten blocking inputs (bridge → main → tool result)

Payload in **`title`** (a notify uses `message`). Same asymmetry, same trap.

```jsonc
{ "kind": "hv.browser-open",        "url": "http://localhost:5173", "intent": "…" }
{ "kind": "hv.browser-navigate",    "url": "https://example.com",   "intent": "…" }
{ "kind": "hv.browser-screenshot",  "intent": "…" }
{ "kind": "hv.browser-get-text" }
{ "kind": "hv.browser-read-console","lines": 100 }
{ "kind": "hv.browser-read-network","limit": 50 }
{ "kind": "hv.browser-click",       "selector": "#save", "intent": "…" }
{ "kind": "hv.browser-type",        "selector": "#q", "text": "hello", "intent": "…" }
{ "kind": "hv.browser-evaluate",    "code": "document.title", "intent": "…" }
{ "kind": "hv.browser-close",       "intent": "…" }
```

Main **always** answers, with a JSON string:

```jsonc
{ "ok": true,  "browserId": "b1", "text": "The browser is open at …" }        // open
{ "ok": true,  "text": "…", "untrusted": true }                              // every read/act
{ "ok": true,  "text": "…", "imageBase64": "iVBOR…" }                        // screenshot, vision model
{ "ok": false, "reason": "This session has no browser open. …" }             // any of them
```

Two fields only this family has:

- **`untrusted: true`** ⇒ `browserReply` prefixes `UNTRUSTED_BANNER` (hv-browser.ts).
  Page bytes must never reach the model dressed as our own words. Prompt
  injection has no mechanical fix; labelling plus the permission gate on what the
  injected text talks the model into is the whole mitigation (§28).
- **`imageBase64`** ⇒ an `{type:"image"}` content block **in addition to** the
  text. Verified, not assumed: `AgentToolResult.content` is
  `(TextContent | ImageContent)[]` in
  `pi-runtime/node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-agent-core/dist/types.d.ts:316-320`,
  so an extension tool CAN hand a model a picture. Main only sets it when the
  session's model advertises `input: ["image", …]` in Pi's registry — otherwise
  the result says so and points at `browser_get_text`. The **user sees the
  screenshot either way**, via the notify below.

### hv.browser — card lifecycle (fire-and-forget notify, payload in `message`)

```jsonc
{ "kind": "hv.browser", "stage": "opened",     "browserId": "b1", "url": "…", "intent": "…", "workspaceId": "/abs/ws" }
{ "kind": "hv.browser", "stage": "navigated",  "browserId": "b1", "url": "…", "intent": "…" }
{ "kind": "hv.browser", "stage": "screenshot", "browserId": "b1", "intent": "…" }
{ "kind": "hv.browser", "stage": "acted",      "browserId": "b1", "action": "click|type|evaluate", "detail": "…" }
{ "kind": "hv.browser", "stage": "closed",     "browserId": "b1" }
```

`opened` is what places the TAB (renderer, `openBrowserTab`) — main creates the
pane, but where it goes on screen is a layout decision and stays in the renderer.

The screenshot notify carries **no image**: §28's "the user always sees it" means
*in the pane*, and the live page is already on screen beside the transcript, so
shipping a multi-megabyte data URL to a renderer that has the real thing would be
waste. The PNG goes to the MODEL (as an image content block) or nowhere.

### Gate placement — navigation gates per HOST, not per tool

| Tool | rule name | `SAFE_TOOLS` | `gatePlanCall` |
|---|---|---|---|
| `browser_open` / `browser_navigate` | **`browser:<host>`** | no | *(unnamed)* → `floor-ask` |
| `browser_get_text` / `_read_console` / `_read_network` / `_screenshot` | own name | **yes** | `PLAN_PASS_TOOLS` |
| `browser_close` | own name | **yes** | `PLAN_PASS_TOOLS` |
| `browser_click` / `_type` / `_evaluate` | own name | no (asks) | `BLOCKED_PLAN_TOOLS` |

`browserRuleName(url)` (hv-browser.ts) builds `browser:<host>` — the same
virtual-name trick as `mcp:<server>_<tool>`, so a user's
`deny browser:*.stripe.com` is an ordinary tool-layer rule in the engine that
already exists. **Consequence worth knowing:** "Allow for session" grants the
HOST, so it says nothing about the next one.

`localhost` / `127.0.0.1` / `[::1]` / `0.0.0.0` are a **safe-default allow**
(exact hostname match — `localhost.evil.com` is a real remote host and does not
qualify), evaluated after the rule engine so an explicit `browser:localhost` rule
still wins. Without it the dev-preview loop would prompt on every page load,
which is the whole feature.

`browser_open`/`browser_navigate` are deliberately **absent from both plan sets**
so they land on `floor-ask`: opening documentation to read it is legitimate
planning, and a GET the user approves per call is not a mutation.

### The egress gate is on the PARTITION, not on the tool call

`session.fromPartition("persist:hv-browser").webRequest.onBeforeRequest`
(browsers.ts) is the enforcement point, because a tool-level gate is bypassable
by the page: one `location.href` from injected JS and `browser_navigate` never
ran. Decisions come from the pure `EgressState` (browserEgress.ts).

- **main-frame** → gated. Refused ⇒ `{cancel:true}` **and** the pane goes to
  `state:"blocked"` with the host, which the renderer renders as an Allow button.
  Chromium then fires `did-fail-load` with **ERR_BLOCKED_BY_CLIENT (-20)** (measured — *not*
  ERR_ABORTED/-3, which is what an ordinary interrupted navigation gives), so that handler skips
  both codes and re-checks `state === "blocked"` or it would repaint the one actionable state as a
  generic failure.
  Clicking it is user consent (§28) and needs no second prompt.
- **subresources of an allowed page** → run silently, but every one is recorded
  in the ring `browser_read_network` serves.
- **redirects inherit** the approval of the navigation that started them, or
  every IdP bounce would break.

Honest limit, stated in §28 and repeated here so nobody over-claims it: in-page
`fetch` reaches any domain the page can. The headline is "the agent's browser
only NAVIGATES where you allow", not "no byte leaves". `browser_evaluate`'s
stricter rule is the companion mitigation.

**One hook per partition.** Electron REPLACES `onBeforeRequest` rather than
stacking, so installing it per pane would silently disarm every pane but the
newest — hence `egressInstalled` + a `webContents.id → entry` map.

### The guest has no privileges, and the picker is why that matters

`sandbox: true`, `contextIsolation: true`, no `nodeIntegration`, **no preload**,
`setPermissionRequestHandler`/`setPermissionCheckHandler` deny everything,
`will-navigate` blocks non-http(s), `setWindowOpenHandler` denies popups (a
`new-window` disposition goes to the OS browser instead). The element picker is
therefore **injected** via `executeJavaScript` (browserPicker.ts) rather than
preloaded — it reads geometry and DOM, i.e. nothing the page did not already
have. Its payload enters the COMPOSER as a chip the user then sends, so it gets
no untrusted banner: the human authors that turn, which is exactly the line the
tool-result rule above draws.

### The composited view has no z-index — visibility IS the z-order

A `WebContentsView` paints over the whole renderer DOM, so anything drawn "above"
it is really drawn *under* it and swallows its own clicks.

**Round 1 correction (2026-08-15).** The rule was `document.querySelector(".hv-overlay")`,
on the belief that every overlay carried that class. Four do; the app has ~35
floating surfaces. Reported as "none of this menu is clickable" — and the menu in
question (the pane `+`) shares neither the class, nor the styling, nor the
dismissal idiom of the other menus, so no selector would have caught it.

`BrowserTab` now asks the question geometrically: a 3×3 grid of
`document.elementFromPoint` samples inside its own rect, rAF-coalesced off a
body `MutationObserver` plus scroll/resize. If the topmost element at any sample
is not the placeholder, something is over the page and the view hides. Nothing to
remember on the other 35 components, and it hides ONLY when the overlap is real —
a menu open in the other half leaves the page up.

The view also insets itself by `DIVIDER_INSET` (6px) on each side that touches
another pane: the divider's 10px drag strip straddles the boundary, so half of it
would otherwise sit under the page (ungrabbable), and a transparent strip at the
very edge would also read as "covered" and hide the page permanently.

### The picker payload (round 1)

`hv:browser-pick` resolves with `{ element, imageBase64 }`, not just the element:

```jsonc
{ "element": { "selector": "#save", "outerHTML": "…", "label": "<button#save> Save",
               "rect": { "x": 12, "y": 40, "width": 88, "height": 32 } },
  "imageBase64": "iVBOR…" }
```

`label` is **not shown in the popup** — the outline already says which element
this is, so printing its name again was one more thing to read for no
information. It survives as the input's accessible name, as the composer chip's
fallback when no comment is typed, and in the sent message. What it contains: what
the element SAYS, never what it is made of — its visible text,
else its accessible name (`aria-label`/`alt`/`placeholder`/`title`), else a plain
word for its kind ("link", "button", "image"). It used to read `<a.nav-play> PLAY`
— a tag and a class are the developer's handle on an element, and the person
pointing at a button means "PLAY". The selector still travels beside it, because
`browser_click` needs one; it just stopped being the label.

`rect` pins the comment popup to the thing being commented on. `imageBase64` is
captured by main **while the view is still visible** (in its own try — a failed
capture must never discard the picked element, which it did until measured) and shown as a still behind
the popup — a popup over the LIVE page cannot be seen at all (no z-index), so the
page has to go, and a frozen frame keeps the user looking at what they clicked
instead of at a blank pane. Both fields are page-controlled and validated:
a rect with a non-finite number degrades to "no rect" (centred popup) rather than
positioning something off-screen.

## pi-subagents 0.50 — what the bump moved (2026-08-17)

**Provenance.** The first half of this section is read out of the vendored 0.50.0
tree with `file:line` or proven by a key-free test; the §"Measured on the wire"
part below is captured from real delegations against
OpenRouter `deepseek/deepseek-v4-flash` and pinned by the re-timed live tests.
The distinction earned its keep: source told us what the code *contains*, and only
the wire told us that `subagent:async-started` never fires on the path we actually
take — a PRD §12 regression no amount of reading would have surfaced.

**A retraction first, because it is the more useful lesson — and note how it ends.**
Four live tests were run at 0.50 before the DeepSeek balance ran out and all four
failed, in a pattern matching the 0.49 audit's inventory: transcript gone from
`results[].messages`, `details.asyncId` missing, no `tool_execution_update`. Those
runs measured NOTHING — all four were a `402 Insufficient Balance`, and the tells
were in the assertions rather than the symptoms (`expected 0 to be greater than 0`
for `tool_execution_start` events; `a real delegation ran: expected undefined to be
truthy`). No delegation ever ran.

The instructive part is what happened when the same three claims were then measured
properly on a funded key: **two were right and one was wrong.**
`tool_execution_update` really is never emitted, and the transcript really is absent
from `results[].messages` (`toolCalls` carries it instead) — while `asyncId` is very
much present at both emit sites (`async-execution.ts:1288,1701`) and on the wire. So
invalid evidence is not the same thing as a wrong conclusion, and "that finding came
from a dead key" is not grounds to discard it — only grounds to re-measure it. The
0.49 audit's red inventory deserves exactly that treatment: re-run, don't trust and
don't dismiss. CLAUDE.md's standing warning ("a live test failing 'model never called
X' is usually NOISE") covers a flaky model; this is the harder version, where the
whole provider is down and every shape assertion fails plausibly at once.

### Prompt redaction — the one break that reaches the UI

`PROMPT_REDACTED = "[prompt redacted]"` (`shared/utils.ts:20`) replaces `task` and
`goal` on every surface an observer reads:

| Surface | Site |
|---|---|
| `subagent:async-started` (`task`, `goal`) | `async-execution.ts:1259-1260, 1682-1683` |
| foreground result (`result.task`, `result.progress.task`) | `foreground/execution.ts:126-129` |
| `status.json` `steps[].description` | `chain-append.ts:155-161` — `statusStepDescription` **ignores its argument** and returns the constant |
| run metadata | `foreground/execution.ts:154` |
| child input artifact + initial transcript message | `foreground/execution.ts:1690, 1704` |

Unconditional: no config key, no env var, nothing in `types.ts` mentioning
redaction. The child still receives the real task via its prompt, so delegation
itself is unaffected — only display is.

Consequence for us: **no surface can give a caption back**, which is why
`hv-subagent-tasks.ts` exists and why it PERSISTS (a respawn or app restart has no

### The delivery repair — giving the parent its child's whole answer (2026-08-19)

Upstream truncates the completion payload at a hardcoded 1,000 chars
(`subagent-executor.ts`, `formatWorkflowValue(v).slice(0, 1_000)`; still present at
0.51). Measured: a 4,107-char child report arrives as 1,108 chars of JSON cut
mid-string, and the model responds by announcing the truncation, calling
`subagent_wait`, polling `subagent {action:"status"}` and reading the artifact —
**four tool calls for one delegation**, three of them visible as plumbing.

`hv-subagent-delivery.ts` repairs it: the bridge remembers `results[].output` from
`subagent:async-complete` and substitutes it into the injected message from the
`context` hook. Measured after: **one** tool call, the model reporting from the full
text, no truncation narration.

Three measured facts the design rests on — each would have broken it silently:

| Fact | Why it matters |
|---|---|
| The notify IS in the `context` hook's `messages`: `{role:"custom", customType:"subagent-notify", content:<string>, …}` | The whole approach depends on it being rewritable. Probed BEFORE building. |
| The id in the message is the **child's** run id (`"runId": "65227ea7"`), not the workflow's async UUID (`a2df09d4-…`) | Keying by the workflow id — the one we track everywhere else — would never match. `results[].runId` is the join. |
| `details` on the persisted message is EMPTY | The full output cannot be recovered from the message; it must be captured at completion. |

It is cheaper than what it replaces: the model reads the artifact anyway, so the
full text enters context either way; the tool call, its result envelope and the
narration are what disappear.

Deliberately NOT persisted, and deliberately not applied to the session file: a
completion and its delivery share a turn, multi-KB outputs through `appendEntry`
would bloat every session, and the file should keep a faithful record of what
upstream actually sent. The repair applies to what the model SEES, per request.

Refusals (all tested): unrecognised header → untouched (a future rewording must
arrive unmangled); more than one child named → untouched (a parallel fan-out would
otherwise get every message replaced by one child's answer); redacted, absent, or
over 32 KB → defer to the artifact, where `describeSubagentArtifact` already labels
the read legibly.

### The fix, and why it is its own extension

`pi-runtime/extensions/hv-owner-seed.ts` claims the registry symbol from
`HV_SUBAGENT_OWNER` (= `hv-<HappyVibe session id>`) at module load. `??=` is the
whole mechanism: a value already in the registry wins and upstream never overwrites
it.

It cannot live in `happyvibe-bridge.ts`. Pi loads `-e` extensions strictly
sequentially — import, then factory, one at a time in argv order
(`core/extensions/loader.js:440`) — and the id is minted inside pi-subagents'
factory, while the bridge is pinned LAST so the permission gate sees post-mutation
tool input. So the seed is a separate extension loaded FIRST. It registers no tools
and no `tool_call` handler, so it cannot change what the gate sees; the invariant is
that the *gate* is last, not that nothing precedes it. It is also import-free, and
`loadExtension` wraps load in try/catch and returns an error string rather than
crashing the session.

Measured end of that chain: with `sessionId` passed, a real delegation's
`status.json` reads `ownerId=hv-probe-session` where the previous runs read
`3ab22fb3-…` and `7200a18a-…`, and the run still reaches `state=complete`.

**RESOLVED 2026-08-19 in the running app — an async run does NOT survive its
parent, and never could have.** A live delegation's `status.json` recorded
`pid: 57451`, and 57451 was one of exactly two `pi` processes on the machine, both
direct children of the Electron main (`ppid 56697`) in the app's own process group
(`pgid 56652`), both started with the app. The delegation's child agent was an
ordinary non-detached child of it (same pgid), and there was **no process group
anywhere on the machine other than the app's** — i.e. no detached runner exists.
`async-execution.ts:521` does spawn with `detached: true`, so that path exists; it is
simply not the one a top-level workflow-mode delegation takes.

That fully explains both probe deaths below, which were never a mystery: killing the
parent Pi kills the process that OWNS the run. It also promotes `activity.asyncRuns`
from belt-and-braces to LOAD-BEARING: it is the only thing preventing hibernation or
MCP live-reload from destroying an in-flight delegation.

**Correction (2026-08-20): this does NOT make the owner-id refusal unreachable, and
saying so here was wrong.** No live *process* survives a respawn — but a result is a
FILE. A child that finished and wrote its result before its parent went away leaves it
on disk, and the next session start scans it: `extension/index.ts` calls
`primeExistingResults({ triggerTurn: !recovering })`, which routes through
`scheduleResult → handleResult → notifier.deliver` — the same owner-scoped guard the
table above exercises. So the reachable sequence is:

1. the sub-agent finishes and its result file is written, stamped with the launching
   process's `completionOwnerId`;
2. the session respawns before delivery (app quit, or an MCP live-reload landing in
   that window);
3. the resumed session primes the file, the ids do not match, and delivery is refused.

And it is refused *permanently*, not transiently: `if (!accepted) scheduleResult(file,
triggerTurn, RETRY_DELAY_MS)` retries without marking the file delivered, so it is
retried forever by a process whose id can never match, and by every process after it.
The answer is lost silently and the result file never clears. With the seed the id is
the HappyVibe session id, which is stable across exactly that respawn, so it delivers.

The window is narrow — seconds between the result landing and the notify — but it is
precisely the case `startClient(meta, true)` exists to protect, and the failure is
invisible. Pinned as a ROUTE assertion in `tests/pi-subagents-contract.test.ts`
(session-start priming, the shared handler, and the retry-on-refusal), because the
behavioural refusal test alone would stay green if upstream ever stopped priming.

The original, now-explained observation: Two `scripts/probe-050.ts respawn` attempts both lost the child on
the parent's SIGTERM — the first killed it ~0 s after dispatch (`state: failed`,
*"Async runner process 12506 exited or disappeared before writing a result"*, 2.7 s
in), the second after a 25 s settle with `aliveBeforeKill=true` confirmed by
`process.kill(pid, 0)` and then `aliveAfterParentKill=false`. The runner is spawned
`detached: true` with `stdio: ["ignore", …]` (`async-execution.ts:521`) and nothing
in pi-subagents kills a runner on shutdown (`terminateRunnerBeforeProceed` is only
on the preflight path), which is consistent with the topology above rather than
mysterious. CLAUDE.md's "detached runs SURVIVE a parent respawn" was simply WRONG and
has been corrected at its source.

The probe's `respawn` mode now settles the child, proves it alive before the kill,
re-checks after, and prints the run's own final state — so "not delivered" can never
again be confused with "the child failed". That confound cost two runs here.

## Subagent delegation concurrency (2026-08-21, pi-subagents 0.53.0 / Pi 0.84.2)

**Question:** can the bridge safely widen a session-scoped capability ceiling for
one approved delegation and restore it afterwards? That design needs our
`tool_call` gate and the child's spawn to be serialized with respect to each
other. **They are not**, and the answer came out of Pi's own agent loop rather
than a behavioural probe — which is the stronger result, because a probe can only
ever show that concurrency *was not observed*.

**Measured in `@earendil-works/pi-agent-core/dist/agent-loop.js`:**

- `executeToolCalls` (`:287-293`) picks between two paths. It takes the sequential
  one only when `config.toolExecution === "sequential"` **or** some tool in the
  batch declares `executionMode === "sequential"`.
- `Agent` defaults `toolExecution` to **`"parallel"`** (`agent.js:134`,
  `runtimeOptions.toolExecution ?? "parallel"`), and pi-coding-agent never passes
  the option at all — zero hits for `toolExecution` in its whole `dist/`. So the
  parallel path is what HappyVibe runs.
- pi-subagents declares `executionMode: "sequential"` on exactly three tools —
  the watchdog permission arbiter, watchdog review, and the LLM intent arbiter —
  and **not** on `subagent`. No Pi builtin declares it either. So a batch of two
  delegations does not opt into the sequential path.
- In `executeToolCallsParallel` (`:331-365`) the `for` loop awaits
  `prepareToolCall` for every call **in order** — and `prepareToolCall` (`:393`,
  hook at `:405`) is where `config.beforeToolCall` fires, i.e. our gate
  (`agent-session.js:223`, `_installAgentToolHooks`). Each non-immediate call is
  then pushed as a **deferred thunk**, and line `:365` runs the lot under one
  `Promise.all`.

**Consequence.** Gates are strictly serialized; executions are concurrent. Since
the child is spawned during *execution*, two delegations approved in one turn
spawn against whatever the session ceiling holds at that moment. A window opened
on A's approval and closed at A's `tool_execution_end` therefore overlaps B's
spawn, and B — if its agent declares no `tools:` — would inherit A's widened set.
`emitToolExecutionEnd` living inside the thunk does not help: the windows still
overlap.

**Design conclusion.** A per-delegation ceiling is not implementable through the
capability-ceiling registry, because that registry is keyed by **session id**
(`capability-ceiling.ts:158-166`) with no per-call key, and nothing in the public
surface lets a caller scope a ceiling to one delegation. The ceiling is therefore
**monotonic within a turn**: it rests at read-only, widens when a human approves
more, and is restored to read-only at a point where nothing can be spawning.

Two things keep that sound rather than merely convenient:

1. **The approval prompt shows the preflight-RESOLVED toolset**, which is computed
   against the live ceiling. So a delegation running under a widened ceiling is
   shown as such — the prompt can never understate what a child will get, which
   is the invariant that actually matters. Honesty replaces isolation here.
2. **An agent declaring no `tools:` is refused while the ceiling is wider than
   read-only.** That is FR3 stated as an enforcement rather than a side effect: an
   undeclared agent's reach must not depend on what some other agent was approved
   for earlier in the same turn.

Restoring at `agent_end` with no async runs in flight is safe for the same reason
the window was not: at that point there is no pending thunk left to spawn.

## The child guard (2026-08-21, FR4 measured end to end)

`hv-child-guard.ts`, injected by `pi-runtime/bin/pi-node.sh` (which IS
`PI_SUBAGENT_PI_BINARY`, i.e. children only). Proven against a real child Pi, not
a mock — `tests/child-guard-bridge.test.ts`, 10.2 s.

The test is built so that one pass exercises four separate mechanisms, because
each is useless without the others:

1. a fixture agent declares `tools: read, write`, so approving it must **widen the
   session capability ceiling** — otherwise the child has no `write` to attempt;
2. the child therefore launches with `write` in its `--tools`;
3. the wrapper injected the guard into it;
4. the guard clamped the write's `ask` to a **deny** and recorded it.

**The row it wrote, verbatim** (`<HV_CHILD_AUDIT_DIR>/<runId>.jsonl`):

```json
{"decision":"deny","tool":"write","wouldHave":"ask","source":"child",
 "summary":"{\"path\":\"note.txt\",\"content\":\"HI\"}"}
```

Four things that row establishes, none of which a unit test could:

- **The wrapper injection works.** The file existing at all means
  `hv-child-guard.ts` loaded inside a child. A wrong path would leave the
  directory empty forever, silently — which is why the test's first assertion is
  simply "a row exists".
- **`PI_SUBAGENT_RUN_ID` is set and is a UUID** — the filename was
  `0381633a-80c6-423d-b51a-c1bfd3bdc69b.jsonl`. (The env var is
  `PI_SUBAGENT_RUN_ID`, not `SUBAGENT_RUN_ID`; set at `pi-args.ts:783`.)
- **The clamp is what fired, not a rule.** `wouldHave: "ask"` says the parent
  would have prompted; there was no `write` rule in the fixture. A deny that
  merely echoed a configured rule would prove nothing about the clamp.
- **Exactly ONE row.** The child attempted the write once and stopped rather than
  retrying or working around it, which is what the block reason asks for in words
  ("Do not retry it and do not work around it"). A model looping on a denied tool
  burns the whole run and the user sees only a timeout, so this is worth noticing.

The test also asserts `note.txt` does not exist afterwards. The audit row could in
principle lie about what happened; the filesystem cannot.

**Why the audit file and not a Pi event:** `tool_execution_start` fires BEFORE
tool_call handlers, so it can never prove a call was blocked — a test asserting on
it passes whether the guard works or not. The audit row is written by the code path
that made the decision, so it is the only honest witness available from outside.

## The child session file (sub-agent cost, 2026-08-22, pi-subagents 0.53.0)

Where sub-agent money comes from, and the retraction of the mechanism first
proposed for it.

**A sub-agent child writes an ordinary Pi session file**, at:

```
<sessionsDir>/<parentSessionBasename>/<runId>/run-<idx>/session.jsonl
```

Measured in the installed tree:

| Claim | Evidence (0.53.0) |
| --- | --- |
| the root sits beside the PARENT's own session file | `src/extension/index.ts:267-273` — `path.join(path.dirname(parentSessionFile), path.basename(parentSessionFile, ".jsonl"))` |
| one directory per run | `src/runs/foreground/subagent-executor.ts:5440` — `sessionRoot = path.join(baseSessionRoot, runId)` |
| one directory per step, leaf `session.jsonl` | `:5454`, `:5470` |
| children always get one | `:3365` passes `sessionDir` unconditionally → `subagent-runner.ts:2333` `sessionEnabled` |
| per-turn cost is recorded | `subagent-runner.ts:728` — `usage.cost += eventUsage.cost?.total ?? 0` |

Two consequences. It is **not** in a tmpdir, so it lives as long as the parent
session — which is what lets a reopened session show the same numbers it showed
live. And it is the same format `src/main/calls.ts` already parses, so a child
needs no new parser, no new price table, and gets the same three-state billing
as the session's own calls (PRD §19).

`status.json` also exposes the live child's path on a public `sessionFile` field
(`shared/types.ts:575`, `:588`; written `subagent-runner.ts:2531`). We do **not**
use it: a completed run's `status.json` is in a tmpdir that is gone by the time a
session is reopened, so the layout resolver has to exist anyway, and reading the
status field for the live case only would be a second mechanism buying nothing.
`store.ts childSessionFiles` is the one resolver; `tests/pi-subagents-contract.test.ts`
pins the layout so a pin bump fails loudly rather than silently returning nothing.

**RETRACTED — `<asyncDir>/events.jsonl` carries no cost data.** The first draft of
the cost page proposed tailing it and summing per-turn `message.usage.cost.total`.
Every append to that file in 0.53 is lifecycle, control, steering, chain-append or
nested-interrupt **diagnostics**; grepping all of them for `cost` returns **zero**
hits, and there is no assistant-usage line in it at all. The claim had been reasoned
from the fact that the runner accumulates cost in memory (`:728`), not measured at
the file — the same failure mode as the 0.50 bump audit. Recorded here so nobody
re-proposes the tailer.

**Known ceiling, stated rather than discovered later:** the `subagent` tool schema
accepts a caller-supplied `sessionDir` (`src/extension/schemas.ts:330`). A
delegation for which the MODEL passes one relocates the child session outside the
resolver's root and contributes no rows. HappyVibe never passes it; the contract
test is what makes a layout change loud.

### The two ids (measured 2026-08-22, in the running app)

A delegation has **two** identifiers, and confusing them is silent.

| id | what it names | where it appears |
| --- | --- | --- |
| workflow **async id** | the `asyncDir` under `pi-subagents-uid-<uid>/async-subagent-runs/` | `details.asyncId`, the status poller's key, `subagent.async_started` / `async_complete` rows |
| run **inner id** | the child session DIRECTORY under the parent's session dir | `steps[].sessionFile`, and the `subagent.audit_rollup` row |

Three real runs:

| async id | child directory |
| --- | --- |
| `72e6fd2e-cc28-4de3-8b36-0d682851079d` | `8a2f9f62-d468-4120-880b-97738d611854` |
| `4d79e293-a2b0-4356-b318-2c39da7e374e` | `439ff3d5-24aa-470f-a153-fdf0271671ab` |

So a child path **cannot** be derived from any id the app holds. The link is
`steps[].sessionFile` on `status.json` — note the RUN level has **no**
`sessionFile` field at all (`sessionRoot` is there, the parent's directory, and
is not enough). `steps[].agent` carries the agent name, which no path contains.

Verified against a real run: upstream's own `totalCost.costUsd` (0.00096917)
equals what `calls.ts` computes from the child's session file, so parsing the

**Why this matters beyond this feature:** the failure mode is a lookup that
returns nothing rather than something wrong, so nothing throws and no test goes

### The six external-CLI builtins — the substantive decision

0.53 shipped 7 builtin agents, all native Pi children the capability ceiling governs. 0.58 ships

### Found during the GUI pass: the ceiling silently rescues a STALE agent file

The GUI pass repaired this developer's installed builtin agents towards the new bundle and left
the documented one-time `<agent>.md.bak`. The backup showed what had been on disk: an agent
declaring `tools: read, grep, glob, list, ls` — the pre-2026-08-02 bundle, i.e. asking for `glob`
and `list`, which **Pi has never registered** and which pi-subagents >=0.40 treats as a FATAL
strict-allowlist error ("Agent 'x' requested unavailable child tools: glob, list").

The first conclusion drawn from that was **wrong and is retracted**: that delegations to
`code-explorer` must therefore have been failing since the 0.40 bump. The Audit log disproved it
on sight — `SUB-AGENT CODE-EXPLORER · RULES WOULD HAVE ALLOWED` rows for `read` on 2026-08-23,
i.e. children that ran fine.

The reason is §12's capability ceiling, and it is worth writing down because nobody designed it
for this. The ceiling is INTERSECTED with the agent's declared list before the launch plan is
built, so the dead names are gone before upstream's strict check ever sees them. Measured
directly against upstream's own `resolvePiLaunchToolPlan`:

```
declared (the stale agent):  read, grep, glob, list, ls
ceiling (read-only):         find, grep, ls, read
effectiveToolAllowlist:      [read, grep, ls]      ← glob and list dropped, not rejected
```

So a bundled-agent file that goes stale across a Pi upgrade degrades to "the tools that still
exist" instead of failing the run. Two consequences worth keeping: the contract test's
"no bundled agent asks for a tool that does not exist" guards the BUNDLE and cannot see a user's
installed copy, and it does not need to — the ceiling is the backstop. And when a future report
says "my sub-agent is missing a tool", the tool list to compare is
`effectiveToolAllowlist`, not the agent file's `tools:` line.

Unrelated but recorded from the same pass: this developer's `pi-agent/agents` held pre-2026-08-02
content until today even though the content-hash install scheme landed on 2026-08-02 itself
(`9b45d1a`), so the repair fires the first time a build containing it actually runs. Which build
they normally launch was not determined and is not inferred here.

### The run-card caption bug: two same-agent delegations swapped (2026-08-29)

Reported from a real session: two sub-agents spawned, and the sticky cards' captions did not
match the runs — inverted. Confirmed from the session file, and it was worse than a swap.

The model emitted **two `subagent` toolCall blocks in ONE assistant message**, both
`code-explorer`:

```
call_1547cde07cdb4ba6a8f460d2   task = "Explain how the game Beat Saber works…"
call_27de2d17418446e1b8502a81   task = "Explain how the Minesweeper implementation…"
```

What each child actually did, from its own transcript: `753c611a` read `minesweeper.html`
(Minesweeper ×6, Beat Saber ×0); `f94ac707` read `beat-saber.html`. And the caption map persisted
in the session file held exactly one entry:

```json
{"runs": {"f94ac707-…": "Explain how the Minesweeper implementation … works."}}
```

**The Beat Saber run was captioned with the Minesweeper task, and the Minesweeper run had no
caption of its own.**

Two independent causes, both fixed.

**1. `hv-subagent-tasks.ts` keyed pending captions by AGENT, one slot, last-write-wins.** Both
calls were `code-explorer`, so the second stash overwrote the first before either run announced.
The module's own header justified the design with *"Pi runs tool calls one at a time, so the slot
is claimed before the next call writes it"* — **that is false**, and this session is the
counter-example: two toolCall blocks in one assistant message means both stashes land first. The
header also framed the risk as needing "started events in the opposite order"; it does not, and
same-agent fan-out is the normal shape rather than a corner.

Pending is now keyed by **`toolCallId`**, and the authoritative pairing is `bindRun(toolCallId,
runId)` called from the bridge's new `tool_result` handler — the one event carrying BOTH the tool
call id and `details.asyncId`. `claimTask`, which serves the `subagent:async-started` notify and
has no tool call id available, now **refuses when more than one dispatch matches** instead of
guessing. Keying by tool call id is what lets it see the ambiguity at all; a per-agent slot had
already destroyed the evidence.

**2. The renderer let the notify's caption win.** `App.tsx`'s re-key read
`next[detached.asyncId] ?? { ...fg }` — so an already-raised async card kept the notify's
best-effort caption and DISCARDED `fg`, whose `label`/`agent` came from `tool_execution_start`'s
own args and are exact per call. It now merges, preferring the exact values.

Note the interaction that made this reachable at 0.58 specifically: `subagent:async-started` fires
again for single-child delegations (0.55's unwrap put them back on the direct async path), so the
notify is raising cards again — with a caption it cannot pair. Under 0.50-0.53's workflow path the
notify never fired and the card was always built from `fg`, which is exact.

Pinned by `tests/hv-subagent-tasks.test.ts` (the real session's two ids and tasks are the
fixture), plus source-scan assertions that the bridge stashes by `event.toolCallId`, subscribes to
`tool_result`, and that Pi's own `ToolResultEventBase` still carries `toolCallId` — if a pin drops
that, the exact pairing degrades silently back to the guess.

## Two things the 0.58 branch found in USE, not in the diff (2026-08-29)

Both were reported by the user after the bump landed, and neither was caused by it. Recording
them here because each is a class of bug the bump audit could not have caught: one needed two
delegations in one turn, the other needed a session to be deleted.

### The run-card captions swapped — see §The run-card caption bug above

Root cause and fix are written up in that section. The measurement worth carrying forward is the
one about IDs: `details.asyncId`, the `<stem>/` child-directory name, and the
`subagent-artifacts/` filename prefix are three id spaces that only sometimes coincide. Anything
that needs to associate a run with its data must collect ids from every available source rather
than deriving one from another.

### A model the app was silently not using

`[pi:stderr] [pi-subagents] Skipping model 'openrouter/qwen/qwen3.8-flash' due to a cached
exclusion (reason: Subagent produced no output …; expires: 2026-08-30T10:35:51.349Z).`

The store, captured verbatim before it was cleared:

```json
{"version": 1, "exclusions": [{
  "modelId": "qwen/qwen3.8-flash", "provider": "openrouter",
  "reason": "Subagent produced no output (possible model cold-start or empty response).",
  "recordedAt": 1787999751349, "expiresAt": 1788086151349 }]}
```

`expiresAt - recordedAt` = exactly **86,400,000 ms**, i.e. upstream's
`DEFAULT_MODEL_EXCLUSION_TTL_MS = 24 * 60 * 60_000`. The file lives at
`<TEMP_ROOT_DIR>/model-exclusions.json` where `TEMP_ROOT_DIR` is
`os.tmpdir()/pi-subagents-<scopeId>` — **per-UID, so one flaky child disables that model for every
session and every workspace on the machine**, and the only signal is `model-fallback.ts:413`'s
`console.warn`, which `PiClient.ts:61` prints to a dev terminal and nowhere else.

Reachability at 0.58 is worse than at 0.57: #1556 fails an *explicitly* requested model closed
rather than falling back, so a per-agent model override plus one empty response makes that agent's
delegations fail outright for a day.

Two mitigations shipped. `modelExclusions.defaultTtlMs = 5 * 60_000` — upstream applies a
configured value with `shortenExisting`, so setting it also caps records already on disk and a
stale 24-hour entry self-heals at the next start rather than needing the file deleted. And a
`model.excluded` audit row per live exclusion, reported at delegation start and deduped by
model+expiry.

**The path is ours, and that is a deliberate reversal of the obvious approach.** Reading upstream's
default location would mean re-implementing `os.tmpdir()/pi-subagents-<resolveTempScopeId()>`,
which is the same move that produced the MCP keychain drift. `PI_MODEL_EXCLUSIONS_PATH` is
upstream's own documented hook (`EXCLUSIONS_PATH_ENV`), so spawn.ts sets it to
`<agentDir>/model-exclusions.json` and main reads a file it chose. `tests/model-exclusions.test.ts`
pins the env name against upstream's source, so a rename fails there rather than leaving main
reading a file nobody writes.

**The audit row is a third TYPE, and that mattered.** The first design put it through the bridge's
existing `hv.audit` envelope — wrong, because `AuditDecision` is `allow | allow-session | deny`, a
permission vocabulary. Forcing "your model was substituted" into it is the same shape as the
`wouldHave` misreport §6 exists to prevent. It follows `assistant.oneshot` instead: main writes it,
`toAuditRow` discriminates on the event TYPE (not on `data.kind`, which is the bug that misfiled
every permission decision once already), and it carries no cost or token figure because it has
none.

## The fleet round (2026-08-29) — items 1–4 + 6 of the P4 ranking

Source shapes below are from the vendored **pi-subagents 0.58.0** tree. Where a
claim is marked MEASURED it came off a live run; where it is marked SOURCE it is
a read of upstream's code and is pinned by `tests/pi-subagents-contract.test.ts`
so a pin bump fails rather than the feature silently disappearing.

### 1. The live child context gauge — two fields, one poll

SOURCE. `AsyncStatus.steps[]` (`shared/types.ts`) carries both halves, and both
survive into the `status.json` projection (`runs/background/async-status.ts:47`
and `:52`), which is the only channel a detached run has to us:

```
steps[].tokens : TokenUsage { input, output, total, window?, windowPeak? }
steps[].contextLimit? : number
```

`window` is **input + cacheRead for the LATEST assistant turn** — occupancy, not
spend — and `windowPeak` is the high-water mark. `contextLimit` is the model's
window, resolved from Pi's own registry
(`subagent-runner.ts:1655`, `findModelInfo(candidate, …)?.contextWindow`), so it
is **absent whenever the resolved model is not registered**. That absence is the
common case for a custom model id, not an edge case, which is why the card
renders no gauge at all rather than a 0%.

The update is genuinely live: `step.tokens` is rewritten on every child
`message_end` (`subagent-runner.ts:3677`), i.e. once per child turn, on the
500 ms poll the app already runs. Upstream's own TUI formats the same pair as
`ctx 12.8k/200k (6%)` (`shared/formatters.ts:25`); HappyVibe renders the
percentage through `zoneOf` instead, so the child's gauge and §9's session gauge
cannot disagree about what amber means.

**Trap worth recording:** `statusUnchanged` decides whether a tick reaches the
renderer at all. A field it does not compare is a field that freezes at whatever
the first pushed tick carried — so the gauge and the per-child rows are both in
that comparison, not only in the read.

### 2. The agent inventory — the app was listing 2 of 9+

SOURCE, and the gap was much wider than the "seven native builtins" the bump
round recorded. `discoverAgents` / `discoverAgentsAll` (`agents/agents.ts:2240`,
`:2311`) read from **six** places plus installed packages:

| scope | where |
|---|---|
| builtin | pi-subagents' own packaged `agents/` dir |
| user | `PI_SUBAGENT_EXTRA_AGENT_DIRS` (PATH-style), `<agentDir>/agents`, `~/.agents` |
| project | `<projectRoot>/.agents`, `<projectRoot>/.pi/agents` |
| package | `<projectRoot>`, `<projectConfigDir>/npm/node_modules`, `<agentDir>/npm/node_modules`, and **the global npm root** (`collectPackageSubagentPaths`, `agents.ts:585`) |

and `projectRoot` comes from `findConfiguredProjectRoot(cwd)`, which walks **up**
— the bridge's old scan used `process.cwd()` directly. So the app's two-directory
enumeration missed upstream's seven native builtins, everything in `~/.agents`
(the probe's stray `10x`), the legacy `.agents` project dir, any parent-directory
project root, and every package agent.

The same function fed `renderSubagentSection`, which told the model verbatim
*"the agents above are the full, current list"* every turn. That sentence was
false; it is gone, and the `{action:"list"}` countermand beside it stayed
(that one is load-bearing — the tool description steers the model to call `list`
first, which costs a turn).

**Precedence, which is what makes authoring `worker` free** (`agent-selection.ts`):

```
builtin  <  package  <  user  <  project        (later scopes overwrite by name)
```

So `<agentDir>/agents/worker.md` shadows upstream's builtin `worker` outright,
taking its `defaultContext: fork` and `defaultReads: context.md, plan.md` out of
play rather than inheriting them. A project-scope agent still shadows ours,
which is the same rule and not a new hole — the boundary modal still names what
any of them may do.

**MEASURED, and the reason the page filters twice.** `discoverAgentsAll` applies
our settings overrides but — unlike the singular `discoverAgents`, which ends
`.filter((agent) => agent.disabled !== true)` — **does not drop what they
disable**. The first implementation filtered only on `disabled`, and
`tests/agents-bridge.test.ts` immediately returned `claude-code` in the roster:
the bridge test's environment has no settings write. CLAUDE.md also records that
a PROJECT-scope `.pi/settings.json` beats the user scope outright, so a cloned
repo can re-enable one. The page therefore filters on **`isExternalCliAgent`,
the same predicate the bridge refuses with**, plus any `runner.type ===
"external-cli"` so a seventh adapter is hidden before the contract test has been
updated to name it. A page that advertises an agent the bridge declines is worse
than one that omits it.

### 3. Child-scoped stop — a different verb from `interrupt`

SOURCE. `SUBAGENT_RPC_METHODS` (`extension/rpc.ts:34`) is
`["ping", "status", "manage", "spawn", "steer", "interrupt", "stop", "resume"]`.
The bridge has driven `interrupt` since the async round; `stop` is the one that
takes a child:

```
stop  { runId, childId }   → { runId, asyncDir, previousState, state: "stopping", childId }
```

`childId` resolves through `resolveAsyncStatusChild` (`runs/shared/child-identity.ts:23`)
against `asyncStatusChildIdentityCandidates(step, index)`, and a malformed one is
**rejected, not widened** — `"RPC stop childId must be a non-empty string…"`
(`rpc.ts:526`). That failure direction is the whole value: a bad id must never
become a run-level stop that kills the siblings the user was keeping.
`isStoppableAsyncStatusStep` is `pending || running`, mirrored in the renderer as
`isStoppableChild` so the ◼ disappears the moment a child finishes.

Reachable only above one child: a `{agent, task}` delegation has exactly one
step. Multi-child runs are `workflowScript` fan-outs (`runs.all([...])`), which
the model writes on its own.

### 4/5. `@agent` and the roster chip

No upstream surface involved — pure renderer. Recorded because of one shape
decision: an agent pick inserts **plain text** and is deliberately never written
to `mentionMap`, the label→relPath map `extractMentions` resolves on send. An
entry there would make the app try to attach a file named after the agent. The
model already receives the roster in its system prompt every turn, so `@worker`
in the prose is enough for it to delegate.

The `@` menu's keyboard index still addresses `mention.items` (files only) — the
agent rows are mouse-picked, which keeps the existing keyboard contract
byte-identical rather than re-deriving a combined index.

### 6. Child thinking — and the confinement root that is easy to get wrong

SOURCE, on top of the bump round's Probe 2 measurement. `transcriptPath` is on
both routes: `results[].transcriptPath` on a foreground delegation and
`steps[].transcriptPath` in `status.json` for a detached one. The compact
`toolCalls` projection the card already renders does **not** carry thinking, so
the file read is the only route.

**The confinement root is the app's SESSIONS dir, not `os.tmpdir()`.**
`readSubagentStatus` guards `os.tmpdir()` because a run dir lives there; but
pi-subagents writes `subagent-artifacts/` **flat into our own session directory**
(`src/main/store.ts:268`). Reusing the status poller's guard here returns an
empty list for every real transcript — and an empty list is indistinguishable
from "this run did no thinking", so the wrong guard ships green. The containment
check is `file.startsWith(root + path.sep)`, not a bare prefix: `<root>-evil`
starts with `<root>` as a string and is not inside it.

Worth stating plainly, and now recorded in the PRD: **HappyVibe renders no
thinking anywhere else** — not even the main agent's — so the sub-agent card is
the app's first and only thinking surface. That asymmetry is deliberate (a
child's reasoning is the one the user has no other way to see) and is the
argument for the toggle being off by default.

### The live batch needs a key the worktree does not inherit

Recorded because it cost a full six-minute run that looked green. `.env` is
gitignored, so a fresh worktree has none, and `tests/liveModel.ts` then leaves
`KEY` undefined and **every `skipIf(!KEY)` test skips**. The batch exits 0 and
reports passes — those are the key-free tests that live inside the live files
(CLAUDE.md documents nine of them) — so the exit code says nothing.

The tell is the FILE count, not the exit code: `6 passed | 12 skipped (18)`
means twelve files never ran a model turn. Copy `.env` in from the main checkout
before believing a live result in a new worktree, and check the provider answers
200 before believing a red one.

### One test that failed for the right reason

`tests/prompt-templates-reserved.test.ts` went red the moment

### The GUI pass corrected two things the source did not (2026-08-29)

Both found by driving the running app, neither visible in the tarball.

**1. `steps[].childId` is declared but NULL on the wire, and it is not what
`stop` resolves anyway.** Measured on a live two-child `workflowScript` run:

```
steps[0]  agent=code-explorer  status=completed  childId=None  workflowKey='a'  runId=None
steps[1]  agent=reviewer       status=running    childId=None  workflowKey='b'  runId=None
```

Upstream's own `asyncStatusChildIdentity` (`runs/shared/child-identity.ts:15`) is
`step.workflowKey ?? step.runId ?? "step:<index>"`, and `resolveAsyncStatusChild`
accepts **any of those three** — `childId` is not among the candidates at all.
The first implementation keyed the per-child STOP on `steps[].childId` because
that is what the type advertises, so the control would have rendered on exactly
zero runs. The reader now mirrors upstream's chain; the contract test asserts
the chain rather than the field. This is the `measure-the-wire-not-the-source`
lesson a second time, on a field whose name made it look authoritative.

**2. A `mode:"workflow"` run's steps carry no `tokens` and no `contextLimit`,
so a fan-out gets no per-child gauge.** Same measurement — both workflow steps
had `contextLimit=None, tokens=None`, while the `mode:"single"` run beside it
had `contextLimit=1000000, tokens={window:73557,…}`. So the context gauge is a
SINGLE-delegation feature in practice at 0.58. It degrades the way it was
designed to (no reading ⇒ no gauge, never a 0%), so nothing misreports — but the
ranking doc's assumption that the gauge lights up per child on a fan-out is
false, and is corrected here rather than left to be rediscovered.

**3. `0%` is the wrong display for a real sub-1% reading.** Qwen3.8 Flash has a
1M window, so a child sits at ~2.2k for the first half-minute — a true 0% after
rounding, which photographs as a broken gauge. `childGauge` now returns `<1%`
when the percentage rounds to zero but the window is non-empty, and a genuine
zero still reads `0%`. Caught only by looking at it.

### 4. Another tool's slash commands were being offered as sub-agents

Found by the user looking at the Agents page, not by any test. `~/.agents` is
**shared**: pi-subagents claims it as its user agent dir, while Claude Code and
tools built on it keep slash commands in `commands/` and skills in `skills/`.
Upstream scans it **recursively** and excludes exactly one subtree —
`isLegacyAgentSkillPath` (`agents.ts:1817`) drops `.agents/skills/**`, which is
why 48 installed skills were correctly ignored. Nothing excludes `commands/`.

Measured on this machine: `~/.agents/commands/superset/{10x,doctor,feedback,setup}.md`
were listed on the Agents page **and injected into the model's roster every
turn** as delegatable sub-agents. They are not agents at all — they carry Claude
Code's `argument-hint` and `allowed-tools` keys and reference
`${CLAUDE_SKILL_DIR}`, so a delegation to one would run a fragment of another
product's UI as a Pi child.

`isSlashCommandPath` (hv-agents.ts) drops any definition with a `commands` path
SEGMENT — upstream's own skills-exclusion shape, one segment name different, and
segment-matched so an agent named `commands-expert` survives. Measured after:
the roster went **13 → 9**, which is exactly upstream's five native builtins
(`delegate`, `oracle`, `researcher`, `reviewer`, `scout`), HappyVibe's three
bundled (`worker`, `agents-md-maker`, `code-explorer`), and one genuine
user-owned file.

It HIDES rather than refuses, and that split is deliberate: these are ordinary
Pi children the capability ceiling governs, unlike the external-CLI six which
are refused because nothing can bound them. A user who explicitly names one
still gets it. The defect was advertising another tool's commands as ours.

**The general lesson, worth carrying into the next round:** a shared directory
is not an inventory. Upstream's discovery answers "what `.md` files with
frontmatter exist under these roots", which is a superset of "what agents does
this user have" — and the gap is filled by whatever other tools the user has
installed. Anything reading `~/.agents` should ask what subtree a file is in.

### The artifacts sweep missed `outputs/`, for the reason that made it safe

Found 2026-08-29 by reading a `[hv] swept 0 orphaned sub-agent dir(s), 3 artifact
file(s)` line and checking what it could reach. pi-subagents writes TWO shapes
into our session dir's `subagent-artifacts/`:

```
<runId>_<agent>_{input.md,output.md,meta.json,transcript.jsonl}   flat, 4 files per run
outputs/<runId>/…                                                 a directory, per run
```

The second appears when a child declares `output:` in its frontmatter — upstream's
`scout` and `researcher` both do (`output: context.md`, `output: research.md`).

Both cleanup halves keyed on the flat filenames and skipped any name without an
underscore. That guard is CORRECT and load-bearing — pi-subagents keeps its own
`.last-cleanup` retention timestamp in the same directory, and without the guard
`slice(0, indexOf("_"))` turns it into a plausible-looking run id — but it also
made `outputs/` permanently invisible to both halves. So a deleted session left
the child's written output behind, and the startup sweep never collected it:
exactly the "delete means delete" gap the flat artifacts had, in the one shape
nobody looked at.

Two passes were needed, not one. `deleteArtifactsFor` now removes
`outputs/<id>/` for each id it is given; and the sweep needs its OWN directory
listing to find candidates, because a run can survive *only* as an output
directory — pi-subagents' 30-day retention can take the flat files while the
directory stays, and such an id appears in no filename for the existing scan to
match. The `outputs/` container itself is never removed, only entries inside it.

Verified read-only against the real install before shipping: the one live
`outputs/` entry is referenced by a session file and is kept.

### The startup sweep was deleting live sessions' child transcripts (2026-08-30)

Found by watching `f64ee3d7_code-explorer_transcript.jsonl` disappear across an app
restart while the session that produced it was still open — noticed only because the
run card had just started reading those files.

`sessionRunIds` (store.ts) takes a UNION of two id spaces, with a comment saying they
"only sometimes coincide" and that deriving one from the other silently misses files:

```
<sessionsDir>/<stem>/<runId>/run-0/session.jsonl   ← child DIRECTORY names
"asyncId" / "runId" strings inside <stem>.jsonl    ← the parent's own record
```

`sweepOrphanedSubagentData` read only the second. So an artifact filed under a child
run id the parent transcript never names looked orphaned, and was deleted — at every
single startup, for sessions that were perfectly alive. Measured on this install:
**10+ child-directory ids appear in no session text at all**, so this was routine, not
a corner case. It had been latent since the sweep landed; it only started costing
anything visible when the card began reading transcripts.

The fix is to build `referenced` from the same union. Order matters and is asserted:
the directory pass runs AFTER half 1 has removed the `<stem>/` of every session whose
`.jsonl` is gone, so a *deleted* session can never protect its own artifacts with the
directories it left behind. A test also pins that the sweep still collects a genuinely
orphaned artifact — widening `referenced` too far would quietly turn it into a no-op.

### Per-agent on/off, and who is allowed to see what (2026-08-30)

The roster is injected into the system prompt on **every turn**
(`happyvibe-bridge.ts`, inside the `before_agent_start` hook), so each listed
agent is a standing context cost — measured on a stock install, **6 agents ≈ 240
tokens per turn**. That makes switching agents off a context lever, not just
tidiness, which is why the Agents page states the cost per agent and in total.

Three facts made it cheap, all verified rather than assumed:

**The roster is rebuilt per turn, so a toggle needs no respawn.**
`enumerateAgents()` is called inside the prompt hook, and `discoverAgentsAll`
re-reads `<agentDir>/settings.json` on every call. Unlike MCP config (which needs
the `scheduleMcpReload` respawn machinery) a switch lands on the very next
message of every live session.

**The estimate is measured from the injected text, not guessed.**
`subagentRosterLine` builds one agent's line and `renderSubagentSection` composes
from it, so the number on the page and the tokens actually spent cannot drift.
Chars→tokens is the bridge's own `Math.ceil(chars / 4)`.

**Only explicit user choices are stored.** Config `agentsEnabled` is SPARSE and
resolution is `userChoice ?? default` — the shape skills already use
(`activation?.[skill.id] ?? true`). Seeding the file with today's defaults would
freeze this round's judgement forever; sparse means a later change to our
defaults still reaches everyone who never expressed an opinion.

**The visibility rule, which took two passes to get right.** The first version
listed every disabled agent so it could be switched back on — and immediately
put `researcher` and `oracle` back in front of the user, which is not what
"disabled" was supposed to mean. The rule that resolves it is about **who**
disabled it, not the state:

| disabled by | listed? | why |
|---|---|---|
| HappyVibe (`UNSUPPORTED_BUILTIN_AGENTS`, `EXTERNAL_CLI_AGENTS`) | no | it cannot do its job here; a switched-off row invites turning it on to find it does nothing |
| the user | yes, dimmed | you have to see it to switch it back on |

Both forced sets are applied last and unconditionally in `resolveDisabledAgents`,
refused by name in `setAgentEnabled`, and dropped in the bridge before the page
or the roster sees them — so a hand-edited config cannot re-open either.

**One writing trap worth keeping.** Re-enabling an agent must write
`disabled: false` **explicitly**. Omitting the key leaves the `disabled: true` a
previous run already wrote into Pi's settings file, so the switch would appear to
do nothing. Pinned by a disable→enable round trip that also asserts a user's
`{model: …}` override survives beside the flipped flag.

## The run rail, and the one instant that holds `asyncId` beside `toolCallId` (2026-08-30, UX-feedback round)

Two reports from a real session. The second one is the interesting measurement.

### The stale in-transcript delegation card

**Symptom, verbatim:** twenty minutes after an async delegation completed, its
card in the chat still read *"Waiting for the subagent to respond…"* with a green
dot titled `dispatched`.

**Cause, and it is structural rather than a slip.** An async delegation's
lifecycle crosses two channels that never met:

| moment | channel | payload |
|---|---|---|
| dispatch | `tool_execution_end` | `result.details.asyncId` present, `details.results` **absent** — a receipt, not an answer |
| completion, minutes later | `hv.subagent` notify, `stage:"complete"` | `{runId, agent?, status, summary?}` — **no `toolCallId`** |

So the notify had no way back to the transcript card and only ever updated the
sticky one, which slides away 2.5 s later. The transcript card — the permanent
record — froze on the dispatch receipt for the life of the session.

**The link exists for exactly one instant.** Both ids are in hand together only
inside the `tool_execution_end` handler (`t.toolCallId` and
`asyncResultInfo(t.result).asyncId`), and that handler used to discard the
pairing. `App.tsx`'s `asyncCards` ref (`asyncId → toolCallId`, per session) is
captured there for that reason and nothing else. It is deliberately **not**
persisted: a reopened session's card is rebuilt by `restore.ts`, which has the
run's cost instead.

**Two fields that existed on the wire with no reader.**

1. `hv.subagent` `complete` has carried `summary` since the relay was written
   (`happyvibe-bridge.ts`, `d.summary?.slice(0, 500)` — capped at 500 chars
   upstream-side). Nothing read it. It is the card's collapsed line now.
2. `window.hv.subagentInspect` was built 2026-08-21 (`src/main/subagentInspect.ts`,
   `ipc.ts:hv:subagent-inspect`) and had **zero renderer callers** until this
   round — `grep -rn subagentInspect src/renderer` returned only the type
   declaration. It answers `/subagents-inspect-rpc` from upstream's own
   artifacts, **costs no model turn**, and **keeps working after the result has
   been delivered**, which is precisely what a finished run's card needs. It is
   scoped to the current session's children and answers `foreign_session` after
   a respawn — the card must NAME that rather than spin, because a card that
   never hears back spins forever.

**Why the card's expand toggle was empty before.** `SubagentTraceView` already
refused to say "waiting" when it had a `cost` — a guard written for the RESTORE
path, whose comment says *"'waiting' would be a lie about a run that finished
long ago."* The live path never set `cost` on a tool card, so that guard had
never once fired live. It now takes an `outcome` beside `cost` for the same
reason.

Pinned by `tests/delegation-card-outcome.test.ts` (the copy as data, the routing
as a source scan, plus an ordering assertion that the final cost is read BEFORE
the sticky card is torn down) and `tests/subagent-inspect-card.test.ts`.

### The rail's geometry

The resting state of both run families is a circle now (PRD §12/§26,
2026-08-30). Four things about it are load-bearing and would each break silently:

1. **The overlay is `absolute` inside a `sticky` container**, which is what makes
   it paint OVER the transcript rather than push it. `absolute` positions against
   the nearest **positioned** ancestor, so that container carries `relative` —
   without it the card escapes to the pane and lands elsewhere. Pinned by an
   exact-class assertion, because the failure is visual and silent.
2. **It stays at `z-20`.** It is a readout, not a modal; `.hv-overlay` /
   `.hv-dialog` own `z-index: 100` and `tests/modal-layer.test.ts` guards that
   scale.
3. **There is no `fixed inset-0` click-catcher**, the idiom every other menu in
   this app uses. `browserCoverage.ts` gathers coverage candidates by class word
   and judges them by BOX, so a full-viewport catcher reads as covering every
   browser pane. Dismissal is toggle-the-same-circle plus Escape.
4. **The hover readout has no gap** between circle and panel — the `pt-1` is
   inside the hover target. A gap means the pointer leaves on the way in and the
   STOP button inside is unreachable, which is the whole point of that panel
   (PRD §12's 2026-08-22 decision put a running delegation's spend on the line
   that stops it, and a circle has no line).

Plus one Tailwind fact: **the avatar's hue is an inline `style`, never a computed
class.** The JIT scanner never sees `` `bg-[hsl(${hue}...)]` `` and emits
nothing, so every circle would render unstyled. Pinned in
`tests/run-rail-layout.test.ts`; the policy itself (state, hue, which runs get
promoted to a full card) is pure in `runRail.ts` and pinned in
`tests/run-rail.test.ts`.

**What went away:** §26's `STACK_CAP` / `visibleRuns` / `summaryLabel` — the
"≤2 cards, then a `N running · titles` strip" rule. It existed only because a
shared cap would have changed delegation-card behaviour, which was out of that
round's scope; the rail IS that shared treatment.

### The GUI pass earned its keep: a restored card had no id to inspect with

Every unit test for the inspect route fed a **live** card, whose `result` is the
structured dispatch object. `restore.ts` flattens a toolResult through
`messageText`, which keeps only its text blocks — so on the one path where the
fetch is actually needed (a live run streams its own transcript and never asks),
`asyncResultInfo(card.result)` found nothing and the expanded card was **125
characters**: honest, and empty.

Measured on a real session file during the pass:

| where the id lives | survives restore? |
|---|---|
| `message.details.asyncId` (structured sibling of `content`) | **yes** — but `messageText` never looks at it |
| the text block, as `Async: code-explorer [02320d30-…]` | yes, as prose |
| `result.details.asyncId` (what the live card reads) | no — `result` is a string by then |

So the id is **read** from `details` and carried
`restore.ts` → `restoreMap.ts` → `ToolCardData.asyncId`, not parsed back out of
the flattened text. A first attempt did try the regex route and is recorded here
because it looked right: a grep for `"asyncId"` in the raw session row matches
the `details` sibling, not the text, so the regex could never have fired on what
`messageText` returns.

Two rules this touches, both of which would break it silently again:

- **`asyncResultInfo` must stay structured-only.** It answers "is this dispatch
  still in flight" and is what raises the "running in the background" line. A
  restored card is by definition a finished run, so widening that function to
  understand the restore shape makes every reopened delegation claim background
  work — the exact bug this round fixed, re-entered through the fix for it.
- **`restoreMap.ts` drops any field it does not NAME**, per its own header. The
  images field was lost that way once already; `asyncId` is named beside `cost`.

Verified end to end in the running app: `subagentInspect` on a reopened session
returned `ok:true`, `status:"complete"`, 8 child messages and 1,801 chars of
`finalOutput` — no model turn.

## §31 Documents — the `hv.document-read` wire (2026-09-04, anydoc 0.2.4)

**The envelope.** `document_read` is a thin shell over ONE blocking input, the
`browser_get_text` shape exactly. Payload on **`title`**, because this is an input — a notify
carries its payload in `message`, and getting that backwards is how a card silently never appears.

```
title: {"kind":"hv.document-read","path":"<workspace-relative or absolute>","offset":<n>?,"limit":<n>?}
```

**Main's reply** (always sent — an unanswered `ctx.ui.input` hangs the turn):

```jsonc
// success
{"ok":true,"path":"/abs/report.docx","name":"report.docx",
 "text":"# Q3 report\n\n…",                       // the Markdown slice
 "facts":{"format":"docx","totalLines":1240,"totalBytes":90112,"from":1,"to":2000}}
// failure — `text` is already the SENTENCE, not a code
{"ok":false,"path":"/abs/a.pdf","name":"a.pdf",
 "text":"This PDF has 2 pages; page 2 is a scanned image and could not be read locally. Ask the user to attach screenshots of those pages."}
```

`facts` has **no `pages`** and that is a measurement, not an omission: no page count exists on a
successful conversion anywhere in anydoc's API (ad1.md §3.1). `pageCount` rides the `needsOcr`
rejection only, which is where the sentence gets the numbers it names.

**The tool result.** `documentReply` (happyvibe-bridge.ts) puts `<name> — <factsLine>` above the
Markdown and passes the whole reply through on `details`, plus a rendered `details.factsLine` which
is what the card shows beside the path.

**The prompt block**, for an attached or `@`-mentioned document:

```
<document path="/abs/report.docx" format="docx">
…markdown…
[truncated at N chars — call document_read with offset=L to continue]
</document>
```

No `pages` attribute, same reason. `stripInjectedBlocks` cuts on `\n\n<document `, so the bubble
shows a chip; `parseDocumentChips` (renderer) and `parseDocumentHeaders` (main) read the header
back, and `tests/mentions.test.ts` pins the two regexes against one fixture.

**The audit row.** `{type:"document.read", data:{path, ok, format, bytes, shown, code}}` — path and
sizes, never content. The `read`-on-a-document refusal emits a separate row with
**`source:"document"`**, which is the only thing that emits it and therefore what the live test
asserts on (`tool_execution_start` fires before the tool_call handlers, so it can never prove a
call was blocked).

**Sidecar protocol** (`pi-runtime/bin/anydoc-bridge.mjs`, argv `<path> [offset] [limit]`, or
`--probe`): one JSON line on stdout, **exit 0 for both outcomes**; a non-zero exit means a real
crash and main turns it into a `crash` sentence carrying the stderr tail. `--probe` answers
`{"ok":true,"probe":true,"version":"0.2.4"}`, or `{"ok":false,"code":"unavailable"}` where there is
no prebuilt — which is what lets the settings row and the `+` row say *not available on this
platform* instead of failing on first use.

### 6. The task file, and the write nobody was watching (added after the first live batch)

The live batch found one real regression, and fixing it produced a second. Both trace to a single
clause 0.63.0 added to `shouldDeliverTaskViaFile` (#1793, "keep macOS subagent tasks out of argv
by delivering them through temporary files"):

```
0.58.0: delivery === "file" ||                          task.length > TASK_ARG_LIMIT
0.64.0: delivery === "file" || platform === "darwin" || task.length > TASK_ARG_LIMIT
```

macOS is our only platform, so what used to fire for tasks over 8,000 chars now fires for every
delegation. No opt-out exists: `SubagentTaskDelivery` is `"auto" | "file"`, there is no `"argv"`
value, and the internal override (`subagent-runner.ts:2072`, after a SIGKILL) only ever moves
towards file.

The measured child argv, from a throwaway probe extension wired into `pi-node.sh`:

```
node .../dist/bundle/cli.js
  --extension .../hv-child-guard.ts
  --mode json -p --session … --model openrouter/deepseek/deepseek-v4-flash
  --tools read,write --no-extensions
  --extension .../subagent-prompt-runtime.ts
  --no-context-files --no-skills
  --system-prompt /var/…/pi-subagent-ltj8yX/writer.md
  @/var/…/pi-subagent-ltj8yX/task.md
```

Note `writer.md` in the SAME directory. That is why the exemption reads the exact argv positional
rather than matching a directory shape — a shape match would have exempted the system prompt too,
and a `pi-subagent-*/task.md` pattern would let a child read a concurrent run's prompt.

**Bug 1 — the child was refused its own task.** The file is outside the workspace, so the parent's
rules resolve a read of it to `ask`, and `ask` means deny inside the guard:

```
{"tool":"read","decision":"deny","wouldHave":"ask","source":"child",
 "summary":"{\"path\":\".../pi-subagent-qCYA24/task.md\"}"}
```

It only surfaced when the model called `read` on the literal rather than Pi expanding the `@`
itself, so it failed **2 runs in 3**. First called deterministic here on two failures; the third
run passed, with a probe attached. Intermittent is worse than always.

**Bug 2 — the fix caused it.** Once the child could read that path, the model began writing its
output next to the task. Correlated by audit-file mtime against the fix commit (14:58:21):

| when | write paths observed |
|---|---|
| 13 runs, 2026-09-01 → 14:57 | relative `ok.txt`, or absolute inside `hv-guard-cwd2-*` |
| 6 runs, 15:10 → 15:18 | two into `<tmpdir>/pi-subagent-*/ok.txt` |

Zero tempdir writes before, two after. The row said `allow` and the user's file was absent — the
exact shape this layer exists to prevent.

The hole underneath was structural and older than any pin: **`childDecision` takes
`(rules, call, opts)` and matches on the TOOL NAME only** — no path logic at all — so
`{layer:"tool", pattern:"write", action:"allow"}` reached the whole filesystem.
`escapesWorkspace` (hv-child-guard.ts) now confines `write`/`edit`, and after it fired:

```
{"tool":"write","decision":"deny","wouldHave":"allow","source":"child",
 "summary":"{\"path\":\".../pi-subagent-s0U8Hv/ok.txt\",\"content\":\"HI\"}"}
```

`wouldHave` reports the RULES, `decision` reports confinement — which is why the check runs after
`childDecision` rather than instead of it.

Three details that are load-bearing: symlinks resolve through the nearest EXISTING ancestor
(the target file is by definition usually absent, and a string check passes a link planted inside
the workspace); containment is `=== root || startsWith(root + sep)`, never a bare startsWith, or
`/tmp/ws-evil` reads as inside `/tmp/ws`; and the tool set is DERIVED from Pi's schemas
(`write.js`, `edit.js` both declare `path: Type.String()`) with the test re-scanning every builtin,
so a future path-taking writer fails there instead of arriving unconfined. `bash` is excluded
because it cannot be path-confined — a documented limit, not an omission.

**Unmeasured, and deliberately not claimed.** The refusal reason now names the workspace, since Pi
feeds a block reason back to the model. 6/6 green after that change — but no deny-then-retry
sequence appeared in those runs, and at the prior ~25% failure rate 6/6 by luck is ~18%.
Attributing it would need interleaved arms, which were not run. Residual weakness, stated: a
refused child does not always retry, so a delegation can still end with no file — loud now instead
of silent.

**The generalisable lesson, worth more than either fix: a permission exemption changes what the
model can SEE, and therefore what it tries next.** Widening one read moved the failure onto a write
nobody was watching. When relaxing a gate, check what the newly visible surface invites.

Two more, both invisible to 3,145 passing tests and a 20-file live batch.

`spawn.ts` now sets `HV_ARTIFACTS_DIR = <sessionDir>/subagent-artifacts` and `escapesWorkspace`

artifacts directory, **not `sessionDir`**, or every session file would become writable — pinned as
an exact string.

```
ALLOW  write  {"path":"…/subagent-artifacts/outputs/3f4b465d-…"}
```

No deny, one write instead of two.

field a reviewer needs — which file — fell past the cap on every write. Both rows in the table
above demonstrate it: one allowed, one denied, neither naming a path. §13's promise is that a user
reviews what RAN; a row that cannot say what it acted on does not keep it. `summarise` hoists
`path` to the front and keeps the row parseable JSON whenever it fits.

Note the order of causation, because it generalises: **the truncation is what made the first
finding undiagnosable.** Until the path was visible there was no way to tell where the allowed
write had gone — and the child's own account was wrong. It reported saving to
`.pi-subagents/artifacts/root-files-context.md`, a file that exists nowhere on the machine. A
model's narration of its own side effects is not evidence; the audit row is, which is exactly why
the row has to be complete.

Incidental confirmations from the same pass, all measured rather than assumed: the boundary modal
lists `bash, find, grep, ls, read, write` (no `glob`, no `list`, so the strict-allowlist contract
holds at 0.64); the chip reads **6 agents**, i.e. 12 bundled minus the 6 external-CLI adapters

## §33 Memory — the `hv.memory-*` wire and what it costs (2026-09-04)

Three registered tools over three BLOCKING envelopes. Main writes, main answers, always — an

contract as `hv.plan-write`, and for the same reason.

### The envelopes

```jsonc
// bridge → main, ctx.ui.input(JSON.stringify(payload), "")
{ "kind": "hv.memory-save",   "scope": "global"|"workspace",
  "type": "user"|"feedback"|"project"|"reference",
  "name": "<free text the model chose>", "description": "<≤150 chars>",
  "content": "<≤4 KB>", "toolCallId": "…" }
{ "kind": "hv.memory-recall", "scope": …, "name": "<slug from the index>", "toolCallId": "…" }
{ "kind": "hv.memory-forget", "scope": …, "name": "<slug>", "toolCallId": "…" }
```

Main's answer is a plain string, and its SHAPE carries the outcome:

| answer | meaning |
| --- | --- |
| `ok:<slug>` | saved as a new memory |
| `replaced:<slug>` | upserted over an existing one |
| `<the body>` | a recall |
| `ok` | forgotten |
| `ERROR: <reason>` | refused, with the store's own sentence |

**The slug comes back on the save answer, and that is load-bearing.** The model supplies a NAME
(free text); main derives the slug and is the only thing that knows it. Handing it back is what
lets the same turn recall or forget what it just saved — without it the model would guess, and
`"Talk like a young engineer!"` does not guess to `talk-like-a-young-engineer`.

`details` on the tool result — the fields the card and the restore path read:

```jsonc
memory_save   → { scope, type, name: "<slug>", description, replaced: boolean }
memory_recall → { scope, name }
memory_forget → { scope, name }
```

### What it costs, measured

Booted against a real Pi with the bridge, reading the bridge's own `/hv-context` snapshot.
"System" is the injected system text; "schemas" is every registered tool's JSON spec at
`chars/4`. Both are per turn.

| | system | tool schemas | total | vs off |
| --- | --- | --- | --- | --- |
| memory off | 1,205 | 4,668 (27 tools) | 5,873 | — |
| on, no memories | 1,498 | 5,410 (30 tools) | 6,908 | +1,035 |
| on, 20 memories | 1,995 | 5,410 | 7,405 | +1,532 |
| on, 100 memories (the cap) | 4,015 | 5,410 | 9,425 | +3,552 |

**The surprise is which half is expensive.** The policy paragraph is 242 tokens; the three tool
SCHEMAS are 743. So most of what the row costs when you have no memories at all is the schemas,
not the prompt — which is why the Built-in tools panel shows the tool descriptions beside the
policy. A panel showing only the policy would understate the saving by three quarters.

An index line is ~25 tokens, so the cap of 100 is worth ~2,500 tokens a turn. That is the honest
ceiling and it is why the Memory page prints the number rather than describing it as small.

**Off costs 0**, verified rather than asserted: with `HV_BUILTINS {"memory":false}` the system
prompt is byte-identical to a build with no memory code, the three tools are absent from Pi's
own registration list, and the snapshot carries no `memory` field at all.

### Two traps this cost

**`--git-common-dir` answers a RELATIVE path from a main worktree and an ABSOLUTE one from a
linked worktree** (measured: `.git` vs `/private/tmp/x/main/.git`). The key resolves both
through `path.resolve(workspace, …)`; without that the two halves of one clone hash differently
and worktree sharing silently does not happen — with nothing on screen to say so.

**`systemBlock` is null until the first turn has run.** It is captured in `before_agent_start`,
so a `/hv-context` taken at boot reports `system: null`. Any test that snapshots before a turn
is measuring nothing; the live tests run a warm-up turn first for exactly this reason.

### What the GUI pass found that neither the gate nor the live batch could (2026-09-04)

Three bugs, all past a green gate and 3,276 passing tests, and the first two are the same
mistake at two different layers: **a test that feeds the shape you wrote proves nothing about
the shape that arrives.**

**1. The permission prompt showed no memory at all.** `summarize()` ends
`JSON.stringify(factual).slice(0, 300)` — it slices the SERIALIZED string, so a memory save
(description plus up to 4 KB of body) reached the modal cut mid-string. `JSON.parse` threw,
`argsFromSummary` returned `undefined`, the fact block rendered nothing, `toolLabel` fell back,
and the dialog read *"The agent wants to run something / Saving a memory"*. The user was being
asked to approve a durable change to what every future session is told, against a sentence that
named neither the memory nor its scope. Every unit test passed a well-formed object.

The fix caps the FIELD, not the serialized string, at the store's own 4 KB body limit — what is
legal to save is always legal to show in full. The 300-char cap stays for every other tool,
where a truncated summary only costs a prettified label (an accepted degradation, already
commented in `describeCommand`).

**2. The LIVE card was empty.** `MemoryCardBody` read `card.memory`, which `restore.ts` fills.
A live card has never been through restore: it carries the tool result, with the same fields on
its `details` sibling. So the card you see the instant you approve a save rendered its headline
and nothing else — no body, no scope, no Forget — while the card you see after a reload was
perfect. **This is §12's delegation-card bug exactly, one feature later** ("a RESTORED card
needs that id handed to it as a FIELD"), arriving from the opposite direction: that time the
restore path was starved, this time the live one. `memoryFromResult` covers it, and a test
asserts the two sources agree field for field rather than testing them separately.

**3. The pointer to workspace settings went nowhere.** `GoTo` takes `{view, workspace}` and
App's `navigate()` selects the workspace before switching views. Passing only `view="workspace"`
produced a link that rendered, was clickable, and landed on whatever page was last open. §20
round 17's rule is that a dead pointer is worse than none, so with no workspace in play the page
now states the fact instead.

**And the regression that fixing (1) caused, found by reading the audit log rather than the
diff.** Lifting the cap for memory made the audit row unbounded too: `audit()` was handed the
same string, so a 4 KB body landed in every `permission.decision` JSONL row of a log that is
long-lived, exportable and read on a page. The prompt and the record want different lengths.
The cap now lives inside `audit()` — one choke point every caller already routes through — so
the record is bounded by construction whatever a future `summarize` arm does. Note this had
been true only by ACCIDENT before: every tool was capped at 300 upstream, so nobody had to
decide it.

Smaller, same pass: the card's two pills both rendered `ABOUT YOU` for a global `user` memory.
They answer different questions — scope is WHERE (everywhere / this project), kind is WHAT.

**Verified in the running app, not inferred:** the nav row sits second in *Abilities*; the
prompt renders name/kind/scope/summary and a red-green diff on an update; the upsert leaves ONE
memory with the new description; a Memory-page edit flips provenance to "Edited by you" and
clears `originSessionId`; the agent then answered the next turn **from the injected index with
no tool call and no respawn** (and in French, obeying the memory it had just been given); the
context panel priced it at 21 tokens with the policy separately at 242, matching the page
exactly and matching the measurements above; the audit log shows `remembered` / `updated a
memory` / `you edited a memory`; Forget on the card flipped it to "Forgotten." and the memory
was gone from the Memory page, cost back to 0.

# §34 — Collect feedback (2026-09-10)

**The wire, measured against the real Inlet at `https://feedback.bzapps.eu`.**

The flow is three calls, and the second is the one with the surprise: `POST
…/submission-intents` returns `{intentId, token, formVersion, expiresAt}`, and the token rides
every later call as `X-Inlet-Intent-Token` — *not* as a bearer, which stays the publishable key.
An attachment is `multipart/form-data` with exactly two parts, `questionId` and `file`, and
returns `{attachmentId, bytes, mediaType, originalMediaType, width, height, scanStatus}` — the
server re-encodes to WebP, so `bytes` is the STORED size and rarely the one you sent. Finalize is
`{formVersion, answers, clientContext}` and answers `201 accepted` or `200 duplicate`.

**`duplicate` is a success, and that is the whole retry story.** Inlet decides sameness on a
canonical form of `formVersion` + `answers` + `clientContext`, so replaying a payload after a
network failure returns the ORIGINAL result rather than a second submission. A *different*
payload on a finalized intent is `409 intent_payload_conflict` and stores nothing. That is why
`sendSubmission` may retry without any bookkeeping of its own.

**The one retry that is not a retry:** `410 intent_expired` needs a NEW intent and a re-upload,
because the attachments were scoped to the dead one. Measured against a fake: two `submission-intents`
calls and two `attachments` calls, one `submit` that fails and one that lands. A second 410 is
surfaced rather than looped.

**Error mapping is by CODE first, status second.** `form_not_published` (409) is a STATE, not a
failure: the dialog says "Feedback is closed right now." and does not fall back to a cached copy of
a form nobody can answer. Everything else falls back to the cache. A non-JSON body (a gateway's
HTML) maps by status alone rather than throwing while parsing the error.

**Keys, measured.** The dev publishable key reads the form: `200`. The same key reading
`/v1/feedback-databases/{db}/submissions`: **`401`** — that refusal is the entire reason an `ipk_`
may be committed, and `tests/feedback-live.test.ts` asserts it rather than trusting the doc. A
SERVER key (`isk_`) hitting `/v1/projects/{id}/credentials` gets `insufficient_scope`: **only a
signed-in human can mint a publishable key**, which is why prod's is null in the committed config
and lands in its own commit.

**Two type traps, both from the same mistake.** Inlet's element union has to be mirrored on both
sides of the tsconfig boundary, and the obvious mirror does not narrow: a member typed
`{type: string, …}` for "an element this build does not know" OVERLAPS every literal, so
`el.type === "choice"` narrows nothing and every field access fails. Same for one member carrying
`type: "title" | "subtitle" | "body_text"` — an early return cannot remove it. Both had to be
split (three content members plus a separate `UnknownElement`, reached through an `isKnown` type
PREDICATE), which is also how Inlet's own schema declares them.

**And one import trap worth more than either.** `import { is } from "@electron-toolkit/utils"` in
`ipc.ts` took **three unrelated tests** down at once — `memory-ipc`, `memory-surfaces`,
`prompt-template-notify` — with *"Named export 'BrowserWindow' not found. The requested module
'electron' is a CommonJS module"*, pointing at the import line rather than the cause. The package
imports `electron` with named imports, which vitest resolves to the real CJS stub. `is.dev` is
`!app.isPackaged`; `app` was already imported. The tell is that the suite reported **0 failing
tests and 3 failing FILES** — a collection error, not an assertion.

**Three bugs the GUI pass caught that the whole test suite could not (2026-09-10).**

**1. A white window.** The pulse decision was an effect placed after App's
`if (keyState === "loading") return …`. The first render has 127 hooks, the second 128, and React
answers *"Rendered more hooks than during the previous render"* by unmounting the entire app —
a blank page and two console errors, nothing else. No test in this repo renders App, so the
position is now pinned as a source fact: the effect must appear before that return.

**2. The wordmark truncated to "HappyV…".** Measured rather than guessed: the sidebar header row
has 214px of content width and its three children plus two 8px gaps needed exactly 214px, so the
brand button's `truncate` gave way by 5px the moment a third icon joined. `gap-1` reclaims 12px
and the wordmark is now `shrink-0`, so the row is sized to fit the name rather than the reverse.
The lesson generalises: a header row that is exactly full has no slack for one more control, and
the control that breaks is the one with `min-w-0`.

**3. The pulse came back to someone who had just rated it.** "Hidden while the agent streams,
back at the next idle" was implemented by UNMOUNTING the component — so the next turn mounted a
fresh one, which knew nothing of the tap, showed the row again and re-stamped `pulseAskedAt`
(measured: 06:13:22 then 06:14:31 on the same session). Hiding is a RENDER decision, not a
lifecycle one: the component now takes a `hidden` prop and returns null, and the answered
outcome lives in App (`pulseDone`) where a remount cannot lose it. Re-verified end to end: rated,
another turn ran, the row stayed gone and the timestamp did not move.
