## Adaptation note — JSONL reader timing

During `session_start`, Pi's JSONL stdin reader is not yet attached (it's set up synchronously after `rebindSession()` returns). Calling `ctx.ui.confirm()` directly inside the `session_start` handler creates a pending promise with no active stdin reader — the Node.js event loop empties and Pi exits with code 0 before processing any response.

**Fix**: The probe extension fires the confirm asynchronously (detached via `void (async () => {...})()`) and returns synchronously from `session_start`. A 50ms delay ensures `rebindSession()` has completed and the JSONL reader is attached before `confirm()` emits `extension_ui_request`. Task 6/10 implementations MUST use the same async-detached pattern (or hook a later lifecycle event) when calling `ctx.ui.*` from RPC mode.

## B4 wire shapes — hv.audit / hv.rules / hv.dangerous (2026-07-05)

All three ride `ctx.ui.notify`, which surfaces over RPC as a **fire-and-forget** `extension_ui_request` with `method: "notify"` — no `extension_ui_response` is ever written (responding is a protocol error; main must only parse). The JSON payload rides the `message` field (notify carries JSON in `message`; input/select carry it in `title` — same convention as `hv.auth`).

### hv.audit — one notify per permission decision (bridge → main → EventLog)

**Verbatim `extension_ui_request` observed in rules-bridge.test.ts (real RPC, rule-deny of `touch forbidden.txt`):**

```json
{"type":"extension_ui_request","id":"…","method":"notify","message":"{\"kind\":\"hv.audit\",\"ts\":\"2026-07-05T…Z\",\"tool\":\"bash\",\"summary\":\"touch forbidden.txt\",\"decision\":\"deny\",\"source\":\"rule\",\"rule\":{\"layer\":\"command\",\"pattern\":\"touch *\",\"action\":\"deny\",\"scope\":\"global\"}}","notifyType":"info"}
```

Payload fields:

| field | values |
|-------|--------|
| `kind` | `"hv.audit"` (constant) |
| `ts` | ISO 8601, written by the bridge at decision time |
| `tool` | Pi tool name (`bash`, `write`, …) |
| `summary` | bash command or JSON'd input, ≤300 chars |
| `decision` | `"allow"` \| `"allow-session"` \| `"deny"` |
| `source` | `"rule"` \| `"user"` \| `"dangerous"` \| `"safe-default"` |
| `rule?` | `{layer, pattern, action, scope: "global"\|"workspace"}` — only when `source: "rule"` |
| `grant?` | `"session"` — user allow riding an earlier "Allow for session" grant |

Main (`src/main/ipc.ts`) intercepts these before renderer forwarding and appends them to the EventLog as `type: "permission.decision"` with `sessionId`/`workspaceId` — the payload above becomes the event's `data`.

### hv.rules — /hv-rules-reload acknowledgment

Rules file (`permission-rules.json` in userData, `{global: Rule[], workspaces: Record<absWorkspacePath, Rule[]>}`) reaches the bridge via the `HV_RULES_FILE` spawn env var. Main rewrites the file on UI edits then broadcasts the `/hv-rules-reload` slash command (fire-and-forget RPC prompt) to every live session.

```json
{"kind":"hv.rules","stage":"loaded","global":1,"workspaces":1}
{"kind":"hv.rules","stage":"error","message":"<parse error>"}
```

On parse error the bridge KEEPS the previous ruleset — a torn write never fails open.

### hv.dangerous — /hv-dangerous on|off acknowledgment

```json
{"kind":"hv.dangerous","on":true}
{"kind":"hv.dangerous","stage":"error","message":"Usage: /hv-dangerous on|off"}
```

Per-session, in-bridge-memory only — never persisted, always off after respawn. The renderer drives its warning banner from this notify (forwarded through `hv:ui-request` like all non-audit requests).

Contract coverage: `tests/rules-bridge.test.ts` (reload + dangerous need no model; the rule-deny hv.audit contract is DEEPSEEK-gated like bridge.test.ts).

## B5 wire shapes — hv.context / hv-context-marks (2026-07-07)

Context visibility rides the same fire-and-forget `ctx.ui.notify` channel as B4
(JSON in the `message` field; the renderer parses it and NEVER opens the modal).
Three `/hv-context*` bridge commands are driven from main via RPC `prompt`
(B3/B4 precedent); their replies stream back as `hv.context` notifies.

### Mark identity (the crux)

The panel identifies items by session-entry id (from `get_entries`), but the
`context` event — the only place removal takes effect — hands the bridge an
`AgentMessage[]` with NO entry ids. The only ids present in BOTH are:

- `toolCall.id` / `toolResult.toolCallId` → mark key `tool:<id>` (a pair)
- `message.timestamp` → mark key `msg:<ts>` (plain user/assistant messages)

So the renderer sends **mark keys**, not entry ids. Pairing is automatic:
`tool:<id>` drops the assistant's toolCall block AND the matching toolResult
(atomic), so selecting either half removes both.

### hv.context — snapshot (reply to /hv-context)

```json
{"kind":"hv.context","stage":"snapshot",
 "system":{"chars":8123,"estTokens":2031,"toolCount":4,
   "contextFiles":[{"path":"/ws/AGENTS.md","chars":512,"estTokens":128}],
   "toolDefs":[{"name":"read","chars":420},{"name":"bash","chars":880}]},
 "items":[
   {"markKey":"msg:1730000000000","entryId":"e1","group":"conversation","role":"user","preview":"turn one","chars":8,"estTokens":2,"removable":true},
   {"markKey":"tool:call-A","entryId":"e2","group":"tool","role":"assistant","toolName":"bash","toolCallId":"call-A","preview":"bash({\"command\":\"ls\"})","chars":21,"estTokens":6,"usage":{"input":100,"output":20,"total":120},"removable":true},
   {"markKey":"tool:call-A","entryId":"e3","group":"tool","role":"toolResult","toolName":"bash","toolCallId":"call-A","preview":"ok","chars":2,"estTokens":1,"removable":true}
 ],
 "marks":["tool:call-A"]}
```

- `system` is `null` until the first turn runs (captured at `before_agent_start`).
- Item sizes (`chars`/`estTokens`) are char-based ESTIMATES (≈ chars/4), labeled
  as such in the UI; `usage.total` on assistant items is MEASURED.
- `removable` reflects the completed-turn gate (s0.3): items at/after the last
  user message (the in-flight turn) are `false`. The bridge refuses to mark them.
- **v5:** `system.toolDefs[]` gives per-tool ESTIMATED sizes (from the LLM tool
  spec, ≈ chars/4) so the panel can drill into tool definitions with a total
  instead of "size not measured". `bashExecution` message entries now group as
  `tool` (not `other`), and the renderer hides any empty group — so "Other" only
  appears when a genuinely unknown entry type shows up.

### hv.context — removed / restored (reply to /hv-context-remove | -restore)

```json
{"kind":"hv.context","stage":"removed","accepted":["tool:call-A"],"refused":["tool:call-B"],"marks":["tool:call-A"]}
{"kind":"hv.context","stage":"restored","restored":["tool:call-A"],"marks":[]}
```

`refused` = keys rejected by the completed-turn gate (in-flight or unknown);
`notifyType` is `"warning"` when anything was refused. `marks` is the full
current kill-set after the operation.

### hv-context-marks — persistence (pi.appendEntry)

The kill-set is persisted as `custom` entries of type `hv-context-marks` with
`data: {marks: MarkKey[]}` — a full snapshot, newest wins. These do NOT enter
LLM context. Restored on `session_start` (survives reload + resume), and
re-appended in `session_before_compact` so they survive compaction. The bridge's
`context` handler applies the set via `filterMessages` (non-destructive — the
session file is never mutated, proven in s0.3).

### Compaction

Main fires the RPC `compact` command (`hv:compact-session`); Pi streams
`compaction_start` / `compaction_end` events (forwarded as `hv:pi-event`),
rendered as transcript notices. The red-zone auto-suggest banner and the
[Compact now] dialog are renderer-only; compaction is NEVER automatic.

Contract coverage: `tests/context-bridge.test.ts` (snapshot shape + in-flight
refusal need no model; the remove→resume-survival guarantee is DEEPSEEK-gated —
it proves the mark persists across a full Pi process restart from the session
file, i.e. the same `pi.appendEntry` + `restoreMarks` machinery
`session_before_compact` re-invokes; a manual `compact` refuses on a session
that small, so persistence is proven deterministically via resume). Pure logic
(marks/pairing/completed-turn gate + gauge/grouping/parsing) is unit-tested in
`tests/hv-context.test.ts` and `tests/context-renderer.test.ts`.

### Subagent delegation trace (ordinary tool_execution_* events, toolName "subagent")

The subagent tool is a normal `tool_call` → the B4 bridge permission gate applies
to it (gate `subagent` via a tool-layer rule). Observed shapes on
pi-subagents 0.33.1 (differs from s0.3's prediction — the transcript is in the

- `tool_execution_update.partialResult.details.results[]` — **LIVE child transcript**:

The renderer keeps the update's `messages` and merges the end's model/usage/finalOutput
onto them (`mergeTrace`), rendering a nested collapsible mini-conversation
distinct from a normal tool card.

## MCP permission tool-name convention (m1.md, 2026-07-13)

The `tool` field in an `hv.permission` select prompt may be a virtual name for MCP
proxy calls:

| Value | Meaning |
|-------|---------|
| `mcp:<serverName>_<toolName>` | MCP invoke — per-tool identity; rules can pattern-match (e.g. `mcp:github_*`) |
| `mcp` | MCP discovery (search/describe/connect) — safe-default-allowed, no prompt |

The actual format is `mcp:<prefix>_<toolName>` where `<prefix>` is the server name
from `.mcp.json` `mcpServers` key (the adapter's tool-prefix behavior).
Empirically confirmed: server `echo`, tool `echo` → `mcp:echo_echo`.

Discovery calls (`search`, `describe`, `connect`) set `ruleTool: "mcp"` (bare) and
are safe-default-allowed at the bridge gate — they never surface as `hv.permission`
prompts unless an explicit rule matches `mcp`.

## WS8 — file-tree mutations + native watching (renderer ↔ main only, no Pi wire)

All confined by `files.ts` `resolveInWorkspace` (the workspaceId trust boundary);
each refuses to clobber an existing path.

- `hv:fs-create-file` / `hv:fs-create-dir(workspaceId, relPath)` — create (mkdir parents).
- `hv:fs-move(workspaceId, srcRel, destDirRel)` — move within the workspace (rename); refuses overwrite / moving into itself. Returns the new rel path.
- `hv:fs-import(workspaceId, destDirRel, srcAbsPaths[])` — copy EXTERNAL OS paths (from an OS drag-drop) into a confined dest (`fs.cpSync` recursive). Sources are absolute + unconfined (they're external); only dest is confined. Returns written rel paths.
- `hv:watch-workspace` / `hv:unwatch-workspace(workspaceId)` — start/stop a recursive `fs.watch` (macOS/Windows; Linux recursive is unsupported → no watcher, renderer keeps working). Debounced changes push `hv:fs-changed {workspaceId, relDirs}`; the tree re-lists expanded dirs (replaces the manual refresh button).
- Drag-out: tree rows set the `application/x-hv-relpath` dataTransfer mime; the center panes drop-open it. Preload exposes `getPathForFile(file)` (`webUtils.getPathForFile`) for OS-drop imports.

Unit coverage: create/move/import confinement + no-clobber in `tests/files.test.ts`.

(permission invariant). Routing is KIND-based: `method:"input"` +
`title.kind:"hv.ask-user"` (hv.auth inputs keep routing to the auth flow).
Input is clamped, never rejected: headers >12 chars truncated, >4
questions/options dropped, previews stripped off multi-select questions —
each adjustment rides back on the tool result as a note.

**Verbatim request (observed live in ask-user-bridge.test.ts, 2026-07-12):**

```json
{"type":"extension_ui_request","id":"…","method":"input","sessionId":"…",
 "title":"{\"kind\":\"hv.ask-user\",\"intent\":\"Choosing a greeting style\",\"questions\":[{\"question\":\"Which greeting should I use?\",\"header\":\"Greeting\",\"multiSelect\":false,\"options\":[{\"label\":\"Hello (Recommended)\",\"description\":\"Plain and friendly\"},{\"label\":\"Hi\",\"description\":\"Casual\"}]}]}",
 "placeholder":""}
```

**Working response — answered** (`value` is `JSON.stringify(AskAnswer[])`;
`answers` carries option labels and/or the renderer's free-text "Other"):

```json
{"type":"extension_ui_response","id":"…",
 "value":"[{\"question\":\"Which greeting should I use?\",\"header\":\"Greeting\",\"answers\":[\"Hello (Recommended)\"],\"note\":\"keep it simple\"}]"}
```

**Working response — dismissed** (renderer `respondInput(id, null)` → main
maps to `{cancelled:true}`; the tool result tells the model "User dismissed
the question — proceed with your best judgment."):

```json
{"type":"extension_ui_response","id":"…","cancelled":true}
```

Tool result to the model is readable markdown ("The user answered:\n-
**Greeting** — Which greeting should I use?: Hello (Recommended) _(note: keep
it simple)_"). Renderer always appends "Other"; the answer also echoes into
the transcript as a user-style item (`answersSummary`) and queues through the
same uiQueue as permission prompts (sidebar badges, headFor routing, dock
badge unchanged). `ask_user` is in SAFE_TOOLS — no permission prompt stacks
on top of the question modal.

## Async subagents — hv.subagent + /hv-subagent-* + discoverability (2026-07-17)

PRD §12: delegations run async by default (`asyncByDefault` in the app-written
`<agentDir>/extensions/subagent/config.json`, `completionBatch.enabled:false`),
so a delegation returns immediately (detached runner) and the user keeps
chatting. pi-subagents emits lifecycle events on the **in-process `pi.events`
bus** (never on RPC stdout); the co-resident bridge subscribes and relays each
as a fire-and-forget `hv.subagent` notify (JSON in `message`, like B4/B5).
Completion itself is auto-delivered by pi-subagents as an injected
`subagent-notify` message + triggered assistant turn (final-output-only, the
same isolation contract as foreground) — the RPC stream serializes that turn;
the `hv.subagent complete` notify is the card-lifecycle signal alongside it.

### hv.subagent — lifecycle relays (bus → bridge → main/renderer)

```json
{"kind":"hv.subagent","stage":"started","runId":"<id>","agent":"code-explorer","task":"map the repo","asyncDir":"/…/pi-subagents-uid-501/async-subagent-runs/<id>"}
{"kind":"hv.subagent","stage":"control","runId":"<id>","activityState":"long-running"}
{"kind":"hv.subagent","stage":"control","runId":"<id>","activityState":"needs_attention"}
{"kind":"hv.subagent","stage":"complete","runId":"<id>","status":"success","summary":"<final output, ≤500 chars>"}
{"kind":"hv.subagent","stage":"complete","runId":"<id>","status":"error"}
{"kind":"hv.subagent","stage":"complete","runId":"<id>","status":"interrupted"}
```

- `started` maps from `subagent:async-started` (`{id, agent, task, asyncDir, …}`).
- `control` maps from `subagent:control-event` (`{event:{type}, asyncDir}`); `runId = basename(asyncDir)` (the run dir is named by id). `activityState`: pi-subagents' `active_long_running` → `"long-running"`, `needs_attention` → `"needs_attention"`.
- `complete` maps from `subagent:async-complete` (`{runId, agent, success, summary, state}`); `status = success ? "success" : state==="paused" ? "interrupted" : "error"`.

### /hv-subagent-interrupt <runId> — stop a running async run (reply notify)

Drives pi-subagents' versioned event-bus RPC (`subagents:rpc:v1:request`, method
`interrupt`) and acknowledges:

```json
{"kind":"hv.subagent","stage":"interrupt-sent","runId":"<id>"}
{"kind":"hv.subagent","stage":"interrupt-error","runId":"<id>"}
```

Interrupt is file-based and resumable (drops `control/interrupt.json`). Driven
from main via RPC `prompt` like the other `/hv-*` commands.

### /hv-subagent-list — active-run resync (reply to a respawn)

`restoreActiveJobs` repopulates pi-subagents' internal job map on session_start
but does NOT re-emit `started`, so main fires `/hv-subagent-list` after every
(re)spawn to resync run cards + the activity counter. The bridge reads
`listAsyncRuns(ASYNC_DIR, {states:["queued","running"], sessionId})`:

```json
{"kind":"hv.subagent","stage":"active","runs":[{"runId":"<id>","agent":"code-explorer","asyncDir":"/…/<id>"}]}
```

### hv:subagent-status — live status poll (internal IPC, NOT a Pi wire contract)

Main tails `<asyncDir>/status.json` (~500 ms; atomic writes → a torn read skips a
tick; asyncDir sanity-checked to start with `os.tmpdir()`) for each active run
and forwards changes to the renderer:

```json
{"sessionId":"…","runId":"<id>","status":{"currentTool":"read","activityState":"long-running","recentTools":[{"tool":"grep","args":"…"}],"turnCount":3,"state":"running"}}
```

### Discoverability — hv.context snapshot `system.agents`

The bridge injects an `## Available subagents` roster (name + description of every
enumerated agent, builtin + project, plus one guidance line) into the system
prompt each turn — the same per-turn replacement mechanism as nested AGENTS.md —
so the model delegates spontaneously instead of having to call
`subagent {action:"list"}`. It rides the `/hv-context` snapshot's `system` block:

```json
{"kind":"hv.context","stage":"snapshot","system":{"…":"…","agents":[{"name":"code-explorer","chars":72},{"name":"agents-md-maker","chars":95}]}}
```

## Plan Mode — hv.plan / hv.plan-write / hv.plan-status / hv.plan.blocked + hv:plan-* (2026-07-19)

PRD §23. Plan Mode is per-session read-only mode; the plan is a workspace file
(`.agents/plans/NNN-<slug>.md`) with front-matter status + a Tasks checklist. The
bridge module `hv-plan.ts` holds `{enabled, planPath?}` (persisted via
`pi.appendEntry("hv-plan-state")`, restored on `session_start` like context marks
— but note: unlike dangerous mode this state SURVIVES respawn), and re-emits the
`hv.plan` notify on `session_start` so the renderer resyncs after a respawn.

### The plan gate (tool_call clamp, BEFORE dangerous + rules)

Inserted in the bridge `tool_call` handler after MCP unwrap (so it sees real tool
names) but **before** the dangerous/bypass check and the rule engine — Plan Mode
wins over bypass. `gatePlanCall(toolName, input)` (pure, in `hv-plan.ts`):

| Result | Tools | Bridge action |
|--------|-------|---------------|
| `block` | `edit`, `write`, `subagent` | `{block:true, reason}` + `hv.plan.blocked` notify + `hv.audit` (source `"plan"`) |
| `block` | `bash` failing the read-only allowlist | same |
| `pass` | `read`/`grep`/`glob`/`list`/`ls`/`ask_user`/`plan_complete`, allowlisted `bash` | fall through to normal gates |
| `floor-ask` | everything else (MCP, unknown) | run `evaluate()`, then clamp `allow → ask` (deny stays deny) |

The bash allowlist is ported from `@narumitw/pi-plan-mode` `tool-policy.ts` (MIT):
fail-closed — read-only commands + safe `git`/`gh`/`npm` subcommands; rejects
redirects, substitutions, subshells, background jobs, and any chain with an unsafe
segment. In-flight async subagent runs are untouched (the gate sees only new calls).

### hv.plan — mode notify (reply to /hv-plan on|off|implement + on session_start)

Fire-and-forget `ctx.ui.notify` (JSON in `message`, like B4/B5); renderer parses,
never opens the modal. Drives the banner + composer toggle + sidebar badge.

```json
{"kind":"hv.plan","enabled":true,"planPath":null}
{"kind":"hv.plan","enabled":true,"planPath":".agents/plans/001-add-auth.md"}
{"kind":"hv.plan","enabled":false,"planPath":".agents/plans/001-add-auth.md"}
```

`off` keeps `planPath` (the file stays on disk). `/hv-plan` is driven from main
via RPC `prompt` (B3/B4 precedent); enter is also reachable via the `plan_start`
registered tool.

### hv.plan-write — BLOCKING plan-file write (plan_complete → main → tool result)

The `plan_complete({intent, plan})` registered tool emits a **blocking**
`ctx.ui.input` (JSON in `title`, like `hv.ask-user`); main writes the file and
answers with the workspace-relative path, which becomes the tool result AND the
new `planPath`. Main MUST always respond (error string on failure) — never leave
the bridge blocked.

```json
{"type":"extension_ui_request","id":"…","method":"input",
 "title":"{\"kind\":\"hv.plan-write\",\"plan\":\"# Add auth\\n\\n## Tasks\\n- [ ] …\\n\\n## Verification\\n…\"}",
 "placeholder":""}
```

```json
{"type":"extension_ui_response","id":"…","value":".agents/plans/001-add-auth.md"}
```

A second `plan_complete` in the same planning phase (planPath already set)
**overwrites the same file** (revision, keeping front-matter `createdAt`); a fresh
mode entry starts a new NNN. The written file carries front-matter `status: draft`
+ timestamps; `parsePlanFile(md) → {status, createdAt?, done, total}` (shared by
bridge, main, tests) counts `- [ ]`/`- [x]`.

### hv.plan-status — terminal status (plan_status_update → main rewrites front-matter)

Fire-and-forget notify; `plan_status_update({intent, status, note?})` records a
terminal fact (the model may only set `implemented` | `cancelled`).

```json
{"kind":"hv.plan-status","status":"implemented","note":"all checks pass"}
{"kind":"hv.plan-status","status":"cancelled"}
```

Main rewrites the plan file's front-matter and audits `plan.status {who:"model"}`.
Human overrides (incl. `reopen` → `implementing`, which is human-only) go through
`hv:plan-status` IPC and audit `{who:"human"}`.

### hv.plan.blocked — skipped-tool notify (renderer renders the "skipped" card)

```json
{"kind":"hv.plan.blocked","toolName":"write","toolCallId":"call-A","reason":"Plan mode is read-only — file edits are blocked."}
```

### Renderer ↔ main IPC (no Pi wire)

- `hv:plan-set(sessionId, enabled)` — disabling while the session is busy aborts
  the turn first (`{type:"abort"}`), then fires `/hv-plan off`.
- `hv:plan-implement(sessionId, model?)` — sets front-matter `implementing`;
  applies the optional session model override (reasonable-model nudge, §23); fires
  `/hv-plan off` then the file-referencing implement message; audits `plan.implement`.
- `hv:plan-discard(sessionId)` — abort-if-busy + `/hv-plan off`; file stays `draft`.
- `hv:plan-status(sessionId, relPath, status)` — human status override / reopen.
- `hv:plan-changed {workspaceId, path, status, done, total}` — pushed from the
  `watch.ts` fs-watcher when a `.agents/plans/*.md` file changes (`.agents` added to
  `DOTFILE_ALLOW`); drives live PlanCard progress. Carries no `sessionId` — the
  renderer maps via `planPath`.

Audit events (EventLog, frozen envelope): `plan.enter`, `plan.exit`,
`plan.blocked`, `plan.ready`, `plan.implement`, `plan.status` (with `who:"model"|"human"`).

Note — `plan_start` mid-turn: the gate applies to the next `tool_call` immediately,
but the 3-phase plan prompt only takes effect on the next turn (`before_agent_start`).
