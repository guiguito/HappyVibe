# D1 Validation — extension_ui_request over RPC (Gate V4)

## Verdict: YES — Path A confirmed

`ctx.ui.confirm()` surfaces over RPC as `extension_ui_request` on stdout and is answered by writing `extension_ui_response` to stdin. The full round-trip was proven empirically.

**Critical**: For `confirm` dialogs, the response field is `confirmed: boolean` (NOT `value`). This is per `RpcExtensionUIResponse` in `rpc-types.d.ts`.

⚠️ **UNVERIFIED — must be confirmed empirically in Task 6.** Per the `rpc-types.d.ts` type definitions (NOT proven by this probe, which only exercised `confirm`), `select` dialogs are expected to respond with `value: string` and cancellation with `cancelled: true`. The bridge extension uses `ctx.ui.select`, so Task 6 MUST log the real `extension_ui_request` for a select and adapt its `extension_ui_response` field to whatever actually round-trips — do not trust `value` blindly.

## Adaptation note — JSONL reader timing

During `session_start`, Pi's JSONL stdin reader is not yet attached (it's set up synchronously after `rebindSession()` returns). Calling `ctx.ui.confirm()` directly inside the `session_start` handler creates a pending promise with no active stdin reader — the Node.js event loop empties and Pi exits with code 0 before processing any response.

**Fix**: The probe extension fires the confirm asynchronously (detached via `void (async () => {...})()`) and returns synchronously from `session_start`. A 50ms delay ensures `rebindSession()` has completed and the JSONL reader is attached before `confirm()` emits `extension_ui_request`. Task 6/10 implementations MUST use the same async-detached pattern (or hook a later lifecycle event) when calling `ctx.ui.*` from RPC mode.
